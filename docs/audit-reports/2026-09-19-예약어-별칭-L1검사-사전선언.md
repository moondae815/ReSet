# 예약어 별칭을 L1 으로 잡는다 — 사전 선언

**작성**: 2026-09-19 · **코드**: main `55c402d2`
**대상 결함**: B23 축 B — 배송본 SQL 펜스의 `AS RowCount` 가 **컴파일 단계에서** 깨진다
**이 문서의 지위**: 구현 **착수 전**에 적는다. 검사가 무엇을 잡고 무엇을 안 잡는지, 무엇으로 검증하는지를 **결과를 보기 전에** 못박기 위해서다.

---

## 0. 물음

**SQL 펜스 안에서 예약어를 대괄호 없이 별칭으로 쓴 자리를 L1 이 잡을 수 있는가, 그리고 그 검사가 오탐 없이 도는가.**

## 1. 착수 전에 이미 잰 것

### 1-1. 자를 한 번 틀렸다 — 이 창에서 잰 수 전부가 그 자를 썼다

배송본 SQL 펜스 **325** 를 로컬 인스턴스(`docker sql-server`, SQL Server 2022)의 `SET PARSEONLY` 로 통과시켰다. 첫 결과는 **322 실패**였고 **그것이 틀렸다.**

원인은 하네스다. `@p_runId` 같은 **앱이 넣는 파라미터**를 SQL Server 가 `Msg 137 — Must declare the scalar variable` 로 고발했고, 그것이 **`Msg 102 — Incorrect syntax` 로 연쇄**했다. 변수를 선언하고 다시 재니 펜스 `0068` 은 깨끗이 **실행**됐다(`ViolationCount` 0).

| 회차 | 실패 펜스 | 무엇이 틀렸나 |
| :-- | --: | :-- |
| 1 차 | 322 / 325 | 출력이 비지 않으면 전부 오류로 셌다 |
| 2 차 | 44 / 325 | `Msg 137` 만 뺐다 — **`Msg 102` 연쇄를 못 뺐다** |
| **3 차(채택)** | **14 / 325** | 펜스마다 미선언 변수를 `DECLARE` 로 채우고 다시 쟀다 |

**이 세션에서 자를 틀린 여섯 번째이고, 처방을 설계하기 전에 잡았다.** 아래 수는 전부 3 차 기준이다.

### 1-2. 진짜 구문 오류 14 의 내역

| 원인 | 펜스 | 판정 |
| :-- | --: | :-- |
| **`AS RowCount`** | **12** | **결함** |
| 의도적 조각(WHERE 절 스니펫) | 2 | **오탐** — 「SQL-09 의 `Stored` CTE 에 다음 필터를 추가한 교정본」이라 적고 `AND ControlName IN (...)` 만 실은 자리다. 완전한 문이 아니므로 파싱 실패가 정상이다 |

`,`·`)`·`AS` 근처 오류는 **같은 펜스 안 `RowCount` 의 연쇄**다. 독립 원인이 아니다.

```
배송본 전체 `AS RowCount`  : 48
그중 ```sql 펜스 안        : 48   ← 산문·다른 펜스에는 0
```

| 파일 | 줄 |
| :-- | --: |
| `docs/BatchMigrationPlan.md` | 24 |
| **`agent/verification/integrity-sql.md`** | **12** |

**검증 세트에 12 가 있는 것이 가장 나쁘다** — 그것이 다른 단계들이 부르는 정본이다.

### 1-4. 「실행 오류」가 아니라 「컴파일 오류」다

```
SELECT COUNT_BIG(*) AS RowCount FROM ...
→ Msg 156, Level 15, State 1
  Incorrect syntax near the keyword 'RowCount'.
```

`[RowCount]` 대괄호는 통과한다(132 반환). 다른 이름(`RowCnt`)도 통과한다. **데이터가 없어도, 권한이 없어도, 그 전에 죽는다.** 그래서 이 결함은 데이터 의존이 아니고 등급이 갈리지 않는다.

## 2. 왜 L1 검사인가 — 한 벌 여섯의 앞 층을 먼저 가른다

| 층 | 판정 |
| :-- | :-- |
| **① 재료** | **필요 없다.** 판정에 외부 재료가 안 든다 — 문서 안의 SQL 펜스 텍스트와 **파서의 예약어 판정**만 쓴다. `SpecExpectations` 를 늘리지 않는다 |
| **② 배선** | **확인해야 한다.** `ValidateConsolidated` 가 통합 계획서를 받는다. 단계 파일·검증 세트가 그 경로를 타는지, 아니면 별도 경로인지 **구현 착수 시 실측한다**(§8) |
| **③ 오탐** | **낮다고 본다 — 그러나 이것이 이 검사의 유일한 위험이다.** 예약어 목록이 넓으면 정당한 별칭을 고발한다. §3 이 오라클을 못박는 이유다 |

**프롬프트가 아니라 L1 인 이유**: 프롬프트는 「예약어를 쓰지 마라」를 **모델이 기억해야** 듣는다. 예약어는 200 개가 넘고 어느 것이 예약어인지는 모델이 자주 틀린다. **판정이 기계적이고 목록이 고정된 자리는 검사가 맞다.** 반대로 프롬프트에 「별칭은 항상 대괄호로 감싸라」를 넣는 것은 산출물을 읽기 나쁘게 만들고 기존 300 여 펜스를 전부 바꾼다.

**이미 있는 L1 과의 관계**: `CheckMachineTableShape`·`CheckDmlScopeTable` 등은 **표의 셀**을 본다. 이 검사는 **SQL 펜스 본문**을 본다 — 축이 겹치지 않는다. 기존 검사가 이 결함을 한 번도 발화하지 않은 것이 그 증거다(B23 배송본이 48 자리를 달고 게이트를 통과했다).

## 3. 판정 오라클 — 「무엇이 예약어인가」를 구현 전에 못박는다

**자체 예약어 목록을 만들지 않는다.** 손으로 적은 목록은 (가) 빠뜨려 못 잡거나 (나) 넓어서 오탐한다. 둘 다 이 저장소가 겪은 실패다.

**오라클은 `Microsoft.SqlServer.TransactSql.ScriptDom` 의 렉서다**(이미 `ReSet.Core.csproj` 의 패키지 참조 — 새 의존성 0).

```
별칭 토큰 T 에 대해:
  ScriptDom 으로 T 를 단독 렉싱한다
  → TokenType == Identifier   이면 예약어 아님 (통과)
  → 그 밖                      이면 예약어      (발화)
```

**이것이 비순환인 이유**: 오라클이 **산출물이 아니라 파서**다. 그리고 그 파서는 SQL Server 와 같은 문법 계열이다 — 실제로 `AS RowCount` 를 거부하는 것이 SQL Server 이고, ScriptDom 이 같은 판정을 내는지는 구현 시 **실물 대조로 확인한다**(§5 양성 대조군).

### 잡는 것

- ```` ```sql ```` 펜스 **안**
- `AS` 뒤에 오는 **식별자 하나**
- 대괄호 `[...]`·큰따옴표 `"..."` 로 **감싸이지 않은** 것
- 그 토큰이 ScriptDom 렉서에서 `Identifier` 가 **아닌** 것

### 잡지 않는 것 (구현 전에 못박는다)

| 자리 | 왜 |
| :-- | :-- |
| `AS` 뒤가 **타입**인 것 — `CAST(x AS INT)`·`DECLARE @t AS TABLE` | 별칭이 아니다. `CAST`/`CONVERT`/`DECLARE` 문맥은 제외한다 |
| `AS` 뒤가 **테이블 별칭** — `FROM T AS A` | 같은 규칙이 적용되지만 토큰이 예약어면 그것도 실제 오류다. **제외하지 않는다** |
| **CTE 이름** — `WITH Foo AS (` | `AS` 뒤가 `(` 이므로 식별자가 아니다. 자연히 안 걸린다 |
| ```` ```sql ```` 밖의 산문·다른 펜스 | 실행되지 않는 텍스트다. 1-3 에서 그런 자리가 **0** 임을 이미 쟀다 |
| 이미 대괄호로 감싼 것 | 정상 표기다 |

## 5. 되돌림과 양성 대조군 — 한 벌 여섯의 뒤 층

**「발화 수」는 활동이지 효력이 아니다.** 셋 다 한다.

| 층 | 무엇을 | 합격 |
| :-- | :-- | :-- |
| **되돌림(효력)** | 검사 본문을 지우고 시험을 돌린다 | **그 시험만 빨갛게** 된다. 초록이면 시험이 검사를 안 재고 있다 |
| **배선(다른 축)** | `SafeCheck(() => Check…)` 호출 줄을 지운다 | **별도 시험이** 빨갛다. 「발화를 재는 자」와 「배선을 재는 자」는 다른 축이다 — 발화 시험은 검사가 아예 안 불려도 같은 값을 낸다 |
| **양성 대조군** | `AS RowCount`·`AS Order`·`AS Group` 을 넣은 픽스처 | 전부 발화. **음성만 재면 자가 안 도는 경우와 결함이 없는 경우를 못 가른다** |
| **음성 대조군** | `AS [RowCount]`·`AS RowCnt`·`CAST(x AS INT)`·`FROM T AS A` | 발화 0 |

**픽스처는 지어내지 않는다.** 양성은 **B23 배송본에서 오려 온다**(`integrity-sql.md` 의 실물 CTE). 규격 기억으로 지은 픽스처는 내 오해를 검사가 확인해 주게 만든다 — 이 저장소가 2026-09-07 에 겪었다.

## 7. 이 선언이 보증하지 않는 것

- **캐시 버전을 올릴지 아직 모른다.** 프롬프트 입력도 출력 계약도 안 바뀌면 올리지 않는다(스킬의 예외 조항). **검사만 더하는 변경이면 인상 없음**이 기본이고, 구현 중 프롬프트를 건드리게 되면 그때 `main` 과 대조해 정한다.
- **B23 산출물을 고치지 않는다.** 이 검사는 **다음 판**부터 막는다. 이미 배송된 48 자리는 재생성으로만 닫히고, 재생성은 별도 결정이다.
- **다른 구문 오류는 안 잡는다.** §1-2 에서 실측한 진짜 구문 오류는 `RowCount` 하나뿐이었다. 펜스 단위 전체 파싱 검사는 **의도적 조각 2 자리에 오탐**하므로 이번에 만들지 않는다 — 조각 표기 규약이 생기면 그때 올릴 자리다.
- **`AS` 없는 별칭은 안 잡는다.** `SELECT COUNT(*) RowCount`(AS 생략)도 같은 오류인데 이번 규칙이 못 본다. **코퍼스에 그런 자리가 있는지 구현 중에 재고, 있으면 규칙을 넓힌다.**
- **예약어가 아닌 이름 충돌은 대상이 아니다.** 컬럼명과 같은 별칭 등은 문법 오류가 아니다.
- **이 검사가 잡는 것은 「컴파일되지 않는다」이지 「의미가 틀렸다」가 아니다.** 축 A·축 B 의 다른 결함과 축이 다르다.

## 8. 착수 시 가장 먼저 잴 것 — 배선

**`AS RowCount` 48 줄이 어느 검증 경로를 타는지 모른다.** `ValidateConsolidated(markdown, steps)` 는 통합 계획서를 받는데, 48 중 24 가 `BatchMigrationPlan.md`(계획서)이고 나머지 24 는 `agent/` 아래 단계·검증 세트다.

**구현 첫 걸음은 그 24 가 `ValidateConsolidated` 가 보는 문자열 안에 있는지 실측하는 것이다.** 없으면 검사를 한 자리에 두는 것으로는 절반만 막힌다 — 그때는 호출 자리를 **경로마다** 걸어야 한다(2026-09-08 실측: 분할 경로를 죽였는데 기존 잠금 12/12 가 초록이었다).

**「프롬프트 잠금은 경로마다 걸어라」와 같은 함정이고, 이번에는 착수 전에 적어 둔다.**
