# 축 B 잔여 결함 22건의 처리 방침 분류

축 B 재감사(`2026-09-05-POQSettleBatch1-축B-재감사.md`)가 남긴 것 중, **검사가 이미 잡게 된 것과
🔴 하나를 뺀 22건**을 「어떻게 닫을 것인가」로 가른다.

**대상**: 잔존 13(§3의 `R`·`R′`에서 T02 제외) + 신규 9(§4의 N4~N12).
**뺀 것 넷**: T02(🔴 — 별도 과제로 크기를 재는 중) · N1·N3(검사 B 접힘을 좁혀 잡음 `83bdf03f`) ·
N2(중복 투영 검사로 잡음 `1f7ea018`).

**이 문서는 분류만 한다. 어느 것도 구현하지 않는다.**

## 어휘 — 결과를 보기 전에 정했다

| 기호 | 뜻 |
| :--- | :--- |
| **K¹** | **기존 검사의 판별자를 넓혀** 닫는다 — 재료는 이미 있고 검사가 그 칸을 안 볼 뿐이다 |
| **K²** | **새 검사**로 닫는다 |
| **P** | **프롬프트·공통 규약**으로 닫는다 — 기계로 판정할 수는 없으나 지시할 수는 있다 |
| **N** | **기록만 한다** — 손댈 수단이 없거나, 상류 계약이 그렇게 정한 것이다 |
| **U** | **분류 불가** — 판정에 필요한 사실이나 결정이 없다. **무엇을 재야 하는지를 함께 적는다** |

`K`를 둘로 가른 것은 동료 세션 `reset-b1`의 지적이다 — **「재료는 있는데 판별자가 느슨한 것」과
「재료가 아예 없는 것」은 처방이 다르다.** 한 건도 분류하기 전에 넣었다.

**미리 못박은 것 둘**
- **「재생성하면 낫겠지」는 분류가 아니다.** 궤적 46 → 42 → 40이 이미 반증했다.
  재생성으로 닫히는 것은 **그 앞에 검사가 있을 때만** `K`다.
- **`U`를 `K`로 올려 적지 않는다.** 같은 날 접힘에서 「가를 수 있을 것 같다」로 갔다가 한 번 되돌렸다.

## 6. 이 분류가 보증하지 않는 것

- **분류이지 판정이 아니다.** 각 건이 진짜 결함인지는 재감사가 이미 판정했고, 여기서 다시 열지 않았다.
- **K로 분류한 8건의 검사를 설계하지 않았다.** 오라클이 있다는 것까지가 이 문서의 주장이고,

  **다른 U에도 그런 것이 있는지는 각 결정 문단의 「재야 할 것」이 스키마 사실인지로 갈린다.**
  (가)·(나)·(다)는 전부 정책·설계 결정이라 그렇지 않다.
- ~~N을 닫을지 열어 둘지 정하지 않았다~~ → **2026-09-05에 닫았다**(§5). 셋은 「상류가 그렇게
  정했다」, 둘은 「결함이 아니다」다. **전자 셋은 그 상류가 바뀌면 다시 열어야 한다** —
  결함이 없어서 닫은 것이 아니기 때문이다.

## 7. T02(남은 🔴)의 크기 — 2026-09-05 스파이크. **⚠ §14 가 이 절의 크기 판정을 뒤집었다. 먼저 §14 를 읽어라**

## 8. 결정 (나)를 닫는다 — 2026-09-05. **사람 판단이 아니라 규칙과 번들이 답했다**

물음은 「후 단계가 세션 옵션·트랜잭션 진입 정리에서 손을 뗀 것이 의도인가」였다.

### T31 → **N (의도다)**

앱이 트랜잭션을 관리하므로 진입 정리도 앱 층의 몫이다.

**격리 수준도 같다** — 규칙 4가 명시한다: *"Every step MUST run under SNAPSHOT isolation -

**왜 `P`이고 `K`가 아닌가**: 단계 문서를 아무리 검사해도 이 공백은 안 보인다 — 단계가 안 쓰는 것이

## 9. 결정 (다) 1차 판단 — A. **§10이 이것을 뒤집었다. 먼저 §10을 읽어라**

### (2) 그러나 A의 비용도 과대평가했다 — **이쪽이 결정적이다**

첫 배선은 단위 테스트를 통과하고도 코퍼스 발화가 0 이었다. 원인은 `ReportMissing` 이

열 사람은 `honorRelocated` 를 갈라야 한다.

### 되돌린 이유 — 만족 가능성을 재니 2 행이었다

```
명세서 DML 행 102 중 ORDER BY 칸이 비지 않은 행 : 2
   dbo.UP_UTIL_SETTLE_PROC_ETC        SELECT 1 → [OutYMD, ClientID]
   dbo.UP_UTIL_STAT_PGCOLLECT_INS     INSERT 1 → [INYMD, CLIENTID, PGNAME, MALLID]
단계 문장 2,637 중 서수 앵커가 붙은 것 : 99
   그중 ORDER BY 를 쓴 것              : 0
```

**그리고 그 2 행에 대응하는 단계 문장이 둘 다 도달 불가다.**
`STAT_PGCOLLECT` 쪽은 **모든 Job 에서 서수 앵커가 없고**(오류 코드 앵커 `-1` 뿐이라 검사 B 가

(`Visit(Update/Delete/Insert)` 셋만 있다 — 이미 알려진 결함이다).

**그러므로 이 검사는 오늘 코퍼스에서 원리적으로 발화할 수 없다.** 코드는 옳고 테스트도 옳지만
값이 0 이다 — 접힘 좁힘 첫 시도를 되돌린 것과 같은 이유다(YAGNI).

### 분류를 고친다 — T22 는 `K¹` 이 아니었다

`K¹` 의 정의는 「**재료는 이미 있고** 검사가 그 칸을 안 볼 뿐이다」인데, 재보니 **재료가 2 행**이고
**둘 다 검사가 닿을 수 없는 문장**에 붙어 있다. 그래서 **`U`(분류 불가)로 내린다** — 선행 결정이
둘 있고 어느 것도 이 문서가 답할 수 없다.

1. **앵커 도달** — 서수 앵커가 없는 문장에 검사 B 가 도달하게 할 것인가(오류 코드 앵커로

2. **`SELECT` 문장을 리더가 읽게 할 것인가** — 이미 기록된 결함이고 T22 보다 크다.

**두 선행이 풀려도 이 검사의 최대 발화는 2 다.** 그 값으로 두 결정을 정당화할 수 없으므로,
**T22 를 다시 여는 근거는 「ORDER BY」가 아니라 그 두 선행 자체여야 한다.**

## 12. ★ 남은 `K` 전부의 상한 — **검사 B 의 도달률이 3.8% 다** (2026-09-05 실측)

§11 이 T22 를 되돌리며 드러낸 것인데, **T22 하나보다 크다.** 여기 따로 적는 이유는

```
코퍼스의 단계 SQL 문장          2,637
```

(코드 하나가 여러 문장에 쓰이면 모호해서 버려진다) 검사 B 는 그 문장에 도달하지 못한다.

T22 가 이 조건을 사서 만들었다 — 게이트까지 통과한 코드를 전량 되돌리고서야 알았다.

   (`ORDER BY` 는 **102 행 중 2 행**이었다.)
2. **그 행에 대응하는 단계 문장의 도달 가능성** — 서수 앵커가 붙는가. 리더가 그 문장 종류를
   읽기는 하는가(`DmlCollector` 는 `Update`·`Delete`·`Insert` 셋만 방문한다 — `SELECT` 는 안 읽는다).

**둘 중 하나라도 0 이면 그 `K` 는 만들어도 발화하지 않는다.** 코드가 옳고 단위 테스트가
통과해도 그렇다 — 오늘 그것을 두 번 확인했다.

### 남은 `K` 다섯에 대한 함의

`K¹` 둘(T21 · T29)과 `K²` 중 검사 B 계열은 **전부 이 4% 안에서 논다.** 그러므로
**가장 값이 큰 다음 걸음은 대조 칸을 넓히는 것이 아니라 「앵커 도달률을 올릴 것인가」다** —
그것은 검사 B 전체의 관할 문제이고 이 문서의 어느 항목보다 크다.

**다만 이 문서는 그것을 판정하지 않는다.** 3.8% 가 결함인지(앵커를 더 달게 해야 하는지),
아니면 의도된 좁음인지(앵커가 있는 문장만 신뢰할 수 있다는 설계인지)를 재지 않았다.

   캡처(`INSERT INTO ' + @v_shadowN … WHERE …`)와 복구(`DELETE FROM <표> … WHERE …`)를 그 표로 붙인다.
   S13 은 한 단계에 쌍이 **넷**(TX·PARTIAL·IN·OUT)이라 **순서로 붙이면 어긋난다.**
2. **ScriptDom 을 쓸 수 없다.** 캡처 술어가 **동적 SQL 문자열 리터럴 안**에 있다.

3. **정규화 둘이 이 검사의 승부처다.** 실측으로 확인된 오탐 원인이 정확히 이 둘이다.

   - **`''` → `'` 는 문자열 리터럴에서 뽑은 쪽에만** 건다. 양쪽에 걸면 평문 쪽
     `ISNULL(INYMD,'')` 가 `ISNULL(INYMD,')` 로 망가져 **가짜 비대칭이 난다.**
4. **짝 탐지가 아직 안 닫혔다.** `S06` 은 `SQL_RESTORE_DELETE` 를 **호출하는데**(`:69`)
   그 SQL 블록을 정규식이 못 찾았다. 착수하면 **이것부터** 닫아라.
5. **양방향이 둘 다 결함이고 뜻이 다르다.**
   캡처에만 있는 조건 → 복구가 더 넓게 지운다 → **영구 손실**.
   복구에만 있는 조건 → 덜 지우고 섀도우를 다시 넣는다 → **중복 행**.
