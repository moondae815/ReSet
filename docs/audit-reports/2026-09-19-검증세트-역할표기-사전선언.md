**작성**: 2026-09-19 · **코드**: `main` `0ddb3b98`
**겨냥**: B23 축 B 감사의 🔴 18 중 **15**(가장 넓은 가족)
**판독**: `docs/audit-reports/2026-09-19-B23-정합성감사-축B-판독.md` §4·§9

## 0. 물음

**세트 블록이 자기 역할을 선언하게 하면, 헐거운 술어가 「배치 전면 중단」이 아니라 「이슈 한 줄」로 내려가는가.**

## 1. 착수 전 측정 — 분모를 먼저 적는다

모든 수는 **계획서 19 편** 기준이고, 자를 세 번 고쳐서 얻었다(§1-4).

| 잰 것 | 값 |
| :-- | --: |
| 검증 SQL 세트의 **블록**(H3 구간 중 ```sql 펜스를 가진 것) | **238** |
| 그중 **역할 표기가 있는 블록** | **0** |
| 세트 안의 ```sql **펜스** | 379 |
| 그중 **`--` 주석으로 여는 펜스** | **240 (63%)** |
| 계획서의 세트 절 ↔ `integrity-sql.md` | **19/19 블록 수 일치** |

### 1-1. 배선 — 계획서 한 자리를 막으면 세트도 막힌다

19 편 전부에서 계획서 `## 통합 데이터 정합성 검증 SQL 세트` 절의 H3 수와 `agent/verification/integrity-sql.md` 의 H3 수가 **같다**. 세트 파일은 계획서에서 **잘라낸 것**이다.

⇒ **`ValidateConsolidated` 한 자리가 238 블록 전부를 덮는다.** 앞 두 검사와 같은 구조이고, 그때와 마찬가지로 **기우일지언정 재고 넘어간다.**

### 1-2. 지금 세트가 역할에 대해 말하는 전부

`integrity-sql.md:10` 공통 규약 한 줄뿐이다:

> 검증 결과가 실패이면 S18이 매개변수화된 INSERT로 `batch.BatchValidationIssue`에 **기록한다**.

**「기록한다」고 적혀 있는데 단계 10 곳이 게이트로 썼다.** 블록마다 아무 표시가 없으니 그 한 줄이 238 블록을 덮지 못한 것이다.

### 1-3. 「단계가 차단한다」를 판정 축으로 쓰면 안 된다 — 실측으로 기각

처음에 `ViolationCount != 0` 비교를 세어 봤다:

| | 차단 비교 |
| :-- | --: |
| B23 | **21** |
| B18 · B19 · B20 | 2 · 2 · 1 |
| 나머지 15 편 | 0 |

**그 5 자리를 열어 보니 세트 블록이 아니라 단계 자신의 지역 변수였다** — `BalanceViolationCount` · `paycoViolationCount` · `pgCollectViolationCount`. 세트를 승격시킨 것이 아니라 자기가 센 값을 자기가 본 것이다.

⇒ **이 축으로 검사를 만들면 그 5 자리가 곧바로 오탐이다.** 귀속이 불가능하면 침묵한다(작성 계약 7). **판정 축을 「단계가 무엇을 했나」에서 「세트가 무엇을 선언했나」로 바꾼다.**

### 1-4. 자를 세 번 고쳤다

1. `^### SQL-[0-9]` 로 블록을 셌더니 19 편 중 **2 편만** 잡혔다 — 블록 이름 공간이 편마다 다르다(`SQL-01`·`V01`·`4.1`·제목뿐). **이름으로 잡지 않고 「H3 + ```sql 펜스」로 잡는다.**
2. ```` ```sql ```` 개수를 2 로 나눴다 — 여는 펜스만 태그를 가지므로 절반이 됐다.
3. 펜스 379 와 블록 238 을 같은 수로 볼 뻔했다 — **한 블록에 펜스가 여럿이다.** 역할은 **블록 단위**로 요구한다(보조 펜스까지 요구하면 과하다).

## 2. 왜 술어 정밀화가 아니라 이것인가

판독 §9 가 같은 🔴 15 에 닿는 후보 둘을 나란히 놨다.

| | 세트 술어를 원본 허용 범위에 맞춘다 | **역할을 못박는다**(이번 것) |
| :-- | :-- | :-- |
| 도달 | 🔴 15 | **같은 15** |
| 비용 | 블록 15 개의 술어를 원본 DDL 과 대조해 다시 쓴다 | 프롬프트 한 절 + 검사 하나 |
| 성질 | 술어가 틀린 것을 고친다 | **틀린 술어의 대가를 낮춘다** |

**둘은 배타가 아니고 순서가 있다.** 역할을 먼저 못박으면 남은 헐거움이 「이슈 한 줄」이 되므로, 술어 정밀화는 그때 **🔴 가 아닌 것을 고치는 일**이 된다. 순서를 뒤집으면 무거운 술어 작업을 하고도 단계가 여전히 승격시켜 같은 🔴 가 남는다.

**이 선언은 술어를 하나도 고치지 않는다.** 그것을 여기 못박는다 — 이번 처방으로 🔴 15 가 사라진다고 주장하지 않는다. 주장하는 것은 **등급이 내려간다**이고, 확정은 실물 판의 축 B 감사 몫이다.

## 3. 표기의 거처 — **SQL 주석**으로 정했고, 이유는 사본이다

후보 셋 중 골랐다.

| 거처 | 사본을 따라가는가 | 코퍼스 관례 |
| :-- | :-- | :-- |
| H3 제목 줄 | ✘ | — |
| 블록 앞 산문 | ✘ | — |
| **SQL 주석 첫 줄** | **✔** | **펜스 240/379(63%)가 이미 `--` 로 연다** |

**결정적인 것은 사본이다.** B23 의 실패 모양은 「단계가 세트 SQL 을 자기 안에 복사해 고쳤다」이고(판독 §5), 산문과 제목은 복사에 안 따라간다. **역할이 SQL 안에 있으면 사본에도 실린다.**

그리고 63% 가 이미 `--` 주석으로 열고 있으므로 **새 관례가 아니라 기존 자리에 한 항을 더하는 것**이다.

### 3-1. 어휘

```sql
-- SQL-07 지급·회수 상태 및 예정일 검증 · 역할: 기록
```
```sql
-- SQL-02 단계 저널 및 체크포인트 완전성 · 역할: 게이트
```

**「게이트」는 커밋 전에 돌려 위반이면 그 트랜잭션을 되돌린다. 「기록」은 사후에 돌려 `batch.BatchValidationIssue` 에 한 줄 남기고 배치는 계속된다.**

**어휘를 좁게 못박지 않는다.** 재생성에서 모델이 쓰는 말은 스윕에 없던 모양을 낸다(스킬의 마지막 실패 항목이 정확히 이 경우다). 검사는 `역할` 다음에 `게이트`·`기록`·`차단`·`사후` 중 하나가 오는 모든 모양을 받는다.

## 4. 세 층 — 프롬프트 둘 + 검사 하나

| 층 | 자리 | 무엇을 |
| :-- | :-- | :-- |
| **생성** | `AiService.cs:2456` 세트 절 지시문 | 블록마다 첫 주석 줄에 `· 역할: 게이트 \| 기록` 을 적게 한다 |
| **생성** | 같은 절의 **Few-Shot 예시** | 예시 블록에도 역할을 단다 — **생성물은 예시를 베끼지 지시문을 베끼지 않는다** |
| **강제** | `MechanicalValidator.ValidateConsolidated` | 세트 절의 블록 중 역할 표기가 없는 것을 고발한다 |

**Few-Shot 을 같이 고치는 것이 이 표의 요점이다.** 이 저장소는 지시문만 고치고 예시를 안 고쳐 배송본이 안 닫힌 일을 이미 겪었다.

## 5. 예측과 결정 규칙 — 결과를 보기 전에 적는다

| 지표 | 예측 | 이것이 아니면 |
| :-- | :-- | :-- |
| 코퍼스 19 편 **발화 문서** | **19/19** | 적으면 검사가 절을 못 찾은 것이다(계약 5 — 헤딩 들여쓰기). **구현을 멈추고 절 탐색을 고친다** |
| 코퍼스 **발화 블록** | **238** | 다르면 §1 의 블록 자가 틀렸다 |
| 코퍼스 **오탐** | **잴 수 없다 — 역할 표기가 0 이라 음성 표본이 코퍼스에 없다** | 그래서 §6 의 음성 시험이 유일한 증거다. **「오탐 0」이라고 적지 않는다** |
| 다른 검사들의 발화 수 | **전부 그대로** | 하나라도 움직이면 내가 남의 자리를 건드린 것이다 |
| 게이트 | 실패 0 · 건너뜀 0 · 경고 0 | 하나라도 어기면 병합하지 않는다 |

### 5-1. 「오탐 0」을 주장할 수 없다는 것이 이 선언의 가장 중요한 줄이다

앞 두 검사는 **코퍼스에 음성 표본이 있었다**(대괄호를 씌운 별칭 · 파싱되는 펜스). 이번 검사의 음성은 **아직 세상에 없다** — 역할 표기를 가진 블록이 0 이기 때문이다.

스킬이 경고한 그대로다:

> 스윕은 **이미 쓰인** 산문만 본다. 재생성에서 모델이 새로 쓰는 산문은 스윕에 없던 모양을 내고, 거짓 양성이면 그 자리에서 재시도를 소진시킨다.

⇒ **처방이므로 결합을 넓게 잡고(§3-1), 재생성 뒤 로그의 `(시도 N/6)` 오류를 반드시 읽는다.** 이것을 §8 의 보증 제외에 적는다.

## 7. 캐시 버전 — **올린다**

프롬프트의 **출력 계약**이 달라진다(블록마다 역할 표기 의무). 스킬 규정 그대로 인상 대상이다.

`main` 의 현재 값은 **22** 이므로 **23** 으로 올린다. 다른 세션이 23 을 먼저 썼으면 24 로 간다 — **인상 직전에 `main` 을 다시 본다.**

**인상은 전건 재생성을 강제하므로 비용이 크다.** 그래서 순서를 못박는다: **스윕을 인상 전에 돌려 오탐을 먼저 잡는다.** 그리고 실물 판은 **사람 승인 뒤에** 돌린다.

## 8. 이 선언이 보증하지 않는 것

- **🔴 15 가 사라진다고 주장하지 않는다.** 주장하는 것은 등급 하락이고, 확정은 **실물 판의 축 B 감사**다. 술어는 하나도 안 고친다(§2).
- **「오탐 0」을 주장하지 않는다**(§5-1). 음성 표본이 코퍼스에 없다. 재생성 로그의 시도별 오류를 읽는 것이 유일한 후속 증거다.
- **단계가 역할을 지키는지는 이 검사가 안 본다.** 이 검사가 보는 것은 **세트가 선언했는가**뿐이다. 「기록」이라 적힌 블록을 단계가 게이트로 쓰는 것은 다음 층이고, 그 층은 귀속이 어려워(§1-3) 이번에 만들지 않는다.
- **이미 배송된 238 블록을 고치지 않는다.** 캐시 인상에 따른 전건 재생성이 그것을 닫고, 그 실행은 사람 결정이다.
- **역할의 옳고 그름은 안 본다.** 「게이트」라 적힌 블록이 정말 게이트여야 하는지는 업무 판단이고 기계가 못 잰다.
- **명세서 경로는 범위 밖이다.** 축 A 산출물에는 검증 SQL 세트 절이 없다(앞 회차 실측: 명세서 31 편의 ```sql 펜스 0).
