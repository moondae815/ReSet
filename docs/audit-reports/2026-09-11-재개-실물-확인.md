> **이 문서의 제목을 먼저 읽어라.** 아래 「정적으로 확인한 것」은 파일을 읽어서 확인한

## 2. 어디서 어떻게 막혔는가

**막힌 것은 도구 오류가 아니라 재개 후보 자체가 안 잡힌 것이다.** 실행은 정상적으로
시작해 브레인스토밍(1/3) 단계로 들어갔다 — **저장된 목차를 이어 쓰는 재개 경로가 아니라
처음부터 새로 만드는 경로**로 갔다는 뜻이다.

콘솔 출력 축자(막 직전까지):

```
경고: 배치 모드에서 CLI provider를 사용합니다. (Actor 역할)
권한 프롬프트 정지나 구독 쿼터 소진이 발생하면 이번 실행이 중단될 수 있습니다 —
이미 만든 단계는 저장되어 같은 Job 이름으로 다시 실행하면 이어집니다.
=== 계획 전용 모드(--plan-only) — 저장된 명세서만 읽고 DB에는 연결하지 않습니다
===

=== 저장된 명세서로 통합 배치 전환 계획 수립 시작 (POQSettleBatch7-resume) ===
배치 스텝 14개 · 정적 분석 정의 14개로 진행합니다.
POQSettleBatch7-resume - AI 통합 배치 전환 계획 수립 중 (claude-cli -
claude-sonnet-5, Effort: high) [1차 분석]...
1/3. 브레인스토밍 중...: 10%
```

**기대했다면** `POQSettleBatch7-resume - run-001 에서 이어서 합니다 (재사용 13/17,
브레인스토밍·목차 생성을 건너뜁니다) — 무인 모드라 묻지 않았습니다.` 같은 줄이 뜨고
1/3·2/3(브레인스토밍·목차 설계)을 건너뛰었어야 한다(`VerificationPipelineOrchestrator.cs:2097-2101`).
그 줄이 **뜨지 않았다.**

같은 시각의 Debug 로그(`output/logs/reset-20260911.log`, 다른 병행 세션과 공유하는
파일이라 전량이 아니라 관련 줄만 발췌)도 재개 시도의 흔적이 없다:

```
2026-09-11 18:34:36.908 +09:00 [INF] 단계 본문 명세서 범위: "Narrow" - 원본 호출 그래프 7편 중 명세서를 가진 1-hop 이웃 2편 (JobName: POQSettleBatch7-resume)
2026-09-11 18:34:37.032 +09:00 [INF] POQSettleBatch7-resume - AI 통합 배치 전환 계획 수립 중 (claude-cli - claude-sonnet-5, Effort: high) [[1차 분석]]...
2026-09-11 18:34:37.040 +09:00 [INF] AI 배치 계획 브레인스토밍 요청 전송 - JobName: POQSettleBatch7-resume, TargetLanguage: C#, Effort: high
```

`PlanAttemptJournal.TryResume`이 예외로 실패했다면 `[PlanAttemptJournal] 재개 후보를
찾지 못했습니다 - 처음부터 만듭니다.`라는 Debug 줄을 남겼을 것이다(코드,
`PlanAttemptJournal.cs:410`) — 그 줄도 로그에 없다. **`TryResume`이 예외 없이 정상
종료하며 `null`을 반환하는 경로(`ReuseKey` 불일치로 어떤 `run-*`도 조건을 못 채운
경우, `PlanAttemptJournal.cs:399-406`)는 애초에 로그를 남기지 않는다** — 소프트페일
계약이 "없으면 없는 대로 조용히"이기 때문이다. 따라서 **로그만으로는 일곱 항목
(`ContractVersion`·`PlanStructureSha256`·`SpecsSha256`·`Provider`·`Model`·
`Effort`·`TargetLanguage`) 중 무엇이 어긋났는지 특정하지 못했다.**

가장 유력한 가설은 `SpecsSha256`이다 — 이 값은 이번 실행이 실제로 읽어 들인
14개 명세서 본문을 결합해 그 자리에서 새로 계산하는데(`VerificationPipelineOrchestrator.cs:1742-1746`),
원본 판이 열린 시각(2026-09-11 10:28)과 이번 실행(18:34) 사이 8시간 동안 병행
세션 여럿이 `output/Procedures/`를 계속 건드리고 있었다(이 저장소가 오늘 하루
동시에 도는 세션이 최소 셋이라는 사실은 다른 감사 문서들에도 반복해서 나온다).
**다만 이 가설을 실측으로 확인하지 않았다** — 좌표자의 지시로 진단을 여기서
멈췄다. 「무엇이 어긋났는가」는 다음 사람의 몫으로 남긴다.

브레인스토밍 API 호출이 진행 중(10%)인 것을 확인한 뒤, **재개가 아니라 처음부터
재생성하는 경로로 가는 것이 명백해진 시점에 프로세스를 강제 종료했다**(추가 비용·
시간을 재개 실증에 쓸 이유가 없었다). 종료 전 디스크 쓰기를 확인한 결과 부작용은
없었다:

- `raw/attempts/run-001/`은 손대지 않은 채 그대로였다(새 `run-002` 디렉터리가
  생기지 않았다 — `OpenRun`은 목차 확정 후에야 불리는데 그 전에 죽었다).
- `raw/Brainstorming.md`·`raw/prompt-context.md`는 복사 시점(18:33) 파일 그대로였고
  `Brainstorming.md`는 원본과 바이트 크기가 같았다(23,244바이트) — 새 브레인스토밍
  응답이 디스크에 쓰이기 전에 죽었다.

## 4. 아직 실물로 확인되지 않은 것 — 이 문서에서 가장 중요한 절

아래는 **하나도 관측하지 못했다.** 다음 사람이 이어서 확인해야 한다.

1. **재개 후보가 실제로 제안되는가** — 「13/17 재사용」 화면 문구, 브레인스토밍·목차
   설계 건너뛰기. **관측 못 함 — 오히려 반대로 브레인스토밍이 시작됐다.**
2. 승인했을 때 **다시 만드는 단계가 정확히 넷(S03·S07·S08·S10)인가.** **관측 못 함.**
3. 새 판(`run-002`)의 manifest에 **`ResumedFrom: "run-001"`**과 재사용 섹션의
   **원래 `Attempt`**가 남는가. **관측 못 함 — `run-002`가 생기지 않았다.**
4. 새 판의 파일에 **BOM이 없는가.** **관측 못 함 — 해당 파일이 생성되지 않았다.**
5. **S03의 결함 사유가 재검증 시 이름 둘로 늘어나는가**(`SQL_CURRENT_RUN_ID` +
   `SQL_CREATE_AND_CAPTURE_SHADOW`). **관측 못 함.**
6. `AnchorKindOrdinalPairTests`의 실패 수가 복사본 존재 중 베이스라인(1건)에서
   늘어나는지도 **실측하지 않았다** — Step 3가 완료되지 못해 Step 3 안의 이 확인
   항목까지 같이 못 했다. (이 항목은 전체 스위트를 복사본 존재 중 돌리지 말라는
   지시와도 맞물린다 — 애초에 돌 계기가 없었다.)

**결론: 이 실행으로는 「재개가 실물에서 작동한다」도 「재개가 실물에서 깨졌다」도
증명하지 못했다.** 증명한 것은 「이 한 번의 시도에서는 재개 후보가 안 잡혔고,
정확한 원인은 로그에서 특정하지 못했다」는 것뿐이다. `SpecsSha256` 드리프트
가설이 가장 유력하지만 미확인이다.
