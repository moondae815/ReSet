## 2. 어디서 어떻게 막혔는가

**막힌 것은 도구 오류가 아니라 재개 후보 자체가 안 잡힌 것이다.** 실행은 정상적으로
시작해 브레인스토밍(1/3) 단계로 들어갔다 — **저장된 목차를 이어 쓰는 재개 경로가 아니라
처음부터 새로 만드는 경로**로 갔다는 뜻이다.

콘솔 출력 축자(막 직전까지):

```
경고: 배치 모드에서 CLI provider를 사용합니다. (Actor 역할)
권한 프롬프트 정지나 구독 쿼터 소진이 발생하면 이번 실행이 중단될 수 있습니다 —
이미 만든 단계는 저장되어 같은 Job 이름으로 다시 실행하면 이어집니다.
=== 계획 전용 모드(--plan-only) — 저장된 명세서만 읽고 DB에는 연결하지 않습니다
===

=== 저장된 명세서로 통합 배치 전환 계획 수립 시작 (POQSettleBatch7-resume) ===
배치 스텝 14개 · 정적 분석 정의 14개로 진행합니다.
POQSettleBatch7-resume - AI 통합 배치 전환 계획 수립 중 (claude-cli -
claude-sonnet-5, Effort: high) [1차 분석]...
1/3. 브레인스토밍 중...: 10%
```

**기대했다면** `POQSettleBatch7-resume - run-001 에서 이어서 합니다 (재사용 13/17,
브레인스토밍·목차 생성을 건너뜁니다) — 무인 모드라 묻지 않았습니다.` 같은 줄이 뜨고
1/3·2/3(브레인스토밍·목차 설계)을 건너뛰었어야 한다(`VerificationPipelineOrchestrator.cs:2097-2101`).

같은 시각의 Debug 로그(`output/logs/reset-20260911.log`, 다른 병행 세션과 공유하는

계약이 "없으면 없는 대로 조용히"이기 때문이다. 따라서 **로그만으로는 일곱 항목

**다만 이 가설을 실측으로 확인하지 않았다** — 좌표자의 지시로 진단을 여기서
멈췄다. 「무엇이 어긋났는가」는 다음 사람의 몫으로 남긴다.

> **★ 2026-09-12 정정: 이 가설은 기각됐다.** 실측 원인은 §7의 「Task 6이 실패한
> 원인이 확정됐다」절을 보라 — 명세서 드리프트가 아니라 **`--plan-only`(배치 모드)
> 대 대화형 TUI**의 진입점 해석 차이였다. `output/Procedures`의 md 70편 중 판이
> 열린 이후 수정된 것은 0건이었다(2026-09-12 재확인).

브레인스토밍 API 호출이 진행 중(10%)인 것을 확인한 뒤, **재개가 아니라 처음부터
재생성하는 경로로 가는 것이 명백해진 시점에 프로세스를 강제 종료했다**(추가 비용·

  생기지 않았다 — `OpenRun`은 목차 확정 후에야 불리는데 그 전에 죽었다).
- `raw/Brainstorming.md`·`raw/prompt-context.md`는 복사 시점(18:33) 파일 그대로였고

### ★ 여기서 읽어야 할 것 셋 — 이 절이 이 문서의 값이다

**(가) 재개의 즉시 이득이 수로 보인다.** 1회차가 **0 대 74** 다. 결함 없는 섹션
13개를 물려받아 훨씬 높은 데서 출발했다.

**(나) 절감은 1회차에 국한된다.** 2회차부터는 리뷰가 지목한 단계를 다시 만든다.
지목 수가 3·2·3 → **12** → 7 로 튀었고, 최종 manifest 를 보면 거의 모든 단계가
`Attempt 5~6` 이며 **골격의 최종 `Attempt` 도 5** 다(1회차엔 재사용됐다). **「13/17
재사용」은 1회차의 사실이지 실행 전체의 사실이 아니다.**

**(다) 88 대 94 를 「재개하면 품질이 떨어진다」로 읽으면 안 된다.** 6회차의 0 은
진짜 0 이 아니라 `JSON 검토 보고서 파싱 중 오류` 다 — 로그가 「최종 보완 실패.
가장 높은 점수를 받은 3차 시도(88/100)를 채택합니다」로 끝났다. **원판은 6회차가
94 로 성공했는데 이 판은 마지막 기회를 파싱 사고로 잃었다.** 한 표본으로는 품질
차이와 사고를 못 가른다. 가리려면 통제 실행이 여러 판 필요하다.

**S13 은 원판에서 `Attempt 1` 에 깨끗했다가 이 판의 `Attempt 6` 에서 결함이 됐다.**
사유는 S03 과 같은 서명(`SQL_CURRENT_RUN_ID` 미정의 블록 참조). 이 저장소에 이미
기록된 **「재시도가 닫힌 결함을 되살린다」**의 또 한 자리로 보인다.

S13 이 덮는 것은 `dbo.UP_UTIL_SETTLE_SUMMARY_ETC` 다. 병행 세션이 **같은 SP** 의
단계에서 결함을 찾았다(Batch6/S13·Batch4/S15). ★ **다만 겹치는 것은 SP 하나뿐이다**
— 그쪽은 배송본의 **의미 결함**이고 이쪽은 재시도 회차에서 생긴 **미정의 블록
참조**다. **「같은 결함이 두 자리에서 났다」로 적지 마라.**

**정정(이 갱신 작업 중 직접 대조):** 좌표자 브리프는 그쪽 기록을
`docs/audit-reports/2026-09-05-축B-잔여결함-분류.md` §22 로 가리켰으나, 그 문서는
§21에서 끝난다(§22가 없다) — **그 인용은 잘못됐다.** 실제 기록은 다음 두 자리다:

- **Batch6/S13** — `output/Jobs/POQSettleBatch6/consistency/ConsistencyReport.md:120`.
  원본은 커서 키와 일치하는 행을 OUTSTATE 무관·B 결합 무관으로 전부 합산하고
  GROUP BY에 OUTSTATE가 있어 OUTSTATE별로 여러 집계 행을 만드는데, 단계 본문이
  `A.OUTSTATE=9`를 술어에 고정해 도메인을 좁혀 SUM 금액이 작아지고 OUTSTATE≠9
  그룹 행이 삽입되지 않는다.
- **Batch4/S15** — `docs/audit-reports/2026-09-06-POQSettleBatch4-재생성-판독.md:120`.
  원본에 없는 필터(`OUTSTATE=9 AND USESTATE=0 AND OUTYMD IS NOT NULL`)를 더했다.

두 자리 다 「원본에 없는 `OUTSTATE=9` 관련 술어를 더해 집계 도메인이 좁아진다」는
의미 결함이고, 이 문서(run-002/S13)의 「미정의 SQL 블록 참조」와는 결함의 종류
(의미 대 형식)가 다르다는 브리프의 구분 자체는 실물 대조로 **성립한다** — 인용
좌표만 틀렸다.
