# GPT 가 가드에 PLTID 조건을 지어내는 원인 — 측정 · 스윕 배너 인공물 수정

**작성 시점**: 2026-09-14. 코드: main `611b2e78`.

# 1. PLTID 날조의 원인

## 1-1. 현상

GPT Consolidator 판 다섯 개 연속으로 `UP_Util_PG_Client_CMRate_Ins` 20 행 가드(`IF EXISTS (SELECT PLTID FROM TSettleMst WHERE YMD = @pi_strYMD AND OutState IN (1,5) AND OutYMD IS NOT NULL)`)를
옮기면서 원본에 없는 PLTID 조건을 붙였다 — B11 `'POQ'` · B12 `1` · B13 `13` · B14 `'POQ'` · B15 `15`. 가드 술어 대조 검사가 판 안에서 닫지만 판마다 재생성 1~2 회를 쓴다.

## 1-2. 프롬프트에 무엇이 실렸나 (비용 0)

Batch15 S03 단계 생성 요청(로그 523 행, 약 88K 자)을 열었다.

- **원본 DDL 이 없다** — `Narrow` 범위라 명세서만 실린다. `PLTID` 는 요청 전체에 **한 번** 나온다.
- 그 한 번은 명세서 CRUD 표 SELECT 행의 **참조 컬럼 칸**이다: `| SETTLE_POQ_DB.dbo.TSettleMst | (없음) | PLTID, YMD, OutState, OutYMD | IF 1 (라인 20~24) | … EXISTS 서브쿼리 |` — SELECT 목록 컬럼과 조건 컬럼이 한 칸에 섞였다.
- **가드의 WHERE 는 어디에도 없다** — 명세서 기계 확정 표(DML 범위 · 집합 술어)에 IF 행이 없다(가드 술어 표류 측정 §4).
- Job 이름 `POQSettleBatch15` 는 두 번 나온다(시스템 첫 문장 · 사용자 머리).

→ 모델은 컬럼 목록만 보고 WHERE 를 재구성해야 하고, `PLTID` 를 조건으로 읽는다는 가설과, 값을 Job 이름에서 가져온다는 가설이 선다.

## 1-3. 인과 — 같은 요청을 한 가지씩만 바꿔 재생 (OpenRouter `gpt-5.6-sol`, 백엔드 openai 고정, 12 호출 약 $1.27)

로그의 S03 요청 JSON 을 그대로 다시 보내고 한 곳만 바꿨다. 판정은 **실제 가드 술어 대조 검사**(`MechanicalValidator.ValidateBatchStep` + 원본 DDL)로 했다.
(처음 쓴 정규식 판정은 WHERE 를 `IN (1, 5)` 의 `)` 에서 잘라 전부 ✘ 로 냈다 — 자가 틀려 버렸고 검사로 다시 쟀다.)

| 변형 | 바꾼 것 | 가드 표류 | 지어낸 값 |
| :-- | :-- | :-- | :-- |
| base | 없음(Batch15 S03 요청 그대로) | **2/3** | `PLTID = 15` |
| job | Job 이름 `POQSettleBatch15` → `SettleNightlyJob`(숫자·POQ 없음) | **3/3** | `PLTID = 1` |
| crud | CRUD 행 참조 컬럼을 「YMD, OutState, OutYMD (조건) · PLTID (SELECT 목록일 뿐)」로 · WHERE 원문을 덧붙임 | **0/3** | — |
| guardblock | 명세서는 그대로 두고 사용자 메시지 끝에 `[Original Guard Conditions]` 표(원본 DDL 의 WHERE 원문 · SELECT 목록 분리) | **0/3** | — |

- **원인은 명세서 재료다** — 조건을 알려 주면(crud · guardblock) 0/3, 안 알려 주면 2/3 · 3/3.
- **Job 이름은 날조를 일으키지 않고 값만 정한다** — 이름에서 숫자를 빼도 날조는 3/3 이고 값이 `15` 에서 `1` 로 바뀐다(B12 의 `1` 과 같은 값).
- **명세서를 다시 만들지 않아도 된다** — 계획서 생성 때 원본 DDL 에서 뽑은 가드 조건 블록(guardblock)만으로 0/3 이다. 표류 0 은 「PLTID 없음」이 아니라 **추가·누락 항 0**(검사 판정)이다.

표본은 변형당 3 이다. 실물 판 다섯 개 연속 날조와 방향이 같다.

## 1-4. 처방 후보(구현 안 함 — 결정 대기)

`[Original Guard Conditions]` 블록을 단계 섹션 생성(과 단일 호출 폴백) 프롬프트에 싣는다 — 재료는 이미 있다(`GuardPredicateFacts.GuardsFromDdl`, 오케스트레이터가 `ddlByProcedure` 를 가진다).
경로가 둘 이상이라 잠금은 경로마다 건다. 명세서 캐시 인상은 필요 없다(명세서 불변).

# 2. 스윕 배너 인공물

## 2-1. 원인

번들 내보내기(`InstructionBundleWriter.BuildFloorBanner`)가 하한 미달·검증 불가 단계 파일 머리에 `> ⚠️ **이 단계는 …**` 배너를 붙인다. 단계 검사 스윕(`SweepCommand`)이 그 파일을 **그대로** 읽어
`ValidateBatchStep` 의 첫 줄 검사가 「`### ` 헤딩으로 시작하지 않습니다」를 발화했다. 판 안의 검사는 배너가 붙기 전 섹션을 봐서 발화하지 않는다 — 스윕만의 인공물이다. 코퍼스의 배너 단계 파일은 36 이다.

## 2-2. 수정과 결과

- `InstructionBundleWriter.StripFloorBanner` — 배너 머리 문구(`> ⚠️ **이 단계는`)로 시작할 때만 인용 블록과 뒤 빈 줄 하나를 벗긴다. 섹션 자신의 인용문은 건드리지 않는다.
