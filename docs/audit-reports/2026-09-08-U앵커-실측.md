**그래서 이 회차가 집은 것은 §9 가 남긴 진짜 다음 걸음이다** —

## 1. ★ 기제를 찾았다 — **유일성 규칙이 「일치하는 중복」을 모호성으로 버린다**

`StepSqlStatementReader.ReadAnchor` 의 마지막 줄이다.

```csharp
return matchCount == 1 ? ordinal : null;   // :587
```

창 안에서 **매치가 둘 이상이면 앵커를 통째로 버린다.** 그런데 이 코퍼스의 표준 관용구가
한 문장 앞에 주석을 **둘** 둔다 — 기계 라벨과 U-앵커다.

```
102: -- SQL_INSERT1 (INSERT 1, 오류코드 -2)      ← 「INSERT 1」 공백 있음 → 원판도 매치
103: /* INSERT1: PG 계약정보 → TPGSettleRate … */  ← 「INSERT1」 공백 없음 → 완화판에서만 매치
104: INSERT INTO SETTLE_POQ_DB.dbo.TPGSettleRate
```

**둘은 같은 서수를 말한다.** 패턴을 완화하면 둘 다 매치해 `matchCount == 2` 가 되고
**앵커가 사라진다.** §9 가 관측한 「Batch1 87 → 84」의 정체가 이것이고, **잃은 다섯은 전부
`S02` 의 INSERT 1~5** 였다(전건 확인).

## 2. 처방과 실측 — **패턴은 안 건드린다. 유일성을 일치로 바꾼다**

`matchCount == 1` → `distinct.Count == 1`(서수 집합의 크기). **일치하는 중복은 인정한다.**

```
                                      Batch1   Batch4   Batch5   합계
원판  \s+ · matchCount==1 (오늘)          87       78       89     254
완화  \s* · matchCount==1 (§9 가 잰 것)   84        -        -       -      ← 손해
원판  \s+ · distinct==1   (이 처방)       90       78       92     260   ← +6 · 잃은 것 0
완화  \s* · distinct==1                   92        -        -       -
```

**§9 가 「패턴 완화는 손해」라고 판정한 것은 옳았다.** 고칠 자리는 패턴이 아니라 **유일성 규칙**이다.
패턴을 그대로 두고도 **+6 을 얻고 하나도 안 잃는다.**

**새 앵커를 전건 열었고 전부 옳다.** 예: `Batch1/S12` 는
`-- … (DELETE 1, 원본 라인 44~50)` 과 `/* DELETE 1: 커서가 순회하던 그룹을 상관 EXISTS로 치환 */`
가 **같은 서수·같은 종류**를 말하는데 유일성 규칙이 그 둘을 모호성으로 버리고 있었다.

## 3. ⚠ 그런데 대가가 있다 — **검사 B·C 가 각각 하나씩 새로 발화한다**

앵커가 없던 문장은 앵커 계열 검사(B·C·D)가 **통째로 꺼져 있다.** 앵커를 되살리면 그 방어가
켜진다 — 이 저장소가 바라던 방향이면서 동시에 위험이다.

```
기준선  A 0 · B 2 · C 1 · D 0 · E 0 · 미분류 27
이 처방 A 0 · B 3 · C 2 · D 0 · E 0 · 미분류 27      ← +2, 둘 다 POQSettleBatch1/S12/INSERT 1
```

| 검사 | 발화 내용 |
| :--- | :--- |
| B | 최상위 술어/조인 키에서 `OUTYMD, PGNAME` 소실 |
| C | 원본에 없는 조건 `EDIReqYmd, AcqType, OutState` 추가 |

**둘 다 「커서를 집합으로 치환」 관용구의 서명이다.** 원본은 `SELECT 1` 이 그룹을 순회하고
그 그룹의 `(OUTYMD, CLIENTID, PGNAME)` 로 `INSERT 1` 을 걸었는데, 이행은 커서를 없애고
`SELECT 1` 의 필터(`EDIReqYmd`·`AcqType`·`OutState`)를 INSERT 의 WHERE 로 올렸다
(`S12.md:127-131`). **단계 자신이 머리에 그렇게 적는다.**

**그러므로 이 둘은 오탐일 공산이 크다 — 그리고 그 판정에 필요한 것이 이미 미결로 적혀 있다.**
분류표 §5 의 「먼저 할 것 6」이 그것이다: **「모양 대조를 문장 구간 단위로 좁히기 — 선결:
이전(移轉) 면제를 먼저 만들어야 한다」.** 커서→집합 치환은 정확히 그 「이전」이다.

## 4. 판정 — **지금 배송하지 않는다**

- **얻는 것**: 앵커 +6(254 → 260), 잃는 것 0, 한 줄 변경.
- **대가**: 검사 B·C 발화 +2 이고 **둘 다 오탐일 공산이 크다.**
- **그 대가가 왜 무거운가**: L1 오류는 **재생성 트리거**다. 거짓 고발은 다음 재생성에서
  `POQSettleBatch1/S12` 의 **재시도를 태운다**(스킬 「완료 기준」이 못박은 자리이고,
  2026-08-23 `CheckParameterColumnClaims` 가 실제로 6/6 을 소진시켰다).

**그래서 순서가 있다: 「이전 면제」가 먼저이고 이 한 줄이 그다음이다.** 반대로 하면 개선이
오탐을 데리고 들어온다.

## 5. 다음 사람에게 — 여기서부터 열어라

1. **`ReadAnchor` 의 유일성을 일치로 바꾸는 한 줄은 이미 검증됐다** — +6 · 손실 0 ·
   새 앵커 전건 옳음. **그 자체는 논쟁거리가 아니다.**
2. **막는 것은 「이전 면제」다.** 커서→집합 치환에서 사라진 최상위 술어를 검사 B·C 가
   결함으로 보지 않게 하는 것. 검사 B 에는 이미 `relocated`(하위 스코프로 옮겨간 컬럼)가
   있는데 **커서 변수는 그것으로 안 걸린다** — 옮겨간 것이 아니라 **없어진 것**이기 때문이다.
3. **T22 는 그 뒤다.** §9 가 「T22 를 여는 길은 S15 의 두 문장」이라 했고, 그 둘은
   패턴 완화(`\s*`)까지 있어야 열린다(이 처방만으로는 안 열린다 — 위 표에서 Batch1 90 대 92).

## 6. 이 판독이 보증하지 않는 것

- **검사 B·C 발화 둘을 「오탐」으로 확정하지 않았다.** 「관용구의 서명이고 오탐일 공산이
  크다」까지다 — 확정하려면 원본 DDL 로 커서 의미까지 대조해야 하고 이 회차는 안 했다.
- **다른 20 편은 이 회차의 관할이 아니다**(규칙 이전 산출물, §8).
- **패턴 완화(`\s*`)는 여전히 안 쟀다** — 이 처방과 함께면 Batch1 이 92 인데, 그때 켜지는
  검사 발화는 재지 않았다.
