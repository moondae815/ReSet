## 0. 공통 규율

- **빌드·테스트는 이 격리 워크트리에서만.** 동료 세션(`reset-67`)은 정화기·배너 구역이고
  `BatchControlContract`·`ControlRowOrigin` 은 안 만진다고 확인했다.
- 게이트는 **실패 0 · 건너뜀 0 · 경고 0.** 절대 통과 수는 게이트로 안 쓴다.
- **발화 수를 판정으로 쓰지 않는다. 새 발화는 전부 열어 본다.**
- **숫자를 맞추려고 아래 조건을 손보지 않는다.** 어긋나면 되돌린다.

## 1. 무엇을 잡는가

`batch.BatchRun.RunStatus` 는 계약이 `Running · Succeeded · Failed · Restarting` 넷을 확정하는데,
**코퍼스 어느 단계도 `Failed` 를 쓰지 않는다.** 실패한 실행이 `'Running'` 으로 남고,
다음 회차가 그것을 **재시작 대상으로 집어 든다**(재감사 §173: 「전은 S02 한 단계의 이탈,
후는 18단계 전부」).

## 2. 오라클 — `BatchControlContract`(커밋된 소스). 비순환

`src/ReSet.Core/Services/BatchControlContract.cs:115` 가 표·컬럼·**허용 어휘**·상태 컬럼을
전부 갖는다. **생성물이 아니라 저장소 소스라 재생성이 지워도 안 없어진다.**

**대장이 적어 둔 「아키텍처의 상태 전이 선언」은 쓰지 않는다** — 그것은 생성물
(`agent/common/00-architecture.md`)이라 **순환**이고 산문이다. 실물이 `:138` 에
`Running --> Failed : 예외 관측` 을 선언하고도 아무 단계가 안 지키는데, 그것은 **결함이
진짜임의 방증**으로만 쓰고 판정 재료로는 안 쓴다.

## 3. 판정 — 비대칭만 본다

계약의 상태 컬럼 `C`(표 `T`)와 그 선언 값 `v` 에 대해:

1. 이 Job 의 단계 본문 **코드 펜스 안**에 `C = 'v'` 대입이 **0 회**인가.
2. 그런데 **같은 값 `v` 가 다른 상태 컬럼에는** 대입되는가.

둘 다 참이면 발화한다. **「선언됐는데 0 회」(A 안)로 넓히지 않는다** — 실측으로 발화 6 중
**5 가 오탐**이었다(`Skipped`·`Pending`·`Info`·`Warning`·`Error` 는 그냥 안 쓰는 값일 수 있고,
안 쓰는 것이 결함이라는 근거가 없다).

**② 가 하는 일**: 「이 값은 이 시스템에서 실제로 쓰이는 어휘다」를 코퍼스 스스로 증명하게
한다. 아무도 안 쓰는 값은 「미구현」이 아니라 「이 판에 해당 없음」일 수 있다.

## 4. ★ 펜스 정책 — 코드 펜스만 읽는다 (실측으로 정했다)

오라클 실측이 열어 둔 **유일한 결정**이었다. 실측:

```
RunStatus = 'Failed'     문서 전체  0 · 코드 펜스 안  0     ← 판정은 어느 쪽이든 같다
RunStatus = 'Running'    전체     26 · 펜스 안     22     ← 4 건이 산문에 있다
RunStatus = 'Succeeded'  전체      3 · 펜스 안      3
StepStatus = 'Failed'    전체      4 · 펜스 안      4     ← 형제 증거는 양쪽 동일
```

**오늘은 결과가 안 바뀐다. 그래도 코드 펜스만 읽는다** — 산문을 세면
「실패 시 `RunStatus` 를 `'Failed'` 로 기록한다」는 **문장 하나가 검사를 침묵시킨다**(거짓 음성).
안전한 실패 방향은 「덜 인정한다」쪽이다.

## 5. 자리 — 단계 층이 아니라 **Job 층**이다

「이 Job 어디에도 없다」는 판정이라 단계 하나만 보는 `ValidateBatchStep` 으로는 **원리적으로
못 한다**(다른 단계의 본문을 못 본다). `ValidateSplitProcedureObligations` 가
`sectionsByStepCode` 로 **모든 단계 본문**을 받으므로 그 옆에 **형제 메서드**로 단다.
그 메서드의 문서 주석이 이미 같은 논거를 적어 뒀다 — 「의무를 단계에서 문서로 올리면
보장을 잃지 않고 불가능한 요구만 없앤다」.

**귀속**: 계약이 `FirstStepInserts` 로 정한 표(`batch.BatchRun`)의 **행 생성 단계**에 건다.
그 해석기가 이미 있다(`BatchControlContract.ResolveRowCreators`). 못 찾으면 **침묵한다**
(귀속 불가면 보고하지 않는다 — 작성 계약 7).

## 7. 되돌림 조건 — 하나라도 어긋나면 되돌린다

- **R1**: 코퍼스 발화가 **0** 이면 되돌린다. 재료가 안 닿은 것이다.
- **R2**: 발화가 **1 을 넘고 그 초과분이 오탐**이면 되돌린다.
- **R3**: **다른 검사(A~E·미분류)의 카운트가 변하면** 되돌린다. 기준선은
  `sweeps/2026-09-07-step-sweep-c.md` — **A 0 · B 2 · C 1 · D 0 · E 0 · 미분류 23(측정 쌍 50 · Job 3)**.
- **R4**: 검사를 되돌렸을 때 **사라지는 발화가 정확히 새 발화뿐**이 아니면 되돌린다.

## 8. 알려진 한계 — 미리 적는다

- **발화 1 은 판별력이 얇다.** T22·G05 와 같은 모양이다. **다만 재료는 두껍다**(선언 값 15) —
  얇은 것은 결과이지 재료가 아니다. 그래도 **이 검사의 발화 0 을 「종료 처리가 온전하다」로
  읽으면 안 된다.**
- **「어디에도 안 쓰는 값」은 영영 안 잡는다**(조건 2 가 거른다). `Skipped`·`Pending`·
  `Info`·`Warning`·`Error` 다섯이 그 자리다. 의도된 침묵이고, 그 다섯이 결함인지는
  **이 검사가 답하지 않는다.**
- **대입만 본다.** `UPDATE … SET RunStatus = 'Failed'` 를 앱 코드(`agent/src`)가 하면
  이 검사는 못 본다. 오늘 코퍼스에는 그런 실물이 없다(골격 스텁이 상태 문자열을 안 쓴다).
- **캐시 버전은 안 올린다** — 프롬프트 계약이 안 바뀐다(L1 만 조인다). 대신 스킬이 요구한
  대로 **코퍼스 전수 스윕의 전후 차분**을 보고에 적는다.
