# 이름 있는 SQL 블록 검사가 공통 규약의 정의를 인정한다 (사전 선언)

**작성 시점**: 2026-09-14, **구현 전**. **코드**: main `75d21e95`.

## 0. 문제

`CheckUndefinedSqlBlockReference`(단계 하한 검사)는 단계가 `execute(SQL_X, …)` 로 부른 이름의 정의(`-- SQL_X`)를 **그 단계 절 안의 SQL 펜스에서만** 찾는다.
그런데 골격의 공통 규약(`BatchPlanAssembler.ExtractSharedConventions` — 단계 섹션 생성 요청에 그대로 실리고, 배송 번들 `agent/common/01-step-contract.md` 가 된다)이 저널·RunId 블록을 한 번 정의하고 모든 단계가 부르는 것이 설계다.
검사는 그 정의를 못 봐서, 호출만 한 단계를 「정의 없음」으로 재생성시키고 재생성은 공통 블록을 절마다 베껴 닫힌다.

- POQSettleBatch16: 하한 재생성 16 이 전부 이 사유 · 베낀 사본 45(16·14·15)이 공백 정규화 후 공통 정의와 **전부 같다**(`2026-09-14-GPT-2회판-Batch16-사전선언.md` §발견 1).

## 1. 측정 (구현 전, 자는 검사와 같은 정의 규칙 — SQL 펜스 안 · 호출부를 지운 뒤에도 이름이 남는 줄 · 별표 접두사)

### 1-1. 판 안 발화 — 요청 본문이 비순환 기준

OpenRouter 판은 단계 섹션 요청 본문이 로그에 남는다. 발화마다 **그 단계가 받은 요청 본문**에서 부른 이름의 정의를 찾았다.

| Job | 발화 | 부른 이름 전부가 요청 본문(공통 규약)에 정의됨 |
| :-- | --: | --: |
| POQSettleBatch11 | 2 | 2 |
| POQSettleBatch13 | 2 | 2 |
| POQSettleBatch15 | 1 | 1 |
| POQSettleBatch16 | 16 | 16 |
| **계** | **21** | **21** |

claude-cli 판(B7~B10)은 요청 본문이 로그에 없고, 디스크의 `raw/attempts/run-*/skeleton.md` 는 마지막 시도의 골격이라 발화 시점 골격과 다를 수 있다(B8 은 디스크 골격에 `SQL_CURRENT_RUN_ID` 정의가 없는데 배송 공통 규약에는 있다). 그래서 이 판들은 판정하지 않는다.

### 1-2. 배송본 — 스윕과 같은 입력(`agent/steps` + `agent/common/01-step-contract.md`)

오늘 스윕의 이 검사 발화 16(전부 「미분류」 칸):

| 분류 | 수 | 자리 |
| :-- | --: | :-- |
| 부른 이름 전부가 공통 규약에 정의 — **침묵해야 한다** | **9** | B1 S02·S11·S12·S14 · B7 S03 · B8 S09·S10 · B10 S08·S15 (전부 `SQL_CURRENT_RUN_ID` · B7 S03 은 `SQL_CREATE_AND_CAPTURE_SHADOW` 포함) |
| 공통 규약에도 없는 이름이 남음 — **계속 발화, 남은 이름만 지목** | **7** | 지목 이름 수 전→후: B1 S08 19→18 · S09 9→8 · S13 9→8 · S15 3→2 · B5 S08 4→4 · S09 4→4 · S10 8→8 |

B1·B8·B10 의 `SQL_CURRENT_RUN_ID` 공통 정의는 `-- SQL_CURRENT_RUN_ID` 뒤 `SELECT RunId FROM batch.BatchRun …` 인 실제 SQL 블록이다(눈으로 확인). 남은 항목 「claude-cli `SQL_CURRENT_RUN_ID`」가 이 오탐이었다.

## 2. 설계

1. `ValidateBatchStep` 에 선택 인자 `sharedConventions`(null 이면 종전 동작). `CheckUndefinedSqlBlockReference` 는 정의를 **단계 절의 SQL 펜스 + 공통 규약의 SQL 펜스**에서 찾는다. 정의 규칙(호출부 줄 제외 · 별표 접두사)은 두 텍스트에 똑같이 적용한다.
2. 호출 수집은 단계 절에서만 한다 — 공통 규약이 부르는 이름은 이 단계의 책임이 아니다.
3. 오류 문구·처방은 그대로(남는 이름은 여전히 이 절에 정의해야 할 이름이다).
4. 배선: 오케스트레이터의 단계 검증 호출이 단계 생성에 쓴 그 `conventions` 를 넘긴다. 스윕은 `SweepJob.SharedConventions` 로 받고, `SweepCommand` 가 배송 번들 `agent/common/01-step-contract.md` 를 읽는다(배송 단계 파일과 짝이 맞는 유일한 공통 규약 — 디스크 골격은 §1-1 처럼 어긋날 수 있다).
5. 프롬프트 불변 · L1 만 느슨해짐 → 캐시 버전 올리지 않음(스윕 차분으로 대신한다).

**오탐 방향**: 이 변경은 발화를 줄이기만 한다 — 새 거짓 양성은 원리상 없다. 대신 **놓침**(공통 규약에 정의가 있다는 이유로 진짜 결함을 침묵)이 위험이다: 공통 정의가 있으면 구현자가 번들에서 그 SQL 을 읽을 수 있으므로 「구현 불가」라는 이 검사의 존재 이유가 성립하지 않는다 — 놓침이 아니다. 공통 정의와 절 안 사본이 **다른** 경우는 이 검사의 관할 밖이다(기록).
