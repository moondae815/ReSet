## 0. 실제로 돌린 명령

## 2. 단계 본문의 펜스 언어 태그 전수

계획서 명령 그대로:

```
$ grep -rhoE '^```[a-zA-Z]+' output/Jobs/*/agent/steps/*.md | sort | uniq -c | sort -rn
1124 ```sql
 154 ```csharp
  84 ```pseudocode
  22 ```text
   1 ```mermaid
```

정규식이 `[a-zA-Z]+` 라 숫자·기호가 든 태그를 놓칠 수 있어 넓혀 한 번 더 쟀다:

```
$ grep -rhoE '^```[^ ]*' output/Jobs/*/agent/steps/*.md | sort | uniq -c | sort -rn
1385 ```
1124 ```sql
 154 ```csharp
  84 ```pseudocode
  22 ```text
   1 ```mermaid
```

여는 태그 합 `1124 + 154 + 84 + 22 + 1 = 1385` 이고 맨 ` ``` ` 가 정확히 1385 다. **펜스가 짝이
맞고, 알파벳 밖의 태그는 하나도 없다.** 즉 위 다섯이 전량이다.

대상 규모: 파일 386 편, Job 25 개.

### 2-1. 태그별 `execute(` 귀속 — 전수

태그 분포만으로는 「검사가 훑을 태그 집합」이 안 정해진다. 바인딩이 실제로 어느 태그에 사는지를
따로 쟀다(파이썬 재구현, 펜스 상태 기계는 계획서 awk 와 같다):

```
   406  pseudocode
펜스 밖 execute( : 0
```

단계 본문 전체의 `execute(` 는 **406 개이고 전량이 ` ```pseudocode ` 안**이다.
`sql`·`csharp`·`text`·`mermaid` 안에는 **0 개**, 펜스 밖에도 **0 개**다.

교차 확인:

```
$ grep -rh 'execute(' output/Jobs/*/agent/steps/*.md | wc -l
     406
$ grep -rl 'execute(' output/Jobs/*/agent/steps/*.md | wc -l
      50
```

## 3-4. 코드 층에서 비순환으로 한 번 더 확인했다

위 세 절은 전부 산출물끼리의 대조라 순환일 수 있다. **검사가 무엇을 받는지**를 코드에서 직접 읽었다.

- `VerificationPipelineOrchestrator.cs:4283` — `_validator.ValidateBatchStep(content, ...)`.
  `content` 는 `GenerateBatchStepSectionAsync` 가 돌려준 **단계 섹션 원문 그대로**다. 조립 전이라
  잘라내기·정화가 끼지 않는다.
- `MechanicalValidator.cs:417` — `Regex.Matches(stepMarkdown, @"(?m)^\s*```").Count < 2` 로 펜스를 센다.
  즉 `stepMarkdown` 은 **펜스를 지운 텍스트가 아니라 펜스가 든 원시 마크다운**이다.
- `SweepCommand.cs:79` — 스윕 도구는 `Path.Combine(jobDir, "agent", "steps", $"{step.Code}.md")` 를
  읽어 그대로 `ValidateBatchStep` 에 넘긴다(`StepSweepService.cs:178`).

따라서 **이 문서가 잰 `output/Jobs/*/agent/steps/*.md` 는 스윕이 검사에 먹이는 바로 그 바이트**이고,
파이프라인이 먹이는 것과도 같은 텍스트다. 코퍼스 측정이 검사가 보는 것을 안 잰 경우가 아니다.

## 4. 판정

- **도달 가능성: 닿는다.** 세 결함 자리의 바인딩은 셋 다 ` ```pseudocode ` 안에 있고,
  `ValidateBatchStep` 이 받는 `stepMarkdown` 은 펜스를 보존한 원시 마크다운이다(§3-4).
  단계 본문의 `execute(` 406 개가 **전량** 그 태그 안이며 펜스 밖은 **0** 이다.
- **Task 3 이 훑을 태그 집합: ` ```pseudocode ` 하나면 충분하다.**
  근거는 §2-1 — `sql`·`csharp`·`text`·`mermaid` 안의 `execute(` 는 각각 0 개다.
  (전수 태그는 `sql` 1124 · `csharp` 154 · `pseudocode` 84 · `text` 22 · `mermaid` 1 이고 이것이 전량이다.)
  다만 조립본 산문에 `execute(` 를 **인용**하는 자리가 2 개 있으므로(§3-3), 검사를 펜스 밖까지
  넓히면 그 둘이 곧바로 오탐이 된다. **펜스 안으로 한정하는 것이 오탐 0 의 조건이다.**
- **조립본과 번들이: 같다.** 계획서가 지정한 여섯 자리 전부, 그리고 Batch4·Batch5 의 단계 32 개
  전부에서 `execute(` 수가 일치한다. 세 결함 줄은 조립본에도 축자로 있고 거기서도 `pseudocode`
  펜스 안이다.

**멈춤 조건 둘 다 해당 없음.** Task 3·4·5 의 전제가 선다.

## 5. 이 측정이 닫지 않는 것

- **오탐은 안 쟀다.** §6-5 의 「23 을 전부 열어 본다」는 여기 없다. 이 문서는 재료가 검사 손에
  닿는지만 잰다.
- **세 자리가 정말 결함인지도 안 되쟀다.** §6-5 가 요구하는 재검은 별도다.
- **`execute(` 라는 자 자체를 검증하지 않았다.** 바인딩 목록이 `execute(` 로만 표현된다는 전제는
  이 측정의 입력이지 산출이 아니다. 다른 표기(예: 펜스 안의 다른 호출 형태)로 쓰인 바인딩이
  있다면 406 은 하한이다.
