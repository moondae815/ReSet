## 2. ★ 파급을 실증했다 — 빨간 것을 눈으로 봤다

`Validate` 30 자리를 `SafeCheck` 로 감싸고 catch-all 은 아직 그대로 둔 중간 상태에서:

```
실패 CheckIsolationTests.Validate_WhenALaterCheckThrows_TheEarlierFindingSurvives
  Assert.Contains() Failure: Filter not matched in collection
  Collection: []                                    ← 앞선 검사의 발화가 실제로 지워졌다
실패 CheckIsolationTests.Validate_WhenALaterCheckThrows_DetailedErrorsSurviveToo
  Assert.NotEmpty() Failure: Collection was empty
```

`Collection: []` 가 이 감사 항목의 전부다. **「조용히 통과」가 아니라 「찾은 것을 지우고
통과」**임이 실물 경로에서 확인됐다. catch-all 을 고친 뒤 6/6 초록.

### 오라클을 `IsValid` 로 두지 않았다

`IsValid` 는 catch-all 이 **직접 조작하는** 값이다. 그것을 기준으로 삼으면 검사가 자기를
채점한다. 기준은 **「앞선 검사가 넣은 구체적 발화 문자열이 `Errors` 에 살아 있는가」**로
뒀다.

### 주입점을 연 근거 — 실물로는 못 던지게 한다

| 재료 | 규모 | catch-all 발동 |
| :--- | ---: | ---: |
| 실행 로그 `output/logs/*.log` | 40 파일 · 2,549,970 줄 · 38 일 | **0** |
| 배송 코퍼스 × 던지게 만들려는 변형 14 가지 | 31 편 × 14 = 434 회 | **0** |

변형 14: 표 행을 파이프 1 개로 · 파이프 전부 제거 · 헤딩 전부 제거 · 줄바꿈 제거 ·
백틱 홀수 · 코드펜스 미닫힘 · 표 헤더만 · NUL·제어문자 · 서러게이트 단독 ·
20 만 자 한 줄 · 헤딩 레벨 7 · 공백만 · mermaid 깨뜨리기 · 원본.

발동은 `ReferenceEquals(result.CleansedMarkdown, markdown)` 로 관측했다 — 소프트 패스
경로만 원문 참조를 그대로 두므로 **제품 코드를 안 건드리고** 잴 수 있다.

**즉 이 가드는 주입 없이는 영영 「없앴을 때 무엇이 지나가는가」로 판정할 수 없다.**
그래서 `SafeCheck` 를 `protected virtual` 로 열었다. 제품 코드에 시험 전용 상태는 두지
않았다.

## 3. ★ 되돌림 판독 — 그리고 그 과정이 잡은 것 셋

방어를 한 자리씩 걷어내고 **정확히 무엇이 빨개지는지** 셌다(시험 14 개 기준).

| 되돌린 것 | 빨개진 시험 | 판정 |
| :--- | ---: | :--- |
| **B** catch-all 의 `Clear()` 제거 | **3** | 효력 있음 |
| **A** `Validate` 30 자리 | **3** | 효력 있음 |
| **A** `ValidateConsolidated` 9 자리 | **2** | 효력 있음 — **단, 처음엔 0 이었다** |
| **A** `ValidateBatchStep` **신규 10 자리만** | **1** | 효력 있음 |
| 스캐너 관할에서 한 자리(`CheckSetPredicates`) 풀기 | **2** | 자리까지 지목해 잡는다 |

### (1) 시험 없는 가지를 잡았다 — `ValidateConsolidated`

처음 감쌌을 때 **걷어내도 빨개지는 시험이 0** 이었다. 아홉 자리가 통째로 시험 없는
가지였다. 원인: 「먼저 찾은 것이 살아남는가」 시험은 `SafeCheck` **바깥** 주입이라
감싸든 말든 같은 결과를 낸다 — **감싸기 자체를 재는 자가 없었다.**

시험 둘을 더해 닫았다: `RunsEveryCheckThroughSafeCheck` ·
`WhenAnEarlyCheckThrowsInside_TheLaterChecksStillRun`. `Validate` 쪽에도 같은 축을 붙였다.

> 이 저장소가 `Distinct()` 와 `PredicativeUniquenessRegex` 에서 두 번 겪은 모양이다.
> **세 번째다.** 되돌림을 안 했으면 감싸기 아홉이 초록에 실려 배송됐다.

### (2) 주입 모드가 하나여서 시험을 하나 틀리게 만들었다

처음엔 `throwAt` 하나였고 그것이 `SafeCheck` **바깥**에서 던졌다. `ValidateBatchStep` 에는
지우는 catch-all 이 없어 그 예외는 감싸든 말든 탈출한다 — 즉 **감싸기를 안 재는 시험**이
됐고 실제로 빨갛게 실패했다. 모드를 둘로 갈랐다:

```
throwOutsideAt  = 감싸지 않은 호출이 던진다   (Validate 에서는 catch-all 로 올라간다)
throwInsideAt   = 감싼 검사가 던진다          (SafeCheck 가 삼켜야 한다)
```

`ValidateBatchStep` 에는 반대편 시험도 같이 뒀다 — 감싸지 않으면 예외가 **실제로**
탈출한다는 것(`WhenAnUnwrappedCheckThrows_ItDoesEscape`). 그것이 없으면 위 시험은
감싸기가 없어도 통과하는 가지가 된다.

### (3) 측정 오류를 스스로 잡았다 — 두 번

**귀속**: `ValidateBatchStep` 26 자리를 통째로 되돌리면 빨강 2 인데, 그중 하나는 **기존
16 이 사 주던 것**이라 이번 판 몫이 아니다. 신규 10 만 되돌리니 빨강 1 이었다.
분모를 안 가르면 자기 몫을 부풀린다.

**관할**: `ValidateConsolidated` 되돌림을 이름 목록으로 했더니 **9 가 아니라 10 자리**를
건드렸다 — `ValidateMarkdownStructure` 가 `Validate` 에도 있어 남의 자리까지 먹었고,
그래서 `Validate` 시험 셋이 같이 빨개져 판독이 오염됐다. 줄 범위로 관할을 좁혀 다시 쟀다.

> **이름 기반은 개명뿐 아니라 스코프에도 눈이 먼다.**

## 4. 코퍼스 전수 스윕 — 차분 0

프롬프트가 안 바뀌었으므로 캐시 인상을 안 한다. 스킬 규정상 그 생략의 조건이 스윕
차분이므로 숫자로 적는다.

```
분모 31 편 (External 7 · Functions 10 · Procedures 14) — find -L 정본
       손 글롭 output/*/*/docs/Spec.md 는 24 편이다. 안 썼다.
캐시   코드 CurrentCacheFormatVersion = 21 · main 21 · 코퍼스 {21: 30, 19: 1}
       v19 하나 = dbo.UP_UTIL_SETTLE_EXCEPTION_PROC (2 판이 L2 미달이라 캐시 미승격)
       세대 차이는 BASE·HEAD 양쪽에 똑같이 나타나므로 차분 판정에 영향 없다.

                        BASE(492db8e5)      HEAD           차분
정  (자기 metadata)     0 발화 ·  0 종류    0 ·  0         0
교차(이웃 metadata)     1915 발화 · 19 종류  1915 · 19      0   (종류별 자릿수까지 동일)
catch-all 발동          0                   0              0
로드 실패 / nullExp     0 / 0               0 / 0          0
```

### ★ 왜 「교차 짝」을 뒀는가

**「차분 0」만 보면 내 수정이 모든 검사를 죽여도 0→0 이라 통과한다.** 배송본은 이미 L1 을
통과한 문서라 정 짝의 기대값이 0 이기 때문이다. 각 명세서를 **이웃 객체의 metadata** 와
짝지어 검사 19 종을 전부 발화시키는 양성 대조군을 만들었고, 그 1915 가 BASE·HEAD 에서
자릿수까지 같다 — 감싸기 44 가 검사를 하나도 안 죽였다는 증거다.

### 관례를 「자기 가드」에서 「호출부 `SafeCheck`」로 단일화했다

계약 §6 은 자기 가드를 요구하지만 `ValidateBatchStep` 은 이미 호출부 `SafeCheck` 16 자리로
반대 관례를 썼다. 후자가 낫다 — **한 자리에서 스캔할 수 있다.** 자기 가드는 30 개 메서드
본문을 각각 열어야 확인되고, 그래서 13/30 이 서 있었다.

**기존 자기 가드 13 은 안 걷어냈다.** 이중이지만 무해하고, 걷어내는 것은 그 가드가 우연히
사 주던 커버리지를 함께 버리는 별개의 위험이다.
