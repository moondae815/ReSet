## 2. ★★ 뿌리를 찾았다 — **U-앵커 계약이 UPDATE 만 정의한다**

오늘 만든 `AnchorKindOrdinalPairTests` 가 **처음 본 새 산출물에서 바로 울었다** — 불일치 **8**.

```
Batch6/S09  /* U22: DELETE 1 기준일 기존 통계 삭제 */    → 서수 22 (원본 라인 번호다)
Batch6/S09  /* U31: INSERT 1 통계 데이터 생성 */         → 서수 31
Batch6/S13  /* U1: 후회수 취소 기존 집계 삭제 (DELETE 1) */ → 서수 1 (자체 순번)
Batch6/S01  … 앵커 6·7·8·9·10                             → 자체 순번
```

**계약 문구가 원인이다**(`AiService.cs:4614`):

> 「각 **DML** 문장 바로 앞에 명세서의 **갱신 번호**를 주석으로 답니다.
>  `/* U13: … */` 형식입니다(**`갱신 13`·`UPDATE 13`도 인정됩니다**).」

**요구는 「각 DML 문장」인데 인정하는 표기 셋이 전부 UPDATE 용어다.**
`INSERT 1`·`DELETE 1` 표기가 **어디에도 없다.** 그래서 모델이 회차마다 발명한다 —
Batch1 은 `SQL_INSERT1 (INSERT 1, …)`, Batch5/S13 은 `U13-DELETE 1`, Batch6 은 `U<원본라인>`과
`U<자체순번>`.

**오늘 리더를 네 번 고친 것이 전부 이 구멍의 보상이었다.**
일치 규칙(`1bb76b67`) · 패턴 완화(`c3762dcc`) · `U<n>-` 배제(`8e971b4f`) · 그리고 탐지기(`379e2b39`).
**리더를 더 고칠 것이 아니라 계약을 고쳐야 한다** — `P` 계열이다.

## 3. 게이트가 빨갛다 — **약화시키지 않았다**

`AnchorKindOrdinalPairTests` 실패 1(불일치 8). **코드가 아니라 코퍼스의 결함이고,
탐지기가 설계대로 운 것이다.** 단언을 느슨하게 해서 초록을 만들면 그것이 바로
「숫자를 맞추려 단언을 손보는 것」이다 — **안 했다.**

**닫는 길은 둘이고 순서가 있다**: ① 계약에 `INSERT n`·`DELETE n` 표기를 명시(`P`)
② 그 뒤 재생성. **①을 건너뛰면 다음 판이 또 다른 표기를 발명한다.**

## 4. 이 회차가 증명한 것

**재생성은 실제로 결함을 닫는다** — 도구 층에서 만든 것이 산출물에서 처음으로 값을 냈다.
2026-09-05 의 「검사 먼저」가 옳았고(검사가 없었으면 무엇이 닫혔는지 몰랐다),
**그 결정의 유효기간이 오늘 끝났다는 것도 같이 증명됐다.**

**그리고 재생성은 새 결함을 만든다** — 신규 넷이 그것이다. 2026-09-05 재감사가
「재생성이 결함 셋을 새로 만들었다」고 적은 것과 같은 모양이고, **이번에는 그중 8 건을
자동 탐지기가 즉시 잡았다.** 그때는 원본 DDL 을 손으로 열어야 보였다.

## 5. 이 판독이 보증하지 않는 것

- **Batch6 전수 감사가 아니다.** 검사가 보는 축만 봤다. 산문·의미 축은 안 봤다.
