# `PromptContextScope` Full ↔ Narrow 대조 판독 — POQSettleBatch4 / POQSettleBatch5

물음 하나였다. **단계 본문 호출이 명세서 전량(421,121자)을 실을 값어치가 있는가.**

`PromptContextScope`가 `Full`을 두는 근거는 「접두사가 단계 간 바이트까지 같아야 캐시가
살기 때문에, 캐시를 사려고 입력을 부풀렸다」였다. 그 전제가 `tencent/hy4-preview`에서
거짓임을 먼저 실측했고(메모리 `hy4-prompt-cache.md` — 히트 10.5% · `cache_write_tokens`
114건 전량 0 · 시간·크기·동시성 무관), 그러면 **대가만 남는다.** 이 판독은 그 대가를 쟀다.

## 1. 실행 조건 — 변인은 모드 하나다

| | POQSettleBatch4 (기준선) | POQSettleBatch5 (대조판) |
| :--- | :--- | :--- |
| 모드 | **Full** | **Narrow** |
| 입력 SP | 14 편 (09-05자 명세서) | **동일** |
| Actor / Consolidator | `OpenRouter` / `tencent/hy4-preview` | 동일 |
| Critic | `OpenRouter` / `z-ai/glm-5.3` | 동일 |
| 실행 | 12:47 ~ 17:49 (5h 02m) | 19:23 ~ 22:24 (3h 01m) |
| 코드 커밋 | `4fcdb938` | `ccd3717f` |
| 로그 | `output/logs-batch4-full-20260906/` | `output/logs-batch5-narrow-20260906/` |

**Job 이름을 갈랐다.** Batch4를 덮어 다시 돌리면 기준값이 사라진다 — 이 저장소의 통제군
관례 그대로다(`POQSettleBatch5R1~R3` · `F1~F2`가 같은 이유로 남아 있다).

**대조 가능성을 확인했다.** `4fcdb938` → `ccd3717f` 사이에 배치 생성 경로는 동작이
바뀌지 않았다: `PromptContextScope`·`VerificationPipelineOrchestrator`·`MechanicalValidator`·
`StepInterfaceFacts` 변경 없음, `AiService.cs` 203줄은 전부 정책(Policy) 기능이고 배치 경로는
주석 한 줄. 명세서 14편은 12:47 이후 수정 0건.

**변인 무결성을 값으로 닫았다.** `INPUT-HASHES-at-start.txt`(설정 3종 SHA-256)를 실행 전에
박고 종료 후 대조해 셋 다 일치했다. 실행 중 두 차례 외부 CLI가 같은 로그 파일에 끼어들어
(§5) 「덮였을 수도 있다」가 아니라 「안 덮였다」를 말할 필요가 있었다.

## 2. 감축 실측 — 접두사

단계 호출의 공유 접두사에서 명세서가 차지하는 몫이다(원본 전량 = 421,121자).

| 단계 | 실린 명세서 | 명세서부 | Full 대비 |
| :--- | :--- | ---: | ---: |
| S00 · S15 | 14 편 (폴백) | 422,195자 | 100.3% |
| S03 | 1 편 | 12,112자 | **2.9%** |
| S01 | 1 편 | 29,735자 | 7.1% |

**S00·S15는 감축되지 않는다.** `LegacyProcedures`가 비어 `NarrowSpecs`의 「하나도 안 맞으면
전량 반환」 폴백을 탄다 — 의도된 안전장치다(빈 목록을 보내면 모델이 「원본 명세서가 없다」로
읽고 지어낸다).

**1-hop 이웃이 실제로 실린다.** `Util_Settle_Summary`가 `Summary_AcqManual`·`SUMMARY_EXTRA`를
호출하므로 S10이 3편을 받았다. 설계가 이웃을 넣은 근거(실측 「필수 수정 1·2」)가 지켜졌다.

**접두사에서 잘리지 않는 것**(440,908 − 421,121 = 19,787자): `[Approved Step List]`(**모든**
단계의 Legacy/Tables/ErrorCodes) · `[Batch Control Table Contract]` · `[Shared Conventions]` ·
`[Original Procedure Interface]`. 이웃 단계의 **요약 사실**은 Narrow에서도 전부 실린다.

## 4. 판독을 오염시킬 뻔한 것 — 도구 결함이 처치 효과로 귀속되는 자리

실행 중 S11·S12·S13이 **어느 쪽으로 고쳐도 통과가 불가능한 닫힌 고리**에 갇혔다.

```
21:17  「원본 오류코드 '-1'·'-2'가 등장하지 않습니다」   → 넣음
21:31  「'-1'을 대입하는데 명세가 정의하지 않습니다」    → 뺌
21:35  다시 「미등장」                                 ← 출발점 복귀
```

L1 검사 둘이 **서로 다른 오라클**을 본 것이다 — `:495`는 목차(`step.ErrorCodes`),
`CheckLegacyStepErrorCodeInvention`은 명세서(`codesByProcedure`). 목차가 배정하는 스텝 검증
코드(`-1`·`-2`)는 원본 명세에 없다.

**모델의 실패가 아니었다.** 그 회차의 산출물 본문이 구별을 정확히 적고 있었다:

> 통합 배치 스텝 목록(S12)에 명시된 파라미터 검증 오류 코드 `-1` 및 `-2`는 … **이는 원본
> 프로시저 명세에 존재하는 코드가 아닌 스텝 자체 검증 코드이다**(rule 5).

고쳤다(`50653f1c`). 되돌리기로 판정했다 — **실물 코퍼스 발화 33 → 3, 판정 단계 수는 244로
동일.** 30건이 오탐이었고 검사는 꺼지지 않았다.

**⚠ 이것이 이 판독의 가장 위험한 자리였다.** 고리에 갇힌 회차가 발화 수를 부풀려
「Narrow에서 발화가 늘었다」로 읽힐 뻔했다. **대조표에는 「도구 결함으로 도는 회차」 열을
따로 두어라** — 없으면 나중에 아무도 가릴 수 없다.

**자를 두 개 쓴다는 것에 유의하라.** §3-1의 142/42는 **로그 기준**(실행 중 재시도를 유발한
발화 전부, 모든 회차·모든 검사)이고, 위의 33/3은 **산출물 기준**(최종 문서에 남은 발화,
검사 B 하나)이다. 분모의 관할이 다르므로 섞어 읽지 마라.

## 5. 실행 중 있었던 일 — 로그 오염 두 차례

20:59와 21:11에 **다른 프로세스**가 같은 로그 파일에 썼다. 원인은 병행 세션이 파견한
수정 워커가 `output` 심링크를 가진 워크트리에서 CLI를 띄운 것이고, `LogDirectory`가
`./output/logs` **상대경로**라 이 실험의 로그로 들어왔다.

**20:59분 증거는 이미 사라졌다.** 21:01에 Critic 페이로드(수 MB)가 그 자리를 덮었다 —
두 프로세스가 같은 파일을 각자 offset으로 쓰면 서로를 덮는다. 그래서 이 사건은 **사후
grep으로 확인되지 않는다.** 관측은 `tail -f` 실시간 수신과 `grep -an`의 27590행, 두 경로가
독립적으로 했다.

**영향은 로그 오염 한정이다.** 설정 해시 3종 일치 · 명세서 14편 실험 시작 이후 변경 0건 ·
`Jobs/` 무변경 · 요청/응답/usage 짝 정합(42/41/41).

**교훈**: 한 파일에 여러 프로세스가 쓰면 **사후 판독이 불가능해진다.** 이번에 한쪽은
「있었다」를, 다른 쪽은 「없었다」를 보고했고 **둘 다 자기 시점에서는 옳았다.** 격리
워크트리도 `output/`에 대해서는 격리가 아니다 — 그 아래에 로그·명세서·산출물이 다 있다.
처방은 절대경로 환경변수로 출력 트리를 가르는 것이고, 통제군 하네스가 이미 그 방식을 쓴다.

## 6. 이 판독이 보증하지 않는 것

- **산문 수준의 로직 보존은 대조하지 않았다.** §3-2의 두 축(오류 코드·UDF)은 **L1이 강제하는
  자리**라 양쪽 100%가 당연하다. `reset-consistency-audit`의 축 B(단계 지시서 ↔ Spec 산문)는
  돌리지 않았다 — 두 판을 다 감사해야 비교가 되어 단위 64개 규모다. 그리고 §4의 도구 결함이
  살아 있는 채로 감사하면 그 결함이 양쪽에 섞여 나온다. **고친 지금이 감사의 적기다.**
- **표본은 Job 하나 · 모델 하나(`hy4-preview`)다.** 다른 모델에서도 같은지 재지 않았다.
  그래서 `ResolveMode`의 기본값은 손대지 않고 `appsettings.local.json` 설정으로만 켜 두었다.
  표본을 더 모은 뒤 사람이 결정할 항목이다.
- **`Narrow`가 이웃을 못 싣는 배치는 재지 않았다.** 이 배치는 명세서를 가진 1-hop 이웃이
  2편 있었다. 서로 호출하지 않는 SP만 모인 배치에서는 각 단계가 자기 명세서만 받는데,
  그 판의 품질은 이 판독이 말하지 않는다(그 경우 경고가 뜬다 — `ccd3717f`).
- **측정 중 자가 한 번 틀렸다.** `Util_Settle_Summary`가 `_AcqManual`의 접두 부분 문자열이라
  매칭에서 빠졌다(`PromptContextScope.MatchesSpecName` 주석이 경고한 바로 그 함정).
  정정해 §3-2 수치에 포함했다.
