grep으로 확인되지 않는다.** 관측은 `tail -f` 실시간 수신과 `grep -an`의 27590행, 두 경로가

**영향은 로그 오염 한정이다.** 설정 해시 3종 일치 · 명세서 14편 실험 시작 이후 변경 0건 ·

**교훈**: 한 파일에 여러 프로세스가 쓰면 **사후 판독이 불가능해진다.** 이번에 한쪽은
「있었다」를, 다른 쪽은 「없었다」를 보고했고 **둘 다 자기 시점에서는 옳았다.** 격리
워크트리도 `output/`에 대해서는 격리가 아니다 — 그 아래에 로그·명세서·산출물이 다 있다.
처방은 절대경로 환경변수로 출력 트리를 가르는 것이고, 통제군 하네스가 이미 그 방식을 쓴다.

## 7-2. 🔴 의 성격이 다르다 — 이것이 이 절의 요점이다

수(11 대 3)보다 **종류**가 중요하다.

**Full 의 🔴 는 계산식·로직이 사라진 것이다.**
- `PGCOMM` 의 `CASE` 두 분기와 `ROUND(…, 0, 플래그)` 3 건 소실 → 반올림 정책 미적용,
  `CommMethod<>0` 경로(`PGCOMM4SUM/1.1`)가 통째로 사라짐
- `PGVT` 계산에서 `PGETC` 항이 두 분기 모두 소실 → PG부가세 과소 산출.
  단계가 `PGETC4SUM` 을 계산해 놓고 쓰지 않는 자체 모순까지 있었다
- `CAST(… AS INT)` 누락 3 컬럼

**Narrow 의 🔴 는 실행 환경 계약이 안 남은 것이다.**
- `@v_valIncVat` 의 `DECIMAL(2,1)` 타입이 방출 SQL 에 `DECLARE` 로 남지 않아 드라이버
  바인딩에 맡겨짐(2 건, 같은 유형) — `11/1.1` 이 float 경로면 `9.9999…` → `9` 로 절사
- 트랜잭션 경계가 하위 SP 호출을 안 감쌈(1 건)

**앞쪽이 더 무겁다.** 사라진 계산은 산출물만 봐서는 복구 근거가 없지만, 타입 선언과 경계는
명세서에 남아 있어 되찾을 수 있다.

같은 자리를 Narrow 가 어떻게 옮겼는지가 대비된다 — `EXCEPTION_PROC` 의 `BB.PGVT` ELSE
분기(중첩 `ROUND` **7 겹**)가 공백 정규화 후 **문자 단위 동일**했고, `/100` 대 `/100.0`
구분과 `ROUND` 2 번째 인자(U5 만 `-1`)까지 보존됐다.

## 7-3. 🟡 가 12 대 19 로 역전된 이유 — 모드와 무관하다

Narrow 의 🟡 상당수가 두 부류다.

| 부류 | 단위 | 성격 |
| :--- | ---: | :--- |
| 목차가 배정한 `-1`·`-2` 를 「원본 코드」라 선언 | 4 | **도구 결함**(§4 의 오라클 충돌) |
| 「성공 시 `0` 반환」 | 사실상 전 단위 | 규칙에서 온 것, 양쪽 공통 |

**둘 다 모드가 만든 것이 아니다.** 첫째는 오늘 고쳤고(`50653f1c`), 둘째는 Full 감사에서도
같은 사실이 잡혔다(거기선 ⚪ 로 매겨졌다). §4 가 예고한 「도구 결함으로 도는 회차」 열이
여기서 실제로 필요했다.

## 7-4. 이 대조가 보증하지 않는 것 — 감사 자체에 분산이 있다

**같은 Job 을 두 번 분할 감사했더니 7 단위 중 6 단위의 결함 목록이 어긋났다.**
Batch4 가 19:46 에 이미 전면 감사를 받은 것을 모르고 7 단위를 중복 실행한 결과인데,
그 사고가 뜻밖의 자료를 냈다.

```
S03 SETTLE_INS      1차 🔴4  ↔  2차 🔴2
S05 INS_EXTRA4PLCARD 1차 정합 ↔  2차 🟠1
S06 INS_EXTRA       1차 🟠1🟡1 ↔ 2차 🟡3
```

합집합도 부분집합도 아니다. 스킬 서두가 「분할 없이 두 번 돌렸더니 어긋났다」고 경고한
것보다 **강한 관측이다 — 두 번 다 분할해서 돌렸는데도 어긋났다.** 기록은
`output/Jobs/POQSettleBatch4/consistency/reproducibility-second-pass.json` 에 남겼다.

**그러므로 위 수치는 ±1~2 의 흔들림을 안고 있다.** 다만 결론을 뒤집지는 않는다 —
`SETTLE_INS` 의 🔴 는 1 차 4 건 · 2 차 2 건으로 **두 번 다 났고**, Narrow 는 정합이다.
`EXCEPTION_PROC` 의 `PGETC` 소실도 양쪽 감사에서 재현됐다.

**그 밖에 보증하지 않는 것**
- **후속 단계 간섭은 28 단위 전부 보류다.** 단위 계약이 다른 단계를 못 열게 한다.
- **상위(나)의 대상 확정이 한 번 틀렸다.** Batch5 S10 이 SP 둘을 흡수했다고 브리프에
  못박았는데 단위가 실측으로 기각했다 — 본문의 SP 이름이 「참고용 비실행」 블록이었고
  의사코드는 한 번도 호출하지 않는다. **단위가 브리프를 의심하고 되잰 것이 옳았다.**
- 조인 종류(INNER/LEFT)는 계약상 축 B 대조 대상이 아니다.

## 7-5. §3-2 를 정정한다

§3-2 는 「산출물은 동등하다」고 적었다. 그 근거는 오류 코드 88/88 · UDF 28/28 이었는데,
**그 둘은 L1 이 강제하는 자리라 양쪽 100% 가 당연했다.** 산문 수준으로 내려가면 동등하지
않다 — Full 이 계산식을 잃은 자리가 여럿이고, Narrow 는 그 자리를 지켰다.

**결론은 강화된다**: 입력을 3 분의 1 로 줄여 과정이 깨끗해졌을 뿐 아니라(§3-1),
**산출물의 로직 보존도 더 나았다.**
