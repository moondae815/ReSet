# K2 를 통합 검증 SQL 세트까지 넓힌다 — 측정·설계·합격선 (구현 전)

**작성 시점**: 2026-09-14, **구현 전**. 코드: main `a6b1618f`.

## 0. 계기

POQSettleBatch13 배송본의 통합 검증 SQL 세트 V04 가 `StepCode = N'S11'` 몫을 `TSettleMst.RowCount`·`TxAmt`·`CLTotal`·`PGTotal` 로 읽는데
S11 은 `SettleFactRowCount`·`SettleFactTxAmt`… 6 개로 쓴다 — 교집합 0 이라 V04 의 `FULL OUTER JOIN` 이 어떤 실행에서도 전부 불일치를 낸다.
K2(`ValidateControlTotalNameConsistency`)는 조용했다. Batch13 판독(`2026-09-13-GPT-2회판-Batch13-사전선언.md` G11)은 원인을 「K2 가 검증 SQL 세트를 입력으로 안 받는다」로 적었다.

## 1. 측정 — 입력만 넣으면 닫히는가 (코드 변경 없이)

검증 SQL 세트(배송본 `## 통합 데이터 정합성 검증 SQL 세트` H2 구간)를 **가상 읽기 단계 `S99`** 로 끼워 지금 K2 를 그대로 돌렸다. 코퍼스 9 Job.

| Job | 검증 세트 통제표 언급 | `StepCode` 리터럴 거름 | K2 기존 | 검증 세트 포함 |
| :-- | --: | --: | --: | --: |
| B1 | 3 | 3 | 0 | 0 |
| B10 | 3 | 0 | 0 | 0 |
| **B11** | 3 | 5 | 1 | **2** |
| B12 | 4 | 2 | 0 | 0 |
| **B13** | 2 | 1 | 0 | **0** |
| B4 | 4 | 0 | 0 | 0 |
| B5 · B7 | 0 | 0 | 0 | 0 |
| B8 | 2 | 0 | 0 | 0 |

- **B11 새 발화 1 — 참.** 검증 세트가 S13 몫을 `ControlName = N'LedgerPOQIncome'` 로 읽는데 S13 이 쓰는 이름은 `POQIncome` 이다(바로 앞 문장은 `LedgerRowCount` 로 맞게 읽는다). 기대값이 늘 NULL 이다. **이미 배송된 결함이고 아무도 짚지 않았다.**
- **B13 은 입력만으로 안 닫힌다.** V04 의 제어 표 읽기 문장(`WITH Recorded AS (SELECT ControlName, MAX(ControlValue) FROM batch.BatchControlTotal WHERE RunId = … AND StepCode = N'S11' GROUP BY ControlName)`)에는
  `ControlName` 리터럴이 없다. 이름은 **다른 CTE**(`CurrentValue AS (SELECT N'TSettleMst.RowCount' AS ControlName, … UNION ALL …)`)에서 오고 `FULL OUTER JOIN … ON C.ControlName = R.ControlName` 으로 붙는다.
  K2 의 읽기 규칙 ②(「제어 표를 읽는 **그 문장**의 `ControlName =`·`IN` 리터럴만」)가 이 모양을 못 본다.

**그래서 층이 둘이다** — ① 입력(검증 SQL 세트) ② 읽기 이름 모양(조인으로 끌어온 이름).

## 2. 설계

### ② 읽기 이름 — 「조인으로 끌어온 이름」 (`ControlTotalNameFacts`)

한 `QuerySpecification` 의 FROM 조인 조건에 `X.ControlName = Y.ControlName` 등식이 있고,

- **X** 가 제어 표 읽기로 해석된다 — 같은 문장의 CTE 로 그 본문이 제어 표를 FROM 으로 읽고 `StepCode` 리터럴 몫이 있는 것(**구현 중 정정**: 처음엔 「`ControlName` 리터럴이 없는 것」으로 좁혔으나 되돌림에서 지키는 것이 없어 뺐다 — 결과 절),
  또는 제어 표 자신(몫은 바깥 문장의 제어 표 한정 `StepCode` 조건)
- **Y** 가 같은 문장의 CTE(또는 인라인 `VALUES`)로, 그 `ControlName` 출력 열이 **전부 문자열 리터럴**인 것

이면 `Read(X 의 몫, Y 의 리터럴)` 을 더한다. 하나라도 리터럴이 아니면 더하지 않는다(K2 의 「덜 보고한다」 그대로).
이 모양은 단계 본문에도 적용된다 — 단계 층 K2 발화가 바뀔 수 있으므로 스윕 차분을 잰다(C7).

### ① 입력과 귀속 — 통합 L1 단계에 붙인다

- **자리**: 오케스트레이터의 통합 L1(`ValidateConsolidated` 직후). 원본 반환 코드 누락(`FindMissingErrorCodes`)이 이미 같은 자리에서 `l1Result` 에 오류를 더한다 — 선례를 따른다.
- **재료**: 조립된 계획서의 검증 SQL 세트(H2 구간) + 단계 섹션 + 목차 단계. 새 검증기 메서드 `ValidateVerificationControlTotalNames`.
  쓰기 이름은 단계 섹션에서 K2 와 **같은 수집**으로 모은다(쓰기 「모름」 단계는 침묵). 검증 세트 안의 쓰기는 몫을 모르므로 쓰기 재료에 넣지 않는다.
- **귀속 — 읽는 쪽(검증 세트 = 골격)**: K2 의 원칙(「읽는 쪽이 쓰는 쪽에 맞춘다」)을 그대로 쓴다. `DetailedError.Lexemes` 에 **검증 세트 원문 줄**(읽기 이름 리터럴이 있는 줄)을 실어
  `L1ViolationAttribution` 이 골격으로 귀속하게 한다 → 골격 **패치** 수리(`SkeletonRevision(errors, lastSkeleton)`, 같은 자리 연속 2 회에만 백지).
  K2 의 공통 규약 동률 규칙도 대칭으로 둔다 — 공통 규약이 검증 세트의 이름을 담고 쓰는 단계 이름을 하나도 안 담으면 어긴 쪽은 단계다 → 어휘를 **쓰는 단계의 원문 줄**로 싣는다.
- **왜 단계 층 하한(floor)이 아닌가**: 하한 위반 사전은 단계 코드 키뿐이라 골격으로 보낼 길이 없다. 단계(쓰는 쪽)로 보내면 K2 원칙과 반대로 쓰는 쪽을 읽는 쪽에 맞추게 되고,
  같은 단계를 읽는 다른 읽기(예: B11 S20)와 번갈아 부딪칠 수 있다.

## 발견

1. **`L1ViolationAttribution.MapRegions` 는 단계 안의 코드 없는 하위 헤딩(`#### 단계 책임과 인터페이스`) 아래를 `Unknown` 으로 둔다.** 실물 B13 S11 의 쓰기 SQL 줄로 귀속하면 단계에도 골격에도 안 붙었다(프로브, 최종 리뷰가 코드로 확인).
   **처음 판독은 이것을 「이 검사 밖의 기존 한계」로 적었는데 틀렸다** — 이 브랜치의 공통 규약 동률 분기(어휘 = 쓰는 단계 원문 줄)가 실물에서 정확히 이 한계에 걸려 전량 재생성으로 떨어진다(최종 리뷰 Important 2). 그 분기는 아래 리뷰 반영에서 직접 귀속으로 고쳤다.
   코퍼스 단계 중 `#### ` 하위 헤딩이 있는 단계: B1 18 중 8 · B4 16 중 3 · B5 16 중 7 · B7 17 중 5 · B8 24 중 9 · B10 18 중 4 · **B11 22 중 18 · B12 18 중 17 · B13 19 중 16**.
   GPT 판은 거의 전부다 — **어휘로 단계에 귀속되는 통합 L1 위반(규칙 3-1·10 류 등)이 그 단계들의 하위 헤딩 아래에 있으면 귀속되지 않고 전량 재생성 폴백으로 떨어질 수 있다.** 이 브랜치 밖의 기존 한계라 고치지 않았고, 실제 판에서 그렇게 떨어졌는지는 재지 않았다.
2. **B11 검증 세트의 `LedgerPOQIncome` 읽기**는 배송된 결함인데 Critic·K2 모두 짚지 않았다(§1).
3. 이 검사는 **교집합 0 만** 잡는다 — B13 에서 S11 이 여섯, V04 가 넷을 대조하는 식의 **부분 겹침**(`FULL OUTER JOIN` 이면 남는 둘이 늘 불일치)은 K2 와 같은 이유로 보지 않는다.
