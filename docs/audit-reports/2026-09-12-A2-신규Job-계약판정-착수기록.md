## 1. 무엇을 판정하는가

지난 두 회차에서 프롬프트 계약 두 개를 넣었다.

| 계약 | 층 | 배송 상태 |
| :--- | :--- | :--- |
| SELECT n 앵커 표기 | 규칙 + Few-Shot + Critic + L1 리더 + 프롬프트 잠금 | **미판정** — 계약 추가 뒤 생성된 Job 이 없다 |
| 파라미터 타입 계약 | 규칙 + Few-Shot + Critic + L1 검사 | **미판정** — 같은 이유 |

둘 다 **코퍼스에는 효력이 0 으로 보인다**. 지금 코퍼스의 네 Job 은 전부 계약 이전에
생성된 것이라, 검사가 초록인 것이 「계약이 듣는다」인지 「잴 대상이 없다」인지 갈리지
않는다. A-2 는 그 갈림을 만드는 유일한 수단이다 — 계약 이후의 표본 하나.

**A-1(Batch1 재생성)이 아니라 A-2 인 이유**: `docs/audit-reports/2026-09-05-POQSettleBatch1-축B-재감사.md` §7.
지난 Batch1 재생성은 결함 셋을 새로 만들었고 검사 B 는 조용했다. 「검사 발화 →
SuggestedPromptFix → 재생성이 고친다」는 경로가 아직 한 번도 끝까지 관측된 적이 없다.
A-2 는 같은 질문에 답하면서 배송본을 건드리지 않는다.

### 2-1. Job 별 도달률 — 이 회차를 위해 자를 갈랐다

전역 도달률 `6/20` 은 Job 넷을 한 분모에 섞는다. 계약이 완벽히 들어도 새 Job 하나는
분모의 1/5 라 전역 값은 조금밖에 안 올라간다. 그 수로는 판정할 수 없으므로
`SelectAnchorPairCorpusTests` 의 역방향 기록자에 Job 별 줄을 더했다(실행 **전**에).

```
[Job] POQSettleBatch1 · 도달률 2/5 · 놓친 선언 행 3
[Job] POQSettleBatch4 · 도달률 0/5 · 놓친 선언 행 10
[Job] POQSettleBatch5 · 도달률 1/5 · 놓친 선언 행 9
[Job] POQSettleBatch7 · 도달률 3/5 · 놓친 선언 행 2
```

**분모가 넷 다 정확히 5 다.** 같은 SP 14 편을 쓰므로 SELECT 행을 선언하는 단계 수가
안 변한다 — 새 Job 도 5 가 나올 것이고, 아니라면 그 자체가 따로 설명할 일이다.

**그리고 분산이 크다.** 계약이 없던 넷이 0·1·2·3 으로 흩어져 있다. 이것이 합격선을
100% 로 잡아야 하는 이유다 — 4/5 가 나와도 「계약이 들었다」와 「Batch7 같은 판이
한 번 더 나왔다」를 가르지 못한다. 3/5 는 계약 없이 이미 관측된 값이다.

## 3. 합격선 (실행 전에 못박는다)

새 Job 하나에 대해서만 잰다. 기존 네 Job 의 수는 판정에 안 쓴다 — 그것들은 계약
이전이라 안 움직이는 것이 정상이다.

| # | 항목 | 합격 | 불합격이 뜻하는 것 |
| :-- | :--- | :--- | :--- |
| G1 | 새 Job 의 SELECT 앵커 **도달률** (명세서가 선언한 SELECT 서수 중 앵커가 붙은 비율) | **100%** | 규칙 층이 안 듣는다 — 계약을 Few-Shot 쪽으로 옮겨야 한다 |
| G2 | 새 Job 의 SELECT 앵커 **불일치** (앵커 서수 ↔ 명세서 선언 불일치) | **0** | 모델이 서수를 지어낸다 |
| G3 | 파라미터 타입 검사 발화 | **0** | 타입 계약이 안 듣는다 |
| G4 | 검사 B·C 의 **새 좌표** | **0** | 계약 추가가 다른 것을 부쉈다 |
| G5 | 전체 시험 | 실패 0 · 건너뜀 0 · 경고 0 | — |

**G1 이 판정의 축이다.** G2 는 0 이 기본값이라(현 코퍼스도 전부 0) 그것만으로는
아무것도 못 가른다. 대조는 §2-1 의 Job 별 도달률 넷(0/5 · 1/5 · 2/5 · 3/5)과 새 Job
하나를 나란히 놓는 것이다 — 전역 `6/20` 이 아니다.

**부분 합격의 해석**: 4/5 이하는 **판정 보류**이지 합격이 아니다. 계약 없이 만든
Batch7 이 이미 3/5 이므로, 4/5 로는 계약의 효력과 판 사이 분산을 가를 수 없다.
그 경우 할 일은 두 가지다 — ① 미달 단계를 열어 「어떤 모양의 SELECT 에서 빠지는가」를
적고 검사가 아니라 Few-Shot 을 고친다, ② 표본이 하나뿐이라는 것을 그대로 적는다.
한 판으로 분산을 이기려면 값이 끝(5/5)에 붙어야 한다.

## 4. 실행 방법 — `--plan-only`, 대화형 메뉴가 아니다

당초 계획은 TUI 메뉴 `2. 통합 배치 마이그레이션 설계` 였으나, 같은 재료를 쓰는
비대화형 경로가 이미 있다.

```
--plan-only --job-name <새 이름> --sp <실행 순서대로 나열>
```

- `Program.cs:758` — 이 경로는 **DB 에 붙지 않는다**(연결·로그인·SP 목록 조회를 건너뛴다).
  그래서 `scripts/regen-job.sh` 의 가드1(스냅샷)·가드2(전용 워크트리)가 걸던 이유가
  여기엔 없다.
- `PlanOnlyMaterialLoader` 는 `output/Procedures/<스키마.이름>/docs/Spec.md` 를 **읽기만**
  한다. 명세서는 재생성되지 않는다 — A-1 을 미루게 했던 위험이 구조적으로 없다.
- `--sp` 의 나열 순서가 곧 배치 스텝의 실행 순서다.
- 재사용 저널은 `output/Jobs/<Job>/raw/attempts` 아래에 있다(`PlanAttemptJournal.cs:417`).
  **새 이름이면 재사용 후보가 0** 이라 캐시가 답을 대신 주지 못한다.

입력 SP 14 편과 그 순서는 Batch7 의 `raw/prompt-context.md` 에서 명세서 구획이
이어 붙은 순서를 그대로 읽어 왔다(추정이 아니라 실측).

## G1 의 4/5 는 모델이 아니라 자가 놓친 것이다

미달 단계 `Batch8/S12` 를 열었더니 **여섯 개를 전부 달았고 서수도 맞다**.

```
-- SQL_FETCH_SETTLE_POST_SOURCE (SELECT 1: 후취정산 대상 커서 원천 조회)
-- SQL_CHECK_MISS_EXISTING     (SELECT 2: TSettleMiss 기등록여부 확인)
… SELECT 3 … 4 … 5 … 6
```

`SelectAnchorPattern` 은 `^\s*(?:/\*|--)\s*SELECT\s*(\d{1,2})\s*:` 라서 주석 여는
기호 **바로 뒤**의 `SELECT` 만 받는다. 단계 형식이 이름 있는 SQL 블록을 `-- NAME` 으로
열도록 요구하므로, 모델은 블록 이름을 먼저 쓰고 앵커를 괄호에 넣었다. 계약의 **내용**은
지켜졌고 **자리**가 다르다.

### 코퍼스 전수 조사 — 자가 좁은 것은 이 한 자리가 아니다

주석 줄 안 어디서든 `SELECT n:` 을 찾으면, 현행 자가 놓치는 줄이 **9** 개다.

```
Batch5/S12:80   -- 원본 SELECT 1: PaymentDB.dbo.TExtraSettleIn 조회…
Batch5/S13:120  -- U13-SELECT 1: 회수 후 취소된 대상 검색
Batch7/S12:78   -- SQL_GET_REQ_YMD (SELECT 1: 차액정산 요청일 조회)
Batch8/S12:94·115·126·150·164·179  (여섯 줄)
```

여기에 더해, 콜론 대신 `·` 나 `/` 를 쓴 줄이 **16** 개 더 있고 그중 다수가 진짜 앵커다.

```
Batch4/S11 여섯 줄   -- SQL_SELECT_CURSOR_SOURCE (SELECT 1 · 커서 원천 집계 …)
Batch5/S14 여섯 줄   -- SQL_SELECT_CURSOR_SOURCE (원본 SELECT 1 / 커서 소스 …)
```

Batch4 가 0/5, Batch5 가 1/5 로 바닥이었던 이유가 이것이다 — 그 Job 들은 앵커를 안 단
것이 아니라 **구분자를 다르게 썼다**. 나머지는 진짜 산문이다(`SELECT 1(커서 소스)과
동일한`, `SELECT1/DELETE1/INSERT1만 등재`).

**따라서 §2 의 기준선 `6/20` 은 코퍼스보다 좁은 자로 잰 값이다.** 같은 축에서 분모를
틀린 것이 두 번째다(착수 전 8 → 실측 16 이 첫 번째).

### 그래서 정규식을 또 넓히지 않는다

같은 것을 재다 세 번 틀렸으면 자가 아니라 **축**이 틀린 것이다. 그리고 순진하게
넓히면 곧바로 오탐한다 — `SELECT1/DELETE1/INSERT1` (Batch8/S09:91) 이
「`SELECT` + 서수 + 구분자」에 걸린다. 물어야 할 것은 「구분자를 몇 개 더 받을까」가
아니라 **「무엇이 앵커임을 표시하는가」** 다. 후보 둘:

1. **자를 고친다** — 앵커의 표시는 「주석 줄이 문장을 연다」이고 이름표는 그 앞에 올 수
   있다. 그러면 계약은 이미 듣고 있었고 고칠 것은 리더뿐이다.
2. **계약을 고친다** — 기계가 읽을 자리를 하나로 못박고(`-- NAME` 과 분리된 줄),
   Few-Shot 을 그 모양으로 바꾼다. 지금 Few-Shot 이 `/* SELECT 1: … */` 단독 줄인데
   실물 단계 형식이 이름표를 요구해 충돌하고 있다.

②가 낫다고 본다. ①은 표기를 자유롭게 두는 대신 자를 계속 넓히게 되고, 그 끝이 오탐이다.
계약의 목적은 **기계가 읽을 수 있는 한 가지 자리**를 만드는 것이다.

# ② 채택 — 계약에 「자리」를 못박았다 (2026-09-13)

사람 결정: 앵커 표시 축은 ②(계약을 고친다).

## 자리를 고르기 전에 형제를 쟀다

「이름표 줄과 분리한다」가 옳은지 코퍼스가 답했다. 형제 앵커(U·INSERT·DELETE)가
붙은 주석 줄 495 개를 모양별로 갈랐다.

| 모양 | 건수 |
| :--- | ---: |
| 앵커가 주석 첫머리 `/* INSERT1: … */` | 385 |
| 이름표 뒤에 접어 넣음 `-- SQL_INSERT1 (INSERT 1, …)` | 96 |
| 산문이 앞섬 | 14 |

그리고 앵커-첫머리 385 건 중 **277 건이 바로 앞 줄에 `-- SQL_NAME` 이름표를 따로
둔다**. 즉 「이름표 줄 + 앵커 줄」 두 줄이 이름 있는 SQL 블록 요구와 앵커 요구를
동시에 만족시키는 **지배적 실물 관행**이고, 접어 넣은 96 건이 소수다. 자리를 이
두 줄 모양으로 못박는다.

## 진짜 구멍은 Few-Shot 이었다

기존 조항은 「앵커와 설명을 하나의 주석에」까지만 말한다. Batch8/S12 는 그것을
**하나도 어기지 않았다** — 앵커도 설명도 한 주석 안에 있고 복합 라벨도 아니다.
빠진 것은 「주석의 맨 앞」이라는 자리뿐이었다.

더 나쁜 것은 예시다. 이름 있는 SQL 블록 Few-Shot(`-- SQL_DELETE_RANGE` → `DELETE …`)에
**앵커가 한 줄도 없었다.** 규칙은 앵커를 요구하는데 예시는 이름표만 보여 주니, 둘을
합치는 법은 모델이 발명할 수밖에 없었다. 모델은 산문보다 예시를 베낀다(`7feb3c54`
에서 이미 겪은 자리).

## 한 자리를 고치다 경로 함정을 다시 밟을 뻔했다

「명세서 행이 있는 문장에만 앵커를 단다」를 처음엔 `ConsolidatedPlanRules` 의 Few-Shot
쪽에만 넣었다. 그런데 **분할 생성 경로(`GenerateBatchStepSectionAsync`)는 그 상수를
아예 안 싣고, Batch8 의 단계를 만든 것이 바로 그 경로다.** 양 경로 잠금
(`AssertBothCarryAsync`)이 그 자리에서 빨갛게 떴다. 잠금을 경로마다 걸지 않았다면
「고쳤다」고 적고 안 도는 쪽만 고친 채 넘어갔을 것이다.

## 바꾼 것

| 층 | 내용 |
| :--- | :--- |
| 규칙 | 「앵커는 그 주석의 맨 앞에 옵니다」 + 이름표에 접어 넣지 말 것 + 두 줄 예시 |
| 규칙 | 「명세서 DML 범위 표에 행이 있는 문장에만 앵커를 답니다」(인프라 조회 제외) |
| Few-Shot | 규칙 블록 안에 SELECT·DELETE·UPDATE 세 갈래의 두 줄 모양 예시(양 경로) |
| Few-Shot | `ConsolidatedPlanRules` 이름표 예시에 `DELETE 1`·`INSERT 1` 앵커 줄 추가 |
| Critic | 접어 넣은 앵커를 감점하고 두 줄 모양을 요구 |
| 잠금 | `StatementAnchorClauseTests` 셋(자리·예시·명세서 행 한정) — 양 경로 |
| 리더 시험 | `FoldedSelectAnchorStep`(Batch8/S12 89~96 행 실물) + 양성 대조군 짝 |

리더(`SelectAnchorPattern`)는 **손대지 않았다.** 넓히면 산문 열거
(`SELECT1/DELETE1/INSERT1`, Batch8/S09:91)까지 앵커가 된다.

전체 시험 4292 → **4297 통과 · 실패 0 · 건너뜀 0**.

## 「0 으로 읽힌다」가 의도임을 시험이 말하게 했다

접어 넣은 형태가 0 으로 읽히는 것은 이제 리더 결함이 아니라 **계약 위반의 탐지**다.
그 구분을 사람 기억이 아니라 파일이 들고 있게 했다 — `FoldedSelectAnchorStep` 은
실물이고, 바로 옆 양성 대조군이 「같은 본문에서 앵커를 자기 줄로 내리면 읽힌다」를
보인다. 대조군이 없으면 0 은 「이 리더가 이 본문을 아예 못 읽는다」와 구분되지 않는다.

## 아직 판정 안 된 것

**계약이 듣는지는 새 판을 한 번 더 돌려야 안다.** 지금 코퍼스의 Batch8 은 계약 수정
**이전** 산출물이라 도달률 4/5 그대로다. 판정은 새 이름(`POQSettleBatch9`)으로
`scripts/run-plan-only-job.sh` 를 한 번 더 돌려 **5/5** 가 나오는지 보는 것이고,
합격선은 §3 을 그대로 쓴다.

## G2 의 1 건 — 자리를 닫으니 다음 구멍이 드러났다

`Batch9/S08` 이 계획이 새로 들인 가드 조회에 `SELECT 1` 을 달았다. 비순환 오라클
둘로 확인했다 — 그 SP 의 DML 범위 표에 SELECT 행이 없고, **원본 DDL 에 `COUNT(` 가
0 건**이다. 원본에 없는 문장이므로 지어낸 서수다.

원인은 또 예시였다. 「명세서 행이 있는 문장에만」이라는 **산문 조항은 이미 있었는데도**
났다. 공유 규칙 블록의 예시가 **모든 문장에 앵커를 달고 있었기 때문**이다 — 앵커 없는
인프라 조회 예시는 `ConsolidatedPlanRules` 에만 있고 단계를 만드는 분할 경로는 그
상수를 안 싣는다. **같은 경로 함정을 한 회차에 두 번 밟았다.**

고쳤다: 공유 예시 안에 앵커를 **안 다는** 문장(`SELECT COUNT(1) …` 가드 조회)을 넣어
다는 문장과 갈랐고, 양 경로 잠금을 걸었다.

# 앵커 프로브 — 4시간을 13분으로

사람 질문: 「한 판에 4시간이면 너무 오래 걸리는데, 한 판 돌리면 결함 없이 나오나?」

**안 나온다.** 두 판 다 재시도 예산 6회를 소진하고 「최고 점수 판 채택」으로 끝났다
(82/100 · 78/100). 하한 발화가 판당 114~144 회이고 검사 B 는 다섯 Job 전부에서
2~3 건씩 난다. 4시간은 **이진 관측 하나**를 사는 값이었다.

그래서 축을 갈랐다 — 계약이 묻는 것은 「배송본이 어떤가」가 아니라 **「프롬프트가
모델을 그 모양으로 이끄는가」** 이고, 그 질문에는 단계당 호출 한 번이면 답이 나온다.

`--probe-anchors <Job>`: 얼어붙은 Job 의 목차·골격·명세서를 재료로, 명세서가 SELECT
행을 선언한 단계만 **첫 생성 한 번씩** 실물로 돌린다. 스텁이 아니라 실제 파이프라인이
부르는 `GenerateBatchStepSectionAsync` 를 그 재료로 부르며, `floorFeedback` 과
`previousBody` 만 null 로 둔다 — 그 둘이 「첫 생성」 축을 만든다.

**첫 실행 결과(13분):**

```
도달률 5/5 · 놓친 선언 행 0 · 지어낸 서수 0 · 접어 넣음 0
S07 1 · S11 1,2,3,4,5,6 · S13 1 · S14 1 · S15 1   (선언 = 앵커, 전부 일치)
```

여섯 서수를 선언한 S11 에서도 전부 붙었다 — Batch4·Batch5·Batch8 에서 이 모양이
매번 무너지던 자리다. **고친 예시가 듣는다.**

프로브가 못 하는 것은 산출물 자신이 적는다: 첫 생성 축이라 배송본을 판정하지 않고,
표본 1 이며, 앵커 모양 하나만 본다.
