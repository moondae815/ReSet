## 0. 무엇으로 쟀는가 — 자를 먼저 밝힌다

`--sweep` 보고서는 **쓰지 않았다.** 그것은 검사별·Job 별 **발화 수**만 싣고 메시지를 안 실어
이 검사가 「미분류」에 합산된다. 대신 `MechanicalValidator.ValidateBatchStep(…)` 를 직접 돌리고
`result.Errors` 에서 「타입 계약」+「드라이버 바인딩」을 **함께** 담은 항목만 걸렀다.

적재는 `SweepCommand.Run` 의 규약을 그대로 본떴다(`raw/PlanStructure.md` → `BatchStepPlanParser`,
DDL 은 `output/Procedures/<dir>/raw/metadata.json` 의 `DdlText`).

> **이 하네스에서 실제로 한 번 데였다 — 기록으로 남긴다.**
> `ddlByProcedure` 를 디렉터리 이름(`dbo.UP_X`)으로 키잉했더니 검사가 `BareObjectName` 으로
> 조회해 **전건 빗나가고 발화가 0** 이 나왔다. 스윕이 `ToBareNameKeyed` 로 맞추는 것과 같은
> 규약으로 **맨이름**을 깔아야 한다. **발화 0 은 「결함이 없다」가 아니라 대개 키잉이
> 어긋난 것이다** — 그 0 을 그대로 믿었으면 이 태스크는 값 0 을 게이트 통과시켰다.

## 5. 오탐이 다수가 아니다

### 5-1. 발화 후보를 전부 열어 봤다 — 후보 **4** · 진짜 **4** · 오탐 **0**

후보는 **오라클을 쓰지 않고** 「소수 리터럴이 바인딩 값 자리에 온 자리」로 따로 셌다(검사와
독립한 자다). 초과분이 없어 열어 볼 초과 후보 자체가 없었다.

```
@@@ 후보 직접(소수 리터럴 바인딩) = 3
   output/Jobs/POQSettleBatch4/agent/steps/S06.md :: execute(SQL_UPDATE5) p_incVat: 1.1
   output/Jobs/POQSettleBatch5/agent/steps/S05.md :: execute(SQL_UPDATE_13) p_v_valIncVat: 1.1

@@@ 후보 모호(두 번 이상 대입 · 그중 소수 리터럴 포함) = 0

넷 다 **방출 SQL 에 해당 변수의 `DECLARE` 가 없다** — 타입을 드라이버가 고른다. 진짜다.

## 좁힌 처방 뮤턴트 — 좁힌 처방이 **옳다**

발화 조건을 「바인딩 대조」 대신 **「`DECLARE` 가 없으면 발화」**로 바꿔 전 스위트를 돌렸다.

**깨진 시험 5:**

```
MechanicalValidatorTests.ValidateBatchStep_InlinesTypedConstantIntoSql_IsSilent      ← 기대한 그것
MechanicalValidatorTests.ValidateBatchStep_BindsIdentifierReassignedInFence_IsSilent
MechanicalValidatorTests.ValidateBatchStep_BindsUnassignedIdentifier_IsSilent
MechanicalValidatorTests.ValidateBatchStep_BindsIdentifierTwoHopsFromTypedConstant_IsSilent
MechanicalValidatorTests.ValidateBatchStep_BindsIdentifierHoldingTypedConstant_MessageNamesTheAssignment
```

`ValidateBatchStep_InlinesTypedConstantIntoSql_IsSilent` 가 깨졌다 — **안전한 인라인
(`CAST(CLComm / 1.1 AS INT)`, `DECLARE` 없음)에 발화한다**는 뜻이고, 그것이 §5-1 의 좁힌 처방이
옳았다는 증거다. **그 시험은 아무것도 안 잠그고 있지 않다** — 고칠 필요가 없다.

> **그런데 코퍼스는 이 축을 못 가른다 — 재서 확인했다.**
> 같은 뮤턴트에서 **코퍼스 발화는 4 로 변하지 않았다.** 오늘 라이브 코퍼스에는
> 「관할 상수가 있고 · 바인딩도 있고 · `DECLARE` 는 없는데 · 리터럴을 인라인해 안전한」
> 단계가 **없기 때문**이다. 즉 **좁힌 처방을 잠그는 것은 코퍼스 시험이 아니라 그 단위
> 픽스처 하나**다. 코퍼스 시험만 초록인 것을 보고 「좁힘이 검증됐다」로 읽으면 안 된다.

## 이월 둘 — 재생성 판정으로 넘긴다

### D9 — 같은 변수에 지적이 두 번 실리는 조합: **오늘 0**

이름 기반 검사(`CheckSpecLocalVariablesDeclared`)에 재료(`statementFactsByProcedure`)를
스윕과 같은 손으로 넘기고 함께 돌렸다.

```
@@@ D9 동시 발화 단계 = 0 (타입계약만 4 · 이름기반만 12)
@@@ D9 같은 변수 동시 지적: (출력 없음)
```

**0 인 이유는 설계가 막아서가 아니다** — 네 발화 자리가 **모두 방출 SQL 에서 변수를
개명**(`@p_valIncVat`·`@p_incVat`·`@p_v_valIncVat`)했기 때문이다. 이름 기반 검사는 개명한
이름을 못 본다.

> **재생성 판정에서 이 조합을 따로 세라.** 재생성이 **원본 이름을 보존하는 순간**
> 같은 변수에 지적이 두 번 실린다 — ① 이 검사의 오탐(아래 「반쪽 이행」) ② 이름 기반
> 검사의 발화. 두 검사는 **오라클이 달라 서로를 모르고 억제가 구현돼 있지 않다**
> (계획 개정 6). **「오류가 2 건이니 결함도 2 개」로 읽지 마라.**

### §8 「반쪽 이행」 — 오늘 교집합 **0**

`sql` 펜스에 `DECLARE` 가 있는데 바인딩에도 리터럴이 남은 상태는 **발화한다**(오탐).
두 집합을 각각 세어 교집합을 냈다 — **목록이 아니라 출력이다**:

- 이름 눈먼 보존 자리(펜스에 `DECLARE @x <정밀도타입> = 1.1`): **24**
- 배송 규칙으로 발화하는 단계: **4**
- **교집합: 0** — 프로브가 보존 24 를 한 줄씩 찍은 출력에서 `발화=` 가 전부 `False` 다.

두 집합이 오늘 서로소인 것은 우연이 아니라 **결함의 정의**다(유출은 `DECLARE` 를 안 둔 것이니까).

> **재생성 판정에서 이 모양을 명시적으로 찾아라.** 오류 메시지가 시키는 처방이 **두 동작**
> (「`DECLARE` 를 두고」 **그리고** 「바인딩 목록에서 그 값을 빼라」)이라, 반만 이행한
> 재생성본은 계속 운다. **발화가 남았다고 곧바로 「안 고쳐졌다」로 읽지 말고 `DECLARE` 가
> 생겼는지를 함께 봐라.** 고치는 중에는 위의 서로소가 깨진다.

### 덧 — 재생성 판정에서 `Batch1/S05` 를 재는 법

넷째 자리는 **애초에 바인딩에 리터럴이 없다**(`p_valIncVat: v_valIncVat`). 「리터럴이
사라졌는지」로 판정하면 **공허하게 통과**한다. **`@p_valIncVat` 가 방출 SQL 에서 `DECLARE` 로
바뀌었는가**로 봐야 한다.

## 이 결함이 지금 무엇을 우연히 덮고 있나 — 넷째 자리, 라이브 코퍼스

방출 SQL 에 `DECLARE @v_valIncVat DECIMAL(2,1) = 1.1;` 추가 · `@p_valIncVat` → `@v_valIncVat`).
