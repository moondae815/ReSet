# 앵커 도달률 판독 — **3.8% 는 검사 B 의 도달률이 아니다** (2026-09-05 실측)

분류 문서(`2026-09-05-축B-잔여결함-분류.md`) §12 가 「검사 B 의 도달률이 3.8% 이고 그것이 남은 `K`
전부의 상한」이라 적었다. **그 수를 층으로 갈라 재니 라벨이 틀렸다.**

- 3.8%(99/2,637)는 **U-앵커 채택률**이다.
- **검사 B 의 도달률은 관할 1,413 문장 중 852 — 60.3% 다**(전체 2,637 대비로는 906, 34.4%).

§12 는 검사 B 가 코드 앵커 경로로도 도는 것을 본문에서는 인정하면서 **분자에서는 뺐고**, 분모에는
**검사 B 가 원리적으로 볼 수 없는 문장 1,224 개**(제어·섀도·스테이징 테이블 대상)를 함께 넣었다.
두 오차가 같은 방향으로 겹쳐 9.2 배 좁은 수가 나왔다.

**그럼에도 3.8% 라는 수 자체는 버릴 것이 아니다.** 라벨을 고치면 이 수가 오히려 더 날카로워진다 —
아래 §4 가 그것이다.

## 1. 어떻게 쟀나

`--sweep` 이 이미 도는 자리(`StepSweepService`)에 **되돌릴 프로브**를 붙여 문장 단위로 덤프했다.
검증기가 실제로 부르는 것과 **같은 함수**(`MechanicalValidator.ResolveOrdinal` ·
`ResolveAnchoredStatements` · `BuildSpecTargets` · `MergeErrorCodeMaps`)를 그대로 불렀다 —
사본을 두면 규칙이 갈린다.

- 격리 워크트리(`ReSet-anchor-reach`, `main` `959be000` 못박음), 코퍼스는 심링크.
- 측정 쌍 328 (Job 18) · 문장 2,637 — 스윕 보고서 머리말과 같은 범위다.
- **프로브는 전량 되돌렸다.** `main` 에도 워크트리에도 코드 변경이 없다.

계정이 닫히는 것으로 검산했다: `898`(코드 앵커 환산) + `88`(U-앵커 전용) = `986`(환산 성공),
`986` − `80`(모호성 가드) = `906`(검사 B 도달). 프로브의 세 계수가 서로 다른 경로로 세는데 합이 맞는다.

## 2. 층 분해 — 관할 분모로 다시 센 값

**분모를 갈라야 한다.** 검사 B 는 명세서 DML 범위 표에 **그 대상 테이블의 행이 있는 문장**만
대조할 수 있다(`candidates` 가 `Ordinal`·`Kind`·`TargetTable` 셋으로 매칭한다). 제어 테이블
(`BatchStepJournal`·`BatchRun`·`BatchCheckpoint` …)과 섀도·스테이징 대상은 **관할 밖**이지
「도달 실패」가 아니다.

```
코퍼스 단계 SQL DML 문장                            2,637
├ 검사 B 관할 밖 (대상이 명세서 DML 표에 없다)      1,224   ← 제어·섀도·스테이징
└ 검사 B 관할 안                                    1,413  (100%)
   ├ 서수 환산 성공                                   907  (64.2%)
   │   ├ **모호성 가드 통과 = 검사 B 도달**            852  (60.3%)
   │   └ 모호성 가드가 버림(한 코드를 여럿이 씀)        55  ( 3.9%)
   └ 미환산                                            506  (35.8%)
       ├ 앵커 없음                                     424
       │   ├ 구간에 아무 코드도 없다                    291
       │   ├ 구간에 **양수 예약 코드만** 있다            67
       │   └ 구간 후보 2 개 이상(리더 유일성 규칙)       66
       ├ 코드는 있으나 명세서 사전에 없다                59
       └ 사전엔 있으나 `Kind` 불일치                     23
```

전체 대비 U-앵커 보유 문장은 99 (3.8%) · 코드 앵커 보유 문장은 1,127 (42.7%)이다.

### 조건 (A) 와 조건 (B) 가 **같다**

스윕 보고서는 「(B) 는 상한이다 — 모델이 오류 코드 표를 완전히 전사한다고 가정한 값」이라 적는다.
실측하니 **오늘 코퍼스에서 둘이 완전히 같다**: 코드 사전 크기 1,144 = 1,144, 환산 986 = 986,
도달 906 = 906. **명세서 오류 코드 표의 전사는 지금 병목이 아니다** — 검사 D·T02 가 겪은
「명세서가 재생성되며 재료를 잃는다」는 이 축에서는 오늘 일어나지 않고 있다.

## 3. 미환산 506 을 누가 소유하는가 — 넷은 서로 다른 층이다

### (a) 291 「구간에 아무 코드도 없다」 — **절반은 의도된 것이다**

실물 둘을 열어 확인했다. `POQSettleBatch1/S11` 은 문장 12 개 중 1~8 이 앵커되고 9~12 가 무앵커인데,
그 넷은 `SQL_RESTORE_DELETE_*` — **이행이 롤백용으로 새로 더한 복구 DML** 이다. 원본 기원이 없으니
원본 오류 코드도 서수도 없다. `POQSettleProc9/S03` 도 같은 모양이다(1~15 앵커, 16~25 복구).

기계 근사(같은 단계에서 앞서 앵커된 `(종류, 대상)` 이 다시 나오는 무앵커 문장)로 세면 **291 중 149**
가 이 부류다. 근사이지 판정이 아니다 — 나머지 142 는 안 갈랐다.

### (b) 67 「양수 예약 코드만 있다」 — **정규식이 음수만 본다**

`ReadCodeAnchor` 의 `CodeAnchorPattern` 은 **음수 리터럴만** 후보로 본다. 그 좁힘의 근거는
「`INT = 0` 초기화와 `SET @v_cnt = @@ROWCOUNT` 같은 관용구를 빼려면 음수여야 한다」였다.
그런데 실물에는 **규칙 6-2 예약 블록 코드**가 있다 — `POQSettleProc2/S15` 는
`SET @v_currentStepId = 4000;` · `4001` · `4002` 로 문장마다 라벨을 달았고, 그 셋은 양수라 통째로
버려진다.

**다만 이 층은 열어도 값이 작다.** 예약 블록 코드는 정의상 원본 기원이 없어 명세서 사전에 없고,
사전에 없으면 서수로 환산되지 않는다. 실제로 그 단계(`Proc2/S15`)는 머리말이
「목차 `ErrorCodes` 가 비어 있어 원본 오류코드 대조를 실행할 수 없습니다」라 적는다 —
**원인이 리더가 아니라 그 위(목차가 코드를 선언하지 않았다)에 있다.**

### (c) 66 「구간 후보 2 개 이상」 — 리더의 유일성 규칙

의도된 침묵이다(태스크 22 가 세운 「구간 내 유일성」). 되돌린 이력이 있는 자리라 손대지 않는다.

### (d) 59 「코드는 있으나 사전에 없다」 — **전량이 원본의 1:다 코드다**

59 건의 코드 분포가 **`-1` 40 · `-2` 19, 그 둘뿐이다.** 명세서 24 편의 오류 코드 표를 전수로 세니
**한 코드가 둘 이상의 문장에 걸린 SP 가 정확히 둘**이고 그 코드가 바로 그 둘이다.

```
dbo.UP_UTIL_SETTLE_EXCEPTION_PROC   -1 · -2   (표 행 4)
dbo.UP_UTIL_STAT_PGCOLLECT_INS      -1        (표 행 2 — DELETE 1 과 INSERT 1 이 같은 -1)
```

**전사 결함이 아니라 원본의 성질이다.** 코드→서수가 1:다면 코드 앵커로는 **원리적으로** 귀속할 수
없고, `MergeErrorCodeMaps` 가 그 코드를 빼는 것이 옳다.

이것이 §11 의 T22 되돌림을 **확증하면서 사유를 고친다**. §11 은 「`STAT_PGCOLLECT` 는 모든 Job 에서
서수 앵커가 없다」고 적었는데, 실측하면 **코드 앵커 `-1` 은 18 개 문장에 붙어 있다.** 도달하지
못하는 이유는 앵커 부재가 아니라 **그 코드가 원본에서 두 문장에 걸려 사전에서 빠진 것**이다.
`TStatPGCollect` 를 대상으로 하는 문장은 코퍼스에 51 개이고 **검사 B 도달은 0 이다** — 이 수치는
§11 의 결론을 그대로 지지한다.

### (e) 23 `Kind` 불일치 — **발화로 바꾸면 대부분 오탐이다**

37 건(전체) · 23 건(관할)을 전부 열어 봤다. 관할 쪽의 지배적 모양이 이것이다:

```
INSERT TSettleMst | 코드 -2 | 명세서 UPDATE 1·2      (Proc8·11·13~19·Prco20 …)
```

이행이 원본 `UPDATE` 를 섀도 재구축 `INSERT` 로 바꾸고 **원본 코드를 그대로 물려준** 자리다.
공통 계약이 「그 문장이 원본 절차에서 가졌던 오류 코드」를 요구하므로 **계약을 지킨 결과**다.
그대로 발화시키면 오탐이 다수가 되고, 이 저장소에서 오탐은 `SuggestedPromptFix` 를 타고 재생성
프롬프트에 실려 재시도를 소진시킨다. **T29 를 「`Kind` 불일치 = 발화」로 만들면 안 된다.**

## 4. 그래서 3.8% 는 무엇인가 — **의도된 좁음인데, 지금 남은 것 전부의 병목이다**

**U-앵커는 어느 층도 요구하지 않는다.** `AiService` 규칙 6-1 이 요구하는 것은 오류 코드 상태 변수이고,
`/* U13: … */` 같은 서수 주석은 **모델 재량**이다. 그러므로 3.8% 는 결함이 아니라 **아무도 요구한
적 없는 것의 채택률**이다. 그 뜻에서는 「의도된 좁음」이 맞다.

**그러나 남은 결함 전부가 그 자리에서 막힌다.** 위 층 분해에서 **U-앵커가 있으면 열리고 없으면
원리적으로 못 여는 것**만 모으면:

| 층 | 관할 문장 | 왜 U-앵커여야만 하는가 |
| :--- | ---: | :--- |
| 모호성 가드가 버림 | 55 | 코드가 여러 문장에 재사용됐다 — 코드로는 못 가른다 |
| 사전 1:다로 미등재 | 59 | 원본이 한 코드를 두 문장에 썼다 — 코드로는 **원리적으로** 못 가른다 |
| `Kind` 불일치 중 진짜 오배정 | ≤ 23 | 같은 종류·다른 서수의 오배정은 독립 서수 없이 안 보인다 |

**합쳐 최대 137 문장.** 지금 U-앵커를 가진 문장은 코퍼스 전체에 99 개다.

**그리고 만족 가능성은 이미 증명돼 있다.** `POQSettleBatch1/S11` 이 자발적으로 이 모양을 쓴다:

```sql
-- SQL_DELETE_TSETTLEBYTX  (DELETE 1, 원본 라인 28, 오류코드 -1)
DELETE FROM SETTLE_POQ_DB.dbo.TSettleByTX
```

`AnchorPattern` 이 `U4`·`갱신 4`·`UPDATE 4`·`INSERT 4`·`DELETE 4` 다섯 표기를 이미 인정하므로
**리더를 손댈 필요가 없다** — 이 주석 하나로 그 단계의 문장 8 개가 전부 서수를 얻는다.
`ErrorCodeTableCorpusTests`·`LocalVariableTableCorpusTests` 가 캐시 인상 전에 만족 가능성을 확인한
것과 같은 자리에 이미 실물 증거가 있다는 뜻이다.

## 5. 이 판독이 남은 `K` 의 순서를 어떻게 바꾸나

§12 는 「남은 `K` 는 대부분 그 4% 안에서 대조 칸을 넓히는 일」이라 적었다. **그 문장은 틀렸다.**

| 항목 | §12 의 말 | 실측 |
| :--- | :--- | :--- |
| 검사 B 의 관할 | 3.8% | **60.3%**(관할 분모) · 34.4%(전체 분모) |
| T21 | 「이 4% 안에서 논다」 | **아니다** — `CheckSpecSetExpressions` 는 앵커를 안 쓰고 단계 본문 전체를 훑는다(`ContainsSetExpressionToken(stepMarkdown, t)`). 앵커 상한과 무관하다 |
| T29 | `K¹`(판별자 확장) | **그대로 만들면 안 된다** — 발화 후보 23 의 다수가 계약을 지킨 섀도 재구축이다(§3-e) |
| T22 | `U`(되돌림) | **유지.** 사유는 「앵커 부재」가 아니라 「원본의 1:다 코드」로 고친다(§3-d) |

**가장 값이 큰 다음 걸음은 「대조 칸을 넓히는 것」도 「검사를 더 만드는 것」도 아니다 —
U-앵커를 모델 재량에서 계약으로 올리는 것이다.** 그것은 `P` 계열(프롬프트·공통 규약)이고,
남은 `K` 여섯 어느 것보다 위에 있다. 동료 세션 `reset-b1` 의 SET 산식 판독 §8-2 가 같은 종류의
상한을 다른 계열에서 재고 있고, 두 계열의 질문이 여기서 하나로 선다.

**다만 이 문서는 그 착수를 승인하지 않는다.** 계약을 늘리면 프롬프트가 바뀌고, 프롬프트가 바뀌면
캐시 포맷 버전과 전건 재생성이 따라온다 — 이 저장소가 세 번 「인상 전에 만족 가능성을 먼저 확인한다」
규칙을 적용한 자리다. **다음 사람이 재야 할 것**은 이것이다:

1. **계약을 어디에 다는가** — `AiService` 규칙 6-1 옆인가, 단계 공통 규약(`01-step-contract.md`)인가.
   후자면 캐시 인상 없이 다음 재생성부터 켜진다.
2. **만족 가능성** — `S11` 하나가 아니라 코퍼스 전량에 대해. 원본 서수를 단계 문장에 사상할 수
   있는가(청크 분할·문장 재배치가 있는 단계에서도).
3. **되돌리는 조건** — 아래 §6.

## 6. 다음에 코드를 만들 사람이 먼저 적을 것 — **되돌림 조건**

어제 두 번 되돌렸다(접기 판별자 · T22). 둘 다 **게이트 녹색 · 단위 시험 통과 · 코퍼스 발화 0** 이었다.
되돌릴 수 있었던 것은 「무엇이 나오면 되돌리는가」를 **착수 전에 파일에 적어 뒀기 때문**이다.
대화에만 두면 숫자를 맞추려고 조건을 손보게 된다.

**이 판독이 다음 착수에 물려 주는 조건 셋:**

1. **발화한다.** 코퍼스 스윕에서 발화 > 0. 단위 시험 통과는 효력이 아니다.
2. **오탐이 다수가 아니다.** 발화 전량을 눈으로 판정하고, 계약을 지킨 자리가 절반을 넘으면 되돌린다
   (§3-e 가 T29 를 이 조건으로 막았다).
3. **없앴을 때 무엇이 지나가는지 잰다.** 발화 수가 아니라 되돌려 본 차분이 효력이다.

**셋 중 하나라도 어긋나면 판별자가 틀린 것이므로 되돌리고 다시 잰다. 숫자를 맞추려고 조건을
손보지 않는다.**

## 7. 이 판독이 보증하지 않는 것

- **291 중 149 「복구 거울」은 근사다.** 같은 단계에서 앞서 앵커된 `(종류, 대상)` 이 다시 나오는지로
  셌다. 실물 둘(`Batch1/S11` · `Proc9/S03`)에서 참인 것을 확인했을 뿐 전수 판정이 아니다.
  나머지 142 는 안 갈랐다.
- **`Kind` 불일치 23 중 진짜 오배정이 몇인지 안 셌다.** 「다수가 오탐」까지가 이 문서의 주장이다.
- **U-앵커 계약화의 비용을 안 쟀다.** 캐시 인상 여부도, 재생성 범위도 §5 의 「재야 할 것」이다.
- **관할 밖 1,224 를 검사 B 가 볼 필요가 없다는 것은 이 문서가 확정한다.** 다만 그 문장들을
  **다른 검사가** 봐야 하는지는 이 문서의 물음이 아니다.

## 8. ★ §4 의 전제가 거짓이었다 — **계약은 이미 있다. 없는 것은 강제다** (2026-09-06)

§4 는 「**U-앵커는 어느 층도 요구하지 않는다** … `/* U13: … */` 같은 서수 주석은 **모델 재량**이다」를
전제로 3.8% 를 「의도된 좁음」이라 판정했다. **그 전제가 실물과 어긋난다.**

```
AiService.cs:4518   "### 문장 앵커와 의미 보존 (필수)"
                    "**각 DML 문장 바로 앞에 명세서의 갱신 번호를 주석으로 답니다.**
                     `/* U13: 카드사 원가 반영 */` 형식입니다"
도입   e6d37eb7  2026-08-26
배선   GenerateBatchStepSectionAsync:4392   ← 단계 지시서 생성 경로에 걸려 있다
강제   `result.Errors.Add` 91 곳 중 **앵커 관련 0 곳**
```

**규약은 `(필수)` 로 있다. 없는 것은 L1 강제다.**

### 그리고 3.8% 는 결함도 의도도 아니라 **산출물의 세대 나이**다

| | 생성 시각 | U-앵커 |
| :--- | :--- | ---: |
| `POQSettleBatch1` (규칙 **후** 재생성) | 2026-09-04 | **~99** — 코퍼스 전체 99 의 사실상 전부 |
| 나머지 20 편 (규칙 **전**) | 2026-08-12 ~ 19 | **~0** |

**20 편은 그 규칙을 받아 본 적이 없다.** 그러니 3.8% 는 「아무도 요구한 적 없는 것의 채택률」이
아니라 **「20/21 이 규칙 이전 산출물이다」**를 재고 있었다.

**다만 규약을 받은 Batch1 도 전량은 아니다** — 규약만으로는 안 붙는 자리가 남는다.
**그래서 강제가 필요하다는 결론은 그대로 서고, 근거만 바뀐다.**

### 사람 결정 (2026-09-06) — **강제 검사만. 재생성은 미룬다**

| | 판독 §4 의 전제대로면 | 실물대로면 |
| :--- | :--- | :--- |
| 해야 할 일 | 프롬프트에 규약 추가 | **없음 — 이미 있다** |
| 캐시 인상 | 필요 | **불필요** |
| 전건 재생성 | 필요(선행) | **불필요**(값은 있으나 선행이 아니다) |
| `AGENTS.md` 상한 | 결정 필요 | **무관** |
| 남는 것 | — | **L1 강제 검사 하나** |

**순서는 「검사 먼저, 재생성 나중」이다.** 재생성이 먼저면 앵커가 **모델 재량으로** 붙고 강제가 없어
다음 회차에 또 흔들린다 — 이 저장소에 전례가 둘 있다(검사 D 가 18 → 0 으로 꺼진 것,
`EXCEPTION_PROC` 가 재생성으로 메워졌으나 **기계가 민 것이 아니었던** 것: 로드맵 5 판독 §4).

### 착수 전에 재야 할 것 — **정규식으로 재지 마라**

강제 검사의 관할(「어느 문장이 앵커를 가져야 하는가」)은 아직 안 쟀다. 알려진 함정 둘:

- **이행이 롤백용으로 더한 복구 DML** 은 원본 기원이 없어 서수가 없다(§3-a 의 근사 149).
  `ReadsOnlyStaging` 이 복구 `INSERT` 는 면제하지만 **복구 `DELETE` 는 원천이 0 이라 면제가 안 된다.**
- 배치 제어 테이블(`BatchRun`·`BatchStepJournal`·`BatchRunLock`·`BatchCheckpoint`)과 섀도우 캡처는
  명세서 DML 표에 없어 관할 밖이다.

**그리고 이 절을 쓰며 정규식으로 여덟 번 틀렸다.** 마지막 것은 `\b(UPDATE)\b` 대안이
주석 `-- UPDATE 3:` 을 문장으로 잡은 것이다. **리더를 다시 구현하지 마라** —
`StepSqlStatementReader` 가 이미 그 일을 하고, 이 문서 §1 의 수치가 그것으로 잰 정본이다.
착수하면 **그 리더를 부르는 일회용 프로브**로 재라(§1 이 쓴 방법 그대로).

## 9. 강제 검사 착수 — **재고 나서 안 만들기로 했다** (2026-09-06)

§8 의 결정(「강제 검사만」)으로 착수해 **리더를 부르는 일회용 프로브**로 관할을 쟀다
(정규식 금지 규정을 지켰다). 코드는 아무것도 안 남겼다.

### 실측 — Batch1 준수율은 **80.6%** 다

```
POQSettleBatch1 :  관할 108 · 앵커 87 (80.6%) · 무앵커 21
   무앵커 21 의 내역
     ├ 복구 구간(`-- SQL_RESTORE` 뒤) 18   → 정당. 이행이 롤백용으로 더한 것이라 원본 서수가 없다
     ├ S04 `SQL_COMPENSATE_DELETE`  1     → 정당. 이행이 더한 보상 삭제다
     └ S15 `TStatPGCollect` DELETE·INSERT 2
```

**「모델이 규약을 안 지킨」 진짜 누락은 0 이다.** 강제 검사가 잡을 것이 없다.
(다른 20 편은 앵커 0~12 인데 **규칙 이전 산출물**이라 강제의 대상이 아니다 — §8.)

### 판별자 후보 셋 중 둘이 실패했고 하나가 섰다

| 후보 | 결과 |
| :--- | :--- |
| `ReadsOnlyStaging` | **실패** — 복구 `DELETE` 는 원천이 0 이라 면제가 안 된다 |
| 「같은 단계에 앞선 앵커 문장」 | **실패** — 원본 자신이 무앵커면 복구와 안 갈린다(S06·S12) |
| 명세서 행 수 초과 | **실패** — 명세서 2 행 · 단계 2 문장으로 **우연히 일치**한다 |
| **`-- SQL_RESTORE` 구간** | **성공** — 18/3 으로 깨끗하게 갈린다 |

### S15 둘의 정체 — **모델은 앵커를 썼다. 리더가 못 읽는다**

```
-- DELETE1: 기준 정산일의 기존 PG 회수 통계 삭제 (원본 라인 22~23, 오류 코드 -1)
-- INSERT1: … 3원천 UNION ALL 집계 재적재 (원본 라인 31~120, 오류 코드 -1)
```

`AnchorPattern` 이 `\bINSERT\s+` 로 **공백을 하나 이상 요구**한다. `INSERT1` 은 공백이 없어 버려진다.
같은 패턴의 `\bU` 와 `\b갱신\s*` 는 공백 없이도 받으므로 **일관성이 없다.**
그리고 **이 둘이 T22 가 막힌 바로 그 자리**다(원본이 `-1` 을 두 문장에 써서 코드로는 원리적으로 못 가른다).

### 그런데 패턴을 건드리면 **손해다** — 두 판 다 그랬다

| 판 | Batch1 앵커 |
| :--- | ---: |
| 원판(`\s+`) | **87** |
| 완화(`\s*`) | **84** |
| 완화 + 종류 대조(`(?<kw>…)` 캡처 후 문장 `Kind` 와 일치 요구) | **84** |

**예측은 89 였고(S15 둘이 열린다) 관측은 84 다. 빗나갔다.** 다른 17 편은 예측대로 **전부 불변**이라
회귀는 Batch1 안에서만 난다. **왜 5 를 잃는지 이 회차에서 못 밝혔다** — 종류 대조를 넣어도 안 막혔다.

관측된 사실 둘은 확실하다.

- **`AnchorPattern` 은 서수만 잡고 종류를 버린다.** 비캡처 그룹
  `(?:\bU|…|\bDELETE\s+)` 이라 `/* INSERT1: … */` 주석이 **`DELETE` 문장 앞에** 있으면
  그 `DELETE` 가 서수 1 을 받는다(S02 의 DELETE-INSERT 관용구가 그 모양이다).
- **오늘은 그것이 안 물린다** — U-앵커의 `(Kind, 서수)` 쌍이 명세서에 없는 경우가 **코퍼스 전체 0** 이다.
  `\s+` 요구가 **우연히** 막고 있다. **방어가 아니라 우연이다.**
- **U-앵커와 코드 앵커의 충돌도 코퍼스 전체 0** 이다(완화판에서 측정).

### 판정 — **강제 검사도, 패턴 완화도 하지 않는다**

- 강제 검사: **잡을 것이 없다**(진짜 누락 0).
- 패턴 완화: **실측으로 손해**이고 그 이유를 아직 모른다. **모르는 채로 넣지 않는다.**

### 다음 사람에게 — 여기서부터 열어라

**T22 를 여는 길은 S15 의 두 문장이고, 그 둘은 「모델이 안 썼다」가 아니라 「리더가 못 읽는다」다.**
그러므로 다음 걸음은 강제도 재생성도 아니라 **「패턴을 고치면 왜 Batch1 에서 5 를 잃는가」를 밝히는 것**이다.
그것을 모르는 채로 패턴을 고치면 도달률이 내려간다 — **이 회차가 그것을 두 판으로 확인했다.**

측정은 **정규식이 아니라 `StepSqlStatementReader` 를 부르는 프로브**로 하라(§8 말미).
이 절을 쓰며 정규식으로 여덟 번 틀렸고, 프로브로 바꾼 뒤에야 수가 섰다.
