# 검사를 재는 관할을 「배송본」에서 「거부된 시도」로 넓힌다 — 설계

**작성 2026-09-09.** 기준 커밋 `8019ecfc`(main). **코드는 안 만졌다 — 이 문서는 결정 자료다.**

**출처**: 같은 날 `dbo.UP_UTIL_SETTLE_EXCEPTION_PROC` 재생성 세 판. 검사 결함 네 개를
멈춤–수정–재실행으로 하나씩 닫았고, 그 반복 자체가 무엇을 말하는지 물은 자리.

---

## 1. 결함 — 검사를 재는 코퍼스가 생존자 편향이다

모든 L1 검사는 착수 전에 `output/**/Spec.md` **31 편**에 대고 「발화 N · 오탐 0」을 재고
배송된다. `CheckErrorCodeUniquenessClaim` 의 주석이 그 관례를 그대로 적고 있다:

> [착수 전 코퍼스 실측] 「고유」가 「코드」와 같은 문장에 있는 명세서는 4 편이고 그중
> 표에 중복이 있는 것은 EXCEPTION_PROC 하나뿐이다 — **발화 1 · 오탐 0**

**그 31 편은 이미 L1 을 통과한 문서다.** 검사의 오탐을 드러내는 텍스트는 **그 검사의
메시지를 읽고 모델이 새로 쓴 문장**이고, 그런 문서는 정의상 통과하지 못했으므로 코퍼스에
못 들어온다. gitignore 된 실행 로그에만 있다.

즉 **검사가 자기 오탐의 입력을 스스로 만들어 내는데, 그 입력을 시험에 한 번도 안 넣는다.**
「오탐 0」은 참이지만 **오탐이 살 수 없는 자리에서 잰 값**이다.

### 오늘 넷이 전부 그 자리다

| 결함 | 오탐을 만든 텍스트의 출처 | 닫은 커밋 |
| :--- | :--- | :--- |
| 「고유」 부정문 | 검사의 처방문 「…가 아니라 중복 포함이라 쓰라」를 **그대로 따른 문장** | `9734825d` |
| 「서로 다른」 수식 범위 | 처방문 「같은 코드를 쓰는 문장이 있다」가 자연히 낳는 「두 **서로 다른** 단계가 **같은** 코드를」 | `6fc130c1` |
| 붙은 표 행 | 처방이 「칸을 지우라」로 읽혀 확정 행을 지우게 유도 | `1e362c0b` |
| 축약어 | 설명 칸의 접속 표현(「위와 동일한 조건 판단(…)에 따라」). 그런 문서는 통과한 적이 없다 | 미해결 |

**넷 중 어느 것도 착수 전에 상상할 수 없었다.** 전부 모델이 실제로 쓴 문장을 보고서야
보였다. 그러니 고칠 것은 우리의 상상력이 아니라 **재료의 관할**이다.

### 탐지 비용

지금 한 결함을 잡는 데 드는 것: 전량 재생성(시도당 8~9 분, 최대 6 회) → 사람이 터미널을
지켜보며 「멈출까 진행할까」를 판단 → 3 만 줄짜리 gitignore 로그에서 실물을 오려냄.
**오늘 이 사이클을 세 번 돌았다.**

## 2. ★ 탐지기를 만들 때 먼저 걸릴 함정 — 폭발 반경 안의 탐지기

`MechanicalValidator` 의 발화 자리를 **가장 안쪽 메서드로 묶어** 세면(2026-09-09 실측):

```
발화 자리(result.Errors.Add)          97
타입 키 자리(result.DetailedErrors.Add) 57
타입 키가 하나도 없는 검사             30 개 · 그 발화 자리 40
```

큰 것부터: `ValidateBatchStep` 7 · `CheckControlStepErrorCodeBand` 3 ·
`CheckShadowBackupContract` 3, 나머지 27 개가 각 1. **그 27 중 하나가 재시도 6 회를
태운 `CheckErrorCodeUniquenessClaim` 이다.**

> 세는 자 주의 — 메서드 범위를 앞뒤로 훑어 합치면 중첩 지역 함수가 겹쳐 세어져
> 합계가 108 로 부푼다. 위 수는 **발화 한 줄마다 가장 가까운 메서드 시그니처를
> 거슬러 찾아** 귀속시킨 값이고, 97 = 57 + 40 으로 닫힌다.

`ErrorType` 으로 수렴을 추적하는 탐지기를 만들면 **정확히 사고를 낸 검사들에 눈이 먼 채
초록을 찍는다.** 「폭발 반경 안에 있는 자는 탐지기가 아니라 피해자다」의 전형이다.
그래서 키 배선이 선행 작업이다.

## 3. 절 1 — 발화마다 키를 단다

### 3.1 결정: `ErrorType` 을 늘리지 않는다

`DetailedErrors` 는 관측용이 아니라 **의미를 지닌 통로**다 —
`RegenerationScopeSelector.FromL1Errors` 와 `BuildSuggestedPromptFix` 가 그것을 소비해
재생성 범위와 프롬프트 처방을 정한다. 키를 달자고 없던 `DetailedError` 를 40 자리에
새로 넣으면 **재생성 범위 선택 동작이 바뀐다.** 관측하려고 의미를 흔드는 셈이다.

대신 순수 관측용 통로를 하나 낸다.

### 3.2 배선

```csharp
public sealed record L1Firing(string CheckKey, string Message);

// ValidationResult
public List<L1Firing> Firings { get; } = new();

public void Report(string message, [CallerMemberName] string checkKey = "")
{
    Errors.Add(message);
    Firings.Add(new L1Firing(checkKey, message));
}
```

**`[CallerMemberName]` 이라 키를 사람이 정하지 않는다.** `CheckErrorCodeUniquenessClaim`
안에서 부르면 키가 저절로 그 이름이다 — 열거형 추가 0, 손으로 붙이는 키 0, 빠뜨릴 방법
없음. 오늘 40 자리가 키를 못 단 이유(사람이 붙여야 했다)가 구조적으로 사라진다.

공용 헬퍼(`ReportTableShapeBreaks`·`ReportIfAbsent` 등)에서 부르면 키가 그 헬퍼 이름이
된다. **의도한 것이다** — 여러 헤딩이 한 헬퍼를 공유하면 그 헬퍼가 한 검사이고, 수렴을
재는 단위도 그것이다.

### 3.3 작업

- `result.Errors.Add(` 97 자리 → `result.Report(` 기계적 치환.
- `DetailedErrors.Add` 는 **한 자리도 안 건드린다** — 재생성 범위 의미 불변.
- Roslyn 스캐너 `L1FiringKeyPolicyScanner`: `MechanicalValidator.cs` 안의 직접
  `result.Errors.Add` 호출을 위반으로 본다. 저장소의 기존 관례
  (`cancellation-policy-baseline.txt`·`orphaned-doc-comment-baseline.txt` 등 셋)와 같은
  모양의 베이스라인 파일을 둔다.
- 베이스라인은 **단방향**이다 — 줄어들기만 하고, 새 위반은 실패다.

### 3.4 판정

되돌림: `Report` 하나를 `Errors.Add` 로 되돌리면 스캐너가 빨개진다. 스캐너 자체는
`CancellationPolicyTests` 와 같은 모양으로 합성 소스에 대고 양·음 표본을 잠근다.

## 4. 절 2 — 거부된 시도를 재료로 만들고, 자기강화를 게이트로

### 4.1 (a) 파이프라인이 시도별 발화를 남긴다

`VerificationPipelineOrchestrator` 의 L1 실패 갈래(`:1048`)에서, 시도마다:

```
output/<객체>/raw/l1-attempts.json
[ { "Attempt": 2, "CheckKey": "CheckErrorCodeUniquenessClaim", "Message": "명세서가 …" } ]
```

키가 PascalCase 인 것은 `L1AttemptFiring` 레코드 속성 이름이 그대로 나가기 때문이다
(`PropertyNamingPolicy` 를 두지 않는다). 승격기와 게이트가 같은 형식을 읽으므로 바꾸지
마라 — 바꾸려면 셋을 한 커밋에서 함께 고쳐야 한다.

**발췌를 따로 만들지 않는다.** 오늘 넣은 「해당 서술 N자리: …」·「해당 행: …」이 이미
메시지 안에 실물 인용을 담고 있다 — 그것이 곧 재료다. 새 추출기가 필요 없다.

이것만으로 **3 만 줄 로그 파기가 사라진다**(부수 효과지만 오늘 세 번 든 비용이다).

### 4.2 (b) 커밋되는 코퍼스로 승격

`output/` 은 gitignore 라 그대로는 CI 도 다음 세션도 못 본다. 승격기를 둔다:

```
scripts/promote-l1-attempts.sh
  output/**/raw/l1-attempts.json
    → tests/ReSet.Core.Tests/Fixtures/rejected-attempts/<객체>/<시도>-<검사키>.md
```

**오늘 내가 손으로 다섯 번 한 그 일이다**(`ExceptionProcAttempt5UniqueDenialExcerpt.md`
외 넷). 건당 ~2KB.

### 4.3 (c) 게이트 — 판단이 필요 없는 서명 하나

> **한 객체의 연속한 두 시도에서 같은 검사키가 발화하면 자기강화 후보다.**

코퍼스 시험이 승격된 코퍼스를 전수로 읽어 그 쌍을 센다. 후보가 있으면 **빨갛다**.
해소했거나 「의도된 것」으로 판정한 자리는 원장에 **근거와 함께** 적어야 초록이 된다:

```
tests/ReSet.Core.Tests/l1-selfreinforcing-baseline.txt
  # <객체> <검사키> — 판정과 근거(커밋 해시 포함)
```

**왜 「연속」인가**: 한 번의 발화는 정상이다(모델이 틀렸고 다음에 고친다). 연속 두 번은
「고쳤는데 또 걸렸다」이고, 그것이 만족 불가능한 지시의 서명이다.

**왜 개수가 아니라 서명인가**: 발화 수·통과 수는 활동이지 효력이 아니다. 「3 자리가
2 자리로 줄었다」는 좋아 보이지만 오늘 실제로 일어난 일은 「같은 문장이 그대로 남고 하나
더 늘었다」였다.

#### 이 서명을 오늘의 실측에 대 보면 — 검사 키 셋 중 둘을 잡는다

오늘 결함은 넷이지만 **검사 키로는 셋**이다(「고유」 검사 하나가 결함 둘을 냈다).
로그에서 시도별 발화 키를 뽑으면:

| 검사 키 | 실측 발화 | 서명 |
| :--- | :--- | :--- |
| `CheckErrorCodeUniquenessClaim` | 1 판 시도 2·3·4·5·6 · 3 판 시도 1·2 | **연속 ✔** |
| 축약어(`CheckForbiddenShortcuts`) | 4 판 시도 1·2 | **연속 ✔** |
| `MachineTableShapeBroken`(붙은 행) | 3 판 시도 1 **단발** | ✘ |

**붙은 행은 이 게이트가 못 잡는다.** 그리고 그것이 옳다 — 그 검사는 만족 불가능하지
않았다. 모델이 다음 시도에서 실제로 고쳤고, 결함은 「처방이 반대 방향을 가리킨다」는
**문구 품질** 문제였다. 사람이 메시지를 읽고 찾았지 루프로 드러난 것이 아니다.

즉 이 게이트의 관할은 **만족 불가능한 지시**이지 **나쁜 문구**가 아니다. 문구 품질은
다른 자를 써야 한다(4.4 의 관할 교체가 일부를 덮는다 — 처방을 따른 텍스트를 코퍼스에서
찾아보는 절차가 「이 처방이 무엇을 낳는가」를 읽게 만든다).

### 4.4 (d) 관할 교체 — 실제 예방 장치

`reset-l1-check` 스킬의 「착수 전 코퍼스 실측」 절을 고친다:

```
- 배송본 31 편에서 발화·오탐을 잰다
+ 배송본 31 편 **과 거부된 시도 코퍼스 전량**에서 발화·오탐을 잰다.
+ 검사가 처방문(「…하십시오」)을 담는다면, 그 처방을 따른 텍스트가 코퍼스에 있는지
+ 먼저 찾아라. 없으면 그것이 「아직 안 재 봤다」는 뜻이지 「오탐이 없다」가 아니다.
```

## 5. 무엇을 증명하고 무엇을 증명하지 못하는가

**증명한다**: 이미 코퍼스에 있는 거부된 시도에 대해, 어떤 검사가 자기강화 루프를 냈는지
기계가 말한다. 그리고 새 검사가 그 재료에서 오탐을 내면 착수 전에 보인다.

**증명하지 못한다**: 둘이다.

1. 완전히 새로운 검사를 **처음** 쓰는 순간엔 그 검사에 대한 재료가 없다. 값어치는
   두 번째부터다.
2. **단발로 끝나는 결함은 게이트가 못 잡는다** — 4.3 의 표대로 오늘 검사 키 셋 중
   하나(`MachineTableShapeBroken`)가 그랬다. 그 관할은 처음부터 「만족 불가능한 지시」이지
   「나쁜 문구」가 아니다.

**그래도 값어치가 있는 근거**: 오늘 넷은 **전부 두 번째 이후**에 드러났다. 「고유」는
2026-09-06 에 배송돼 09-09 에 세 번 고쳤고, 세 번 다 앞 판의 거부된 시도가 재료였다 —
다만 그 재료를 사람이 로그에서 손으로 꺼냈다.

## 6. 하지 않기로 한 것

**B안 — 처방 준수 픽스처를 스캐너로 의무화.** 「…하십시오」를 담은 발화 자리마다
「처방을 따른 텍스트가 침묵한다」 시험을 요구하는 안. 싸고 즉시 예방적이지만
**픽스처를 우리가 상상해서 쓴다.** 축 B 에서 이미 밟은 자리다(합성 판별자가 실물보다
단순해 코퍼스 발화 0). 규칙으로는 값어치가 있으므로 **A안이 실물 재료를 낸 뒤** 그
재료로 픽스처를 고르게 하는 형태로 되살린다 — 4.4 의 관할 교체가 그 자리를 이미 연다.

**C안 — 재시도 예산을 검사별로 가른다.** 한 검사가 N 회 연속 발화하면 그 피드백을 빼고
나머지로 계속 가는 안. 미통과본 배송은 줄지만 **결함 있는 검사가 나가는 것 자체는 안
막고**(고른 목표와 어긋난다), 진짜 결함을 조용히 가릴 위험이 있다.

## 7. 순서와 규모

| 순서 | 작업 | 규모 |
| :--- | :--- | :--- |
| 1 | `L1Firing`·`Report()` 배선, 97 자리 치환 | 기계적. 4,000 시험이 회귀를 잡는다 |
| 2 | `L1FiringKeyPolicyScanner` + 베이스라인 | 기존 스캐너 셋과 같은 모양 |
| 3 | `raw/l1-attempts.json` 쓰기 | 파이프라인 한 자리 |
| 4 | 승격기 `scripts/promote-l1-attempts.sh` | ~50 줄 |
| 5 | 자기강화 게이트 + 원장 | 코퍼스 시험 하나 |
| 6 | `reset-l1-check` 스킬 관할 교체 | 문서 |

**1~2 와 3~5 는 독립이다** — 1~2 만으로도 키가 생기고, 3~5 만으로도(키 없이 메시지
접두사로) 대충 돌지만 40 자리에 눈이 먼다. 순서대로 가는 것이 맞다.

각 단계는 이 저장소의 판정 규율을 따른다: **실패 시험 먼저 · 되돌림으로 효력 판정 ·
게이트는 실패 0 · 건너뜀 0 · 경고 0.**
