# AGENTS.md 재구조화 및 문서 예산 게이트 설계

**작성일**: 2026-08-13
**상태**: 설계 확정

## 목표

AGENTS.md가 매 세션 컨텍스트에 자동 로드되는 문서라는 사실에 맞게, **에이전트의 행동
규칙만** 담게 한다. 설계 근거는 이미 그것을 갖고 있는 곳(코드 주석, architecture.md,
테스트)에 돌려주고, 다시 흘러들어오지 못하도록 게이트를 건다.

1순위는 축소가 아니라 **재발 방지**다. 축소는 그 결과물이다.

## 배경 — 108KB, 약 51,000 토큰

| 항목 | 값 |
|---|---|
| 파일 크기 | 108 KB / 320줄 |
| 토큰 (도구 계측) | 약 51,000 |
| 최장 단일 라인 | L51 `VerificationPipelineOrchestrator` = **4,162 바이트** |
| 상위 12개 라인 합계 | 22 KB (전체의 20%) |

섹션별 분량:

**항상 참이고 항상 필요한 부분(개요·보안·워크트리·빌드 커맨드·체크리스트)은 합쳐서
약 6.5KB — 전체의 6%다.** 나머지 94%는 특정 클래스를 건드릴 때만 필요한 설계 근거다.

## 배경 — 같은 사실이 세 번, 많게는 네 번 적혀 있다

§2 카탈로그 72개 항목을 `docs/architecture.md`와 대조한 실측:

| | 항목 | 분량 | 판정 |
|---|---|---|---|
| architecture.md가 이미 같거나 더 두껍게 다룸 | 53개 | **26.8 KB** | 삭제만 하면 됨 |
| architecture.md에 없음 | 19개 | 14.0 KB | 이관 후보로 분류했었음 |

그 19개를 코드 주석과 다시 대조하자 이관 후보 자체가 사라졌다. `src/`의 139개 파일 중
**84개가 이미 한국어 `<summary>`를 갖고 있고**, 무거운 항목은 전부 AGENTS.md보다 두껍다.

| 클래스 | AGENTS.md | 코드 주석 |
|---|---|---|
| VerificationPipelineOrchestrator | 4,162 | **12,852** |
| CriticFeedbackLog | 493 | 1,947 |
| BestAttempt | 1,104 | 1,949 |
| RegenerationScope | 682 | 1,847 |
| StructureRedraftPolicy | 1,330 | 1,812 |
| RetryRescue | 1,270 | 1,434 |
| StepDefect | 709 | 1,549 |

`BestAttempt.cs`의 `<summary>`는 AGENTS.md L57과 같은 논증("네 값이 흩어지면 두 가지가
깨진다")을 이미 담고 있다. **AGENTS.md L57은 세 번째 사본이다.**

결론: **§2 카탈로그 54KB는 사실상 전량 중복이며, 이관할 것이 거의 없다.** 집이 없는 것은
소형 모델 클래스 8개(`DependencyInfo`, `ColumnInfo`, `TableIndexInfo`, `AiResult`,
`IMultiProgressScope`, `NullProgressScope`, `SettlementPolicyService`, `ValidationUiProxy`,
합계 1.7KB)뿐이다.

## 배경 — 규칙만으로는 막지 못한다는 증거

`reset-doc-sync` 스킬은 이미 **"과도한 세부 묘사 방지"**와 **"문서 간 균형성 보존"**을
명시하고 있다(3단계 공통 원칙). 그런데도 108KB가 됐다.

원인은 스킬이 **"추가하라"만 있고 "어디에"가 없다**는 것이다. AGENTS.md 작성 원칙의
첫 줄이 *"새 클래스가 생기면 §2 카탈로그에 링크 추가"* — 순수 append 지시이고, 무언가를
덜어내는 대응 지시가 없다.

두 번째 원인은 스킬 §1이 *"세 문서는 합계 1,200줄이 넘는다"*고 적어 둔 채 전문 읽기를
금지한다는 것이다. 실제로는 302KB(README 57 + AGENTS 108 + architecture 137)다.
동기화 에이전트는 비대화를 **구조적으로 볼 수 없다.**

부수적으로, 스킬 4-3의 검증 커맨드 하나는 이미 죽어 있다.
`grep -n "개의 단위 테스트" AGENTS.md` → **0건**. AGENTS.md L310이 *"기대 개수를 여기
적지 않는다"*며 그 숫자를 의도적으로 제거했는데 스킬은 아직 그것을 찾고 있다.

## 설계 1 — 문서 소관

| 문서 | 담당 | 자동 로드 | 크기 예산 |
|---|---|---|---|
| **AGENTS.md** | 에이전트의 **행동 규칙**만. "무엇을 하라/하지 마라"와 어겼을 때의 증상 한 줄 | O (매 세션) | **있음 (래칫)** |
| **docs/architecture.md** | 여러 모듈에 걸친 설계·메커니즘·근거 서술 | X | 없음. 단일 파일 유지 |
| **클래스 `<summary>`/`<remarks>`** | 그 클래스 안에서 닫히는 계약 | X | — |
| **테스트 게이트** | 기계 검사 가능한 규칙 | — | — |
| **README.md** | 외부 개발자용. 이번 범위 밖 | X | — |

architecture.md를 쪼개지 않는 근거: 실측된 순증가분이 1.7KB에 불과해 137 → 139KB이고,
자동 로드되지 않으므로 토큰 비용이 없다.

## 설계 2 — 거처를 나누는 판정 기준

판정 질문은 하나다. **"이 문장을 어긴 코드가 나왔을 때, 무엇이 그것을 잡는가?"**

| 답 | 거처 | AGENTS.md에 남는 것 |
|---|---|---|
| 테스트가 잡는다 | 테스트 게이트 | 한 줄 + 테스트 파일 링크 |
| 그 파일을 여는 사람만 잡는다 | 해당 클래스 `<summary>` | 없음 |
| 여러 파일을 함께 봐야 안다 | architecture.md §4.x | 라우팅 표 한 줄 |
| **사람/에이전트의 판단만이 잡는다** | **AGENTS.md 본문** | **규칙 전문** |

마지막 칸만 AGENTS.md에 남을 자격이 있다.

적용 예:

- **L218** 캐시 워밍 순서 → `RunConsolidatedPipeline_WarmsCacheBeforeFanningOut`가 잡는다 → 1번 칸, 한 줄로 축소
- **L168** SQL 타입 판정(2,307B) → `TypeClassificationPolicyTests`가 잡는다 → 1번 칸. 스캐너의 "알려진 한계" 서술은 삭제(이미 `TypeClassificationPolicyScanner.cs` 상단 주석에 있고 본문이 그렇게 밝히고 있다). 약 85% 축소
- **L57** `BestAttempt` 엄격 부등호 → 그 클래스 안에서 닫힌다 → 2번 칸, 삭제
- **L213** "코드가 강제하는 제약은 프롬프트에도 실으십시오" → 기계가 잡을 수 없다 → **4번 칸, 한 글자도 줄이지 않는다**
- **L250** 통합 배치 5대 제약(NOLOCK/INSERT-only/Chunk Key/멱등성/예외) → 4번 칸, **원문 유지**

## 설계 3 — AGENTS.md의 새 형태

```
# 헤더 + 프로젝트 개요                     0.8 KB   유지
## 라우팅 표          ← 신규, 카탈로그 대체  ~3 KB
## 핵심 준수 규칙 (범주 1~8)               ~20 KB   47KB에서 근거 이관
## 로컬 작업 커맨드                        1.6 KB   유지
## 작업 완료 체크리스트                     2.4 KB   유지
<!-- synced-through: ... -->
```

**라우팅 표는 클래스 단위가 아니라 작업 단위로 쓴다.** 82개 클래스를 나열하면 카탈로그가
이름만 바꿔 부활한다. 10행 내외:

| 만지는 대상 | 먼저 읽을 것 |
|---|---|
| 검증 파이프라인 재시도·구제·목차 재설계 | `architecture.md §4.4` |
| 프롬프트 캐시·중단점 | `architecture.md §4.13` + 범주 2 |
| 지시서 번들·회차 코드 생성 | `architecture.md §4.11` + 범주 6 |
| 정적 분석·SQL 타입 판정 | `architecture.md §4.3` + `TypeClassificationPolicyTests` |

**예상 결과: 108KB → 25~35KB (약 51k → 13k 토큰).** 이것은 추정이다. 정확한 값은 기준을
실제로 적용해야 나오며, 래칫 기준선은 **그 실측값으로 고정한다** — 목표 숫자를 먼저 정하고
거기 맞추는 것이 아니라, 기준을 적용한 결과를 못 박는 순서다.

## 설계 4 — DocumentationBudgetTests

`tests/ReSet.Core.Tests/DocumentationBudgetTests.cs` + `documentation-budget-baseline.txt`.
레포 루트는 기존 `RepoPaths.FindRepoRoot()`를 재사용한다.

**검사 1 — 총량 상한.** AGENTS.md만 대상이다(설계 1의 소관과 일치: 자동 로드되는 문서에만
예산이 있다).

**검사 2 — 라인 길이 상한 600바이트.** 이쪽이 더 중요하다. 실제 병리는 총량이 아니라 L51의
4,162바이트짜리 "목록 항목"이었다. 총량 상한은 여러 항목에 분산시켜 우회할 수 있지만 라인
상한은 병리 그 자체를 겨냥하고, 문서가 정당하게 자라도 계속 참이다.

단위는 **UTF-8 바이트**다(문자 수가 아니다). 600바이트는 한글 약 200자에 해당한다.
현재 AGENTS.md는 320줄 중 **54줄**이 이 상한을 넘는다.

**기존 게이트와 의도적으로 다른 점: 단방향이다.**
`cancellation-policy-baseline.txt`는 *"양방향으로 잠겨 있어야 목록이 썩지 않는다"*며 정확
일치를 요구한다. 문서 크기에는 그 방식을 쓰지 않는다 — 오타 한 글자만 고쳐도 실패하는 검사가
되고, 그것은 AGENTS.md L310이 직접 경고한 함정(*"낡은 숫자는 올바른 빌드에서 항목을
실패시켜 다음 사람이 이 체크리스트를 무시하도록 길들인다"*)에 그대로 걸어 들어가는 것이다.
**상한 초과만 실패하고 밑으로는 자유다.** 위반 개수는 0이 목표지만 문서 크기는 0이 목표가
아니라는 차이에서 온다.

상한 값은 실측치 + 약 15% 여유로 잡는다. 올리려면 기준선 파일을 사람이 고쳐야 하고, 그것은
리뷰에 남는 의도적 행위가 된다. **이 게이트가 주는 것은 불가능이 아니라 가시성이다** —
숫자 한 줄 고치면 뚫린다. 기존 두 게이트도 마찬가지다.

실패 메시지는 숫자만 알리지 않고 **설계 2의 4분류 표를 그대로 출력한다.** 게이트에 걸린
사람이 "어디로 옮겨야 하는가"를 그 자리에서 알아야 한다.

## 설계 5 — reset-doc-sync 스킬 변경

1. **3단계에 라우팅 판정을 선행 단계로 삽입.** 새 정보를 쓰기 전에 *"이걸 어긴 코드를
   무엇이 잡는가"*를 먼저 답하고 거처를 정한다. AGENTS.md에 쓰는 것은 4번 칸일 때뿐이다.
2. **AGENTS.md 작성 원칙 교체.** 현행 *"새 클래스가 생기면 §2 카탈로그에 링크 추가"*를
   삭제한다(그 섹션 자체가 없어진다). 대신 *"새 클래스는 architecture.md §2.2 표에만
   추가한다. AGENTS.md는 새 **규칙**이 생겼을 때만 손댄다."*
   — **이 한 줄이 재발 방지의 핵심이다. 108KB를 만든 것이 이 지시문이다.**
3. **4-3 검증에 예산 검사 추가.** `dotnet test --filter DocumentationBudget`.
4. **죽은 검사 제거.** 테스트 개수 grep을 삭제하고 "실패 0, 건너뜀 0" 확인으로 대체한다.
5. **§1의 "합계 1,200줄" 수정.** 실제 302KB. 이 낡은 숫자가 "전문을 읽지 마라"와 결합해
   동기화 에이전트가 비대화를 볼 수 없게 만들고 있다.

## 안전장치

1. **삭제 대장.** 지우는 모든 줄에 `(원문 위치 / 사유 / 근거 위치)`를 남긴다.
   예: `AGENTS.md L57 → 중복, BestAttempt.cs <summary> L5-16`.

   근거 위치를 대지 못하는 줄은 **삭제하지 않고 셋 중 하나로 처리한다** — 설계 2의 판정을
   적용해 (a) 해당 클래스 `<summary>`에 새로 쓰거나, (b) architecture.md §4.x에 새로 쓰거나,
   (c) 4번 칸이면 AGENTS.md에 그대로 남긴다. 어디에도 해당하지 않는다고 판단될 때만
   "의도적 삭제"로 분류해 **개별 승인**을 받는다. 기본값은 삭제가 아니라 이동이다.
   대장은 커밋에 포함해 리뷰 가능하게 둔다. **"내용 손실 0"을 주장이 아니라 검증 가능한
   사실로 만드는 장치다.**
2. **링크 검증.** 스킬 4-3의 기존 커맨드를 그대로 쓴다.
3. **빌드·테스트.** 체크리스트대로 경고 **정확히 8건**(`dotnet clean && dotnet build`로
   센다), `dotnet test` 실패 0·건너뜀 0.
4. **`synced-through` 주석은 올리지 않는다.** 이번 작업은 코드 반영 범위를 넓히지 않는
   순수 재구조화이므로, 올리면 다음 동기화가 아직 미반영인 구간을 건너뛴다. 스킬 4-2의
   *"'검토했으나 변경 불필요'와 '동기화됨'은 다르다"* 원칙의 정확한 연장이다.

## 범위 밖

- `README.md` 재구조화 — 자동 로드되지 않고 외부 독자용이라 성격이 다르다.
- `docs/architecture.md` 분할 — 실측된 순증가분이 1.7KB라 필요가 없다.
- **일괄** 코드 주석 보강 — 이미 84/139 파일이 갖고 있고, 주석이 없는 8개는 소형 모델
  클래스라 architecture.md §2.2 한 줄로 충분하다. 다만 안전장치 1에 따라 갈 곳 없는 근거가
  나오면 그 클래스에 한해 `<summary>`를 새로 쓴다 — 그것은 이번 범위 안이다.
