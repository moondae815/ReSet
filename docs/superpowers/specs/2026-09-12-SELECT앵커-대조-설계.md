**작성 2026-09-12.** 기준 커밋 `64d4eddc`(main). **코드는 안 만졌다 — 이 문서는 결정 자료다.**

**출처**: `2026-09-08-U앵커-계약-표기-설계.md` §8-7 조건 5 가 「사람 결정으로 남긴다」고
적은 자리. 그 문서의 정정 문단이 「계약에 `SELECT n` 을 정하더라도 리더·검사 쪽을 함께
열지 않으면 대조는 여전히 안 선다」고 경고했고, **이 회차가 그 경고를 실측으로 검증했다 —

## 1. 결함 — 앵커 열여섯이 옳은데 아무도 안 본다

코퍼스에 `SELECT n` 앵커가 **열여섯** 있고 **전부 명세서와 일치한다.**

| 자리 | 표기 | 앵커 | 레거시 SP | 명세서 `SELECT` 행 |
| :--- | :--- | :--- | :--- | :--- |
| `POQSettleBatch1/S09` | `-- ` | `SELECT 1`~`6` | `UP_UTIL_SETTLE_PROC_ETC` | `1`~`6` |
| `POQSettleBatch1/S14` | `-- ` | `SELECT 1` | `UP_UTIL_SETTLE_SUMMARY_ETC` | `1` |
| `POQSettleBatch5/S11` | `/* ` | `SELECT 1` | `UP_Util_Settle_Summary_AcqManual` | `1` |
| `POQSettleBatch7/S07` | `/* ` | `SELECT 1` | `UP_UTIL_SETTLE_INS_EXTRA` | `1` |
| `POQSettleBatch7/S11` | `-- ` | `SELECT 1` | `UP_Util_Settle_Summary_AcqManual` | `1` |
| `POQSettleBatch7/S15` | `/* ` | `SELECT 1`~`6` | `UP_UTIL_SETTLE_PROC_ETC` | `1`~`6` |

`PROC_ETC` 를 이행한 두 단계(`B1/S09`·`B7/S15`)는 **서수까지 1:1 로 같다.** 모델은 이미 옳게 적고 있다.

> **★ 정정 (2026-09-12, Task 1 리뷰가 잡았다). 착수 전 실측이 「여덟」이라 적었는데 실제는 열여섯이다.**
> 내가 쓴 자가 `/\*\s*SELECT\s*[0-9]+\s*:` 로 **블록 주석만** 봤고, 실물의 절반은
> `-- SELECT n:` **줄 주석**이다(`B1/S09` 여섯 · `B1/S14` 하나 · `B7/S11` 하나 = 일곱을
> 통째로 놓쳤다). **명세하려는 대상보다 좁은 자로 재고 그 수를 명세에 박았다.**
> 리뷰어가 배송된 `ReadSelectAnchors` 를 실물에 돌려 16 을 얻었고, 열여섯 전부가 각 SP 의
> 명세서 서수와 일치함까지 확인했다 — **스캐너 결함이 아니라 분모 오류다. 처방의 방향은
> 안 바뀐다.** 교훈: 계약의 표기가 둘이면(`/*` 와 `--`) 자도 둘을 받아야 한다.

**그러므로 이 회차의 결함은 「모델이 틀리게 적는다」가 아니라 「틀려도 아무 시험이 안
빨개진다」다.** `AnchorKindOrdinalPairTests` 는 문장에 붙은 앵커만 보는데, 이 열여섯은
문장이 되지 않는다(§2). 조용한 공백이고, 불일치로는 **절대** 드러나지 않는다.

**오라클은 이미 있다** — 명세서 DML 범위 표의 `SELECT` 행이 **80 개 · SP 다섯**
(`INS_EXTRA`·`PROC_ETC`·`Summary_AcqManual`·`SUMMARY_ETC`·`SUMMARY_EXTRA`)이고,
`StatementCellPattern` 이 `SELECT` 를 받으므로 `SpecStatementFactsExtractor` 가 이미 낸다.

## 2. ★★ 반경을 쟀다 — 「리더를 넓힌다」는 안 된다

착수 전 프로브로 `DmlCollector` 에 `Visit(SelectStatement)` 를 더해 문장 단위 SELECT 를
문장으로 담아 봤다. 격리 워크트리, 해시로 치환 적용을 판정, 측정 뒤 원본 해시로 복원.

| 기준 | 기대 | 실측 | 판정 |
| :--- | :--- | :--- | :--- |
| ① 앵커 보유 문장 | 354 → 362 (+8) | 354 → **355 (+1)** | **실패** |
| ② 검사 A·B·C·D·E·P·미분류 | 증가 우려 | `0·11·1·0·0·2·38` **전부 불변** | 통과 |
| ③ 사라진 발화 | 0 | **0** | 통과 |

**①이 결정적이다. 프로브는 `SELECT n` 앵커에 하나도 도달하지 못했다 — 막는 것이 세 겹이다.**

| 겹 | 무엇이 막는가 | 확인 |
| ---: | :--- | :--- |
| ① | `DmlCollector` 가 `Update`·`Delete`·`Insert` 만 방문한다 | `Visit(SelectStatement)` 가 없다 |
| ② | 방문자를 더해도 `AnchorPattern` 에 **`SELECT` 대안이 없다** | `StepSqlStatementReader.cs:236` — `U`·`갱신`·`UPDATE`·`INSERT`·`DELETE` 뿐 |
| ③ | **방문자만 넓혀도** 다른 종류의 앵커 주석이 앞에 있는 SELECT 는 그 앵커를 물려받는다 | `AnchorPattern` 의 **기존** `INSERT` 대안이 산문의 `INSERT 1` 에 맞는다 — 실물 `B1/S06:114` 바로 뒤가 SELECT |

②가 있으므로 **`SELECT n` 주석이 앞에 있는 열여섯은 방문자를 더해도 `Anchor = null`**
이다 — 「앵커 보유 문장」에 안 잡힌다. 반면 ③의 자리는 앞 주석이 `INSERT 1` 이라 기존
대안에 걸려 앵커를 받는다. **그래서 354→355 로 하나만 늘었고 그 하나가 오탐이다.**
**즉 프로브가 도달한 진짜 SELECT 앵커는 0 이다.**

> **★ 정정 세 번째 (2026-09-12, T1 수정 2 재리뷰가 잡았다).** 이 표의 ③을 나는 처음
> 「`AnchorPattern` 을 넓히면」이라 적었다. **프로브는 `AnchorPattern` 을 건드리지 않았다**
> — 방문자만 넓혔고, 오탐은 기존 `INSERT` 대안이 낸 것이다. 같은 문단의 「전부
> `Anchor = null`」도 과했다(③의 자리는 앵커를 받는다). 증거(`B1/S06:114` · 354→355)는
> 그대로이고 **원인 라벨만 틀렸다.** 이 문단에서 내가 세 번 틀렸다는 사실을 남긴다.

> **★ 정정 두 번째 (2026-09-12, T1 수정 재리뷰가 잡았다).** 이 자리에 나는 먼저 「여덟 중
> 일곱이 커서 선언 안에 있다」고 적었고, 고치면서 「커서 선언과 대입문에 흩어져 있다」로
> 바꿨다. **둘 다 틀렸다.** 리뷰어가 열여섯 자리를 전부 열어 보니 `DECLARE … CURSOR FOR
> SELECT` 도 `SELECT @v = …` 대입문도 **0** 이고 전부 평범한 최상위 SELECT 다
> (`-- SQL_CURSOR_SOURCE`·「커서 소스」는 주석 안의 **라벨**이지 SQL 구문이 아니다).
> 위 세 겹이 실측으로 확인한 진짜 기제다. **결론(리더 확장은 안 된다)은 안 바뀌고 근거가
> 바뀌었다** — 내가 두 번 지어낸 설명보다 이쪽이 줄 번호로 확인된다.

**그리고 새로 잡힌 하나는 오탐이다.** `POQSettleBatch1/S06` 에는 `SELECT n` 주석이 **없다** —
있는 것은 `/* DELETE 1 */`·`/* INSERT 1 */`·`/* UPDATE 1 */`·`/* UPDATE 2 */` 뿐인데 그
파일에 SELECT 문장이 다섯 있다. **DML 용 앵커가 SELECT 문장에 붙어 `(SELECT, 1)` 로
읽혔고**, 그 SP(`INS_EXTRA4PLCARD`)의 명세서에는 SELECT 행이 0 이라 불일치가 난다.

> **그러므로 이 안은 「진짜 탐지 0 · 새 오탐 1」이다 — 안 하느니만 못하다.**
> `2026-09-08` 설계서 §7 의 「리더를 더 안 고친다」는 이 반경 때문이었고, 그 판단이 옳았다.

**②는 반대로 기쁜 결과다.** 문장 집합을 넓혀도 검사 A~E 와 P 가 **하나도 안 움직였다.**
「SELECT 를 흘리면 검사들이 일제히 발화한다」는 착수 전 걱정은 **실측으로 기각됐다.**

## 3. 처방 — 문장이 아니라 **주석**을 대조한다

`StepSqlStatementReader` 에 `ReadSelectAnchors(stepMarkdown)` 를 더해 SQL 펜스 안의
`/* SELECT n: … */` 주석에서 서수 목록을 낸다. 그 `(SELECT, n)` 이 그 단계 레거시 SP 의
명세서 DML 범위 행에 있는지 코퍼스 전수로 본다.

**열여섯에 전부 도달한다** — 주석은 위 세 겹 **어느 것과도 무관하기 때문이다.**
문장이 될 필요가 없다. 이것이 리더 확장과 갈리는 핵심이다.

**리더가 이미 쓰는 세 조각을 재사용한다** — `FencePattern` 의 펜스 열거 ·
`TSql160Parser` 의 토큰화 · `PrecededByNewline` 의 꼬리 주석 배제. **날 마크다운에
정규식을 대지 않는다.** 이 저장소는 앵커를 파일 전체에서 긁어 산문과 오류 코드 표까지
세어 틀린 적이 있다(`2026-09-08` 설계서 §8-7 말미).

**`ReadAnchor` 는 재사용하지 않는다.** 그것은 문장 사이의 토큰 창에서 찾는데 SELECT 는
창이 없다. 새 스캐너는 펜스의 **모든** 주석 토큰을 훑고 **`SELECT n` 표기만** 받는다 —
`U n`·`INSERT n` 을 안 받으므로 §2 가 만든 오탐 기제가 **구조적으로 불가능**하다.

**계약 조항 한 줄을 함께 넣는다.** `AppendStatementAnchorRules` 에 `SELECT` 는
`/* SELECT 1: … */` 형식을 더한다. 나머지 세 문장(서수는 명세서 표 그대로 · 종류가
다르면 겹쳐도 됨 · 복합 라벨 금지)은 이미 있고 그대로 적용된다.

## 7. 안 하는 것 · 알려진 한계

- **★★ 더 큰 구멍 — 이 자는 방향이 하나다.** 「앵커가 있는 것이 옳은가」만 보고 「선언이
  있는데 앵커가 아예 없는 것」은 안 본다. 불일치 표는 **실재하는 앵커**를 명세서와 맞대는
  것이라, 애초에 안 적힌 앵커는 대조할 대상 자체가 없어 조용하다. **직접 재서 확인했다
  (2026-09-12, `SelectAnchorPairCorpusTests.LogsStepsWhereTheSpecDeclaresSelectRowsButNoAnchorWasWritten`)**:
  명세서 DML 범위 표에 `SELECT` 행이 선언된 단계가 **20** 인데, 그중 앵커가 **0** 인 단계가
  **14**(그 단계들이 놓친 선언 행 합계 **24**) 이고 선언·앵커가 둘 다 있는 단계는 **6** 뿐이다.
  즉 **도달률 6/20.** 실물 한 자리: `POQSettleBatch4/S11` 은 `POQSettleBatch1/S09`·
  `POQSettleBatch7/S15` 와 **같은 SP**(`UP_UTIL_SETTLE_PROC_ETC`, 선언 서수 1~6)를 이행하는데
  SELECT 앵커가 **0** 이다 — 그 SP 를 이행한 세 단계 중 하나가 이미 조용히 빠져 있다.
  이 방향은 §9-4 의 판정 기준을 도달률로 바꾸는 이유이기도 하다.
- **★ 이 자는 「라벨이 명세서에 있는가」만 본다. 「그 라벨이 옳은 문장에 붙었는가」는 못 본다.**
  DML 앵커 검사는 후자까지 보는데 주석을 문장에 결합하기 때문이다. SELECT 는 일곱이 커서
  안이라 결합할 문장이 없다. **이것은 `2026-09-08` 설계서 §8-7 「탐지기의 한계」가 적은
  것과 같은 종류의 약함이다** — 거기서 `U2`~`U5` 넷이 쌍의 존재만으로 통과했다.
  **약한 것을 아는 채로 넣는다.** 강화하려면 커서 선언 방문이 필요하고 그건 별건이다.
- **`IF n` 은 넣지 않는다.** 코퍼스 실물 1 건(`POQSettleBatch7/S08`)인데 **DML 범위 표에
  IF 행이 0** 이다. `| IF n |` 행은 **잠금 힌트 표**에만 있고(여섯 행) 그 표는 앵커 대조의
  오라클이 아니다. 모델이 `IF 1` 을 쓴 것은 발명이 아니라 **명세서의 다른 표 이름을 따온
  것**이다. 계약에만 넣으면 **검증되지 않는 조항**이 하나 늘 뿐이다.
- **L1 검사를 안 넣는다.** 실측 결함이 0 이라 지금 넣으면 **한 번도 발화해 본 적 없는
  검사**가 는다 — 이 저장소가 `CheckErrorCodes` 로 그 위험을 산 적이 있다. 계약이 먹었는지는
  다음 Job 재생성이 판정하고, 발화 표본이 생기면 그때 붙이는 것이 순서다.
- **리더의 문장 집합을 안 넓힌다**(§2).
- **기존 산출물은 안 고쳐진다** — 고칠 것이 없다. 열여섯이 이미 옳다.

### 9-4. 남은 것

- **★ 판정 기준 정정 (2026-09-12, Important 리뷰가 잡았다).** 이 자리에 먼저 「그 Job 의
  `SELECT n` 앵커가 0 이 아니고 불일치가 0 이면 먹은 것이다」라 적었는데, **오늘 상태가 이미
  그 조건을 만족한다**(앵커 16·불일치 0) — 그래서 이 기준으로는 「계약이 먹었다」와 「아무것도
  안 변했다」를 구분하지 못한다. §7 이 잰 것처럼 이 검사는 **있는 앵커만** 보고 **없는 앵커는**
  안 보므로, 절대 개수나 불일치 0 만으로는 도달하지 못한 단계가 그대로 남아도 초록이 난다.
  **판정 기준을 도달률(앵커를 단 단계 수 / 명세서에 `SELECT` 행이 선언된 단계 수)로 바꾼다.**

  `SelectAnchorPairCorpusTests.LogsStepsWhereTheSpecDeclaresSelectRowsButNoAnchorWasWritten`
  으로 다시 재서, 분모(선언 있는 단계 수)가 늘어난 상태에서 분자(도달한 단계 수)의 비율이
  6/20 보다 뚜렷이 오르면 계약이 먹은 것이고, 비가 그대로거나 떨어지면 표기를 모델이 여전히
  안 쓰고 있다는 뜻이다.
