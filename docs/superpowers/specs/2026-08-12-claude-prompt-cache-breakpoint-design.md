# Claude 프롬프트 캐시 중단점 설계

- 작성일: 2026-08-12
- 상태: 설계 승인됨 (구현 계획 수립 전)
- 선행: [2026-08-08 단계 오류코드 검증](2026-08-08-step-error-code-verification-design.md)의 후속 작업 205번

## 배경

`ClaudeClient`의 프롬프트 캐시 중단점은 시스템 프롬프트에만 걸려 있다. 저장소 전체에서
`cache_control`은 정확히 한 번, `ClaudeClient.cs:77`에만 나온다. user 메시지는 블록 배열이
아니라 평문 문자열(`ClaudeClient.cs:104`)이라 중단점을 붙일 구조 자체가 없다.

그 사이에 들어온 캐시 관련 커밋 `5c9c8a3`은 OpenAI/gpt-5 경로 전용이었다.
`PromptCacheBreakpointTests`의 테스트 12개가 전부 `Gpt5_*` 또는 `ChatCompletions_*`이고
Claude를 다루는 테스트는 없다. Anthropic API는 암묵적 캐싱이 없어 명시적 중단점이 유일한
수단이므로, 시스템 블록 밖의 모든 것은 매 호출 전액 청구된다.

현재 설정도 영향권이다. `appsettings.json`과 `appsettings.local.json` 양쪽 모두
`Critic.Provider = Claude`이고, Claude는 L2 통합 배치 계획서 리뷰에만 쓰인다.

### 결정적 관측

2026-08-08 로그에 Claude 호출 4건의 usage가 남아 있다. `cache_creation_input_tokens`가
로그 전체에서 4번 나오고, 그 4번이 정확히 4번의 L2 리뷰다.

| 호출 | input_tokens | cache_creation | cache_read | 직전 응답과의 간격 |
|---|---|---|---|---|
| Daily5 | 326,024 | 1,818 | 0 | — |
| Daily6 R1 | 220,365 | 1,818 | 0 | — |
| Daily6 R2 | 356,460 | 1,818 | 0 | 6분 16초 |
| Daily6 R3 | 357,560 | 0 | **1,818** | 1분 04초 |

캐시되는 것은 **시스템 프롬프트 1,818토큰뿐**, 호출당 입력의 0.5%다. Daily6 3회차 합계
934,385토큰이 사실상 전액 청구됐다. R2가 미스하고 R3가 히트한 것은 Anthropic 기본 TTL
5분과 정확히 일치한다 — TTL 경계가 실측으로 확인된다.

**205번 항목의 서술은 표적을 잘못 짚었다.** 항목은 "계획서 본문을 매번 전액 지불한다"고
적었으나, 계획서 본문은 회차마다 재생성되어 바뀌므로 애초에 캐시 대상이 아니다. 실제로
낭비되는 것은 그 앞에 오는 **명세서 블록**이다. POQSettleProc3 실측으로 명세서 14개 합계
481 KB, 계획서 본문 315 KB — 캐시 가능한 쪽이 더 크다.

### 순진한 구현은 순손실이다

Anthropic 가격: 캐시 쓰기 1.25×(5분 TTL) / 2.0×(1시간 TTL), 읽기 0.1×. 관측된 회차 분포는
5개 잡 중 4개가 1회차에 종료, Daily6만 3회차다. 명세서 블록에 대한 손익은 다음과 같다.

| 방식 | 1회차 잡 (4건) | Daily6 (3회차) | 합계 |
|---|---|---|---|
| 항상 켬 · 5분 TTL | 1.25× (−0.25) | 1.25+1.25+0.1 = 2.6× (+0.4) | **−0.6× 순손실** |
| 항상 켬 · 1시간 TTL | 2.0× (−1.0) | 2.0+0.2+0.2 = 2.4× (+0.6) | **−3.4× 순손실** |
| 2회차부터 중단점 | 1.0× (0) | 1.0+1.25+0.1 = 2.35× (+0.65) | **+0.65× 순이득** |

1회차에 캐시를 쓰는 순간 그 잡의 손해가 확정되는데, 잡 5개 중 4개가 1회차에 끝난다.
1시간 TTL로 R2 미스를 구제하려 하면 1회차 잡의 손해가 4배가 되어 더 나빠진다.

### 별개의 결함: 접두사 맨 앞의 가변 값

`AiService.ReviewConsolidatedPlanAsync`는 잡 이름을 명세서 블록보다 **앞에** 넣는다.
캐시는 접두사 일치라 맨 앞 한 줄이 바뀌면 뒤 481 KB가 전부 무효가 된다. 같은 SP 집합으로
여러 잡을 연속 실행할 때 공유될 수 있었을 캐시가 이 한 줄 때문에 죽는다.

## 목표와 범위

**목표**

1. 재생성 회차(2회차 이후)의 L2 리뷰에서 명세서 블록이 캐시를 읽게 한다.
2. 1회차에 끝나는 잡에 비용을 추가하지 않는다.
3. 캐시 동작을 로그로 확인할 수 있게 한다.

**범위 밖**

- 1시간 TTL. 관측 데이터가 없는 상태에서는 1회차 잡의 손해(2.0×)가 크다. 계측을 먼저
  넣고 실제 회차 간격 분포를 본 뒤 판단할 항목이다.
- Google/Ollama/Z.ai 등 나머지 제공자. 각자 캐시 API가 달라 검증 비용이 크다.
- SP별 L2 Critic 경로. 호출마다 접두사가 달라 공유할 접두사가 없다.

## 설계

핵심 착상은 **"2회차인가?"가 "이 접두사를 전에 보낸 적 있는가?"와 같은 질문**이라는 것이다.
클라이언트가 접두사를 기억하면 회차를 인자로 전달받을 필요가 없고, 따라서 `IAiService`를
바꾸지 않아도 된다.

`ReviewConsolidatedPlanAsync`에 회차 인자를 추가하는 대안은 기각했다. NSubstitute 스텁이
인자 5개를 명시하고 있어, 선택적 6번째 인자를 붙이면 컴파일은 통과하지만 스텁이 기본값
호출에만 매칭한다. 운영 코드가 다른 값을 넘기면 매칭이 빗나가 null이 반환되고, 컴파일
오류 없이 런타임에 깨진다. 호출부 약 100곳을 손봐야 하며 대부분 이 기능과 무관하다.

### 1. `PromptCacheBreakpointPolicy`

안정 접두사를 기억하고 중단점 여부를 판정하는 클래스다.

```
bool ShouldMarkBreakpoint(string systemPrompt, string userPrompt)
```

- 접두사를 SHA-256으로 해싱해 기록한다. 본문이 아니라 해시만 들고 있는다.
- 처음 보는 해시면 `false`(중단점 없음), 이미 본 해시면 `true`를 돌려준다.
- 시계를 쓰지 않는다. 결정론적이라 단위 테스트가 가능하고, 재생성 회차 판정에 시각은
  필요하지 않다.
- 항목 수 상한을 둔다(64개). 장시간 프로세스가 SP를 계속 분석해도 무한히 자라지 않는다.
- `StepConcurrency: 4`로 동시 호출이 있으므로 동시성 안전한 자료구조를 쓴다. 같은 접두사가
  병렬로 두 번 나가면 두 번째가 중단점을 찍는데, 첫 응답이 스트리밍을 시작하기 전에는
  캐시를 읽을 수 없으므로 그것은 읽기가 아니라 또 한 번의 쓰기가 된다. 낭비지만 해롭지
  않고, L2 리뷰 경로는 직렬이다.

**프로세스 재시작으로 기억이 사라지는 것은 결함이 아니다.** 실제 캐시 TTL도 함께
만료되므로 방향이 같다.

### 2. `ClaudeClient`

`volatileUserSuffix`가 있을 때만 user 메시지를 타입 블록 배열로 보낸다.

```
[ { type: "text", text: userPrompt, cache_control: {...} },   ← 정책이 참일 때만 cache_control
  { type: "text", text: volatileUserSuffix } ]
```

접미사가 없으면 지금의 평문 문자열을 그대로 유지한다. `OpenAiClient.cs:89-91`이 같은 이유로
형식을 바꾸지 않는다 — 빈 메시지나 형식 변경 자체가 접두사를 바꿔, 접미사 없는 호출들끼리의
캐시를 깨기 때문이다.

시스템 블록의 기존 중단점은 무조건 유지한다. 이미 동작 중이고(실측 1,818 히트), user 블록이
달라진 호출에서도 최소한의 폴백 접두사 역할을 한다. 중단점은 요청당 최대 4개까지 허용되므로
둘을 함께 두는 데 제약이 없다.

### 3. `AiService.ReviewConsolidatedPlanAsync`

프롬프트를 두 조각으로 나눈다. **시그니처는 바뀌지 않는다.**

| 조각 | 내용 | 성질 |
|---|---|---|
| `userPrompt` | 명세서 전문 | 회차 간 고정 |
| `volatileUserSuffix` | 잡 이름 + 계획서 본문 + 마무리 지시 | 회차마다 변함 |

잡 이름이 명세서 뒤로 이동한다. 이것이 위에서 지적한 silent invalidator의 수정이며, 같은
SP 집합을 쓰는 서로 다른 잡이 접두사를 공유할 수 있게 된다.

### 4. 불변식: 제공자 간 동일한 프롬프트

모델이 받는 텍스트는 모든 제공자에서 같아야 한다. Claude는 블록 두 개로, 나머지는
`PromptComposition.MergeVolatileSuffix`가 `\n\n`으로 이어붙인 한 덩어리로 받지만 내용은
같다. 이것이 깨지면 제공자마다 프롬프트가 미묘하게 어긋나는데, `PromptComposition`이
존재하는 이유가 바로 그것을 막기 위해서다.

"오늘과 바이트가 같다"는 불변식이 아니다. 잡 이름 위치를 의도적으로 옮기기 때문이다.

### 5. 관측

`ClaudeClient`는 현재 응답의 `usage`를 전혀 읽지 않는다. 캐시 미스는 오류를 내지 않고 조용히
지나가므로, 읽지 않으면 이 기능의 동작 여부를 **확인할 방법이 없다.**

응답에서 `cache_creation_input_tokens`, `cache_read_input_tokens`, `input_tokens`를 파싱해
Information 수준으로 남긴다. 이것은 선택이 아니다 — 선행 명세서가 "사람이 직접 확인해야
하는 것"을 남긴 채 닫혔고 그 항목은 지금까지 미확인 상태다. 같은 자리에 또 하나를 만들지
않으려면 계측이 함께 들어가야 한다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| 정책 판정 중 예외 | `false` 반환. 중단점 없는 요청이 나가며 이는 오늘과 동일한 동작이다 |
| 해시 계산 실패 | 위와 같음 |
| usage 필드 부재 또는 파싱 실패 | 로그만 생략하고 응답 처리는 계속한다 |
| 회차 간격이 TTL(5분)을 초과 | 쓴 캐시가 읽히지 못하고 버려진다. 그 회차의 1.25×는 낭비다 |

마지막 항목은 **알려진 손실**이다. Daily6의 R1→R2가 6분 16초로 실제 이 경우였다. 모든
회차 간격이 5분을 넘는 잡이라면 1.0+1.25+1.25 = 3.5× > 3.0×로 손해가 난다. 간격을 예측해
회피하려는 시도는 과적합이므로 하지 않는다. 관측 데이터가 쌓이면 1시간 TTL을 재검토한다.

정책 실패가 파이프라인을 멈추는 경로는 없다.

## 테스트

- **정책**: 첫 호출은 false / 두 번째는 true / 다른 접두사는 서로 독립 / 상한 초과 시
  축출된다 / 동시 접근에서 깨지지 않는다
- **ClaudeClient**: 접미사 없음 → 평문 문자열 유지 / 접미사 + 첫 전송 → 타입 블록이되
  `cache_control` 없음 / 접미사 + 재전송 → 공유 블록에만 `cache_control` / 시스템 블록의
  중단점은 두 경우 모두 유지된다
- **AiService**: 리뷰 프롬프트가 명세서 경계에서 갈린다 / 잡 이름이 가변 조각에 있다 /
  합쳐진 텍스트가 제공자 간 동일하다
- **회귀**: 기존 `PromptCacheBreakpointTests` 12개가 그대로 통과한다 (gpt-5 경로 무변경)

## 완료 기준

1. 다회차 L2 잡에서 2회차 이후 `cache_read_input_tokens > 0`이 로그에 남는다
2. 1회차로 끝나는 잡에서는 `cache_creation_input_tokens`가 시스템 프롬프트분(1,818)만 남는다
3. 모델이 받는 프롬프트가 제공자 간 동일함을 테스트가 보장한다
4. 전체 테스트 통과, 빌드 경고 8개 기준선 유지

## 사람이 직접 확인해야 하는 것

실제 배치 잡을 L2가 두 번 이상 도는 조건으로 한 번 돌려, 2회차 호출의 로그에
`cache_read_input_tokens`가 명세서 블록 크기만큼 찍히는지 눈으로 확인해야 한다. 이 브랜치의
테스트는 요청이 어떤 모양으로 조립되는지까지만 보장하며, Anthropic이 실제로 캐시를
돌려주는지는 검증하지 않는다.
