# 계획서의 SQL 거처 기준 설계서

작성일 2026-08-27 · 기준 커밋 `339e430`

## 1. 무엇을 정하는가

배치 통합 계획서가 같은 로직을 **C# 인라인 SQL로 쓸지 신규 저장 프로시저로 쓸지**를 정하는
기준이 없다. `docs/known-defects.md`의 「정책 결정이 선행되어야 하는 것」에 있던 항목이며,
그 표가 경고한 대로 **기준 없이 프롬프트만 손대면 다음 회차에 반대로 쏠린다.**

### 실측 — 문서가 적은 것보다 심하다

문서는 "한 계획서가 같은 로직을 함께 지시한다"고 적었다. 코퍼스 전수를 세니 **전체가
갈려 있다.**

```
Job                SP정의   C#블록   SQL블록
POQSettleProc2       18       13       80
POQSettleProc8       14        9       82
POQSettleProc10      11        9       93
POQSettlePrco20      11        9       66
  …
POQSettleProc4        0       11       70
POQSettleProc6        0        6      137
POQSettleProc7        0        2       30
POQSettleProc9        0       11       66
```

측정 조건: `output/Jobs/*/docs/BatchMigrationPlan.md` 20건. `SP정의`는
`CREATE (OR ALTER )?PROCEDURE` 매칭 수, `C#블록`·`SQL블록`은 각 코드펜스 수.

**20개 전부가 C#과 SQL을 함께 쓴다.** 그런데 신규 저장 프로시저 정의 수가 **0에서 18까지**
흩어진다. 같은 프롬프트·같은 규칙 15개로 만든 산출물이다. 규칙에 SQL의 거처를 정하는
문장이 하나도 없으니 모델이 매번 다르게 찍는다.

### 결정

**SQL은 앱으로 가져온다. 신규 저장 프로시저를 만들지 않는다. 트랜잭션 경계와 오류 처리는
C#이 소유한다.**

## 2. 오류 코드의 거처 — 이미 있다

> **[정정]** 이 절의 초안은 "오류 코드가 집을 잃는다"였다. `ErrorCode`로 grep해 없다고
> 단정했으나 실제 컬럼명은 `LegacyReturnCode`다. **거처는 이미 계약에 있다.**

`batch.BatchStepJournal`이 이미 갖고 있다.

```csharp
new ControlColumn("LegacyReturnCode", "int", true),   // BatchControlContract.cs:147
new ControlColumn("ErrorMessage", "nvarchar(max)", true)
```

### 현재 상태

| | 횟수 |
|---|---:|
| 프롬프트(`AiService.cs`)가 `LegacyReturnCode`를 언급 | **0** |
| L1(`MechanicalValidator.cs`)이 검사 | **0** |
| 생성 계획서가 언급 (20개 중) | **14** |

계약은 `BatchControlContract.RenderPromptTable()`로 프롬프트에 실린다. 그래서 모델이
컬럼을 **스스로 발견해** 14개에서 쓴다. 여섯 개는 안 쓴다. **아무도 강제하지 않는다.**

### 결정

**`LegacyReturnCode`를 오류 코드의 정본 거처로 못박는다.**

- 레거시 출신 단계는 **원본 오류 코드를 그대로** 이 컬럼에 기록한다
- 레거시 없는 제어 단계는 **예약 음수 대역**을 이 컬럼에 기록한다
- C#이 오류를 소유해도 이 기록 의무는 안 바뀐다 — **예외를 잡아 이 값을 쓰는 것**이 단계의
  계약이 된다

이렇게 하면 언어 이전이 오류 코드 체계를 건드리지 않는다. T-SQL 반환값이 C# 예외로 바뀌어도
**기록되는 값은 같다.** 규칙 9의 "원본 코드 정확히 재사용"은 스타일이 아니라 **레거시
호출자가 의존하는 계약**이므로, 언어 밖에 거처가 있어야 한다.

## 3. 규칙 변경 범위

### 3-1. 새 규칙 하나 — 이 작업의 본체

> **[SQL 거처]** 단계 로직은 `{targetLanguage}` 코드가 소유한다. **신규 저장 프로시저를
> 만들지 않는다** — SQL은 C#이 실행하는 문장으로 쓴다. 트랜잭션 경계와 오류 처리는 C#이
> 소유한다. 이 문서에 `CREATE PROCEDURE`가 나오는 유일한 경우는 **원본 레거시 프로시저를
> 인용할 때**다.

### 3-2. 다시 쓰는 규칙 다섯

| 규칙 | 지금 | 바뀔 것 |
|---|---|---|
| 4 | `SET TRANSACTION ISOLATION LEVEL SNAPSHOT`, 그림자 메커니즘 (a)~(e) | 격리는 연결·트랜잭션에서 설정. 그림자 **순서 요구 (a)~(e)는 살아남되** C# 순서로 서술 |
| 6-1 | `TRY...CATCH` + `XACT_ABORT ON`, `@v_currentStepId`를 CATCH에서 반환 | C# `try/catch`, 단계 지역 상태 변수, **`LegacyReturnCode`에 기록** |
| 8-1 | 청크마다 `BEGIN TRAN`/`COMMIT TRAN` | 청크마다 C# 트랜잭션. **요구(각 청크가 독립 커밋)는 불변** |
| 11 | INSERT 전용은 `ROLLBACK TRAN` 또는 보상 `DELETE` | 같은 요구, C# 트랜잭션 기준 |
| **4-1** | 신규 배치 객체에 **"helper procedure"를 허용** | **그 항목만 뺀다.** `batch`·`batch_shadow` 스키마 강제는 그대로 — 스테이징·저널·그림자 **테이블**은 여전히 필요하다 |

규칙 4-1이 지금 `helper procedure`를 신규 배치 객체로 명시 허용한다. 3-1의 새 규칙과 정면
충돌하는 유일한 자리다.

### 3-3. 표적만 바꾸는 규칙 둘

- **6-2**(`ControlStepErrorCodes.PromptClause`) 예약 음수 대역 → 기록 대상이 "반환값"에서
  **`LegacyReturnCode`**로
- **9** 원본 코드 정확히 재사용 → 같은 대상으로

**2026-08-26 회차에 닫은 제어 단계 코드 작업이 그대로 산다.** 코드 체계는 안 바뀌고 어디에
적히는지만 명시된다.

### 3-4. 자연히 맞아떨어지는 것 — 규칙 13

규칙 13이 레거시 출력 파라미터(`@po_intRetVal`·`@po_strErrMsg`)를 "인터페이스에 매핑하라"고
하는데 **어디에** 매핑하는지 안 말한다. 계약의 `LegacyReturnCode` + `ErrorMessage` 두
컬럼이 정확히 그 짝이다. 이제 말할 수 있게 된다.

### 3-5. 규칙 2에 한 줄

`## 단계별 이행 상세 및 의사코드`가 "classes/components **와** pseudocode"를 함께 요구하는데
그 의사코드가 C#인지 T-SQL 프로시저 본문인지 안 말한다. **이것이 원래 모호함의 발원지다.**

### 3-6. 안 바뀌는 규칙

1·3·5·7·7-1·8·10·12·14·15 — 문서 구조, 실행 순서, 재시작(오케스트레이터 소관이라 이미
언어 중립), 비즈니스 로직 보존, NOLOCK 금지, 청크 키 검증, 서식.

## 4. L1 재조준

> **[정정]** 이 절의 초안은 "검사 48개가 T-SQL 토큰을 68번 참조하므로 대거 침묵한다"였다.
> 프레이밍이 헐거웠다. 그 48개 **대부분은 `Spec.md`(레거시 SP 명세서)를 보고, 레거시는
> 영원히 T-SQL이다.** 실제 위험은 배치 단계 경로의 12개뿐이다.

### 4-1. 실제로 위험한 것 — 12개 중 셋

`ValidateBatchStep`이 부르는 검사 12개 중 T-SQL 토큰에 실제로 기대는 것:

| 검사 | 무엇에 기대나 | 판정 |
|---|---|---|
| `CheckCatchDiscardsReturnCode` | `CATCH` 블록이 `RETURN`으로 코드를 버리는지 | **죽는다** |
| `CheckStepIdInitialValue` | `DECLARE @v_currentStepId INT = 0` | **죽는다** |
| `CheckControlStepErrorCodeBand` | `DECLARE @v_stepCode INT = …` | **죽는다** |
| `CheckShadowBackupContract` | `BEGIN TRAN` 전후 순서 | **부분** — 그림자는 남되 발행 주체가 C# |

나머지 여덟(`CheckBatchControlRowOrigin`·`CheckBatchControlVocabulary`·
`CheckFirstStepRowCreation`·`CheckForbiddenShortcuts`·`CheckMissingConditionColumns`·
`CheckNonCanonicalBatchSchema`·`CheckStepInterface`·`CheckUnknownTableReferences`)은
**테이블 이름·상태 어휘·인터페이스**를 보므로 언어가 바뀌어도 산다.

### 4-2. 재조준의 원칙 — 구문이 아니라 기록을 본다

죽는 셋이 전부 "T-SQL이 오류 코드를 어떻게 다루는가"를 본다. §2의 결정이 그 질문을
**"단계가 `LegacyReturnCode`에 무엇을 적는가"**로 옮긴다.

- `CheckCatchDiscardsReturnCode` → **예외를 잡고 코드를 기록하지 않는 단계**를 잡는다
- `CheckStepIdInitialValue` → 상태 변수 초기값 규약을 **기록 계약** 기준으로 본다
- `CheckControlStepErrorCodeBand` → 예약 대역 판정은 **그대로**, 값을 어디서 읽는지만 바뀐다

## 5. 순서와 정지 조건

**규칙과 검사를 같은 회차에 바꾸면, 그 사이 무엇이 조용히 죽는지 볼 수 없다.** 새 검사를
같이 넣으면 초록이 유지되지만, 그게 "새 검사가 일한다"인지 "둘 다 아무것도 안 잡는다"인지
구별이 안 된다.

### 5-1. 1단계 — 기대 집합을 먼저 확정한다 (코드 변경 없음)

코퍼스 20개에서 `LegacyReturnCode`에 **기록하지 않는** 계획서를 이름으로 적는다. 이 목록이
2단계의 채점표다.

**언급(mention)과 기록(record)을 구별해야 한다.**

- **언급**: 문서 어디에든 `LegacyReturnCode` 문자열이 나온다. 계약 스키마 표를 그대로
  옮겨 적기만 해도 여기 걸린다.
- **기록**: 그 단계가 `batch.BatchStepJournal`에 **값을 쓰는 문장**(`INSERT` 또는
  `UPDATE`)에서 이 컬럼을 대상으로 삼는다. 이것만이 §2의 계약을 만족한다.

현재 확보한 것은 **언급 기준** 측정이며, 그것으로 뽑은 여섯은 다음과 같다.

```
POQSettleProc1   POQSettleProc4   POQSettleProc7
POQSettleProc10  POQSettleProc11  POQSettleProc13
```

**이 여섯은 출발점이지 답이 아니다.** 언급만 하고 기록하지 않는 계획서가 나머지 14개 안에
있을 수 있다. 1단계는 그것을 가려 목록을 확정한다.

**검사를 만들기 전에 이 목록을 뽑는다.** 검사를 먼저 만들면 검사가 찾은 것을 기대라고
부르게 된다.

### 5-2. 2단계 — 검사를 기록 기준으로 재조준한다 (규칙·계획서 불변)

§4-1의 셋을 `LegacyReturnCode` 기록을 보게 바꾼다. **규칙과 계획서는 T-SQL 그대로 둔다.**

계획서가 안 바뀌었으므로, 새 검사가 발화하면 **검사가 일한 것**이지 계획서가 달라진 게
아니다. 둘을 같이 바꾸면 이 구별이 사라진다.

> **정지 조건**: 발화 집합이 1단계 목록과 **정확히 일치**해야 한다. 어긋나면 3단계로 가지
> 않는다.

**"발화 > 0"으로는 부족하다.** 재조준한 검사가 실물보다 **좁으면** 발화는 하되 일부만 잡고,
그 발화를 "살아 있다"로 읽고 넘어가게 된다. 같은 날 다른 세션이 겪은 실패다 — 진단서가
CTE 별칭의 인라인 `AS` 한 형태만 서술했는데 실물 셋 중 둘은 명시 컬럼 목록에 위치로 붙었고,
**틀린 서술이 아니라 좁은 서술이라 읽어서는 드러나지 않았다.**

### 5-3. 3단계 — 규칙을 바꾸고 재생성한다

§3의 변경을 넣고 전건 재생성한다.

> **정지 조건**: 재조준한 검사가 **계속 발화하거나**, 발화가 0이 되되 **그 이유가 "1단계
> 목록의 계획서들이 고쳐졌기 때문"임을 실물로 확인**해야 한다.

**발화가 조용히 0이 되는 것이 이 작업의 유일한 실패 모드다.**

## 6. 비용과 전제

- **전건 재생성이 필요하다.** `ConsolidatedPlanRules`는 공유 프롬프트 접두사다. 여기를
  고치면 접두사 캐시가 전부 무효화된다. 부작용이 아니라 **본질 비용**이다 — 규칙만 바꾸면
  기존 20개는 옛 규칙 산출물로 남는다.
- 캐시 버전 승격이 별도 대기 항목으로 있다. 이 작업은 **그 승격에 얹혀 가는 것**이 맞다.
- **1·2단계는 재생성 없이 끝난다.** 값비싼 3단계 전에 검사가 제대로 조준됐는지를 **공짜로**
  확인할 수 있다. 이것이 이 순서의 값이다.
- ⚠️ **재생성을 워크트리에서 돌리면 안 된다.** `src/ReSet.Cli/appsettings.json`의
  `OutputSettings.Directory`가 `./output`(cwd 상대)이고, 코퍼스 테스트를 위해 심링크를 건
  워크트리에서 실행하면 **941M 공용 코퍼스에 직접 쓴다.**

### 6-1. 셸 작업 디렉터리가 흐르는 함정

이 설계서를 쓰는 중에 사고가 났다. 코퍼스를 재려고
`cd /Users/payletter/git-root/ReSet && for f in output/Jobs/…`를 돌렸는데, **Bash 호출
사이에 작업 디렉터리가 유지되어** 그 뒤 명령이 전부 공유 체크아웃에서 돌았다. 그래서
`git checkout -b`가 거기서 돌아 **다른 세션이 작업 중이던 브랜치에서 HEAD를 뗐다.**
약 1분 뒤 복구했고 reflog 대조로 피해 없음을 양쪽이 확인했다(커밋 생성·소실 0).

같은 원인으로 그 자리에서 돌린 `git status`가 **메인 저장소의 미커밋 작업**(다른 세션 것)을
보고했고, 잠시 자기 트리의 이상으로 오해했다.

**워크트리 격리 가드는 `git -C`로 남의 워크트리를 겨누는 것은 막지만, 셸이 이미 그 자리에
서 있는 것은 막지 않는다.**

가드로는 절대경로 접두사보다 **단언을 같은 명령에 묶는 것**이 낫다 — 접두사는 빼먹으면
조용히 통과하는데, 단언은 빼먹으면 눈에 띈다.

```bash
cd <경로> && [ "$(git branch --show-current)" = "<내 브랜치>" ] && git <변경 명령>
```

`cd`와 단언과 변경이 한 줄에 있어 「어디서 도는가」가 명령 자체에 적힌다.

## 7. 이 설계서가 답하지 못하는 것

- **1단계의 기대 집합이 확정되지 않았다.** §5-1의 여섯은 언급 기준이고, 기록 기준으로 다시
  가려야 한다. 그 수가 여섯보다 많을 수 있다.
- **재조준한 검사가 무엇을 놓치는지 모른다.** 좁은 검사의 위험은 §5-2의 정지 조건으로
  줄이지만 없애지는 못한다.
- **C#이 트랜잭션을 소유할 때 그림자 메커니즘 (a)~(e)가 어떤 모양이 되는지** 구체가 없다.
  규칙 4를 다시 쓸 때 정해야 하며, 이 설계서는 "순서 요구는 살아남는다"까지만 정한다.
- **재생성 비용을 재지 않았다.** Job 20개 전건 재생성의 AI 호출 비용이 얼마인지 모른다.
