# 명세서 기반 요구사항 도출(PRD Derivation) 설계

- 작성일: 2026-09-03
- 대상: `ReSet.Cli` 새 메뉴 「명세서 기반 요구사항 도출」과 이를 지탱하는 Core 서비스
- 산출물: `output/Procedures/<스키마.이름>/docs/Prd.md`

## 1. 배경과 문제

1번 메뉴(개별 SP 역공학 분석)는 SP 하나를 분석해 설계 문서 `Spec.md`를 낸다.
`Spec.md`는 「어떻게 동작하는가」를 적는다 — 파라미터, CRUD, 로직 흐름, 흐름도.

업무 담당자가 알고 싶은 것은 그 앞이다: **이 SP가 어떤 업무 요구를 구현하고
있는가.** 지금은 그것을 읽으려면 설계 문서를 읽고 사람이 역산해야 한다.

이 설계는 그 역산을 문서로 고정한다.

### 1.1 이름 충돌 주의

저장소에 이미 `docs/prd.md`가 있다. 그것은 **ReSet 도구 자신의** 제품 요구사항
정의서다. 이 설계가 만드는 것은 **분석 대상 SP의** 요구사항 문서이며 위치가
`output/Procedures/<스키마.이름>/docs/Prd.md`로 완전히 다르다. 두 문서는 관계가
없다.

## 2. 근본 위험 — 코드에는 요구사항이 없다

코드에는 「무엇을 했는가」만 있고 「무엇을 요구했는가」는 없다. `Spec.md`만
근거로 삼으면 도출된 PRD는 필연적으로 둘 중 하나다.

- **재서술** — 설계 문서를 말만 바꿔 옮긴 것. 문서가 남아돈다.
- **추론** — 사실들을 엮어 재구성한 것. 사람이 이것을 「원래 업무 요구」로
  오독하면, 이 프로젝트가 `Spec.md`에서 그토록 막아온 환각이 **문서의 목적**으로
  둔갑한다.

따라서 이 설계의 중심은 문서의 문장력이 아니라 **모든 요구 항목이 자기 근거를
들고 다니게 만들고, 재서술과 추론을 눈에 보이게 갈라놓는 것**이다.

## 3. 확정된 전제 (사람 결정)

| 축 | 결정 |
| :--- | :--- |
| 소비자 | **사람 이해관계자 검토용.** 하류 산출물(배치 계획서·코딩 지시서)의 입력이 아니다 |
| 근거 | **완성된 `Spec.md`만.** 원본 DDL·정적 분석·DB를 다시 읽지 않는다 |
| 기동 | **별도 메뉴.** 1번 분석 실행에 이어 붙이지 않는다 |
| 검증 | **L1 귀속 검사만.** L2 Actor-Critic·L3 승인 루프에 진입하지 않는다 |
| 형태 | **Spec 섹션 파생 고정형.** PRD 섹션이 Spec 섹션의 파생으로 못박힌다 |

근거가 `Spec.md`뿐이므로 순서는 이미 정해져 있다 — PRD는 Spec 확정 이후에만
존재할 수 있다. 「별도 단계냐 동시 생성이냐」는 파이프라인의 문제가 아니라
기동 지점의 문제였고, 별도 메뉴를 택한 실질적 배당금은 **이미 쌓인 산출물에
재분석 없이 소급 적용된다**는 것이다.

## 4. 아키텍처

### 4.1 새로 두는 것

| 구성 요소 | 자리 | 책임 |
| :--- | :--- | :--- |
| `IPrdDerivationService` / `PrdDerivationService` | `ReSet.Core/Services` | Spec.md 읽기 → AI 호출 → 귀속 검사 → 저장. **DB 의존 없음** |
| `IAiService.GeneratePrdFromSpecAsync` | `ReSet.Core/Services` | PRD 생성 프롬프트 조립과 호출 |
| `PrdAttributionValidator` | `ReSet.Core/Services` | §6의 귀속 검사 |
| `OutputPathResolver.PrdFileName` 상수 | 기존 클래스에 추가 | `Prd.md` 파일명의 단일 출처 |

`PrdDerivationService`의 입력은 파일 하나다. 연결 문자열도, 정적 분석도, 스키마
카탈로그도 받지 않는다. 이 좁은 입력이 소급 적용과 재생성을 싸게 만든다.

경로는 `CodeObjectKey`가 아니라 **발견한 docs 디렉터리에서 파생**한다. 키를 만들려면
분석 루트 DB 이름이 필요한데 이 경로는 DB에 접속하지 않으므로 그것을 알 수 없고,
알아내려고 설정을 다시 읽으면 좁은 입력이라는 이점이 사라진다. 대신 파일명 상수만
`OutputPathResolver`에 두어 조립처가 갈라지지 않게 한다.

### 4.2 `MechanicalValidator`에 넣지 않는 이유

`MechanicalValidator`는 9,643줄이고 문서 종류를 `IsConsolidated`라는 **bool**로
가른다. 세 번째 종류를 받을 자리가 없다.

크기는 부차적 이유다. 결정적인 이유는 **검사 재료가 겹치지 않는다**는 것이다.
`MechanicalValidator`의 재료는 `SpecExpectations`(원본 DDL·정적 분석 유래)인데,
PRD의 오라클은 **`Spec.md` 텍스트 단 하나**다. 재료가 다른 검사를 같은 클래스에
넣으면 `IsConsolidated` 분기가 3분기로 번지고, 그 파일이 커진 경로가 정확히
그것이었다.

재사용하는 것은 `MarkdownSectionLocator`뿐이다.

### 4.3 일부러 건드리지 않는 것

- **캐시.** PRD는 캐시를 타지 않고 `CurrentCacheFormatVersion`도 올리지 않는다.
  올리는 순간 PRD와 무관한 SP 전건이 재생성 대상이 된다.
- **L2 / L3.** 검증 파이프라인에 진입하지 않는다. 4번 정책 룰북과 같은 등급이며
  `VerificationDocumentFormatter`의 **미검증 문서** 경로로 배너를 단다.
  「검증된 척」을 만들지 않는다.
- **2·3번 메뉴.** `Prd.md`는 배치 계획서에도 코딩 지시서에도 입력으로 들어가지
  않는다. 하류가 읽기 시작하면 사람용 문서에 형식 계약이 생기고, 그때는 캐시
  버전과 L1 계약을 다시 논의해야 한다. 지금은 하지 않는다.

### 4.4 기존 코드의 결

`SaveDocumentsAsync`(`Program.cs`)는 `OutputPathResolver`를 쓰지 않고 docs 경로를
직접 조립한다. 기존 호출부는 이 설계의 범위가 아니므로 건드리지 않되, **새 코드는
반드시 `OutputPathResolver`를 경유한다.** 경로 조립처를 하나 더 늘리지 않는다.

> **정정(2026-09-04).** 위 첫 문장은 더 이상 현재형이 아니다 — `SaveDocumentsAsync`는
> 분석 경로 통일로 삭제됐고 CLI에 남아 있던 손조립 경로도 함께 닫혔다
> (`2026-09-04-unify-analysis-path-design.md`). 이 설계가 그때 세운 규칙(**새 코드는
> 해석기를 경유한다**)은 그대로 유효하다.

## 5. 문서 계약

### 5.1 섹션과 파생 관계

| `Prd.md` 섹션 | 파생 원천(`Spec.md`) |
| :--- | :--- |
| `## 배경 및 목적` | `## 개요` |
| `## 수행 조건 및 입력 계약` | `## 파라미터 목록` |
| `## 데이터 요구사항` | `## CRUD 분석` |
| `## 기능 요구사항` | `## 로직 흐름 요약` |
| `## 예외 및 비기능 요구사항` | `## CRUD 분석` + `## 로직 흐름 요약` |

`## 비즈니스 흐름 시각화`(Mermaid)는 파생 원천에서 제외한다. 다이어그램은
요구가 아니라 표현이며, PRD에 Mermaid를 넣지 않으므로 Mermaid 린팅도 필요 없다.

### 5.2 요구 항목 형식

각 요구는 표 한 행이다.

```
| ID | 요구사항 | 근거 | 확신도 |
| :--- | :--- | :--- | :--- |
| REQ-DATA-03 | 정산 마감 시 미집계 건은 일별 집계 테이블에 신규 적재되어야 한다 | ## CRUD 분석 > "TB_SETTLE_DAILY에 INSERT" | 도출 |
```

- **ID** — `REQ-<섹션약어>-<두 자리>`. 섹션약어는 `BG`(배경 및 목적),
  `IN`(수행 조건 및 입력 계약), `DATA`(데이터 요구사항), `FUNC`(기능 요구사항),
  `NFR`(예외 및 비기능 요구사항).
- **근거** — `<Spec 헤딩> > "<원문 구절>"`. **줄번호를 쓰지 않는다.** 줄번호는
  Spec을 다시 생성하는 순간 전부 거짓이 되지만, 헤딩과 원문 구절은 두 문서가
  같은 이야기를 하는 한 살아 있다.
- **확신도** — `도출` 또는 `추정` **둘뿐**이다. 인용 구절이 그 요구를 직접
  지지하면 `도출`, 여러 사실을 엮어 재구성했으면 `추정`이다. §2의 위험을 막는
  유일한 장치이므로 프롬프트와 검사 양쪽에서 필수로 둔다.

## 6. 귀속 검사 (`PrdAttributionValidator`)

### 6.1 재는 것 — 참거짓이 서는 여섯 가지

1. **섹션 존재** — §5.1의 다섯 섹션이 모두 있는가.
2. **파생 대응** — 두 겹이다. (a) 표 안 ID 접두사가 자기 섹션과 일치하는가
   (`## 데이터 요구사항` 안의 `REQ-FUNC-*`는 위반). (b) **근거 칸의 헤딩이
   §5.1이 그 섹션에 허용한 원천 집합에 속하는가** (`## 기능 요구사항`의 근거가
   `## 파라미터 목록`이면 위반). (b)가 없으면 파생 고정형이 문서에만 있고 검사에는
   없게 된다.
3. **헤딩 실재** — 근거 칸의 `## …`가 원본 `Spec.md`에 실제로 있는 헤딩인가.
   `MarkdownSectionLocator`로 대조한다.
4. **인용 실재** — 따옴표 안 구절이 **그 헤딩 아래 본문에** 실제로 있는가.
   공백·마크다운 강조·표 파이프를 정규화한 뒤 부분 문자열로 대조한다.
5. **확신도 어휘** — `도출`·`추정` 외의 값과 빈 칸은 위반.
6. **근거 없는 행 0** — 근거 칸이 빈 요구는 그 자체가 결함이다. `추정` 항목도
   면제되지 않는다 — 재구성의 **출발점**이 된 인용을 달아야 한다.

기준값의 출처가 **원본 `Spec.md`**라는 점이 중요하다. 모델이 채운 것은 「주장」
쪽뿐이고 「기준」 쪽은 모델이 건드릴 수 없는 파일이다.

### 6.2 못 재는 것 — 명시적으로 남기는 구멍

인용은 진짜인데 요구 서술이 그 인용과 무관한 경우 — **귀속 오배치** — 는 이
오라클로 잴 수 없다. 모델이 Spec에서 아무 구절이나 복사해 붙이면 6.1의 여섯
가지를 전부 통과한다.

이것은 L1의 능력 밖이고 PRD에는 L2가 없으므로 **사람 검토에 남는다.** 문서 상단
배너에 다음을 박아 독자가 무엇을 믿어도 되는지 알게 한다.

> 근거 인용의 **실재**만 기계 검증되었습니다. 요구와 근거의 **대응**은
> 미검증이며, `추정` 항목은 원본에 없는 재구성입니다.

검사가 실제보다 강한 척하는 쪽이 검사가 약한 것보다 위험하다.

### 6.3 실패 처리

L2 보정 루프가 없으므로 다음과 같이 한다.

1. 검사 실패 시 결함 목록을 피드백으로 붙여 **1회만** 재호출한다.
2. 그래도 남으면 결함을 상단 배너에 박고 **저장한다.**

`Spec.md`의 「임계치 미달 문서도 배너를 달아 보존」 규칙과 같은 처리다. 결함이
있다고 문서를 버리면 사람이 볼 것이 사라지고, 무엇이 틀렸는지도 사라진다.

## 7. CLI 동선

메인 메뉴에 `5. 명세서 기반 요구사항 도출 (PRD Derivation)`을 넣고 기존
`5. 프로그램 종료`를 6으로 민다.

진입 후 흐름:

1. `output/Procedures/`를 훑어 **`docs/Spec.md`가 존재하는** 객체만 목록에 올린다.
2. 다중 선택 + 「전체」를 제공한다.
3. 기존 `Prd.md`가 있으면 덮어쓰기를 확인받는다.
4. 선택 순서대로 순차 처리하고 진행도는 기존 진행 스코프에 위임한다.

**DB 연결을 요구하지 않는다.** 이미 쌓인 산출물에 재분석 없이 그대로 돌아간다.

### 7.1 1차 범위

`Procedures/`만 대상으로 한다. `Functions/`(UDF)와 `External/`은 제외한다 —
함수 명세서에서 「업무 요구」를 뽑는 것은 의미가 얇다. 필요해지면 그때 넓힌다.

## 8. 테스트와 도입 검증

### 8.1 단위 테스트 (TDD)

`PrdAttributionValidator`를 먼저 쓴다. §6.1의 여섯 항목 각각에 대해 통과 1건과
위반 1건:

- 인용 실재 / 인용 부재
- 헤딩 실재 / 헤딩 오타
- 확신도 어휘 정상 / 위반 어휘 / 빈 칸
- 근거 있는 행 / 빈 근거 행
- ID 접두사 일치 / 불일치
- 근거 헤딩이 허용 원천 / 허용 밖 원천

### 8.2 결함 주입 회귀

실제 코퍼스 표본의 인용을 **한 글자만** 바꿔 넣고 반드시 발화하는지 확인한다.
이것이 없으면 검사가 살아 있는지 알 수 없다.

### 8.3 도입 스윕 (합격 기준 사전 선언)

만든 검사를 기존 코퍼스 전건에 돌려 **발화량을 센다.**

- **발화 0은 합격 신호가 아니다.** 검사가 죽었다는 의심 신호로 다룬다. 이 경우
  8.2의 주입 표본이 발화하는지부터 다시 확인한다.
- 발화가 나오면 최소 3건을 눈으로 열어 오탐인지 진짜 결함인지 판정하고 결과를
  기록한다.

### 8.4 게이트

프로젝트 기준 그대로 **실패 0 · 건너뜀 0 · 경고 0**이다. 통과 수 절대값은
환경 안에서도 흔들리므로 게이트로 쓰지 않는다.

## 9. 범위 밖

- `Prd.md`를 하류 산출물(배치 계획서·코딩 지시서)의 입력으로 배선하는 것
- UDF·외부 DB 객체의 PRD 도출
- 여러 SP를 묶은 통합 PRD (4번 메뉴 「통합 정산 정책 문서」가 인접 영역이며,
  둘의 관계 정리는 별도 과제다)
- 귀속 오배치를 잡는 L2 상호 대조 리뷰
