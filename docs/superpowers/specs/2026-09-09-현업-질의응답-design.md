# 현업 질의응답 — 승인된 답만 사외로 나간다

ReSet 은 개발자용 CLI 로 설계됐다. 이 문서는 이미 쌓인 산출물(`Spec.md` 코퍼스)을
근거로 **현업이 정책·프로세스를 질문하고 답을 받는 경로**를 설계한다.

기존 경로와의 관계: `architecture.md` §4.14 PRD 도출 · §4.10 정책 도출과 같은 계보다 — DB 에 다시 붙지
않고 이미 쌓인 산출물만 읽는다. 다른 점은 **산출물이 사외로 나간다**는 것이고, 설계
전체가 그 한 가지 사실에서 파생된다.

## 1. 관측

### 1-1. 코퍼스는 답할 재료를 갖고 있다

`output/` 실측(2026-09-09):

| | |
| :--- | :--- |
| `Spec.md` | **31편** · 1.4MB |
| 헤딩 절 | **610** (기계 확정 **241** / 산문 **369**) |
| 고유 테이블 · 컬럼 | 72 · **1,550** |
| 한국어 업무 설명이 붙은 컬럼 | **1,548 (99%)** — AI 추론 보완 **0건**, 전부 사람이 쓴 `MS_Description` |
| `Prd.md` · `BatchMigrationPlan.md` | 14 · 18 |

31편은 전부 정산·수수료 도메인이고, `UF_GET_COMM4CLIENT4PARTIALCANCEL`(부분취소
수수료)처럼 예상 질문에 정면으로 맞는 객체가 실재한다.

**어휘 다리의 대부분이 이미 코퍼스 안에 있다.** 초기 판단("현업 어휘와 코드 어휘 사이에
사전이 없다")은 틀렸다:

```
TSettleMst.InYMD  → PG 회수일자        TTxMst.PLTID    → POQ 거래번호(대사KEY)
TSettleMst.OutYMD → 고객사 지급일자     TTxMst.TID      → PG사 거래번호
TSettleMst.CYMD   → 취소일자           TTxMst.ClientID → 고객사 ID
```

없는 것은 사전이 아니라 **그것을 역방향으로 찾을 인덱스**다.

### 1-2. 그러나 검증이 정반대 방향으로 걸려 있다

지금 검증이 가장 두꺼운 문서는 개발자가 읽는 `Spec.md`(L1 + L2 + L3)이고,
검증이 **가장 얇은** 문서가 현업이 읽을 `Prd.md`·`SettlementPolicy.md` 다 — 둘 다
헤더에 `검증 상태: 검증 없음` 이 찍혀 나간다.

개발자는 그 배너를 읽고 의심하지만 현업은 답만 읽는다. 대상을 넓히면 **오답 한 건의
대가가 커지는데 검증은 얇아지는** 구간으로 들어간다. 이 문서의 §4(사람 승인)는 그
역전을 되돌리기 위해 존재한다.

### 1-3. 전제 (사람 확인, 2026-09-09)

| 전제 | 값 |
| :--- | :--- |
| 질문 유형 | **조회형**이 다수 ("취소 수수료는 어떻게 계산되나") |
| 코퍼스 범위 | 문의 **대부분이 위 31편 안**에 있다 |
| 답의 도달점 | **그대로 고객·가맹점에 전달된다** |

셋째가 설계를 지배한다. 여기서 못 박아야 할 것 셋이 자동으로 나온다 —
① 근거 없는 답은 내지 않는다 ② 「모른다」를 낼 수 있어야 한다 ③ 나간 답은 이력이 남는다.

## 2. 채택한 접근과 기각한 것

| | 내용 | 판정 |
| :--- | :--- | :--- |
| A | §4.10 정책 도출을 완주시켜 `SettlementPolicy.md` 를 내고 현업이 검색한다 | 답이 고정이라 사외 계약에 맞지만 **질문에 답하지 않는다** — 문서를 열어 줄 뿐 |
| B | 질문마다 코퍼스에서 근거를 찾아 답한다 | UX 는 맞지만 **매 답이 새 산출물**이라 매번 검증해야 하고, 그 검증이 인용의 실재까지만 간다 |
| **C** | **B + 사외로 나가는 답은 사람이 한 번 승인하고 축적된다** | **채택** |

A 의 **코드값 사전**은 어느 쪽을 골라도 필요하므로 C 의 선행 재료로 흡수한다(§3-2 ②층).

### 2-1. 측정을 앞에 두지 않은 것에 대한 기록

원 권고는 스파이크 선행이었다 — 현업 질문 15~20개로 **도달률**(코퍼스만으로 근거 붙은
답이 나오는 비율)을 반나절에 재고 그 숫자로 설계를 확정하는 것. **사람이 C 로 바로
진행을 결정했다(2026-09-09).**

그래서 도달률이 미지수인 채로 설계가 선다. 이 빚은 두 자리에서 갚는다:

* §5-3 「모른다」가 **미해결 용어를 어휘 사전 대기열로 자동 적재**한다 — 쓸수록 도달률이 오른다
* §8-4 E2E 가 **「모른다」 비율을 매 실행 출력**한다 — 스파이크가 쟀을 숫자가 1차 가동 시점에 나온다

측정을 생략한 것이 아니라 뒤로 미룬 것이 되게 한다.

## 3. 경계와 재료

### 3-1. 프로젝트 배치

| 프로젝트 | 역할 |
| :--- | :--- |
| `ReSet.Answers.Core` | 코퍼스 인덱스, 답변 생성, 근거 검증, 승인 저장소 |
| `ReSet.Answers.Web` | 질의 화면 + 승인 화면 (ASP.NET Core) |

`ReSet.Cli` 는 건드리지 않는다. `ReSet.Answers.Core` 는 `ReSet.Core` 를 **참조만** 하고
역방향 참조를 만들지 않는다. 재사용 대상은 넷: `EvidenceQuoteMatcher`(62줄 static,
DB·AI 의존 0) · `PolicyCorpusLoader`(74줄) · `ConstantComparisonExtractor` ·
`CodeTableProfiler`, 그리고 AI 제공자 배선 `IAiService`.

새 프로젝트로 가르는 이유는 생명주기다. CLI 는 한 번 돌고 끝나지만 웹은 상주하고,
`ReSet.Core` 는 이미 서비스 142개를 이고 있다.

### 3-2. 못 박는 경계 셋

**① `output/` 은 읽기 전용이다.** Answers 는 `output/` 에 한 글자도 쓰지 않는다. 자기
상태는 별도 최상위 `answers/` 에 쓴다. `output/` 은 `.gitignore` 대상이고 재분석으로
통째로 갈아엎히는 자리라서, 사람이 승인한 답 — 이 시스템에서 유일하게 사외로 나갈
자격이 있는 자산 — 을 거기 두면 재생성 한 번에 사라진다.

**② DB 에 붙지 않는다.** `architecture.md` §4.14 · §4.10 과 같은 판단. 예외는 코드값 사전의 우변 하나이고
그것도 `OfflineSnapshotPath` 로 대체 가능하게 둔다. 운영 DB 자격증명을 웹 프로세스가
들고 있지 않는 편이 사외 답변 계약에도 맞다.

**③ 종착 산출물이다.** Answers 의 출력은 다른 ReSet 경로의 입력이 되지 않는다. 승인된
답이 명세서 생성 재료로 돌아가면 **근거가 순환한다** — 모델이 쓴 답을 모델이 근거로
인용하게 되고, 그 시점부터 「근거는 원본 명세서뿐」이라는 계약이 조용히 깨진다.

### 3-3. 인덱스 단위는 헤딩 절이다

**610개 헤딩 절**을 단위로 쓴다. 취향이 아니라 강제다 —
`EvidenceQuoteMatcher.ExtractSectionBody(lines, heading)` 가 헤딩 절 단위로 동작하고,
PRD·정책서의 근거 형식이 이미 `<Spec 헤딩> › "<원문 구절>"` 이다.

**인덱스 단위 = 근거 단위 = 검증 단위**가 셋 다 헤딩 절로 정렬된다. 문단 청킹 같은 다른
단위를 고르면 §5 의 근거 검증을 통째로 새로 써야 한다.

절마다 **기계 확정 여부**(241 / 369)와 원본 `Spec.md` 헤더의 **검증 상태**(통과 · L1
미통과 · 리뷰 미수행 · 품질 미달)를 메타로 싣는다. 답이 사외로 나가는 이상 AST 가 만든
절과 모델이 쓴 산문을 같게 취급할 수 없다(§5-4 등급).

### 3-4. 어휘 다리는 세 층이다

| 층 | 출처 | 규모 | 소유 |
| :--- | :--- | ---: | :--- |
| ① 컬럼 용어 | `metadata.json` 의 `Dependencies[].Columns[].Description` | 1,548 | 기계 (이미 있음) |
| ② 코드값 사전 | `ConstantComparisonExtractor` + `CodeTableProfiler` (`architecture.md` §4.10 재사용) | 미측정 | 기계 |
| ③ 현업 용어 | `answers/glossary.md` | 0 (신규) | **사람** |

①은 `고객사 지급일자 → TSettleMst.OutYMD` 역인덱스로 만든다. ②는 그 §4.10 코드를 그대로
쓴다(`S02 → 정산보류`); 우변은 DB 없이 오프라인 스냅샷으로도 채우고, 매칭이 안 되면
「의미 미상」으로 남긴 채 완주한다.

**③이 승부처다.** "익일정산" · "미수" · "PG 정산" 같은 현업 말은 코드에도 컬럼 설명에도
없다. `settlement-process.md` 와 같은 패턴 — 사람이 소유하고, 파일이 없으면 초안을
자동 생성한 뒤 채우기를 기다린다. §5-3 의 「모른다」가 이 파일을 채워 나간다.

### 3-5. 검색은 2단이고 임베딩을 쓰지 않는다

① 질문을 어휘 사전으로 정규화 → 610절에 BM25 → 상위 N절
② **그 N절만** LLM 에 넣는다.

임베딩을 빼는 이유 셋: 610절이면 BM25 로 충분하고, 임베딩은 외부 호출·비용·재인덱싱을
새로 지우며, **이 프로젝트는 큰 프롬프트가 비싸다는 것이 이미 실측돼 있다**(hy4 는 12K
토큰을 넘으면 캐시 적중 0%, 확립된 처방은 캐시가 아니라 입력 축소). 임베딩이 필요해지는
건 「모른다」가 많은데 원인이 **검색 실패로 판명될 때**이고, 그때도 ③층을 채우는 게 훨씬
싸다. BM25 는 순수 .NET 으로 짓는다 — 외부 의존 0.

### 3-6. 인덱스 생애주기

`answers/index/` 에 저장하고 입력 파일의 복합 SHA-256 해시로 무효화한다
(`CacheManager` 의 기존 패턴). `output/` 이 재생성되면 인덱스를 다시 짓는다.
승인된 답의 근거가 재생성으로 증발하는 문제는 §6-4 에서 다룬다.

## 4. 답변 계약

답은 자유 산문이 아니라 **각주 달린 문단**이다.

```
취소가 발생하면 원거래 수수료를 취소 금액 비율로 안분해 재계산합니다[1].
부분취소는 전용 함수가 별도 계산식을 적용합니다[2].

[1] dbo.UP_UTIL_SETTLE_CANCEL_INS › ## 로직 흐름 요약 › "…원문 구절…"
[2] dbo.UF_GET_COMM4CLIENT4PARTIALCANCEL › ### 실행 의미 (기계 확정) › "…원문 구절…"
```

근거 형식은 PRD·정책서와 **같은 것**을 쓴다 — `EvidenceQuoteMatcher` 를 그대로 쓰기
위해서다.

PRD 와 다른 점 하나: PRD 는 `도출`(직접 지지)과 `추정`(재구성)을 둘 다 허용하지만
**여기서는 `추정`을 없앤다.** 사외로 나가는 답에 재구성이 섞이면 그 문장이 어디서
왔는지 아무도 되짚을 수 없다.

## 5. 「모른다」는 모델이 판단하지 않는다

모델에게 "모르면 모른다고 하라"고 시키는 설계는 작동하지 않는다. 모델은 모른다고
말하기를 싫어하고 그 성향은 프롬프트로 안정적으로 눌리지 않는다. **기계가 정의한다.**

### 5-1. 관문 0 — 검색이 빈손이면 LLM 을 호출하지 않는다

BM25 상위 절의 점수가 임계 미만이면 즉시 「모른다」. 비용을 아끼는 것이자, 없는 것을
지어낼 기회를 애초에 주지 않는 것이다.

### 5-2. 관문 셋 — 전부 기계

| 관문 | 검사 | 도구 |
| :--- | :--- | :--- |
| **G1 근거 실재** | 각주의 인용이 그 객체의 그 헤딩 절에 실제로 있는가 | `EvidenceQuoteMatcher.QuoteExistsIn` |
| **G2 근거 출처** | 각주가 가리키는 절이 **이번 검색이 모델에게 실제로 준 N절 안**인가 | 인덱스 대조 |
| **G3 무근거 0** | 각주 없는 주장 문장이 하나라도 있는가 | 파서 |

하나라도 걸리면 재시도 1회(PRD 와 같은 정책), 그 후에도 걸리면 **「모른다」 확정**.

G2 를 G1 과 따로 두는 이유는 재현성이다. G1 만으로는 "코퍼스 어딘가에 있는 문장"이면
통과하지만, G2 는 "이 답이 이 검색 결과로부터 나왔다"를 보증한다. 같은 질문에 같은
근거가 나오는지 되짚을 수 있어야 사외 답변의 이력이 의미를 갖는다.

### 5-3. 「모른다」는 실패가 아니라 산출물이다

빈손으로 끝나지 않고 셋을 담아 돌려준다:

* **미해결 용어** — 질문에서 뽑았는데 어휘 사전 세 층 어디에도 없던 말 → §3-4 ③층 대기열로 직행
* **근접했으나 못 미친 절** — 사람이 보면 "이건 여기 있는데"를 바로 판단할 수 있는 재료
* **어느 관문에서 걸렸는지** — 관문 0 이면 검색 문제, G1/G2 면 모델 문제, G3 면 계약 문제. 원인이 다르면 처방도 다르다

### 5-4. 답의 신뢰 등급은 근거들의 최솟값이다

| 등급 | 조건 |
| :--- | :--- |
| **A** | 모든 근거가 기계 확정 절 — AST 가 보증 |
| **B** | 산문 근거가 섞였고, 그 명세서가 `검증 통과` |
| **C** | 산문 근거가 섞였고, 그 명세서가 `L1 미통과`·`리뷰 미수행`·`품질 미달` |

사람이 매기지 않고 기계가 계산한다. C 등급 답은 §6-2 승인 화면에서 경고와 함께 뜬다.

### 5-5. 하지 않는 것

* **대화하지 않는다.** 질문 하나 = 답 하나. 멀티턴을 허용하면 승인 단위가 흐려지고, 이전 턴의 내용이 근거 없이 다음 턴에 새는 것을 막을 방법이 없다.
* **코퍼스 밖을 추론하지 않는다.** 답할 수 없으면 「모른다」가 정답이다.
* **요약하지 않는다.** 표와 수치는 원문 그대로 옮긴다 — L1 Anti-Shortcut 검증과 같은 판단.

### 5-6. 이 검사가 증명하지 않는 것

G1~G3 가 증명하는 것은 **인용이 실재하고 · 출처가 이번 검색 안이며 · 무근거 문장이
없다**는 것까지다. **근거와 답의 대응이 옳은지는 증명하지 않는다.**

PRD 도출에서 이미 겪은 한계이고 그 문서 배너가 지금도 그렇게 적고 있다. 프롬프트를 잘
써서 메울 수 있는 구멍이 아니다. **그래서 C 접근법에서 사람 승인이 선택이 아니다** —
승인 층은 편의 기능이 아니라 정확히 이 구멍 하나를 메우기 위해 존재한다.

## 6. 승인과 근거의 수명

### 6-1. 저장 구조

```
answers/
├── glossary.md          사람 소유 (§3-4 ③층)          [git 추적]
├── pending/             승인 대기 초안 + 「모른다」      [git 추적]
├── approved/            승인된 답 — 사외 전달 가능      [git 추적]
├── retired/             내려간 답 — 삭제하지 않음        [git 추적]
└── index/               BM25 인덱스                    [gitignore]
```

`index/` 만 무시한다. 나머지는 전부 추적한다 — 승인 이력이 곧 "우리가 언제 무슨 답을
밖에 냈는가"의 기록이고 그것은 재생성 가능한 물건이 아니다.

### 6-2. 승인 화면이 보여줘야 하는 것

상태는 `초안 → 검토중 → 승인 | 반려 | 모름`. 중요한 것은 상태 기계가 아니라 승인자에게
무엇을 보여주느냐다. §5-6 의 구멍이 "인용은 실재하는데 답이 그 인용이 말하는 바가
아니다"이므로, 화면이 그 구멍을 볼 수 있게 만들어야 한다. 넷을 나란히 놓는다:

1. **답**
2. **각주마다 인용된 절 전체** — 인용 구절만 보여주면 안 된다. 구절의 실재는 G1 이 이미 봤고, 사람이 볼 것은 *그 절의 맥락에서 이 답이 맞는가*다
3. **등급(A/B/C)과 근거 문서의 검증 상태**
4. **검색이 줬는데 답이 쓰지 않은 절** — 놓친 근거가 있는지 사람이 본다

4번이 빠지면 승인자는 "쓴 것이 맞는가"만 볼 수 있고 "빠뜨린 게 있는가"는 못 본다.
사외 답변에서는 후자가 더 위험하다.

### 6-3. 유사 질문을 자동 적중시키지 않는다

질문을 어휘 사전으로 정규화한 키가 **완전히 일치**하면 LLM 호출 없이 승인 답을 낸다.

유사한 질문은 **자동으로 매칭하지 않는다.** "비슷한 승인 답이 있습니다"로 보여 주고,
현업이 "이거 맞다"를 고르면 그때 그 표현이 **별칭으로 승인 답에 추가**된다. 별칭도
사람이 승인한다.

유사도 임계값으로 자동 적중시키면 미묘하게 다른 질문에 옛 답을 내보내게 되고 그 답은
그대로 사외로 나간다. 이 시스템에서 가장 비싼 실패 모드라 편의와 바꾸지 않는다.

### 6-4. 근거 증발

명세서가 재생성되면 승인된 답의 인용이 원문에서 사라질 수 있고 이것은 **조용히**
일어난다.

처방은 **승인 답이 자기 근거의 스냅샷을 들고 있는 것**이다 — 승인 시점의 인용 구절 ·
그 절의 SHA-256 · 원본 `Spec.md` 의 해시를 답 파일에 함께 저장한다. 승인 답 전량을 원문과 재대조하는 시점은 셋으로 못박는다 — **웹 프로세스 시작 시** ·
**인덱스 재빌드 직후** · **수동 트리거**. 610절 대조라 싸므로 「주기적으로」로 두지 않고
확정한다. 근거가 사라졌거나 절 해시가 바뀌면:

* 그 답을 `approved/` 에서 **자동으로 내린다**(`retired/` 로) + 재검토 큐에 올린다
* 내려간 답은 **지우지 않는다** — 이미 밖에 나간 답이므로 "언제부터 언제까지 이 답을 냈다"가 남아야 한다

두 가지를 의도적으로 고른다.

**자동으로 내리되 자동으로 갱신하지 않는다.** 근거가 바뀌었으면 답도 바뀌었을 수 있고
그 판단은 사람 몫이다. 내리는 것은 안전한 방향, 갱신은 위험한 방향이다.

**재대조는 인덱스에 기대지 않는다.** 승인 답 파일이 든 스냅샷과 `output/` 원문을 직접
비교한다. 인덱스 재빌드에 딸려 돌게 만들면 인덱스 빌드가 깨지는 고장에 이 검사가 눈이
먼다 — 탐지기가 자기가 감시할 고장의 폭발 반경 안에 있으면 안 된다.

### 6-5. 지표

| 지표 | 왜 |
| :--- | :--- |
| **「모른다」 비율** | 스파이크가 쟀을 그 숫자(§2-1) |
| 캐시 적중률 | LLM 호출 없이 답한 비율 — 자산이 쌓이는 속도 |
| 반려율 | 높으면 §5 생성이 문제, 낮은데 「모른다」가 높으면 §3 어휘가 문제 |
| 자동 내림 건수 | 근거 증발이 실제로 얼마나 일어나는가 |
| glossary 대기열 | 사람이 갚아야 할 빚 |

인덱스 빌드가 매번 찍는 숫자: `절 610(기계확정 241 / 산문 369) · 컬럼 용어 1548 ·
코드값 K · 현업 용어 L · glossary 미해결 대기 P`.

## 7. 표면과 개인정보

### 7-1. 화면 둘

**질의 화면**(현업) — 질문 입력, 답 + 각주, 등급 배지, "이 답은 YYYY-MM-DD 승인본".
승인 전 답에는 `검토 중 — 사외 전달 불가` 배너를 답 위에 단다.

**검토 화면**(담당자) — §6-2 의 넷을 나란히 놓은 승인 큐, glossary 대기열, §6-5 지표판.

역할은 둘(질의자·승인자). 사내망 배포에 기존 사내 인증을 붙이고 그 이상은 짓지 않는다.

### 7-2. 개인정보 — 마스킹은 입력 직후다

현업은 반드시 개별 건을 물어본다. *"○○가맹점 8월 정산이 왜 안 들어왔나요"* 에는
상호·사업자번호·거래번호가 붙는다. **두 자리에서 샌다:**

① **외부 LLM 으로 나간다** — 제공자가 OpenRouter·OpenAI·Claude 등 외부이고 질문
텍스트가 그대로 프롬프트에 실린다.
② **git 추적 저장소에 남는다** — `pending/` 이 커밋되면 고객 정보가 이력에 영구히 박힌다.

**마스킹은 저장 전이 아니라 입력 직후에 한다.** 숫자열(카드·사업자·거래번호 패턴)과
상호·성명 패턴을 기계로 가리고 **원문은 어디에도 저장하지 않는다.** LLM 호출도 저장도
전부 마스킹된 문장으로 한다. 순서가 중요하다 — "저장할 때 마스킹"으로 설계하면 ①이
안 막힌다.

**그리고 이 시스템은 개별 건에 답할 수 없다는 것을 화면이 먼저 말한다.** DB 에 붙지
않으므로(§3-2 ②) 개별 거래 조회는 구조적으로 불가능하고 물어도 「모른다」가 나온다.
입력 화면에 *"정책·프로세스 질문에만 답합니다. 개별 거래 조회는 원장 시스템에서
확인하세요"* 를 붙여 기대를 먼저 맞춘다.

### 7-3. 사외 전달은 시스템이 하지 않는다

승인된 답을 현업이 복사해 간다. 도구가 고객에게 직접 보내는 경로는 만들지 않는다 —
만드는 순간 발송 이력·수신자 관리·철회가 전부 딸려 오고 그것은 이 도구의 일이 아니다.

## 8. 테스트 전략

합격 기준은 이 저장소의 기존 게이트를 그대로 쓴다: **실패 0 · 건너뜀 0 · 경고 0.**

### 8-1. 관문은 「없앴을 때」로 판정한다

G1/G2/G3 각각을 **꺼 보고 무엇이 통과하는지** 재는 회귀 시험을 짝으로 둔다. "관문이
N번 발화했다"는 활동이지 효력이 아니다. 껐을 때 통과 건수가 0 이면 그 관문은 하는 일이
없다는 뜻이고, 그 사실이 시험 결과로 나와야 한다.

### 8-2. 오라클은 순환하면 안 된다

기준값은 `output/**/Spec.md` 원문이다. Answers 가 만들지 않는 파일이므로 비순환이다.

**위험한 것은 픽스처다.** 관문 시험용 절을 규격 기억으로 지어내면 오해를 검사가 확인해
주는 구조가 된다. 픽스처는 **실제 코퍼스에서 오려 와** `tests/` 아래에 커밋한다.
`output/` 은 gitignore 대상이고 재생성으로 갈아엎히므로, 테스트가 그것을 직접 읽으면
코퍼스가 없는 환경에서 조용히 건너뛴다.

### 8-3. 시험 다섯 층

| 층 | 무엇을 | 주의 |
| :--- | :--- | :--- |
| 어휘 인덱스 | `TSettleMst.OutYMD → 고객사 지급일자` 같은 **알려진 항목이 역인덱스에 있는가** | 「1548개 로드」 같은 개수 하한이 아니라 **모양 불변식**으로 — 개수는 코퍼스가 바뀌면 흔들린다 |
| 관문 회귀 | G1/G2/G3 각각을 통과·차단하는 픽스처 쌍 | §8-2 |
| 되돌림 | 관문을 끄면 몇 건이 통과하는가 | §8-1 |
| 근거 증발 | Spec 을 실제로 바꿨을 때 승인 답이 `retired/` 로 내려가는가 | §6-4 |
| 캐시 **부정** 시험 | 유사하지만 다른 질문이 **자동 적중하지 않는가** | §6-3. 긍정 시험보다 이것이 중요하다 |

### 8-4. E2E — 스파이크의 빚을 갚는 자리

실제 현업 질문 15~20개를 회귀 시험으로 고정하고 **「모른다」 비율을 매 실행 출력**한다.
스파이크에서 반나절에 알 수 있었던 숫자가 여기서는 1차 가동 시점에 나오고 이후로도
계속 나온다.

**질문 표본은 사람이 주어야 한다.** 이 재료가 없으면 §8-4 는 성립하지 않고, 도달률은
가동 후 실사용 로그가 쌓일 때까지 계속 미지수로 남는다.

## 9. 미해결

| | 내용 |
| :--- | :--- |
| 질문 표본 | 현업 질문 15~20개 — 사람이 제공 (§8-4) |
| `glossary.md` 초기값 | 현업 용어 ③층 — 초안은 기계가 쓰되 채우는 것은 사람 (§3-4) |
| 코드값 사전 규모 | ②층이 실제로 몇 개인지 미측정 — 구현 1단계에서 실측 |
| BM25 임계값 | 관문 0 의 컷오프. 실제 질문 표본 없이는 정할 수 없다 (§5-1) |

## 10. 구현 순서

한 계획서로 다 짓기에는 크다. 넷으로 가르고, **각 단계가 끝나면 그 자체로 쓸모가
있는지**를 기준으로 잘랐다.

| 단계 | 내용 | 끝나면 무엇이 되나 | 선행 |
| :--- | :--- | :--- | :--- |
| **1. 재료** | 헤딩 절 인덱스(§3-3) · 어휘 다리 ①②(§3-4) · BM25(§3-5) | CLI 에서 "이 용어가 어느 절에 있나"를 물을 수 있다. 웹 없이 도달률의 절반이 보인다 | — |
| **2. 관문** | 답변 계약(§4) · 관문 0·G1~G3(§5) · 등급(§5-4) | CLI 에서 질문 하나에 근거 붙은 답 또는 「모른다」가 나온다. **§8-4 E2E 를 여기서 처음 돌린다** | 1 |
| **3. 승인** | `answers/` 저장소(§6-1) · 승인 상태 기계 · 근거 스냅샷·자동 내림(§6-4) · 캐시(§6-3) | 승인된 답이 축적되기 시작한다. 아직 화면은 없다 | 2 |
| **4. 표면** | 질의·검토 화면(§7-1) · 마스킹(§7-2) · 권한 | 현업이 쓴다 | 3 |

**1과 2 사이에 판단 지점이 있다.** 2단계 끝의 E2E 가 내는 「모른다」 비율이 스파이크가
쟀을 숫자다(§2-1). 그 값이 나쁘면 3·4 로 가기 전에 §3-4 ③층(현업 용어)을 채우는 것이
먼저다 — 도달률이 낮은 채로 표면을 지으면 「모른다」만 내는 웹앱이 된다.

마스킹(§7-2)이 4단계에 있는 것은 3단계까지 외부 LLM 호출이 개발자 손에서만 일어나기
때문이다. **현업 입력을 받는 순간이 4단계이므로 마스킹은 4단계와 같은 커밋에 있어야
하고, 그보다 늦어서는 안 된다.**
