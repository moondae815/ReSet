# 정산 정책 문서 도출(메뉴 4) 재설계

- 작성일: 2026-09-06
- 상태: 설계 승인 대기 → 구현 계획 수립 예정
- 대상: `SettlementPolicyService`, `AiService.GenerateSettlementPolicyRulebookAsync`, `Program.cs` 메뉴 4 / `--policy` 경로

## 1. 왜 고치는가

### 1.1 지금의 흐름

메뉴 4는 DB에 붙어 SP 목록을 읽고, 사용자가 SP를 **하나씩 순차 선택**한 뒤 Job 이름을
입력하면, `SettlementPolicyService`가 SP별 DDL과 의존성을 다시 수집하고 이름에
`Code|Master|Policy|Setting|Map|Type|Group|Rate`가 들어간 의존 테이블을 `SELECT TOP 100 *`로
읽어, 그 전부를 한 프롬프트에 실어 AI를 **한 번** 부른 뒤 응답 원문을
`output/<Job>_Settlement_Policy_Rulebook.md`로 저장한다. L1도 L2도 거치지 않는다.

### 1.2 실측으로 확인한 결함 넷

**(1) 순서를 묻는데 순서를 쓰지 않는다.** 순차 선택 루프는 메뉴 2(배치 설계)에서 온 형태이고
거기서는 선택 순서가 곧 배치 실행 순서다. 메뉴 4의 서비스는 `spFullNames`를 `foreach`로
훑기만 하며 순서는 프롬프트 나열 순서 외에 아무 의미가 없다. 화면은 `분석 대상 SP #1`,
`#2`로 번호를 매겨 순서가 중요한 것처럼 보인다.

**(2) 고르려면 이미 답을 알아야 한다.** "정산 정책이 어느 SP에 있는가"는 도구가 알려줘야 할
것이지 사용자가 입력할 것이 아니다. 실제로 `output/Procedures`의 14편은 **전부 정산 SP**이고,
`output/Jobs/POQSettleBatch1`이 그 14편을 하나로 묶고 있다. 고를 것이 없다.

**(3) 검증된 자산을 버리고 원문으로 되돌아간다.** DDL의 문자열 비교 리터럴이
**`Spec.md`에 거의 전량 살아 있다** — (SP, 상수) 출현 건수 115건 중 **114건(99.1%)**.
분자는 「그 SP의 명세서 본문에 그 상수 문자열이 등장한 건수」, 분모는 「등호·`<>`·`IN`·
`LIKE`·목록 자리의 문자열 리터럴이 SP별로 출현한 건수」이며, 관할은 명세서가 있는 SP
14편 전량이다. 고유 상수 값으로 세면 82개다. 명세서만 근거로 삼아도 코드 상수를 잃지
않는데, 지금은 DB에서 DDL을 다시 긁어 대조 기준이 없는 문서를 만든다.

**(4) 이 기능의 간판이 0건을 겨누고 있다.** 프롬프트는 `'S02'`를 `정산보류`로 번역하라고
지시하는데, 이름 휴리스틱에 걸리는 의존 테이블 9개가 **전부 요율표**(`TClientCMRate`,
`TClientSettleRate`, `TPGSettleRate` 계열)다. `'impaymobile'`·`'payco'`·`'INIBANK'` 같은
코드값의 의미를 담은 공통코드 테이블은 한 개도 걸리지 않는다. 한편 의존 테이블 전체는
**37개뿐**이라 이름으로 추릴 이유가 애초에 없다.

### 1.3 확정한 방향 (사람 결정, 2026-09-06)

| 축 | 결정 |
| --- | --- |
| 문서의 수요자 | **업무 인수인계 문서** — 레거시를 모르는 실무진·신규 인력이 현행 정산 규칙을 이해하는 용도 |
| 범위 | 분석된 명세서 **전량 자동 수집** + 업무 순서는 사람이 파일로 입력 |
| 순서의 거처 | 편집 가능한 **파일 한 장 + 그룹핑**(단계 이름 → 소속 SP) |
| 근거 | **`Spec.md` 한정** + 기계 매칭된 코드값만 |
| 기능의 자리 | 메뉴 4를 유지하되 **재작성**. PRD 귀속 검사기를 공유 자산으로 끌어올린다 |

## 2. 전체 구조

```
[오프라인 · DB 불필요]                          [DB 있으면 켜지는 부분]

output/Procedures/*/docs/Spec.md ──┐
   (근거의 유일한 원천, 14편)      │
                                   ├─→ ③ 코드값 사전 ←── 의존 테이블 37개
output/Procedures/*/raw/metadata   │      (기계 매칭)      행 수가 작은 것만 읽어
   .json (상수 추출 보조·DDL 사본) ┘                        상수와 대조
                                   │
output/settlement-process.md ──────┤  ② 프로세스 명부 (사람이 고치는 파일)
   (단계 이름 + 소속 SP + 순서)    │
                                   ▼
                          ④ 단계별 서술 생성 (AI, 단계 수만큼)
                             근거: 그 단계 SP의 Spec.md 인용 + 사전에 있는 코드값
                                   ▼
                          ⑤ 기계 조립 (목차·부록) + 개요만 AI 1회
                                   ▼
                          ⑥ 귀속 검사 → 배너 → 저장
```

### 2.1 구조가 지켜야 할 다섯

1. **DB는 선택 사항이다.** ③의 우변만 DB를 쓰고, 없으면 코드값이 `의미 미상`으로 표기된 채
   문서가 완주한다. 근거(`Spec.md`)도 상수 추출용 DDL 사본(`raw/metadata.json`)도 이미
   디스크에 있다.
2. **이름 휴리스틱을 버린다.** 의존 테이블 전량에 행 수를 먼저 물어 **작은 것만** 읽는다.
   코드·마스터 테이블은 작다는 성질로 판정하므로 이름 규칙이 다른 조직에서도 선다.
3. **AI는 조립하지 않는다.** 목차·부록·단계 순서는 기계가 만든다.
4. **"단계"가 유일한 축이다.** SP 이름은 부록에만 나가고 본문은 업무 언어로 쓴다.
5. **42만 자를 한 번에 싣지 않는다.** 명세서 14편 합계는 421,121자(약 19만 토큰)로,
   단발 호출은 넣더라도 품질이 무너진다. 단계당 그 단계 SP의 명세서만 싣는다.

### 2.2 범위 밖으로 남기는 것

현재 CLI는 메뉴 진입 전에 DB에 붙어 SP 목록을 읽는다(`Program.cs:740-758`). 메뉴 5(PRD)도
같은 처지다. 이 진입 구조를 오프라인 가능하게 고치는 것은 이번 범위 밖이며, 기존과 동일하게
DB 연결 뒤 메뉴로 들어간다.

## 3. 프로세스 명부 (`output/settlement-process.md`)

### 3.1 왜 사람이 입력하는가 — 실측 근거

업무 순서는 코드 안에 없다.

- 코퍼스 전체의 `EXEC` 간선은 **2개**뿐이다
  (`UP_Util_Settle_Summary` → `UP_Util_Settle_Summary_AcqManual`,
  `UP_Util_Settle_Summary` → `UP_UTIL_SETTLE_SUMMARY_EXTRA`).
  나머지 11개 SP는 호출 그래프에 전혀 걸리지 않는다.
- `StaticAnalysis`의 쓰기/읽기로 만든 의존 그래프는 간선 **99개**로 거의 완전 그래프가 된다.
  사유가 전부 허브 테이블 `TSettleMst`(7개 SP가 쓴다) 하나다.
- 허브 둘(`tsettlemst`, `tsettlebyout`)을 제외하면 간선이 **5개**만 남고 전부 출발점이
  `UP_Util_PG_Client_CMRate_Ins`다(요율 스냅샷을 적재하고 나머지가 읽는다).

따라서 기계가 확정할 수 있는 것은 다음뿐이다.

| 아는 것 | 근거 |
| --- | --- |
| `CMRate_Ins`가 맨 앞이다 | 5개 SP가 그 산출(요율표)을 읽는다 |
| `Settle_Summary` → `AcqManual`, `SUMMARY_EXTRA` | `EXEC` 간선 |
| 나머지 11개의 상호 순서는 **모른다** | 허브 테이블에 묻혀 판별 불가 |

초안은 이 이상을 지어내지 않는다. **아는 것과 모르는 것을 갈라 적는 것**이 초안의 일이다.

### 3.2 생애주기

도구는 파일이 **없을 때만** 초안을 쓴다. 있으면 읽기만 하고 **절대 덮어쓰지 않는다.**
사람의 편집이 도구에 의해 사라질 경로를 두지 않는다. 다시 받고 싶으면 파일을 지운다.

### 3.3 형식

H2가 단계(업무 이름), 그 아래 목록이 소속 SP, 순서는 문서에 나타난 순서다.
**H2 제목이 그대로 정책서의 목차가 된다.**

```markdown
# 정산 프로세스 명부
<!-- 도구는 이 파일이 없을 때만 초안을 만들고, 있으면 읽기만 합니다. -->
<!-- 단계 순서 = 등장 순서. H2 제목이 정책서의 목차가 됩니다. -->

## 1. 수수료율 스냅샷 적재
```

### 3.4 명부 대조 검사 (중단 조건)

발견된 명세서는 명부에 **정확히 한 번씩** 나타나야 한다. 어기면 문서 생성을 **중단한다.**
세 가지를 발화한다: 누락된 SP, 중복된 SP, 명부에만 있고 명세서가 없는 이름(오타).

배너로 넘기지 않고 중단하는 이유는, 누락된 SP의 규칙이 문서에서 **아무 흔적 없이 사라지고**
읽는 사람이 그 사실을 알 방법이 없기 때문이다. `## 제외` 섹션이 의도한 제외를 명시적으로
허용하므로, 조용한 누락은 구조적으로 불가능해진다.

초안의 자리표시자(`단계 이름을 붙여 주세요 ①`)가 남아 있어도 중단한다. 무인 배치가 도구
초안대로의 순서로 인수인계 문서를 배송하는 것이 이 설계에서 가장 나쁜 결말이다.

## 4. 코드값 사전 (`output/Policy/settlement-codebook.json`)

좌변(코드 상수)과 우변(업무 의미)을 잇되, **연결을 AI가 아니라 기계가 한다.**

1. **좌변 확정 (오프라인).** `raw/metadata.json`의 `DdlText`에서 **비교식의 (컬럼, 리터럴)
   쌍**을 뽑고, **그중 `Spec.md`에 등장하는 값만 채택**한다. 추출은 DDL로 정확하게 하고
   채택은 명세서가 결정하므로 "근거는 `Spec.md`뿐"이라는 계약이 지켜진다. 채택률은
   (SP, 상수) 출현 기준 114/115. 떨어진 것은 버리지 않고 `명세서 미수록 상수`로 사전에
   기록한다 — 그 자체가 명세서 품질 신호다.

   **추출기는 반드시 파서(ScriptDom) 기반이어야 한다.** 정규식으로 재 봤더니 고유 상수
   82개 중 **18개가 동적 SQL 문자열 조각**이었고(`' +  @v_strClientID+ '`, `'+'`, `','`),
   `NOT`을 컬럼명으로 잡기도 했다. 이 코퍼스는 동적 SQL 조립이 많아 정규식으로는 좌변이
   오염된다. `StaticAnalysis`가 이미 ScriptDom으로 테이블·컬럼을 뽑고 있으므로, 비교식의
   (컬럼, 리터럴) 쌍을 그 재료에 **새 필드로 추가**한다.
2. **우변 후보 수집 (DB 있을 때만).** 의존 테이블 전량에 `COUNT(*)`를 던지고 **임계
   (초기값 500행) 이하만** 읽는다. 부수 효과로 거래 테이블이 크기에서 걸러져, 지금처럼
   실거래 100행을 무조건 긁어 프롬프트에 싣는 일이 사라진다.
3. **기계 매칭 — 2단이다.** 읽은 행의 문자열 셀을 좌변과 **정확 일치**(대소문자 무시)로
   대조하고, 맞으면 그 **행 전체**를 후보 의미로 채택한다. "설명 컬럼이 어느 것인지"는
   추정하지 않는다. 한 상수가 여러 테이블에서 나오면 전부 싣고 출처 테이블을 명기해
   AI가 문맥으로 고르게 한다.

   - **1단 (컬럼까지 아는 경우)** — (컬럼, 값) 쌍으로 대조한다. 같은 이름의 컬럼을 가진
     테이블에서 그 값을 찾는다. 정밀하다.
   - **2단 (값만 아는 경우)** — 값만으로 대조하되 **길이 3 이상**만 한다.

   2단에 길이 조건이 필요한 이유는 `'Y'`·`'N'`·`'1'` 같은 값이 아무 테이블에서나 걸려
   매칭이 잡음이 되기 때문이다. 실측으로 실질 상수 64개 중 **13개가 길이 2 이하**다.
   이들은 매칭을 시도하지 않고 `의미 미상 (값이 짧아 판별 불가)`로 표기한다 — 플래그성
   `'Y'/'N'`의 의미는 코드 테이블이 아니라 컬럼 이름과 명세서 서술에 있고, 그건 AI가
   `Spec.md` 인용으로 이미 다룬다.

   컬럼까지 잡히는 비율은 실측으로 값 29개 / 82개다. 즉 **2단이 다수 경로**이므로 길이
   조건이 실질적인 잡음 차단선이 된다.
4. **사전이 문서를 구속한다.** 정책서에는 사전에 있는 번역만 실린다. 미매칭 상수는
   `의미 미상 (마스터 데이터에서 찾지 못함)`으로 명시적으로 나간다 — 인수인계 문서로서는
   "이 값의 의미를 아는 사람을 찾아야 한다"는 목록이 되어 오히려 유용하다.

**DB가 없으면** 2·3을 건너뛰고 전량 미매칭으로 완주하며, 배너에 `코드값 번역 0건 (DB 미연결)`을 단다.

이 사전이 §5의 코드값 대조 검사의 **비순환 오라클**이 된다. 검사가 보는 파일(정책서)과
기준이 되는 파일(사전)이 다르다.

## 5. 문서 계약과 귀속 검사

### 5.1 문서 구조

현행 5개 H2는 폐기한다. `4. 프로그램별 정산 영향도 매핑`은 SP 축이라 인수인계 독자에게
읽히지 않고, `5. 예외 처리`를 뒤에 몰아 두면 각 단계의 예외가 그 단계에서 떨어져 나간다.

```
## 정산 업무 개요                    ← AI 1회 (전체 조망)
## 1. <명부의 H2 이름 그대로>        ← AI, 단계마다 1회
   …
## N. <명부의 H2 이름 그대로>
## 부록 A. 코드값 사전               ← 기계 생성
## 부록 B. 단계별 원본 프로시저      ← 기계 생성 (SP 이름은 여기에만)
```

목차를 AI가 정하지 않는다. 사람이 명부에 붙인 단계 이름이 그대로 목차다.

### 5.2 단계 본문의 계약

2~4문장 산문 개요(업무적으로 무엇을 하는 단계인가) 다음에 규칙 표 하나를 둔다.

```
| ID | 업무 규칙 | 근거 | 코드값 |
```

- `ID` — `S<단계번호>-<두자리>`, 단계 안에서 01부터
- `업무 규칙` — 업무 언어 한 문장. SQL·조인·제어흐름 서술 금지
- `근거` — `dbo.UP_… · ## <명세서 헤딩> > "축자 인용"`. PRD와 달리 원본이 여럿이라 SP
  식별자가 앞에 붙는다. 인용 속 `|`는 `\|`로 이스케이프한다
- `코드값` — 사전에 있는 상수만. 없으면 `-`

`PolicySectionContract`가 이 규칙 전부(헤딩·ID 접두사·표 헤더·근거 셀 형식·이스케이프)를
단독 소유하고, 프롬프트는 계약에서 문구를 읽어 간다. `PrdSectionContract`가 이미 같은 자리를
지키고 있다.

### 5.3 귀속 검사기의 공유

`PrdAttributionValidator.Validate(prd, spec)`의 본체는 "인용문이 그 헤딩 섹션 안에 축자로
있는가"이고, 정책서에 필요한 차이는 **원본이 여럿**이라는 것뿐이다. 공통 검사기를 추출하고
PRD는 원본 1개짜리 호출부로 남긴다. PRD 쪽 회귀는 기존 PRD 테스트가 지킨다.

### 5.4 정책서 고유 검사 셋

| 검사 | 무엇을 막는가 |
| --- | --- |
| 코드값 대조 | 문서의 코드값이 `settlement-codebook.json`에 없으면 AI가 지어낸 번역이다 |
| 단계 완전성 | 명부의 단계가 전부, 같은 순서로 H2에 있는가 |
| SP 인용 커버리지 | 명부에 넣은 SP가 한 번도 근거로 인용되지 않았는가 |

셋째가 조용한 누락의 두 번째 문이다. §3.4의 명부 대조는 "명부에 SP가 있는가"를 보지만,
명부에 있어도 AI가 그 명세서를 읽지 않고 지나가면 규칙이 통째로 빠지고 문서는 멀쩡해 보인다.

### 5.5 교정 재호출

단계 단위로 1회. 결함이 늘면 첫 초안을 지키는 PRD 규칙
(`retryValidation.Defects.Count <= validation.Defects.Count`)을 그대로 쓴다.

가리킬 대상이 없다.

### 6.1 헤더에 근거의 상태를 집계한다

`FormatUnverifiedDocument`는 `sourceOutcome`을 하나만 받는데 정책서의 근거는 14편이다.
집계 오버로드를 더한다.

```yaml

근거 명세서 검증 상태: 통과 11 · 품질 미달 2 · L1 미통과 1

```

정책서가 품질 미달 명세서 위에 서 있을 수 있다는 사실이 문서 첫 줄에 보여야 한다.

## 7. 테스트 전략

이 저장소의 규약(`verify-by-removal`)대로 **여섯 조건을 착수 전에 파일에 적고 커밋한 뒤**
검사를 만든다. 새 검사는 넷이다.

### 7.1 앞 층 — 재료가 있는가

| 검사 | ① 행 수 | ② 도달 가능성 | ③ 그 자를 쓰는가 |
| --- | --- | --- | --- |
| 명부 대조 | 명세서 14편 | 파일 파싱만, DB 무관 | 명부 파서와 대상 탐색기가 같은 식별자 표기를 쓰는가 |
| 코드값 대조 | 고유 상수 82개(실질 64, 매칭 대상 51) | 문서의 `코드값` 열을 읽는가 | 사전 키와 문서 셀의 정규화 규칙이 같은가 |
| 단계 완전성 | 단계 수(명부가 정함) | H2 파싱 | 명부 H2와 문서 H2의 비교 규칙 |
| SP 인용 커버리지 | 명세서 14편 | 근거 셀의 SP 식별자를 읽는가 | 근거 셀 파서가 `PolicySectionContract` 형식을 쓰는가 |

③이 특히 위험하다. "자를 안 쓰는 대상에 자의 눈금을 씌운 것"이 이 저장소에서 3.8%/60.3%
오독을 낳은 자리다.

### 7.2 뒤 층 — 효력이 있는가 (역변이)

| 검사 | 무엇을 되돌리면 실패해야 하는가 |
| --- | --- |
| 명부 대조 | 명부에서 SP 한 줄을 지운다 → 중단되어야 한다 |
| 코드값 대조 | 문서에 사전에 없는 매핑 한 줄을 심는다 → 발화해야 한다 |
| 단계 완전성 | 단계 H2 하나를 지운다 / 두 단계 순서를 바꾼다 → 발화해야 한다 |
| SP 인용 커버리지 | 한 SP의 근거 인용을 전부 지운다 → 발화해야 한다 |

각 역변이는 빨간불을 본 뒤 되돌려 초록을 확인하고 **되돌린 상태로 커밋**한다. 이것이 낡은
어셈블리를 물지 않았다는 증거를 겸한다.

### 7.3 픽스처와 게이트

- 픽스처는 **실물 코퍼스에서 뜬다.** 합성 픽스처가 실물보다 단순해 코퍼스 발화가 0이었던
  전례가 있다. 양성 예와 음성 예를 둘 다 갖춘 상태로 만든다.
- 게이트는 **실패 0 · 건너뜀 0 · 빌드 경고 0**이다. 통과 수는 게이트로 쓰지 않는다.
- 워크트리를 만들 때 **코퍼스 심링크 재료 넷을 처음부터 다 건다.** 안 걸어서 건너뜀이 난
  일이 세 세션에서 3/3이다.

### 7.4 이 설계가 사 주는 것

기본 경로가 DB 없이 완주하므로 **네 검사와 파이프라인 전체가 DB 없이 돈다.** 현재
`SettlementPolicyService`는 `IDbMetadataService`가 필수라 사실상 테스트가 없다.

## 8. 미해결 둘

1. **한 단계에 SP가 몰릴 때.** 초안 상태에서는 11개가 한 단계에 있어 컨텍스트가 크다.
   사람이 나누면 해결되지만, 단계 하나의 명세서 합계가 임계를 넘을 때 **경고만** 하고 분할은
   사람에게 맡긴다. 자동 분할은 목차를 도구가 바꾸는 일이라 §3의 원칙과 충돌한다.
   임계값은 구현 시 정한다.
2. **코드값 사전의 행 임계(초기값 500행)** 는 임의 값이다. 실제 DB에 붙는 회차에 재서 정한다.
3. **2단 매칭의 길이 조건(3자 이상)** 도 이 코퍼스 한 벌에서 나온 값이다. 다른 코퍼스에서
   `'DX'` 같은 두 글자 코드가 실재하면 조건을 컬럼 쌍 우선으로 더 밀어야 한다.
