# 단계 오류코드 검증의 신뢰성 회복 설계

- 작성일: 2026-08-08
- 상태: 설계 승인됨 (구현 계획 수립 전)
- 선행: [2026-08-06 단계별 분할 생성](2026-08-06-batch-plan-step-split-design.md), [2026-08-07 지시서 번들 분할](2026-08-07-migration-instructions-split-design.md)

## 배경

`MechanicalValidator.ValidateBatchStep`의 하한 검사는 목차(`PlanStructure.md`)가 선언한 `TargetTables`와 `ErrorCodes`를 단계 본문에서 찾는다. 두 검사 모두 선언 배열을 `foreach`로 돈다. 배열이 비면 0회 반복하고 통과한다.

실측 두 회차에서 그 배열은 거의 항상 비어 있었다.

| Job | 단계 수 | 목차가 선언한 오류코드 | 명세서에서 추출 가능한 오류코드 |
|---|---|---|---|
| POQSettleProcDaily5 | 12 | 0개 | 91개 |
| POQSettleProcDaily6 | 14 | 1개 (S01) | 82개 |

`POQSettleProcDaily5`는 12/12 단계의 오류코드 검증이 무실행인 채 로그에 `에러 개수: 0개`로 기록됐다. `POQSettleProcDaily6`은 13/14가 무실행이었고, 유일하게 검사가 돈 `S01`도 목차가 1개만 선언해 본문의 10개 중 1개만 대조했다.

**모델이 코드를 못 쓰는 것이 아니다.** `S06`의 목차 `ErrorCodes`는 빈 배열이지만 그 단계 본문에는 `-1`부터 `-23`까지 16개가 적혀 있다. 모델은 산문에는 빠짐없이 쓰고 기계 판독 배열만 비운다. 프롬프트는 이미 정확한 반환 코드 재현을 요구하고 있다(`AiService.cs:1964`).

`fcf534f`는 이 상태를 **보이게** 만들었다 — 빈 배열을 결함으로 들고, 재생성으로 고칠 수 없는 실패는 재시도 없이 기록한다. 실측에서 14건이 로그와 배너로 드러났고 재생성 호출 13회를 아꼈다. 그러나 값을 채우지는 못했고, 기존 위반 채널을 재사용한 탓에 14개 중 13개에 "품질 미달" 배너가 붙어 진입점 §0의 "모두 통과"와 정면으로 모순됐다.

### 결정적 관측

명세서에서 오류코드를 결정론적으로 뽑을 수 있다. 반환 변수는 14개 명세서 전체에서 `@po_intRetVal` 하나뿐이고(247회), 「로직 흐름 요약」에 `오류 시 @po_intRetVal = -1을 설정하고 롤백합니다` 형태로 일관되게 나타난다. 목차의 `LegacyProcedures`는 두 회차 모두 정확히 채워져 있어 단계→프로시저 대응이 이미 존재한다.

추출한 코드로 두 회차의 단계 본문을 실제로 대조한 결과 **24개 단계 전부, 코드 173개가 이미 본문에 등장한다. 미달 0건.** 검사를 진짜로 돌려도 재시도 폭주나 배너 홍수는 발생하지 않는다.

## 목표와 범위

**목표**

1. 목차의 `ErrorCodes`를 명세서에서 추출한 값으로 채워, 하한 검사가 실제로 대조하게 만든다.
2. 채운 값을 `PlanStructure.md`에 기록해, 나중에 파일만 보고도 무엇을 검사했는지 확인할 수 있게 한다.
3. "품질 미달"과 "검증 불가"와 "해당 없음"을 출력에서 구별한다.

**범위 밖**

- `TargetTables` 보강. 명세서의 「갱신 대상 테이블」 절에서 같은 방식으로 뽑을 수 있으나, 그것은 회차별 스키마 스코프 주제에 속한다.
- Claude 클라이언트의 프롬프트 캐시 중단점.
- 목차 재수립을 유발하는 새 정책. 보강은 재수립 예산을 쓰지 않는다.

## 설계

### 1. `SpecReturnCodeExtractor`

명세서 컬렉션에서 `프로시저명 → 오류코드 목록`을 만드는 순수 함수다.

```
IReadOnlyDictionary<string, IReadOnlyList<string>> Extract(
    IEnumerable<(string FileName, string Content)> specs)
```

- 패턴은 `@po_intRetVal\s*=\s*(-?\d+)`. 변수명을 고정하는 이유는 좁히기 위해서가 아니라 노이즈를 배제하기 위해서다. 명세서 본문에는 `취소거래의 금액을 -1배 처리합니다`처럼 오류코드가 아닌 음수가 흔하고, 날짜(`2026-08-05`)에서도 `-05`가 나온다. 일반 음수 패턴으로 훑으면 그 전부를 코드로 오인한다.
- 키는 파일명의 마지막 점 뒤를 소문자화한 것(`dbo.UP_UTIL_SETTLE_INS` → `up_util_settle_ins`).
- 등장 순서를 유지하며 중복을 제거한다. 정렬하지 않는다 — 명세서의 서술 순서가 곧 단계 진행 순서라 사람이 읽기에 낫고, 결정론에는 등장 순서로 충분하다.
- 매치가 하나도 없는 명세서는 키를 만들지 않는다. 빈 목록과 "그런 프로시저 없음"을 구별한다.

**파일 I/O가 없다.** 명세서 본문은 오케스트레이터가 이미 `specs`로 들고 다니며 골격·단계 생성에 넘기고 있다. 같은 컬렉션을 재사용한다.

### 2. `PlanStructureEnricher`

목차 마크다운을 받아 보강된 마크다운을 돌려주는 순수 함수다.

```
string Enrich(
    string planStructureMarkdown,
    IReadOnlyDictionary<string, IReadOnlyList<string>> codesByProcedure)
```

- ```json 블록은 `BatchStepPlanParser`와 **같은 정규식**으로 찾는다. 블록이 여러 개면 파서와 같은 규칙 — 첫 번째 유효 블록 — 을 따른다. 두 곳이 다른 블록을 고르면 기록된 목차와 쓰이는 목차가 갈라진다.
- 각 단계의 `LegacyProcedures`를 마지막 점 뒤·대소문자 무시로 대조해 코드를 모으고, 기존 `ErrorCodes`와 **합집합**한다. 명세서 추출분은 원본 보존 의무라 반드시 포함해야 하고, 모델이 추가로 선언한 코드는 어차피 본문에 있으므로 검사 범위만 넓어진다.
- 합집합의 순서는 **원본 선언 순서 먼저, 그다음 추출분을 명세서 등장 순서로**. 같은 입력에 같은 출력이고, 보강된 결과를 다시 보강해도 같다(멱등).
- `ErrorCodes` **외의 필드는 손대지 않는다.** 각 단계 객체를 보존한 채 그 배열만 교체한다. `Chunkable`처럼 이미 있는 필드나 나중에 늘어날 필드가 재직렬화에 쓸려나가면 안 된다.
- JSON 블록의 바깥 — 목차 마크다운의 산문 — 은 그대로 둔다.

**실패는 예외가 아니라 원본 반환이다.** 블록을 못 찾거나 파싱이 깨지면 입력을 그대로 돌려주고 `Log.Warning`만 남긴다. 보강은 개선이지 필수 단계가 아니다. 이미 분할 생성이 같은 철학으로 폴백한다.

### 3. 배선

목차 마크다운이 **새로 만들어지는 곳은 두 군데뿐**이다.

| 지점 | 처리 |
|---|---|
| 최초 목차 수립 (`DraftBatchPlanStructureAsync` 직후) | `Enrich`를 태운 뒤 `PlanStructure.md`에 기록 |
| `DraftReplacementPlanStructureAsync` 내부 | 반환 직전에 `Enrich`. 재수립 경로와 L3 사용자 요청 경로가 이 헬퍼를 공유한다 |

구제 채택(`AdoptPlanStructureForRescueAsync`)은 이미 보강을 거친 문자열을 되쓰므로 자동으로 덮인다.

이 두 지점을 지나면 파일 기록·`TryParse`·골격 생성·단계 본문 생성·하한 검사·번들 내보내기가 **전부 보강된 같은 문자열**을 본다. 별도 전파 경로를 만들지 않는다.

부수 효과로 단계 본문 생성 프롬프트가 실제 코드 목록을 받게 된다. 지금은 빈 값이라 모델이 명세서만 보고 알아서 쓰고 있다.

**프롬프트 캐시에 미치는 영향은 없다.** 이 값은 `AppendSharedStepContext`의 `[Approved Step List]`에 들어간다(`AiService.cs:2240`) — 즉 회차별 휘발 구간이 아니라 **공유 접두사**다. 다만 그 목록은 전 단계를 한꺼번에 찍으므로 한 회차 안의 모든 단계 호출에서 바이트가 동일하고, 캐시는 지금과 똑같이 1회 쓰기 + N-1회 히트로 동작한다. 접두사가 단계마다 달라지는 경우가 아니다.

### 4. 결함 3분류

`ValidateBatchStep`이 지금 한 통에 담는 것을 셋으로 가른다. 판정에 필요한 `LegacyProcedures`는 이미 `BatchStepPlan`에 있어 새 입력이 필요 없다.

| 상태 | 조건 | 재시도 | 배너 |
|---|---|---|---|
| **품질 미달** | 본문이 최소 요건 미달 — 코드 블록 없음, 헤딩 틀림, 선언된 테이블·코드가 본문에 없음 | 1회 | "이 단계는 품질 미달로 기록되었습니다" |
| **검증 불가** | 보강 후에도 `ErrorCodes`가 비었는데 `LegacyProcedures`는 있음 / `TargetTables`가 빔 | 없음 | "이 단계는 대조할 재료가 없어 검증되지 못했습니다" |
| **해당 없음** | `ErrorCodes`가 비었고 `LegacyProcedures`도 빔 | 없음 | **없음.** `Log.Information`만 남겨 침묵과 구별 |

두 축은 독립적으로 판정한다. `LegacyProcedures`가 비어 오류코드가 "해당 없음"인 단계라도 `TargetTables`가 비면 그 축은 "검증 불가"다 — 레거시 출신이 없다는 것과 쓰는 테이블이 없다는 것은 다른 사실이고, 단계가 아무것도 쓰지 않는다는 선언은 그 자체로 확인이 필요하다. 실측 두 회차에는 이 조합이 없었다(`S00`은 5개, `S08`은 1개를 선언한다).

"해당 없음"이 결함이 아닌 이유: 레거시 출신이 없는 단계는 보존할 원본 코드가 애초에 없다. `POQSettleProcDaily6`의 `S00`(실행 잠금 사전검증)과 `S08`(수수료 총액 확정)이 그런 경우로, 둘 다 계획이 새로 설계한 단계다. 이것을 결함으로 들면 정상 설계에 배너가 붙어 배너의 변별력이 사라진다.

`RegenerationCanFix`는 그대로 유지한다 — "검증 불가"만 있으면 false라 재시도를 건너뛰고, 품질 미달이 하나라도 섞이면 true다.

### 5. 인터페이스 변경

`stepFloorViolations`의 값 타입을 올린다.

```
IReadOnlyDictionary<string, string>
  → IReadOnlyDictionary<string, StepDefect>

record StepDefect(StepDefectKind Kind, string Reason)
enum StepDefectKind { QualityFloor, Unverifiable }
```

영향 범위는 `PlanLayout`, `InstructionBundleWriter`(`BuildFloorBanner`), `VerificationBanner`(`AttachPipelineBanners`), `VerificationPipelineOrchestrator`와 테스트 2종에 걸쳐 약 90개 참조다. 기계적이지만 작지 않다.

값에 종류를 실어 통을 하나로 유지하는 이유: 사전을 둘로 쪼개면 `RestoreAdoptedGenerationState`, `ClearSplitGenerationCacheAfterRedraft`, 분할 생성 캐시가 전부 두 벌을 원자적으로 다뤄야 한다. 그 원자성은 이미 까다롭게 짜여 있어 손대는 비용이 타입 변경보다 크다.

### 6. 출력 형태

- **문서 배너**(`AttachPipelineBanners`): 종류별로 두 블록. 각 블록의 머리글이 그 종류가 무엇을 뜻하는지 말한다. 해당 종류가 없으면 그 블록을 내지 않는다.
- **단계 파일 배너**(`BuildFloorBanner`): 종류에 따라 문구가 갈린다. "검증 불가"에는 "원본 프로시저를 직접 확인해야 합니다" 같은 과잉 지시를 붙이지 않는다 — 섹션 자체는 멀쩡할 수 있다.
- **진입점 §0**: 보강이 정상 작동하면 목록이 비어 모순이 사라진다. 그래도 "검증 불가"가 남는 경우, §0의 문구가 L1/L2 통과와 미검증 단계의 존재를 함께 진술하도록 고친다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| JSON 블록 없음 / 파싱 실패 | 입력 마크다운 그대로 반환, `Log.Warning`. 하한 검사가 "검증 불가"로 잡는다 |
| 명세서에 해당 프로시저 없음 | 그 프로시저는 건너뛴다. 단계의 다른 프로시저에서 나온 코드는 그대로 쓴다 |
| 명세서에 매치 0건 | 코드 없음으로 취급. `LegacyProcedures`가 있으므로 "검증 불가" |
| 보강 후 목차가 파서에 다시 안 읽힘 | 왕복 테스트가 막는다. 실행 시에는 `TryParse`가 null을 내고 기존 단일 호출 폴백이 받는다 |

보강 실패가 파이프라인을 멈추는 경로는 없다. 실패는 두 겹으로 덮인다 — 보강이 실패하면 검사가 그 사실을 기록하고, 검사까지 실패하면 기존 폴백이 받는다.

## 테스트

**왕복이 가장 중요하다.** 보강한 마크다운을 `BatchStepPlanParser`가 다시 읽었을 때 보강한 값이 그대로 나와야 한다. 이것이 깨지면 파일에 기록된 값과 실제 검사에 쓰인 값이 갈라지는데, 그것은 지금 고치려는 결함과 정확히 같은 종류다.

- **추출기**: 실제 명세서 형태에서 코드를 뽑는다 / `-1배 처리` 같은 서술을 코드로 오인하지 않는다 / 날짜의 `-05`를 잡지 않는다 / `@po_intRetVal` 아닌 변수는 무시한다 / 등장 순서를 유지한다 / 매치 없는 명세서는 키를 만들지 않는다
- **보강기**: 빈 배열을 채운다 / 기존 값과 합집합한다 / `LegacyProcedures`가 빈 단계는 비운 채 둔다 / `Chunkable` 등 다른 필드를 보존한다 / JSON 블록 밖 산문을 보존한다 / 멱등이다 / 블록이 여러 개면 파서와 같은 블록을 고른다 / 파싱 실패 시 원본을 돌려준다
- **왕복**: 보강 → `TryParse` → 값 일치
- **3분류**: 세 조건이 각각 의도한 상태로 판정된다 / `RegenerationCanFix`가 조건대로 갈린다
- **배너**: 두 종류가 문서와 단계 파일에 다른 문구로 찍힌다 / "해당 없음"은 찍히지 않는다 / 한 종류만 있으면 그 블록만 나온다
- **회귀 픽스처**: 실측 두 회차의 목차와 명세서를 축약해 체크인한다. 실 산출물은 git 추적 대상이 아니라 픽스처로 쓸 수 없다

### 이 설계에서 틀렸던 것

**「오류 처리」 절의 "보강 실패가 파이프라인을 멈추는 경로는 없다"는 거짓이었다.**
`PlanStructureEnricher`의 `try`가 `JsonNode.Parse` 한 줄만 감싸고 `catch`는 `JsonException`만
잡았는데, JSON 객체에 중복 프로퍼티 이름이 있으면 `JsonNode`는 파싱이 아니라
`TryGetPropertyValue`에서 `ArgumentException`을 던진다. 그 예외는 잡히지 않고, 재수립 헬퍼
경로에는 감싸는 `try`가 없어 파이프라인 밖으로 나갔다. 같은 입력을 `BatchStepPlanParser`는
무사히 처리하므로 이 브랜치가 새로 들여온 회귀였다. `TryRewriteBlock` 본문 전체를
`catch (Exception ex) when (ex is not OperationCanceledException)`으로 감싸 닫았다.

교훈: "실패는 원본 반환"이라고 설계에 적는 것과 그 계약이 실제로 성립하는 것은 다르다.
순수 함수라도 예외 탈출 경로는 호출부까지 따라가 확인해야 한다.
