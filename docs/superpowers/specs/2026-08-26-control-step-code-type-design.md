# 제어 단계 코드의 타입 — 지어낸 어휘의 나머지 절반

`2026-08-26-step-obligation-attribution-design.md`가 레거시 출신이 없는 단계에
예약 음수 대역을 세웠다. 그 회차는 `INT` 축만 닫았다. 코퍼스에는 **문자열로
코드를 돌려주는 제어 단계**가 남아 있고, 검사는 그 형태에 침묵한다 — 금지도
승인도 아니다.

즉 `B100`~`B161`을 낳은 결함("규약이 없으니 모델이 자기 체계를 지어낸다")이
절반만 닫혔다. `INT` 자리에서는 예약 코드로 대체됐지만, 문자열 자리에서는
`N'B120'`·`N'BATCH-LOCK-001'`이 그대로다.

## 배경 — 실측

측정 조건: `output/Jobs/*`에서 `raw/PlanStructure.md`를 `BatchStepPlanParser`로
읽고(`MaxSteps` 40 초과 Job은 파서가 버리므로 제외), `LegacyProcedures`가 빈
단계만 골라 `agent/steps/<Code>.md`를 본다. 대상 **131개 제어 단계**.

### 문자열 코드는 17단계다 — 앞서 센 26·27은 부풀려진 수였다

상태 변수(`@\w*[Ss]tep\w*`)가 비`INT`로 선언된 단계를 세면 27개가 나온다.
그러나 그 안에 **세 종류가 섞여 있다.**

| 구분 | 단계 수 | 판정 |
|---|---|---|
| 문자열 **오류 코드** (`N'B120'`, `N'BATCH-LOCK-001'`) | **17** | 규약 위반 |
| **단계 식별자** (`N'S01'` — 자기 코드) | 12 | 정당 |
| 타임스탬프·플래그 (`SYSUTCDATETIME()`, `0`) | 2 | 정당 |

식별자가 정당한 이유: `BatchControlContract`가 `batch.BatchStepJournal.StepCode`를
**`nvarchar(10)`으로 규정**한다. 단계가 자기 신원을 저널에 쓰려면 문자열이어야
한다. 이것을 위반으로 잡으면 제어 계약을 어기라고 요구하는 셈이다.

**결정적 관찰**: 정당한 `@v_stepCode nvarchar(10) = N'S01'`과 위반인
`@v_currentStepCode NVARCHAR(10) = N'B120'`은 **타입이 같다.** 가르는 것은
값이다 — 앞은 그 단계의 신원이고 뒤는 지어낸 오류 어휘다.

17단계의 분포:

- `POQSettleProc13`(6): S01, S02, S03, S16, S17, S18
- `POQSettleProc19`(4): S02, S03, S04, S17
- `POQSettleProc14`(3): S03, S16, S17
- `POQSettleProc18`(2): S01, S18
- `POQSettleBatch1`(1): S03
- `POQSettlePrco20`(1): S16

값 표본: `B011`, `B020`, `B030`, `B120`, `B172`, `BATCH-FINALIZE-001`,
`BATCH-LOCK-001`, `BATCH-PROTECT-001`.

### 변수 이름 패턴을 넓히면 안 된다

`@\w*[Ss]tep\w*`를 `step|err|code|ret`로 넓히면 무엇이 걸리는지 쟀다.

| 걸리는 변수 | 건수 | 성격 |
|---|---|---|
| `@po_strErrMsg` | 88 | 오류 **메시지** |
| `@v_sqlErrorMessage` | 43 | 메시지 |
| `@v_sqlErrorNumber` | 42 | `ERROR_NUMBER()` 값 |
| `@po_intRetVal` | 167 | 반환값 파라미터 |

메시지와 SQL 오류 번호가 대량으로 딸려 온다. 이름으로 코드·메시지·번호를
가르는 것은 **오늘 두 번 실패한 방식**이다(아침의 `SET @v = @LegacyCode`
거짓 단정, 그 전의 값 자리 정규식). 넓히지 않는다.

**넓힐 필요도 없다.** 두 실물 예시 `@v_currentStepCode`·`@v_currentStepId`가
기존 좁은 패턴에 이미 걸린다. 지금 안 걸리는 이유는 패턴이 `INT` 선언만 보기
때문이다.

## 목표

레거시 출신이 없는 단계의 상태 코드 값을 예약 대역의 음수 정수로 통일하고,
문자열 코드를 기계로 잡는다.

## 비목표

- **출력 파라미터 타입은 검사하지 않는다.** §4에 근거를 수치로 남긴다.
- 변수 이름 패턴을 넓히지 않는다.
- 기존 침묵(`NULL`·변수 참조·`CASE`·함수 호출)을 되돌리지 않는다.
- 기존 산출물의 강제 재생성을 하지 않는다(§5).
- `MaxSteps`·`POQSettleProc5` 재생성은 이 설계 밖이다.

## 설계 §1 — 무엇을 위반으로 보는가

**규칙**: 레거시 출신이 없는 단계의 상태 코드 값은 자기 예약 블록의 음수
정수여야 한다.

**검사**: 상태 변수(`@\w*[Ss]tep\w*`)에 **문자열 리터럴**(`'...'`와 `N'...'` 둘 다)이
대입되면 위반이다.
**예외**: 그 리터럴이 **그 단계 자신의 코드**(`S01` 단계의 `N'S01'`)이면 침묵한다 —
제어 저널에 신원을 쓰는 정당한 용법이다.

예외는 **자기 코드에만** 걸린다. `S01` 단계가 `N'S02'`를 대입하면 발화한다.
남의 신원을 자기 상태 변수에 담는 것은 정당한 용법이 아니고, 예외를 "단계 코드
형태이면"으로 넓히면 `N'S99'` 같은 없는 단계까지 통과한다.

이 규칙이 실측과 맞물린다: 17건이 걸리고, 12건(식별자)과 2건(타임스탬프·플래그)은
걸리지 않는다. 후자 둘은 애초에 문자열 리터럴이 아니다.

## 설계 §2 — 검사

`MechanicalValidator.CheckControlStepErrorCodeBand`에 두 번째 경로를 더한다.

현재 발화 게이트는 "같은 펜스에서 `INT`로 선언된 변수"를 요구한다. 문자열로
선언된 변수는 그 집합에 못 들어와 대입이 통째로 건너뛰어진다. 그래서 문자열
리터럴 경로를 따로 연다.

**발화 조건이 하나만 늘어난다** — 문자열 리터럴이면서 자기 단계 코드가 아닐 때.
나머지는 그대로 침묵한다: `NULL`, 변수 참조(`@LegacyCode`), `CASE` 식, 함수
호출(`ERROR_NUMBER()`), 정수 `0`, 레거시 출신이 있는 단계.

**발화 문구는 새로 쓴다.** 예전 `"컴파일되지 않습니다"`는 거짓이었다 —
`N'B120'`은 컴파일된다. 그래서 걷어냈고, 되살리면 안 된다. 새 문구는
"문자열 코드를 쓰는데 규약은 예약 블록의 음수 정수를 요구한다"는 **참인
진술**이어야 한다.

## 설계 §3 — 프롬프트

`ControlStepErrorCodes.PromptClause`(규칙 6-2)에 두 가지를 더한다.

1. 상태 코드는 `INT`이고 예약 블록에서 나온다.
2. **단계 식별자(`N'S01'`)는 문자열 그대로다.** 이 구분을 명시하지 않으면
   모델이 저널의 `StepCode`까지 숫자로 바꾸려 들 수 있고, 그것은
   `BatchControlContract`(`StepCode nvarchar(10)`) 위반이 된다.

Critic 채점 기준에도 이 축을 한 줄 더한다. 생성 규칙이 요구하는데 아무도
채점하지 않으면 어긋나도 통과하고 자가 수정이 그 축에 영영 닿지 않는다 —
직전 회차에서 실측으로 확인한 실패 방식이다.

**미룬 Minor 둘을 함께 닫는다.** 직전 최종 리뷰가 "다음에 `PromptClause`를
어차피 건드릴 때 함께 다듬어라 — 캐시 무효화 비용을 한 번으로"라고 권했다.

- **M2**: "MUST NOT invent one" 직후에 "owns a reserved block"이 붙어 급하게
  읽히는 문면.
- **M4**: 블록 시작을 "일반 실패 코드"라고 하면서 초기값 규약을 말하지 않아,
  모델이 블록 시작으로 초기화하면 `CheckStepIdInitialValue`("어느 코드와도
  겹치지 않는 값으로 초기화하라")와 부딪힌다. 규칙 6-1이 `= 0`을 예시로 주므로
  정상 경로는 열려 있으나, 두 발화가 한 회차에 같이 나오면 모델이 갈피를 잃는다.

## 설계 §4 — 출력 파라미터 타입을 검사하지 않는 근거

`@po_strRetCode NVARCHAR(10) OUTPUT` 같은 인터페이스는 프롬프트로만 규정하고
검사하지 않는다. 근거는 둘이며 **둘 다 실측이다.**

**첫째, 덮는 범위가 27%다.**

| | |
|---|---|
| 레거시 없는 제어 단계 | 131 |
| `CREATE PROCEDURE`가 있는 단계 | **36** |
| 없는 단계(C# 컴포넌트) | 95 |

대상 Job의 target language가 C#이라 제어 단계 대부분이 T-SQL 프로시저가 아니다.

**둘째, 그 36개 안에서도 "어느 파라미터가 반환 코드인가"를 이름으로 가려야 한다.**

```
24  @po_intRetVal    int        코드
21  @po_strErrMsg    varchar    메시지 — 걸면 안 됨
 2  @po_strIssueCode nvarchar   코드
 2  @po_isValid      bit        플래그 — 걸면 안 됨
 1  @po_runId        bigint     식별자 — 걸면 안 됨
 1  @po_intRetVal    nvarchar   이름은 int인데 타입이 nvarchar
```

이름으로 코드·메시지·플래그·식별자를 가르는 것이 오늘 두 번 오탐을 낸 방식이다.
값 축은 131개 전부를 균일하게 덮는다(프로시저든 C# 컴포넌트든 상태 변수에
문자열 리터럴을 대입하면 걸린다).

**남겨 두는 여지**: 위 표 마지막 줄(`@po_intRetVal`인데 `nvarchar`)은 이름
추정이 필요 없다 — 이름이 `int`라고 말하는데 타입이 아니다. 다만 1건이라 지금
검사를 만들 값어치가 없다고 판단했다. 이 축을 열려는 다음 사람은 이 수치부터
다시 재라.

## 설계 §5 — 기존 산출물

**강제 재생성을 하지 않는다.** 검사는 켜 둔 채로 두고, 해당 Job을 다시 돌릴
일이 생길 때 자연히 걸려 고쳐지게 한다. 유예 장치는 넣지 않는다 — 새 코드가
필요하고 "유예를 언제 끝낼 것인가"라는 새 미결을 만든다.

이 회차 뒤 비순응 단계 총계:

| 축 | 단계 |
|---|---|
| 숫자 축(예약 블록 밖) | 44 |
| 문자열 축(신규) | 17 |
| 겹침(`POQSettlePrco20/S16`) | −1 |
| **합계** | **60** (10개 Job) |

## 테스트

오탐 방어가 중심이다. 규칙이 타입이 아니라 값인 근거가 실측에서 나왔으므로,
그 실측을 그대로 픽스처로 굳힌다.

| 픽스처(실물 형태) | 기대 |
|---|---|
| `@v_currentStepCode NVARCHAR(10) = N'B120'` | 발화 |
| `@v_stepCode nvarchar(10) = N'S01'` (S01 단계) | 침묵 |
| `@v_stepStartedAtUtc DATETIME2(3) = SYSUTCDATETIME()` | 침묵 |
| `@v_isStepCompleted BIT = 0` | 침묵 |

기존 침묵이 되돌아가지 않았는지 함께 고정한다 — `NULL`, `@변수`, `CASE`,
함수 호출, 레거시 출신 있는 단계, 정수 축의 기존 동작.

**변이 세 곳**을 확인한다.

1. 문자열 경로 무력화 → 17건 픽스처가 실패해야 한다
2. **식별자 예외 제거** → 식별자 픽스처가 걸려 실패해야 한다. 예외가 실제로
   일하는지 보는 유일한 방법이다
3. 정수 축 무력화 → 기존 테스트가 실패해야 한다

프롬프트 축: 새 조항·M2·M4 문면·Critic 기준이 실제로 실리는지. 단언 토큰은
프롬프트 안에서 고유해야 한다.

## 회귀 실측 — 통합 시점에 코퍼스로 잰다

워커 워크트리에는 `output/`이 없어 손으로 만든 픽스처만 돈다. 직전 회차에 그
공백에서 Critical이 하나 나왔다(코퍼스 실물 오탐). 기대값을 미리 못박는다.

| 항목 | 기대 |
|---|---|
| 문자열 축 새 발화 | **17단계** (6개 Job) |
| 식별자·타임스탬프·플래그 | **0건** — 하나라도 걸리면 규칙이 틀렸다 |
| 숫자 축 "예약 블록 밖" | **161건 / 44단계 불변** |
| "컴파일되지 않습니다" 거짓 발화 | **0건 유지** |

## 문서 갱신

`docs/known-defects.md`의 미결 셋을 결정됨으로 바꾼다.

1. 문자열 코드 제어 단계 → **INT 통일**, 대상 17단계(측정 조건과 목록 포함)
2. 소급 범위 → **강제하지 않고 수렴**, 총 60단계
3. T4·T5 도달 불가 → **기록만 유지**(`MaxSteps` 인상·`POQSettleProc5` 재생성은
   별건)

그리고 §4의 근거(36/131, 이름 추정의 실패 이력)를 남긴다.

## 미확정 사항 — 구현 첫 단계에서 확인한다

- 식별자 예외의 비교를 대소문자 무시로 할지. 실측 표본은 전부 대문자
  (`N'S01'`)지만 코퍼스가 바뀌면 재확인한다.
- 한 단계가 상태 변수를 둘 이상 두는 경우가 있는지. 있다면 어느 것이 코드인지
  가려야 하고, 그것은 §4가 피한 이름 추정과 같은 문제가 된다. 구현 첫 단계에서
  세고, 있으면 **보고하고 멈춘다.**

## 완료 기준

- `@v_currentStepCode NVARCHAR(10) = N'B120'`이 걸린다
- `@v_stepCode nvarchar(10) = N'S01'`(S01 단계)은 걸리지 않는다
- 코퍼스 실측에서 문자열 축 17단계·식별자 0건·숫자 축 161/44 불변
- "컴파일되지 않습니다" 발화가 코퍼스에서 0건
- 변이 세 곳이 전부 red로 확인된다
- 빌드 경고 0·오류 0, 테스트 실패 0·건너뜀 0(코퍼스 연결 시)
