# 오류 코드 앵커 — 문장 신원의 축을 주석에서 계약으로 옮긴다

**목표:** 검사 B·C가 닿는 코퍼스를 326개 단계 파일 중 2개(0.6%)에서 197개(60%)로 넓히고,
그 결과로 POQSettleBatch1/S11 🟠(갱신 9의 조인 키 `YMD`·`UseState` 결측)을 닫는다.

**실행 계획:** 별도 회차로 돌지 않는다. `docs/superpowers/plans/2026-08-24-machine-table-expansion.md`
(미착수)에 세 번째 표와 태스크 둘로 흘려넣는다 — §5 참고.

**출처:** `docs/known-defects.md`의 「문장↔spec 행 대응 재설계(2026-08-24, Task 22)」가
남긴 활로 (a). 그 항목이 적은 "`SpecStatementFactsExtractor.cs`를 넓혀 오류코드→Ordinal
매핑을 기계 확정 재료로 뽑는 것"을 실측으로 다시 조준한 결과가 이 문서다 — **조준점이
바뀌었다**(§1).

## 배경 — 전제가 뒤집혔다

태스크 22는 S11을 "앵커가 없는 예외 좌표"로 다뤘다. 코퍼스를 세면 반대다.

| 단계 파일이 쓰는 신원 표기 | 파일 수 | 비율 |
| :--- | ---: | ---: |
| U-표기 앵커 (`/* U13: … */`) | **2** | 0.6% |
| 음수 오류 코드 라벨 (`SET @v_currentStepId = -13;`) | **197** | 60% |
| 둘 다 없음 | 127 | 39% |

U-앵커를 쓰는 파일은 `POQSettleBatch1/S07`과 `POQSettleProc10/S08` **둘뿐**이다
(`grep -lE '\bU[0-9]{1,2}\b|갱신 ?[0-9]{1,2}' output/Jobs/*/agent/steps/S*.md`, 2026-08-25 실측).

**그래서 태스크 22가 검사 B를 1건만 발화시킨 것은 검출이 정밀해서가 아니라 닿는 파일이
사실상 하나여서다.** S11은 소수 예외가 아니라 다수파고, 이 회차의 대상은 한 좌표가 아니라
관용구 하나 전체다.

### 왜 코드 라벨이 주석보다 단단한가

U-앵커를 요구하는 규약은 없다. 태스크 8이 프롬프트 문구로 권했을 뿐이라 모델이 안 달아도
계약 위반이 아니다 — 실측 2/326이 그 결과다.

코드 라벨은 다르다. **두 규약이 강제한다.**

- `AiService.cs:2006` **[Precise Error Tracking]** — *"You MUST declare a state variable at
  the top (e.g., `DECLARE @v_currentStepId INT = 0;`), update it before each DML with the
  exact original error code (e.g., `SET @v_currentStepId = -101;`)"*
- `AiService.cs:2011` **[Error Codes]** — *"You MUST strictly reuse the EXACT original error
  codes from the source SPs. DO NOT remap or invent new error codes"*

즉 단계 쪽 `SET @v_currentStepId = -13;`은 관례가 아니라 **이미 강제되고 이미 197개 파일에
있는 신원 축**이다. 우리가 안 쓰고 있었을 뿐이다.

### 원본 쪽도 관용구가 규칙적이다

`UP_UTIL_SETTLE_EXPECT_PROC`(S11의 레거시)의 DDL은 각 DML 뒤에 같은 모양을 둔다.

```sql
    IF @@ERROR <> 0 BEGIN
        ROLLBACK TRAN
        SET @po_intRetVal = -1
```

`object_definition.sql:41-43`, `62-64`, `82-84` … 11회 반복. AST로 집으면 추론 없이 뽑힌다.

## 목표

1. `오류 코드 ↔ 갱신 번호` 기계 확정 표를 명세서에 세운다.
2. `StepSqlStatementReader`가 코드 라벨을 앵커로 읽는다.
3. 검사 B·C가 두 신원 축을 같은 자리에서 받는다.
4. S11 갱신 9의 조인 키 결측이 실물에서 잡힌다.

## 비목표

- **위치 기반(개수 일치) 매칭을 만들지 않는다.** 태스크 22가 사전 측정으로 UPDATE 703위치 중
  predicate 132·join 101건이 "결측"으로 뜨고 다수가 오탐임을 확인했다. 코드 앵커는 위치가
  아니라 신원으로 맞추므로 그 갈래를 아예 열지 않는다.
- **U-앵커 관용구를 없애지 않는다.** 2개 파일이 계속 그렇게 쓰고, 그 축은 그대로 둔다.
- **검사 A를 손대지 않는다.** 검사 A는 개수 대조라 앵커를 안 쓴다. 그 잔여 오탐
  (Shadow/Stage 스왑 등)은 이 회차 밖이다.
- **오류 코드가 없는 SP를 억지로 덮지 않는다.** 표가 0행이면 검사가 그 SP에서 침묵한다.

## 설계 §1 — 재료: `DmlScopeExtractor`에 다섯 번째 표를 더한다

**별도 추출기를 만들지 않는다.** 갱신 번호를 채번하는 주체는 `DmlScopeExtractor`의 방문자
(`NextOrdinal("UPDATE")`, `DmlScopeExtractor.cs:898`)다. 밖에서 같은 번호를 다시 세면 두
채번이 조용히 어긋나고, 어긋난 매핑은 **엉뚱한 행과 대조하는 거짓 시정 지시**가 된다 —
태스크 4 리뷰가 이미 같은 모양의 Critical을 냈던 자리다.

같은 방문자가 DML을 지날 때 뒤따르는 오류 가드에서 리터럴을 집어 같은 행에 싣는다.
`DmlScopeExtractor`는 이미 표 제목을 넷 소유하므로(`DmlScopeTableHeading` ·
`SetPredicateTableHeading` · `LockHintTableHeading` · `ReferencedFunctionTableHeading`)
다섯 번째를 더하는 것이 이 저장소의 기존 패턴이다.

### 오류 코드 (기계 확정 — 수정 금지)

| 문장 | 오류 코드 | 설정 대상 |
| :--- | :--- | :--- |
| UPDATE 1 | -1 | @po_intRetVal |
| UPDATE 2 | -2 | @po_intRetVal |
| … | … | … |
| UPDATE 9 | -13 | @po_intRetVal |

**행을 만드는 조건** — DML 문장 바로 뒤에 오는 `IF` 문의 본문에서 `SET <출력 파라미터> =
<정수 리터럴>` 대입을 찾는다. 찾으면 한 행, 못 찾으면 그 문장은 행이 없다.
「바로 뒤」는 AST 형제 순서 기준이며, 사이에 다른 DML이 끼면 중단한다.

**추론 금지 항목** — 가드 조건식(`@@ERROR <> 0`)을 해석하지 않고, 코드에 의미를 붙이지 않고,
연속 범위로 접지 않는다(규약 9가 프롬프트에서 금지하는 것과 같은 이유). 리터럴 원문만 담는다.

## 설계 §2 — 판독: 코드 앵커

`StepSqlStatementReader.ReadAnchor`는 지금 문장 앞 구간의 **주석**만 본다. 같은 구간에 두 번째
축을 단다 — `SET @<변수> = <음수 정수 리터럴>;`이 **정확히 하나** 있으면 그 리터럴을 코드
앵커로 잡는다.

태스크 22가 세운 「구간 내 유일성」 규칙(직전 문장의 끝 ~ 이 문장의 시작)을 **그대로 재사용**
하므로 오귀속 안전성이 같다. 둘 이상이면 침묵한다 — 미구현 자리의 잔여 라벨이 뒤따르는
무관한 DML을 훔치는 태스크 11의 실패 모드가 여기서도 자동으로 막힌다.

**변수 이름을 고정하지 않는다.** 규약 6-1은 `@v_currentStepId`를 예시로 들 뿐 이름을 못
박지 않는다. 이름이 아니라 「음수 정수 리터럴 대입이 구간에 하나」라는 모양으로 잡는다.

**왜 단계 쪽만 음수로 좁히는가 — §1과 일부러 비대칭이다.** §1(원본 쪽)은 리터럴 부호를 가리지
않고 담는다. 표는 사실의 기록이므로 원본이 `0`을 설정하면 `0`을 적는 것이 맞다. 반면 §2(단계
쪽)는 **판독**이라 좁혀야 한다 — 규약 6-1이 요구하는 `DECLARE @v_currentStepId INT = 0;`
초기화와, 구간에 흔히 섞이는 `SET @v_rowCount = 0;` 같은 관용구가 전부 비음수라, 음수로
좁히면 이들이 자연히 후보에서 빠지고 「구간에 정확히 하나」 규칙이 실제로 성립한다.
부호를 안 가리면 대부분의 구간에서 후보가 둘 이상이 되어 검사가 통째로 침묵한다.

이 비대칭 때문에 원본 표에 담긴 비음수 행은 환산 상대를 영영 못 만난다 — 그 행은 표에
기록으로 남되 대조에는 쓰이지 않는다. 그런 행이 실제로 몇 개인지는 「미확정 사항」 2번이
실측으로 닫는다.

## 설계 §3 — 해석: 검사 B·C가 두 축을 받는다

`MechanicalValidator`가 코드 앵커를 §1의 표로 Ordinal에 환산한 뒤, 기존 (Ordinal, Kind,
TargetTable) 대조 경로에 그대로 흘려보낸다. 검사 B·C의 대조 로직 자체는 바뀌지 않는다.

**두 축이 충돌하면 침묵한다.**

| U-앵커 | 코드 앵커 | 판정 |
| :--- | :--- | :--- |
| 있음 | 없음 | U-앵커 사용 (기존 동작 보존) |
| 없음 | 있음 | 코드 앵커를 환산해 사용 |
| 있음 | 있음·일치 | 사용 |
| 있음 | 있음·**불일치** | **침묵** |
| 없음 | 없음 | 침묵 (기존 동작) |

불일치 침묵은 새 규칙이 아니다 — "귀속할 수 없으면 침묵"은 태스크 3·4·12·22가 연속으로
세워 온 이 저장소의 규약이고, 두 신원이 다투는 자리가 정확히 그 경우다.

## 설계 §4 — 오탐 게이트

### 닭-달걀을 하네스로 푼다

새 표는 어느 `Spec.md`에도 아직 없다(현행 세대 15). 그런데 `reset-l1-check` SKILL.md는
**재생성 전에 코퍼스 스윕으로 오탐을 먼저 잡으라**고 요구한다 — 거짓 양성을 안은 채 전건을
돌리면 재시도가 소진된다.

스윕 하네스가 명세서를 기다리지 않고 **`DmlScopeExtractor`를 원본 DDL에 직접 돌려** 매핑을
만들고, 그것을 명세서에서 온 재료인 양 검증기에 먹인다. 기계 확정 표는 축자 전사 계약이라
**추출기 출력 = 재생성 후 표 내용**이므로 이 스윕이 재는 것이 곧 재생성 후의 상태다.

축 B 계약(원본 `.sql`을 안 읽는다)은 **런타임 검사**에 걸리는 제약이지 측정 하네스에 걸리는
제약이 아니다. 하네스는 저장소에 커밋하지 않는다.

### predicate 쪽 CTE 사각지대는 미리 접지 않는다

태스크 22가 `HasOpaqueJoinSource`로 **조인 키 체크만** 접었다. 최상위 WHERE 술어 체크가 같은
사각지대에 걸리는지는 그때 표본에서 안 보였을 뿐 확인된 것이 아니고, 코드 앵커를 켜면 60%
코퍼스에서 드러날 수 있다.

**미리 접지 않는다.** 접으면 S07 갱신 13처럼 이 체크가 실제로 잡아낸 진짜 결함까지 함께
죽는다(태스크 22의 유일한 성과가 바로 그 자리다). 스윕이 실측한 뒤 오탐이 확인되면 그때
좁히고, 좁힌 근거를 수치로 남긴다.

### 게이트 기준

| 항목 | 기준 |
| :--- | :--- |
| 검사 B·C 발화량 | 측정하고 기록한다 (사전 목표치를 두지 않는다) |
| 표본 오탐 검사 | 발화 ≤30건이면 전건, >30건이면 최소 10건 |
| 회귀 | 검사 A·D·E 발화량이 스윕 전과 동일 |
| S07 갱신 13 | 계속 잡힌다 |
| S11 갱신 9 | 새로 잡힌다 |

## 설계 §5 — machine-table-expansion 계획에 흘려넣는다

그 계획의 골격(추출기 → `SpecExpectations` → 프롬프트 표 뼈대 → L1 전사 대조 → 커버리지 맵
→ 캐시 인상)이 이 표에 그대로 맞는다. 표가 셋이 되고 태스크가 둘 는다.

| 그 계획의 자리 | 이 회차가 더하는 것 |
| :--- | :--- |
| Task 1·2 (추출기 신규) | **`DmlScopeExtractor` 확장** — 신규 파일이 아니라 기존 추출기 수정 |
| Task 3 (`SpecExpectations` 배선) | 속성 1개 + null 체인 1항 추가 |
| Task 4 (`MachineConfirmedTables` + 프롬프트) | `All` 맨 끝에 세 번째 항목, 표 뼈대 1개 |
| Task 5 (L1 검사) | **검사 신규 대신 검사 B·C 배선 수정** — 코드 앵커 환산 |
| — (신규) | **`StepSqlStatementReader` 코드 앵커 판독** — §2 |
| Task 6 (코퍼스 스윕) | 스윕 항목에 검사 B·C 발화량·오탐율 추가 |
| Task 7 (커버리지 맵) | 오류 코드 재료를 `ExtractorFactLines`에 |
| Task 8 (캐시 인상 15 → 16) | 그대로 — **한 번의 인상, 한 번의 재생성** |

`MachineConfirmedTables.All`의 순서 제약(프롬프트 접두사 캐시가 바이트 일치로 걸리므로 맨 끝에
append)은 그 계획의 Global Constraints가 이미 못 박았다. 세 표의 append 순서는 계획이 정한다.

## 설계 §6 — 테스트

**단위(TDD)**
- `DmlScopeExtractor` — 가드 있음/없음, 사이에 다른 DML이 낀 경우, 리터럴이 양수인 경우,
  같은 코드가 둘 이상 문장에 붙는 경우.
- `StepSqlStatementReader` — 구간에 코드 하나 / 둘(침묵) / 주석과 코드 공존 / 변수 이름 변형.
- `MechanicalValidator` — §3 판정표 5행 각각.

**실물 회귀 둘**
- `UP_UTIL_SETTLE_EXPECT_PROC` DDL에서 11행 매핑(`-1,-2,-3,-4,-5,-10,-11,-12,-13,-15,-17`)이
  나온다. 이 목록은 그 명세서 `docs/Spec.md:80`의 산문과 이미 일치함을 태스크 22가 대조했다.
- `POQSettleBatch1/S11`에서 갱신 9의 `YMD`·`UseState` 결측이 잡힌다.

**코퍼스 스윕은 단위 테스트가 아니라 병합 게이트다**(§4).

## 미확정 사항 — 구현 첫 단계에서 확인한다

1. **197개 중 몇 개가 실제로 환산되는가.** 코드 라벨을 가진 단계 197개 중 183개가 자기 레거시
   SP의 `Spec.md`에 `@po_intRetVal` 서술을 갖지만(2026-08-25 실측), 그것은 "산문이 있다"는
   뜻이지 "DDL에 `IF @@ERROR` 가드가 있다"는 뜻이 아니다. 표가 실제로 몇 행 나오는지는
   `DmlScopeExtractor` 확장 직후 코퍼스 31개 DDL에 돌려 센다.
2. **`SET @po_intRetVal = 0`(성공 경로)이 섞이는가.** EXPECT_PROC는 성공 경로에서 설정하지
   않지만 다른 SP는 다를 수 있다. 실측 후 「가드 안의 대입만」으로 좁힐지 정한다.
3. **TRY…CATCH로 이미 현대화된 원본이 있는가.** 있으면 `IF @@ERROR` 가드가 없어 표가 비고,
   그 SP는 침묵한다 — 결함이 아니라 적용 밖이다. 개수만 세어 기록한다.
