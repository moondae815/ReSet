# U-앵커 계약에 `INSERT n`·`DELETE n` 표기를 명시한다 — 설계

**작성 2026-09-08.** 기준 커밋 `22bac170`(main). **코드는 안 만졌다 — 이 문서는 결정 자료다.**

**출처**: `2026-09-08-Batch6-재생성-판독.md` §2 가 「뿌리를 찾았다」로 지목한 자리.

## 1. 결함 — 계약이 「각 DML 문장」을 요구하면서 UPDATE 표기만 정의한다

`AiService.cs:4605`(`AppendStatementAnchorRules`, 조항은 4611):

> 「**각 DML 문장** 바로 앞에 명세서의 **갱신 번호**를 주석으로 답니다.
>  `/* U13: 카드사 원가 반영 */` 형식입니다(**`갱신 13`·`UPDATE 13`도 인정됩니다**).」

**요구는 INSERT·UPDATE·DELETE 전부인데, 인정하는 표기 셋이 전부 UPDATE 용어다.**
`INSERT 1`·`DELETE 1` 을 어떻게 적어야 하는지 **어디에도 없다.**

### 그래서 모델이 회차마다 발명한다 — 실측 넷

| 판 | 표기 | 리더가 읽는 서수 |
| :--- | :--- | :--- |
| `Batch1`(09-04) | `-- SQL_INSERT1 (INSERT 1, 오류코드 -2)` + `/* INSERT1: … */` | 1 (우연히 맞음) |
| `Batch5/S13`(09-06) | `/* U13-DELETE 1: … */` | **13** ← 틀림 |
| `Batch6/S09`(09-08) | `/* U22: DELETE 1 … */` (`U` = **원본 라인**) | **22** ← 틀림 |
| `Batch6/S13`(09-08) | `/* U1: … (DELETE 1) */` (`U` = **자체 순번**) | 1 (우연히 맞음) |

**해가 조용하다** — 서수가 틀리면 명세서에 그 `(Kind,서수)` 행이 없어 **앵커 계열 검사
(B·C·D)가 대조할 행을 못 찾고 그냥 지나간다.** 발화도 오류도 없이 커버리지가 사라지고,
**앵커가 있어 보이기까지 한다.**

## 2. ★ 리더를 또 고치지 마라 — 오늘 네 번 고친 것이 전부 이 구멍의 보상이었다

```
1bb76b67  유일성 → 일치        (기계 라벨과 U-앵커가 같은 서수를 말하는데 버려졌다)
c3762dcc  패턴 완화 \s+ → \s*   (`DELETE1` 처럼 공백 없는 표기를 못 읽었다)
8e971b4f  `U<n>-` 배제          (`U13-DELETE 1` 이 13 을 집었다)
379e2b39  탐지기               (그 오귀속을 자동으로 잡는다)
```

**넷 다 「모델이 발명한 표기를 리더가 따라가는」 일이었다.** 발명이 계속되는 한 리더는
계속 뒤쫓는다 — `Batch6` 의 `U<원본라인>` 이 그 증거다(리더 셋을 다 고친 뒤에 나왔다).
**고칠 자리는 리더가 아니라 계약이다.**

## 3. 처방 — 조항 한 줄을 갈아 끼운다

```
- **각 DML 문장 바로 앞에 명세서 DML 범위 표의 그 문장 표기를 주석으로 답니다.**
  `UPDATE` 는 `/* U13: 카드사 원가 반영 */`(`갱신 13`·`UPDATE 13`도 인정),
  `INSERT` 는 `/* INSERT 1: … */`, `DELETE` 는 `/* DELETE 1: … */` 형식입니다.
  **번호는 명세서 표의 서수를 그대로 씁니다** — 원본 라인 번호나 이 단계의 자체 순번을
  쓰지 마십시오. **종류가 다르면 서수가 겹쳐도 됩니다**(`DELETE 1` 과 `INSERT 1` 은
  서로 다른 문장입니다). **`U13-DELETE 1` 같은 복합 라벨은 쓰지 마십시오.**
```

**네 문장이 각각 실측된 오답 하나씩을 막는다.**

| 문장 | 막는 실측 오답 |
| :--- | :--- |
| `INSERT n`·`DELETE n` 형식을 명시 | 표기가 없어 발명하는 것(뿌리) |
| 「명세서 표의 서수를 그대로」 | `U22`(원본 라인) · `U1`(자체 순번) |
| 「종류가 다르면 겹쳐도 된다」 | 서수 충돌을 피하려 번호를 옮기는 것 |
| 「복합 라벨을 쓰지 마라」 | `U13-DELETE 1` |

## 4. ★★ 비용 — **캐시 인상도 명세서 재생성도 필요 없다**

**이것이 이 설계의 가장 중요한 사실이다.** 스킬(`reset-l1-check`)의 인상 규정은
「프롬프트에 실리는 것이 달라졌으면 `CurrentCacheFormatVersion` 을 올린다」인데,
**이 조항이 실리는 프롬프트는 그 캐시의 관할이 아니다.**

**코드로 확인했다.**

```
AiService.cs                          CacheManager 참조 0 회
CurrentCacheFormatVersion             CacheManager.cs 안에서만 쓰인다(소비자 5 중 4 가 그 파일)
VerificationPipelineOrchestrator
  RunCodeObjectPipelineCoreAsync      _cacheManager 사용 (SP 분석 = 명세서 경로)
  RunConsolidatedPipelineAsync        _cacheManager 사용 0 회 (Job 계획·단계 경로)
```

**단계 생성은 아예 캐시를 안 탄다.** 2026-09-05 F1′ 회차가 같은 이유로 인상하지 않은 전례가 있다.

| | |
| :--- | :--- |
| 캐시 인상 | **불필요** |
| 명세서 전건 재생성 | **불필요** |
| 드는 것 | **Job 재생성 1 회** — 새 이름으로 돌리면 기존 산출물도 안 덮는다 |

**비용이 「전건 재생성」이 아니라 「Job 하나」다.** 이 사실을 모르면 이 항목이 부당하게
비싸 보여 계속 미뤄진다 — 실제로 오늘까지 그랬다.

## 6. 되돌림 조건

- **R1**: 다음 Job 에서 `AnchorKindOrdinalPairTests` 불일치가 **0 이 아니면** 조항을 다시 본다.
  **되돌리지는 않는다** — 표기를 안 정한 상태보다 나쁠 수 없다.
- **R2**: 앵커 **보유 문장 수가 줄면** 되돌린다. 표기를 좁혀 모델이 아예 안 붙이게 되는 것이

- **R3**: 프롬프트 잠금 시험(`AiService` 문구 고정)이 있으면 함께 갱신한다 —
  안 하면 게이트가 그 문구로 빨개진다.

## 7. 안 하는 것 · 알려진 한계

- **기존 산출물은 안 고쳐진다.** `Batch1`·`Batch5`·`Batch6` 의 오귀속은 그대로 남고,
  **게이트는 다음 Job 이 나올 때까지 빨갛다.** 그 빨간불을 없애려고 탐지기를 약화시키지 마라.
- **`Batch6/S09` 의 `U22`·`U31` 이 원본 라인 번호라는 것은 관측이지 확인이 아니다** —
