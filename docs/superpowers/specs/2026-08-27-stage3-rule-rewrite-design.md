# 3단계 규칙 본문 다시 쓰기 설계서

## 0. 이 설계서의 자리

선행 설계서가 **SQL의 거처**를 정했다 — SQL은 앱으로 가져오고, 신규 저장 프로시저를
만들지 않으며, 트랜잭션과 오류 처리는 C#이 소유한다.

그 설계서의 §3이 바뀔 규칙을 **표로** 정했으나 "어떻게 쓸지"는 정하지 않았고, §7이
"그림자 메커니즘 (a)~(e)가 C#에서 어떤 모양이 되는지 구체가 없다"를 답하지 못한 것으로
적었다. **이 설계서가 그 구체를 정한다.**

1·2단계(결속 실측과 검사)는 `fe89b5d`로 병합됐다.

## 1. 결정적 사실 — 겨누는 C# 앱이 존재하지 않는다

```
TaskletResult 가 src/ 에 있는가        →  0건
생성 계획서 한 편(Proc2)에 나오는 횟수  →  52회
```

ReSet은 **문서만 만든다.** 계획서가 서술하는 C# 배치 앱은 아직 없다. 그래서 20개
계획서가 각자 다른 C# 모양을 지어낸다.

```
StepResult        18개 계획서 (1~46회)
TaskletResult      1개만  (Proc2, 52회)
SqlTransaction     9개
TransactionScope   2개
```

**신규 SP 정의 수가 0~18로 흩어진 것과 정확히 같은 형태다** — 규칙이 정하지 않은 것을
모델이 매번 다르게 찍는다. 이번엔 SQL의 거처가 아니라 C#의 모양에서.

### 결정 — 규칙은 의무만 정하고 API는 정하지 않는다

규칙은 **무엇을 보장해야 하는지**만 말한다. `SqlTransaction`인지 `TransactionScope`인지는
정하지 않는다. 존재하지 않는 API 계약을 지어내지 않기 위해서다.

**대가**: 생성물의 C# 모양은 계속 제각각이다. 이는 **의도된 결과**이며, 4단계 재생성에서
결함으로 오독되지 않도록 미리 기록한다.

## 2. 규칙 넷 다시 쓰기 — 옷과 알맹이

실물을 읽어 보니 **옷을 벗겨야 하는 곳은 생각보다 적다.** 지금 규칙은 이미 대부분 의무이고
T-SQL 옷을 입고 있을 뿐이다.

### 2-1. 규칙 4 (트랜잭션 격리·그림자 표) — (c) 하나만 바꾼다

| 메커니즘 | 판정 |
|---|---|
| (a) `SELECT INTO`를 `BEGIN TRAN` 전에 | **의무로 다시 쓴다**: 롤백될 수 있는 트랜잭션 **밖에서** 먼저 만든다 |
| (b) 복원은 지운 범위와 정확히 같게 | 이미 언어 중립 — 그대로 |
| (c) `EXEC()` 안에서 외부 배치 변수 참조 금지 | **T-SQL 고유. 다시 쓴다**: 값을 **파라미터로 넘긴다, 문자열로 잇지 않는다** |
| (d) 여러 대상 표면 전부 덮는다 | 그대로 |
| (e) 저장 수명·정리 정책을 정한다 | 그대로 |

`SET TRANSACTION ISOLATION LEVEL SNAPSHOT`은 **"이 단계는 스냅샷 격리에서 돈다"**는
의무로 남기고 거는 자리는 정하지 않는다. `ALTER DATABASE … READ_COMMITTED_SNAPSHOT ON`
금지는 DB 수준 지시라 그대로 유지한다.

### 2-2. 규칙 6-1 (정밀 오류 추적) — 셋으로 갈린다

| 알맹이 | 어디로 가는가 |
|---|---|
| 원본 코드를 그대로 (일반 `-1` 금지) | **규칙 9 + 결속 검사가 이미 덮는다.** 규칙 6-1에서 뺀다 |
| 상태 변수를 각 DML 앞에서 갱신 | ~~**§3의 새 검사로 옮긴다**~~ → **규칙 6-1에 의무로 남기되 L1 기계 강제는 없다** (아래 정정) |
| 구조적 `TRY...CATCH`, `GOTO` 금지 | C# 예외 처리로 자동 대체. **규칙에서 뺀다** |

`XACT_ABORT ON`은 **"실패한 문장이 부분 커밋을 남기지 않는다"**는 의무로 다시 쓴다.

> **[2026-08-27 실행 정정]** 위 표의 둘째 행은 원래 "**§3의 새 검사로 옮긴다**"였다.
> **그 검사는 만들어지지 않았다** — §3의 정지 조건이 62건으로 발동했다(§3 머리의 상자).
>
> **규칙 6-1 다시 쓰기 자체는 유효하다.** 실패한 DML마다 다른 원본 코드를 실어 실패 지점을
> 남기는 의무는 언어 중립 서술로 규칙에 남는다. **다만 그 항목은 L1 기계 강제를 갖지 않는다.**
> 지금 그것을 강제하는 것은 `CheckStepIdInitialValue` 하나뿐이고, 그 검사는 T-SQL 구문
> (`DECLARE @v_currentStepId INT = 0`)에 묶여 있어 언어 이전 뒤에 침묵한다. 이 절의 규칙 넷
> 가운데 **이 항목만 대신할 검사 없이 규칙 본문에만 의존한다** — 의도된 상태이며, 4단계
> 재생성에서 "검사가 빠졌다"로 오독되지 않도록 여기 적는다.

### 2-3. 규칙 8-1 (청크 트랜잭션 경계) — 철자만 벗긴다

이미 "각 청크가 독립 커밋하고, 중간 실패가 앞선 청크를 durable하게 남긴다"는 의무다.
`BEGIN TRAN`/`COMMIT TRAN`이 그 철자다. **의무는 그대로, 철자만 뺀다.**

### 2-4. 규칙 4-1 — `helper procedure`를 뺀다

지금 규칙 4-1이 신규 배치 객체에 `helper procedure`를 **명시적으로 허용**한다. 선행
설계서의 새 규칙("신규 저장 프로시저를 만들지 않는다")과 정면 충돌하는 유일한 자리다.

`batch`·`batch_shadow` 스키마 강제는 그대로 — 스테이징·저널·그림자 **테이블**은 여전히
필요하다.

### 2-5. 규칙 2에 한 줄

`## 단계별 이행 상세 및 의사코드`가 "classes/components **와** pseudocode"를 함께
요구하는데 그 의사코드가 C#인지 T-SQL 프로시저 본문인지 말하지 않는다. **이것이 원래
모호함의 발원지다.**

### 3-1. 실측 — "등장"과 "대입"은 다르다

`raw/PlanStructure.md`의 `Steps[].ErrorCodes`를 `agent/steps/<Code>.md` 본문과 대조했다.
Job 17개 · 단계 241개 · 선언 코드 1,476개.

```
문서에 등장    1476 / 1476  (100%)   ← 이 기준으로는 검사가 아무것도 안 잡는다
대입 자리에    1325 / 1476  ( 90%)   ← 151개가 표에만 있고 대입되지 않는다
```

Job별로 **76%~100%**로 갈리고 `Proc19`가 76%로 가장 낮다.

**오늘 회차가 배운 구별이 그대로 반복된다** — "문서에 있다"와 "실제로 그 값을 싣는다"는
다르다. 처음 제안한 "도달성"은 전자였고, 그 기준이면 검사가 무의미했다.

⚠️ **이 90%는 근사다.** 대입 자리를 `=\s*(-?\d+)\s*[;,)]`와 `SET\s+@\w+\s*=\s*(-?\d+)`로
잡았다. 이 회차에서 창 휴리스틱이 세 번 틀렸으므로 **151개의 정체는 확정되지 않았다.**

### 3-2. 검사가 재는 것

**단계가 선언한 레거시 오류 코드 하나하나가 그 단계 문서의 대입 자리에 나타나야 한다.**
오류 코드 표에 나열만 된 것은 이행이 아니다.

### 3-3. 결속 검사와 달리 단계 단위로 성립한다

결속 검사(`CheckLegacyReturnCodeBinding`)는 **문서 단위**로 갈 수밖에 없었다 — 실패 14건 중
13건이 계약 표를 문서 어디에서도 부르지 않아 단계 귀속이 불가능했다.

이 검사는 다르다. **코드는 `step.ErrorCodes`로 단계마다 선언되고, 대입되어야 할 자리도 그
단계 문서다.** 귀속이 자연히 성립하므로 **어느 단계의 어느 코드가 빠졌는지 지목할 수 있다.**

### 3-4. 151개의 세 갈래 — 셋째가 이 설계의 위험이다

| 갈래 | 뜻 | 조치 |
|---|---|---|
| **진짜 결손** | 코드를 선언하고 어디서도 안 싣는다 | 검사가 잡아야 할 것 |
| **정규식의 맹점** | `CASE`·`ISNULL`·변수 경유로 실린다 | 기준을 넓힌다 |
| **정당한 미대입** | 그 코드가 이 단계에서 발생할 수 없다 | 침묵해야 할 것 |

셋째가 위험이다. 레거시 SP가 코드 10개를 정의했는데 그중 셋이 **이 단계가 대체하지 않는
분기**의 것이라면 안 싣는 게 맞다. 그러면 검사는 "선언 전부"가 아니라 "이 단계가 대체하는
분기의 코드"만 봐야 하고, **그 판정은 새 추정이다.**

> **정지 조건: 1단계 실측이 「정당한 미대입」을 하나라도 찾으면 멈추고 보고한다.**
> 검사 설계를 다시 해야 한다.

## 4. 순서

```
1단계  실측     코드 대입 실패 집합 확정        재생성 없음
2단계  검사     그 집합을 채점표로 검사 추가    재생성 없음
3단계  규칙     규칙 넷 다시 쓰기               재생성 없음
4단계  재생성   전건 재생성 후 대조             비쌈
```

**1·2단계에서 규칙을 건드리지 않는 이유**는 직전 회차와 같다. 계획서가 안 바뀐 상태에서
검사가 발화하면 그것은 **검사가 일한 것**이다. 규칙을 같이 바꾸면 그 구별이 사라진다.

**3단계도 재생성 없이 끝난다.** 규칙을 고쳐도 기존 산출물은 옛 규칙 그대로이므로, 규칙
변경 자체는 안전하게 커밋하고 검증할 수 있다.

### 4-1. 정지 조건

- **1단계**: 「정당한 미대입」이 하나라도 나오면 멈춘다(§3-4)

  이 회차에서 **코퍼스 일치조차 판정을 보증하지 않는 것이 네 번** 드러났다. **판정마다
  변이를 넣는다**(조건마다가 아니라)

## 5. 4단계의 성공 기준 — 원래 목표에 답하는 자리

재생성 후 무엇을 보는지가 정해져야 한다. 셀 수 있는 것 셋이다.

| 무엇 | 지금 | 규칙이 옳다면 |
|---|---|---|
| **신규 SP 정의 수** | 0~18로 흩어짐 | **전부 0으로 수렴** |
| 결속 실패 | 14/20 | 줄어야 함 |
| 코드 대입 실패 | ~~1단계가 확정~~ → **진짜 결손 2건**(아래 정정) | **손으로 잰다. L1 기계 강제 없음** |

**첫째가 핵심이다.** 새 규칙이 "신규 저장 프로시저를 만들지 않는다"이므로 **SP 정의 수가
0으로 수렴하지 않으면 규칙이 안 먹은 것**이다.

**C# 모양(`StepResult` vs `TaskletResult` 등)은 수렴하지 않는다** — §1의 결정대로 API를
정하지 않으므로. 이는 실패가 아니라 **의도된 결과**다.

> **[2026-08-27 실행 정정] 셋째 행은 기계가 재 주지 않는다.**
>
> 앞의 두 행(신규 SP 정의 수 · 결속 실패)은 L1이 잰다. **셋째 행만 재는 검사가 없다** —
> 대입 도달성 검사는 만들지 않기로 결정됐다(§3 머리의 상자). 이 표를 "기계가 다 재 준다"로
> 읽지 말 것.
>
> **재는 방법**: 1단계가 쓴 **프로브를 다시 돌린다.** 그 방식(`Steps[].ErrorCodes`를
> `agent/steps/<Code>.md` 본문과 대조하는 절차)과 정본 수치는 측정 보고서
> `docs/audit-reports/sweeps/2026-08-27-error-code-reach-sweep.md`에 있다. 그때도 **「등장」이
> 아니라 「대입」으로 재야 한다**(§3-1) — 「등장」으로 재면 재생성 전후가 똑같이 100%라
> 아무것도 안 보인다.
>
> ⚠️ **비교 대상은 「진짜 결손 2건」이지 151개가 아니다.** 151개 중 **정당한 미대입 62건은
> 재생성 뒤에도 여전히 정당할 가능성이 높다.** 그 62건의 원인은 `Steps[].ErrorCodes`가 통합

## 6. 재생성 안전 절차

`InstructionBundleWriter`가 **하위 트리를 통째로 지우는 경로 둘**을 갖는다(실물 확인).

3. **한 Job으로 먼저 돌려 비용과 동작을 잰다** — 20개를 한 번에 돌리기 전에

### 9-3. 회귀 — `GOTO` 금지를 3단계가 지웠다

§8-1의 표에서 규칙 6-1의 「`TRY...CATCH`·`GOTO` 조항 제거」가 그것이다. 근거는
"C# 예외 처리로 자동 대체된다"였고, 같은 회차에 채점 기준의
`..._ForbidsGotoErrorBranching`도 신규 SP 검사로 갈아 끼웠다. 그래서 **규칙에도 채점에도
명시 조항이 하나도 남지 않았다.** 모델은 여전히 T-SQL 스크립트를 쓰고 있었으므로 전제가
성립하지 않았고, `IF @@ERROR <> 0 GOTO ERR_HANDLER`가 21번 돌아왔다.

> **정정 — Critic은 눈이 멀지 않았다.** 처음 이 절을 쓸 때는 「아무도 안 보고 있었다」로
