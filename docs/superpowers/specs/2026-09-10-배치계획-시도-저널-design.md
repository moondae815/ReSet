# 배치 계획서의 시도를 디스크에 남긴다 — 1단계 설계

작성일 2026-09-10 · 기준 커밋 `1bc33ada` (main)
**코드는 안 만졌다 — 이 문서는 착수 전 설계다.**

계기: 사용자 질문 「통합 배치 계획서 생성 시 결함으로 회차가 넘어갈 때, 결함이 있더라도
문서와 피드백이 저장되는가」 → 판독 결과 **「목차 말고는 아니오」** → 「그러면 API 오류나
구독 쿼터 소진으로 중단됐을 때 나중에 이어서 재시도하고 싶다」

인접 축: `docs/superpowers/specs/2026-09-09-거부된-시도-코퍼스-design.md` — 같은 문제의
옆면(버려진 시도를 재료로 남긴다)이고, 그 관할은 **단일 SP 경로뿐**이다. 이 설계는 배치
계획 경로를 맡되 목적이 다르다(그쪽은 검사 코퍼스, 이쪽은 재개).

> **[인용 규칙]** 코드는 **심볼로** 인용한다. 행 번호를 쓰지 않는다 — `2026-09-09` 설계가
> `StepValidationResult` 의 행 번호가 **세 커밋 연속** 무효가 되고 그때마다 인용 고치기를
> 두 번 빠뜨린 것을 기록했다. 심볼은 안 밀린다.

## 1. 판독 — 지금 무엇을 잃는가

### 1-1. 회차가 넘어갈 때 디스크로 나가는 것은 목차뿐

`VerificationPipelineOrchestrator.RunConsolidatedPipelineAsync` 의 재시도 루프를 읽었다.

| 무엇 | 회차 중 저장되나 | 사는 곳 |
| :--- | :--- | :--- |
| 계획서 본문 | **아니오** | `BestAttempt` — 최고점 후보 **하나만** |
| Critic 피드백 | **아니오** | `feedbackHistory` (`List<string>`) |
| 단계 섹션 | **아니오** | `lastStepSections` |
| 골격 | **아니오** | `lastSkeleton` |
| 목차 | **예** | `raw/PlanStructure.md`, 재작성 시 `PlanStructure.superseded-N.md` |
| 채택 회차의 사고·프롬프트 | 최종 저장 시에만 | `docs/Thinking.md`·`raw/prompt-context.md` |

L1 실패 갈래도 L2 결함 갈래도 그 회차의 본문을 파일로 쓰지 않고 `continue` 한다.
피드백은 `CriticFeedbackLog.MaxRetainedRounds` 가 3이라 **4회차부터는 앞 회차가 조용히
밀려 나간다** — 메모리 안에서도 전부 살아 있지 않다.

### 1-2. 최종에는 결함이 있어도 저장된다

재시도가 소진되면 `RetryRescue.TryRescue` 가 최고점 회차를 채택하고(`QualityRejected`),
후보가 없으면 마지막 판을 `VerificationBanner.L1Exhausted` 와 함께 그대로 쓴다. CLI 는
`Plan` 이 비어 있지만 않으면 무조건 `docs/BatchMigrationPlan.md` 에 쓴다.

실물 근거: `output/Jobs/POQSettleBatch1`·`POQSettleBatch4` 의 계획서가 `검증 상태: 품질 미달`
(46/100)로 저장돼 있고 Critic 피드백 전문이 `[!CAUTION]` 배너에 실려 있다.

**그러니 잃는 것은 「버려진 회차」뿐이다. 그런데 중단은 정확히 그 자리에서 난다.**

### 1-3. 쿼터 소진의 실제 경로

- `CliFailureKind.QuotaExhausted` 라는 분류가 **이미 있다**. 그런데 `AiRetryPolicy.Classify`
  는 CLI 예외 중 `Timeout` 만 `Transient` 로 보고 나머지를 전부 `Fatal` 로 둔다 — 쿼터
  소진은 재시도 없이 즉시 포기다.
- HTTP 429 는 `Transient` 지만 `RetryPlan.Default` 가 **2회 시도 · 0.5~1.5초 지연**이다.
  시간 단위로 풀리는 쿼터를 그 지연으로 넘을 수는 없다.
- 그 뒤 생성 실패 갈래가 `RetryRescue.TryRescue` 를 부르는데, **1회차가 L1 에서 죽었으면
  채점을 못 받아 `BestAttempt.Current` 가 `null`** 이라 구제가 없다. 파이프라인은
  `ConsolidatedPipelineResult(null, …)` 를 반환하고 CLI 는 「중단되었거나 실패」만 찍는다.

**최악은 「1회차 L1 실패 → 2회차 도중 쿼터 소진」이고, 그때 잃는 것은 단계 16~18개의
생성 비용 전부다.**

## 2. 무엇을 만드는가

**1단계는 쓰기만 한다.** 읽는 쪽(재개)은 2단계에서 만든다.

- **1순위 독자**: 2단계 재개 도구. 감사·코퍼스는 부산물로 얻되 포맷을 정하지 않는다.
- **범위**: 단계 섹션 + 골격 + 회차별 리뷰(점수·피드백·지목).
- **범위에서 뺀 것**: 회차별 계획서 본문 사본. `BatchPlanAssembler.Assemble` 이 골격과
  섹션에서 재조립하므로 중복이고, 회차당 190KB 가까이 쌓인다.

### 왜 피드백이 범위에 드는가

`CriticFeedbackLog` 클래스 주석이 사고를 기록해 두었다 — Actor 는 매번 백지에서 다시
쓰므로, 피드백이 빠진 회차는 **앞 회차에서 이미 정리된 결함을 되살린다**(2026-08-04 실행:
시도 3이 앞서 정리됐던 조인 서술을 「자체조인」으로 되돌렸다). 피드백 없이 재개하면
재개 후 첫 회차가 정확히 그 상태가 된다.

## 3. 이름 — 「회차 파일」은 임자가 있다

이 저장소에서 **「회차 파일」은 지시서 번들의 `task-NN-*.md`** 를 가리킨다
(`ReSet.Cli/Program.cs` 의 번들 판정, `CodegenStage`, `InstructionBundleWriter`).
새 산출물을 그 말로 부르면 두 뜻이 섞인다.

**이 설계는 「시도(attempt)」로 부른다** — 코드의 `attempt` 변수, `BestAttempt`,
`L1AttemptLog` 와 이미 같은 말이다.

## 4. 파일 규약

```
output/Jobs/[Job]/raw/attempts/run-001/
  manifest.json             이 판이 무엇을 전제로 도는가 + 무엇이 언제 쓰였는가
  skeleton.md               골격 — 최신 하나
  steps/S01.md …            단계 섹션 — 코드마다 하나, 최신
  reviews/attempt-01.json   회차별 리뷰 결과
```

`output/` 은 gitignore 다. 이 자료는 로컬 전용이고, 재개가 같은 트리에서 일어나므로
그것으로 충분하다.

### 4-1. 왜 골격·섹션은 회차별이 아니라 「최신 하나」인가

회차 2가 S03 만 다시 만들면 나머지는 회차 1의 것이 그대로 유효하다 — 그게
`lastStepSections` 가 하는 일이고 재개가 복원하려는 것도 그 **누적 최신 상태**다.
회차별로 전부 쌓으면 재개는 어차피 최신만 쓰고 디스크만 붇는다. 무엇이 언제 덮였는지는
`manifest.json` 이 기록한다.

### 4-2. 왜 리뷰는 회차별인가

누적이 아니라 시계열이고, `feedbackHistory` 가 최근 3라운드만 들고 있어서 **디스크가
메모리보다 오래 기억하는 유일한 자리**가 된다(§1-1).

### 4-3. manifest.json

`openedBy` 는 `run-start`·`structure-redraft`·`rescue-adopt` 셋 중 하나다(§5). 재개 판정에는 목차 해시만
쓰이므로 필수가 아니지만, **감사에서 「이 판이 왜 생겼나」를 묻는 자리가 여기밖에 없고
1단계에 안 넣으면 나중에 만들 수 없다.**

```json
{
  "SchemaVersion": 1,
  "Run": 1,
  "Job": "POQSettleBatch5",
  "StartedAt": "2026-09-10T14:03:11+09:00",
  "OpenedBy": "run-start",
  "ReuseKey": {
    "ContractVersion": 1,
    "PlanStructureSha256": "…",
    "SpecsSha256": "…",
    "Provider": "OpenRouter",
    "Model": "tencent/hy4-preview",
    "Effort": "high",
    "TargetLanguage": "C#"
  },
  "Skeleton": { "Attempt": 2, "Sha256": "…" },
  "Steps": { "S01": { "Attempt": 1, "Sha256": "…" } }
}
```

> **[정정 2026-09-10 — Task 1 리뷰 발견]** 이 예시의 첫 판은 키를 camelCase 로 적었는데
> 실제 직렬화는 **PascalCase** 다(`JsonSerializerOptions` 에 `PropertyNamingPolicy` 를
> 두지 않는다). `L1AttemptLog` 가 「언제나 PascalCase 로 직렬화」를 계약으로 못박고
> 그 클래스를 이 설계가 본보기로 삼았으므로 실물이 옳고 예시가 틀렸다. **키의 대소문자는
> 계약이다** — `L1AttemptLog.Read` 가 camelCase 파일을 예외 없이 `Attempt=0` 으로 조용히
> 읽는 사고를 이미 겪었고, 2단계가 이 파일을 읽을 때 같은 자리를 만든다.

### 4-4. 기존 도구를 오염시키지 않는다 (실측)

`output` 트리를 재귀로 훑는 자들을 전수 확인했다. `raw/attempts/` 는 어디에도 안 걸린다.

| 훑는 자 | 관할 | 걸리나 |
| :--- | :--- | :--- |
| `LocalVariableTypeContractCorpusTests` | `*.md` 중 `/agent/steps/` 경로만 | 아니오 |
| `AnchorKindOrdinalPairTests` | `Spec.md` 이름 지정 | 아니오 |
| `FileMappingService` | `BatchMigrationPlan.md` 이름 지정 | 아니오 |
| `ArtifactChangeDetector` | 코딩 에이전트 작업 디렉터리 | 아니오 |
| `InstructionBundleWriter` | `agent/` 아래 | 아니오 |

## 5. 판 경계 — 판이 열리는 계기는 셋

1. **실행 시작**
2. **목차 재작성** (`StructureRedraftPolicy` 가 발동해 `WritePlanStructureFilesAsync` 가
   도는 그 자리)
3. **구제 채택이 재설계 이전 목차로 되돌아갈 때** (`AdoptPlanStructureForRescueAsync`,
   [정정 2026-09-10 — 최종 리뷰 Critical] 아래 참고)

### 왜 목차 재작성이 새 판을 여는가

목차가 바뀌면 기존 섹션은 전부 무효다 — `ClearSplitGenerationCacheAfterRedraft` 가
인메모리에서 하는 그 일이다. 이걸 「manifest 에서 steps 를 지운다」로 표현하면 삭제 로직과
그 실패 경로가 생기지만, **판을 새로 열면 무효화가 디렉터리 전환으로 표현되어 지울 것이
없다.**

부수 효과로 `run-NNN` 이 `PlanStructure.superseded-N.md` 와 대응하고, 판 하나가 곧 「목차
하나에 대한 작업」이 된다. 2단계의 판 고르기는 「지금 목차 해시와 같은 최신 판」으로 끝난다.

### 왜 구제 채택도 새 판을 여는가

> **[정정 2026-09-10 — 최종 전체 브랜치 리뷰 Critical]** 이 절의 첫 판은 계기를 둘로
> 적었다. 재수립 이후 회귀 롤백·예산 소진 구제(다섯 자리, `AdoptPlanStructureForRescueAsync`
> 의 호출부 문서 참고)가 재설계 이전 목차로 되돌아갈 때도 `TryCommitPlanStructureAsync` 를
> 거쳐 `OpenRun` 을 부른다는 사실을 빠뜨렸다 — 목차 재작성과 코드 경로를 공유하므로
> 계기 자체를 놓쳤다.
>
> 되돌아가는 목차의 해시가 이미 있는 더 오래된 판(재료가 있다)과 같더라도 그 판을 다시
> 열지 않는 이유는 「판 하나는 목차 하나에 대한 작업」을 지키기 위해서다 — 옛 판을
> 다시 열면 그 판이 실제로 끝난 시각이 거짓이 된다. 그런데 판만 새로 열고 재료를
> 다시 적지 않으면 그 판은 비어 있다 — `RestoreAdoptedGenerationState` 가 골격·섹션을
> 복원하는 자리는 메모리(살아있는 지역 변수)뿐이기 때문이다. 그래서
> `AdoptPlanStructureForRescueAsync` 는 판을 연 직후 `adopted`(교체 직전에 붙잡아 둔
> `AdoptedGenerationState`)가 이미 들고 있는 골격·섹션을 그 자리에서 곧바로 다시
> 적는다 — 그 재료를 실제로 만든 시도 번호(`AdoptedGenerationState.Attempt`)를 함께
> 실어, `PlanAttemptArtifact.Attempt` 가 이 판을 연 시도(구제가 일어난 시도)가 아니라
> 본문을 만든 시도를 가리키게 한다.

### 왜 판 번호를 유도하지 않는가

`L1AttemptLog.ResolveRun` 은 「판 번호를 넘겨줄 자리가 **없다**」며 시도 번호의 단조성에서
판 경계를 유도하고, 그 클래스 주석이 스스로 취약하다고 적어 두었다. 새로 만드는 쪽은 그걸
반복할 이유가 없다 — **디렉터리가 곧 판 경계다.**

## 6. 재사용 키 — 1단계는 쓰기만 하고 판정하지 않는다

넉넉히 적어 두면 2단계가 엄격도를 자유롭게 고를 수 있다. 반대로 **지금 빠뜨린 항목은
그때 만들 수 없다.**

| 항목 | 왜 | 빠뜨리면 |
| :--- | :--- | :--- |
| `planStructureSha256` | 목차가 바뀌면 섹션 전부 무효 | 옛 목차 기준 섹션이 새 목차 문서에 섞인다 |
| `specsSha256` | 원본 명세서가 바뀌면 무효 | 없어진 SP 의 섹션이 살아남는다 |
| `provider`·`model`·`effort` | 모델이 바뀌면 섞이면 안 된다 | 출처가 다른 문장이 한 문서에 든다 |
| `targetLanguage` | 대상 언어가 계약이다 | — |
| `contractVersion` | 프롬프트·규약이 바뀌면 옛 섹션이 새 규약을 안 지킨다 | **나중에 만들 수 없다** |

`contractVersion` 은 **사람이 올리는 상수**다. 규율에 기대는 약한 장치이므로 그물을 하나
더 둔다: **재사용한 섹션도 문서 전체 L1 을 다시 통과해야 한다**(§11). 안 올리고 지나가도
L1 이 잡을 기회가 남는다.

## 7. 배선 자리 넷

| 무엇 | 어디 | 왜 거기 |
| :--- | :--- | :--- |
| 판 열기 | `RunConsolidatedPipelineAsync` — 목차 확정 직후 | 목차 해시가 판의 정체라 그 전엔 열 수 없다 |
| 골격 | `GenerateBySplitAsync` 안, `GenerateSkeletonWithGuardAsync` 가 돌려준 골격이 확정된 직후 | 그 메서드가 앵커 상실 재시도까지 마치고 채택을 끝낸 자리다 |
| 단계 섹션 | `GenerateBySplitAsync` 의 로컬 함수 `RunStepAsync` 반환 직전 | 병합 루프는 `Task.WhenAll` 뒤라 **회차 도중 죽는 경우를 못 건진다** |
| 단계 섹션(하한 재시도) | `GenerateStepSectionWithFloorRetryAsync` — 하한 미달로 다음 시도에 넘어가기 직전 | **[2026-09-10 추가]** 아래 참조 |
| 리뷰 | `EnforceScoreThreshold` 직후, `BestAttempt.TryRecord` 앞 | 이 회차의 채점이 확정되는 유일한 지점 — 축 게이트가 `HasDefects` 를 덮은 뒤라 `AxisThresholdForced` 까지 확정된 값이 남는다 |

> **[다섯째 자리를 더한다 — 2026-09-10, Task 4 구현 중 발견]** 이 표의 첫 판은 넷이었다.
> 구현이 드러낸 것: 단계 본문의 재시도는 **두 층**이다. 외부 `attempt` 루프와,
> `GenerateStepSectionWithFloorRetryAsync` 안의 **하한 재시도 루프**(`maxTries=5`, 같은
> `attempt` 안)다. 표가 지정한 `RunStepAsync` 반환 직전은 **하한 재시도가 끝난 뒤**라,
> 하한 재시도 도중에 중단되면 그때까지 뽑은 본문이 하나도 안 남는다 — 쿼터 소진이
> 정확히 그 자리에서 날 수 있다.
>
> 그래서 하한 미달로 다음 시도에 넘어가기 직전에도 한 번 기록한다. 같은 단계 코드를
> 덮으므로 §4-1 의 「최신 하나」와 어긋나지 않고, 중단되지 않으면 마지막에 건강한 본문이
> 덮는다. 중단돼 하한 미달 본문이 최신으로 남더라도 2단계가 재사용할 때 **문서 전체
> L1 을 다시 통과해야 하므로**(§11-2) 그물이 받는다. 되돌림으로 실효성을 확인했다 —
> 이 자리를 지우면 그 시험의 핵심 단언이 빨개진다.
>
> **이 발견이 드러낸 더 큰 것**: 「회차」라는 말이 이 파이프라인에서 **두 가지**를 가리킨다.
> §9(b)가 「본체」로 지정한 시험은 **외부 `attempt` 루프**를 뜻하는데, Task 4 의 첫 구현은
> 하한 재시도 루프를 태우고도 그것을 회차 전환으로 읽었다. 시험을 쓸 때 **`attempt` 가
> 실제로 2 에 닿았는지를 단언하라** — 호출 횟수가 늘었다는 것은 회차가 넘어갔다는 증거가
> 아니다.

### 전달

`GenerateBySplitAsync` 에 **인자 하나 추가**(`PlanAttemptJournal? store`). 호출부는 둘(최초
생성 · L3 피드백 재생성)이고, `RunStepAsync` 가 로컬 함수라 클로저로 잡는다.

이미 인자가 스물 넘는 메서드에 하나 더 붙이는 것이 마음에 걸리지만, 대안(오케스트레이터
필드에 실행 상태를 두기)은 재진입 위험을 들이는 쪽이라 더 나쁘다. `null` 이면 아무것도 안
쓰므로 기존 테스트가 그대로 돈다.

L3 재생성 경로도 같은 인자를 받아 자동으로 기록된다. 재개 가치가 낮은 경로지만, **거기서
섹션이 갱신되는데 manifest 가 모르면 manifest 가 거짓말을 한다.**

### 왜 전용 클래스인가

`L1AttemptLog`(78줄)와 `AgentProgressStore` 가 이미 이 모양의 선례다. 경로 규약·직렬화·
소프트페일을 한 클래스가 소유하면 임시 디렉터리로 단위 테스트가 되고, 2단계에서 읽는 쪽이
생길 때 `Read` 가 같은 클래스에 들어가 규약이 갈라지지 않는다.

`CacheManager` 확장은 **기각한다.** 키 체계가 다르고(SP 단위 `compositeHash`), 더 중요하게는
**캐시와 재개는 무효화를 틀렸을 때의 대가가 다르다** — 캐시는 틀려도 성능만 손해지만 재개가
틀리면 다른 목차 기준의 섹션이 문서에 섞여 나간다. 한 클래스에 두면 그 구분이 흐려진다.

## 8. 실패 처리 — 진실은 manifest 다

- 개별 쓰기 실패는 `Log.Debug` 를 남기고 계속한다. **관측이 파이프라인을 죽이면 안 된다**
  (`L1AttemptLog` 가 세운 규칙, `MechanicalValidator.Validate` 의 소프트 패스와 같은 이유).
- **판 열기가 실패하면 store 를 `null` 로 두고 그 실행 내내 조용하다.** 경고는 한 번만 —
  매 단계마다 실패 로그를 쏟으면 진짜 신호를 덮는다.
- `manifest.json` 갱신은 **lock + 원자적 쓰기**(임시 파일 → `File.Move(overwrite: true)`).
  동시 생성이 최대 `StepConcurrency`(기본 4)라 경합은 작지만, 잃어버린 갱신이 나면
  「섹션 파일은 있는데 manifest 가 모른다」가 된다.
- **단계 코드는 파일명으로 검증하고 쓴다.** `BatchStepPlanParser` 는 `Code` 의 빈 값과
  중복만 보고 **파일명 안전성은 보지 않는다** — 그 값은 모델이 목차에 채운 것이다.
  경로 구분자·`..`·예약 이름이 섞이면 그 단계의 기록만 건너뛰고 로그를 남긴다(판 전체를
  버리지 않는다). 판정은 store 안에 두어 호출부가 몰라도 되게 한다.
- **2단계가 지킬 계약을 지금 못 박는다: `manifest.json` 의 `steps` 목록이 진실이고,
  디렉터리에 파일이 있다는 것만으로 신뢰하지 않는다.** 반쯤 쓰인 판이 나중에 거짓 재료가
  되는 것을 막는 유일한 장치다.

## 9. 검증

**(a) `PlanAttemptJournalTests`** — 임시 디렉터리 단위 테스트. 판 번호 증가, 원자적 쓰기,
병렬 쓰기 N개 뒤 manifest 에 N개가 다 남는지(잃어버린 갱신), 쓰기 불가 디렉터리에서 소프트페일.

**(b) 오케스트레이터 통합 테스트 — 이것이 본체다.** 가짜 AI 로 *1회차 L1 실패 → 2회차 진입*
을 만들고, **2회차가 시작된 시점에** `steps/*.md` 와 `reviews/attempt-01.json` 이 이미
디스크에 있는지 본다. 사용자가 물은 것이 정확히 이 질문이고 지금 답이 「아니오」인 자리다.
기존 `VerificationPipelineOrchestratorTests` 에 붙는다.

**(c) 되돌림 확인** — 쓰기 호출을 지웠을 때 (b)가 **실제로 빨개지는지** 손으로 확인하고
결과를 기록한다. 테스트 코드가 아니라 실행 절차라 구현 계획의 한 단계로 넣는다.
이 저장소는 「발화를 재는 자와 배선을 재는 자는 다른 축」이라 되돌림 없이 초록을 믿었다가
세 번 데였다.

### 배선 잠금 정책 테스트는 만들지 않는다

`L1AttemptLogWiringPolicyTests` 가 필요했던 이유는 **그쪽 코퍼스가 커밋된 픽스처라 배선을
통째로 지워도 4,045개가 전부 초록**이었기 때문이다(그 클래스 주석의 실측). 여기는 (b)가
실동작을 직접 관찰하므로 같은 사각지대가 없다. 나중에 (b)를 픽스처 기반으로 바꾸는 변경이
들어온다면 그때 이 문단을 다시 읽고 잠금을 세워라.

## 10. 범위 밖

- **L1 발화 기록(`raw/l1-attempts.json`)의 배치 경로 확장.** `L1AttemptLogWiringPolicyTests`
  가 `Append` 호출을 **정확히 하나로 잠가** 두었고, `2026-09-09` 설계는 넓히려면
  `StepValidationResult` 에 `Firings`/`Report` 를 놓는 것과 배선을 **한 커밋에서 같이** 해야
  한다고 못박았다(하나만 하면 「값은 채워지는데 아무도 안 읽는 자리」가 생겨 거짓 신호만
  남는다). 재개에 불필요하고 반경이 크다 — **별도 작업.**
- **읽기·재개 자체.** 2단계.
- **`QuotaExhausted` 를 `AiRetryPolicy` 의 제3 판정으로 빼는 것.** §1-3이 드러낸 실제
  결함이지만 이 설계의 관할이 아니다. 2단계에서 「이어서 하려면 이 명령」을 안내할 자리와
  함께 다루는 것이 맞다 — **별도 작업으로 적어 둔다.**

## 11. 2단계가 지킬 계약 (미리 적어 둔다)

1. **`manifest.json` 의 `steps` 가 진실이다.** 파일 존재만으로 재사용하지 않는다.
2. **재사용한 섹션도 문서 전체 L1 을 다시 통과해야 한다.** 「재사용했으니 검사 생략」이라는
   지름길을 만들지 마라 — `contractVersion` 이 사람 규율에 기대는 것을 이 그물이 받친다.
3. **판 고르기는 「지금 목차 해시와 같은 최신 판」이다.** 해시가 다르면 새 판을 판다.
4. **재개는 이전 판을 이어 쓰지 않고 새 판을 파되 이전 판에서 섹션을 읽어 온다.** 각 판은
   자기가 한 일만 기록한다.
5. **골격·섹션이 모두 없는 판(`skeleton.md` 부재이고 `steps/` 가 비었거나 없는 판)은
   재개 불가로 판정한다.** [정정 2026-09-10 — 최종 전체 브랜치 리뷰 Important 1]
   `BatchStepPlanParser.TryParse` 가 실패해 단일 호출 폴백(`GenerateConsolidatedBatchPlanAsync`)
   으로 가는 경로는 골격도 섹션도 없어 그 판에 본문이 전혀 남지 않는다 — `manifest.json`
   과 `reviews/attempt-NN.json` 만 있고 재조립할 재료가 없다. §2 가 본문 사본을 뺀 근거
   (「`BatchPlanAssembler.Assemble` 이 골격·섹션에서 재조립하므로 중복」)는 이 경로에는
   성립하지 않는다 — 이 경로는 **알려진 공백으로 남긴다**(사람 결정, 코드는 안 고친다).
   2단계는 이 조건으로 그 판을 걸러야 한다.
