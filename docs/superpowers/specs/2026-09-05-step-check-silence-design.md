**① 검사는 판별력이 있다.** 되돌린 판에서 7건 발화하고 현행 판에서 0건이다. 판정이 갈린다 —

**② 진짜 사각지대는 토큰 0인 27건(52%)이다.** 판정 규칙은 이렇다.

```csharp

if (tokens.Count == 0) continue;                                   // ← 27건이 여기서 나간다
if (tokens.Any(token => ContainsToken(stepMarkdown, token))) continue;
```

`DistinctiveExpressionTokens`(8162행)가 보는 것은 셋뿐이다 — 인용 리터럴(2자 이상), `UF_*`,
2자리 이상 숫자. 순수 컬럼 산술(`CLCOMM * (-1)`, `A.CLTOTAL - A.CLCOMM`)은 토큰이 0이라
**구조적으로 못 본다.** 갱신 52개 중 27개가 여기 있다.

**③ 검사 D는 재료가 통째로 없다.** 코퍼스 명세서에서 `### 지역 변수`를 세었다.

그 하나는 reset-ab 가 오늘 12:27 에 재생성해서 생겼다 — 그 전에는 0/14 였다

재생성 하나가 검사 D를 **0 → 9**로 켰다(reset-ab 실측). **재료 부재가 원인이라는 것의 직접 증거다.**

## 3. 설계 — 세 갈래, 순서 고정

**순서는 A-3 → A-2 → A-1이다.** A-1(재생성)이 마지막인 이유는 §5에 있다.

### A-3. `OmissionCommentScanner`의 판별자를 교체한다

```csharp
// OmissionCommentScanner.cs:36-38
// "유지하라/보존하라"는 생략 지시가 아니라 보존 지시다.
private static readonly string[] PreservationMarkers = { "유지한다", "보존한다", ... };
```

감사가 S07 🔴에 적은 판정문이 이것이다 — *"S07.md:353이 산문으로 **'원본대로 유지한다'**고만 적는다."*
**코퍼스 최악의 결함을 나르던 문구가 화이트리스트에 있다.**

화이트리스트의 원래 취지는 옳다(원본 로직을 지키라는 요구를 결함으로 들면 배너의 변별력이 사라진다).
틀린 것은 **판별 기준**이다. 문구가 무엇인지가 아니라 **그 주석이 선 자리에 실행 가능한 SQL이 있는가**로
판정을 옮긴다.

### A-2. 판별 토큰 없는 27건을 보게 한다

**이 갈래는 규칙을 미리 못 박지 않는다.** 후보를 정하고, 두 판에 돌려 재고, 그 표로 고른다.

`DistinctiveExpressionTokens`에 보탤 후보:

| 후보 | 예 | 오탐 위험 |
| :--- | :--- | :--- |
| `별칭.컬럼` 참조 쌍 | `B.TXAMT` · `A.ALLOTPERIOD` | **높음** — 단계 문서 어디에나 나온다 |
| 구조 토큰 | `CAST(… AS INT)` · `ISNULL(` · `IIF(` | 중간 |
| 부호 반전 | `* (-1)` · `* -1` | 낮음 |

**넓히기 전에 오탐을 재야 한다.** 컬럼명은 `any` 규칙과 결합하면 오히려 침묵을 늘릴 수 있다 —
현행 규칙이 「토큰 하나라도 있으면 통과」이므로, 흔한 토큰을 보태면 발화가 **줄어든다**.
그래서 후보마다 결함 판 발화 증가와 현행 판 오탐 증가를 **따로** 재고, 규칙(`any` 유지 / `all` / 과반)도
같은 표에서 함께 고른다.

### A-1. 재료 없는 검사에 재료를 준다 (별도 승인 필요)

남은 13개 SP 명세서를 재생성해 「지역 변수 표」를 채운다. `dbo.UP_UTIL_SETTLE_PROC_ETC`는
reset-ab가 이미 했으므로 제외한다.

**재생성은 이 설계의 부산물이 아니라 검증 대상이다.** 다만 그 위험을 **재료 단위로** 재야 한다.
PROC_ETC 전후를 두 단위로 판독한 결과가 갈렸다.

**헤딩 단위 — 갈라지는 것처럼 보인다**

전에만 있는 헤딩 14 · 후에만 있는 헤딩 10. 그러나 그중 여럿이 **개명**이다.

| 전 | 후 |
| :--- | :--- |
| `### SELECT 대상 테이블` | `### SELECT 조회 테이블` |
| `### 비실행 조건 (주석 처리된 원본 조건)` | `### 원본 주석 전문 기록 (비실행 주석 건)` |
| `### 반환값 규약` | `### 반환값(@po_intRetVal) 매핑 정리` |

**절 이름은 모델 재량이다.** 13개 × 모델 재량이면 대조표가 개명으로 가득 찬다.
**헤딩 단위 대조는 오탐을 낸다 — 쓰지 않는다.**

**재료 단위 — 손실이 0이다**

추출기가 실제로 먹는 것은 산문 절이 아니라 **기계 확정 표**(헤딩이 `(기계 확정 — 수정 금지)`로 끝나는 것)다.

| | 전 | 후 |
| :--- | ---: | ---: |
| DML 범위 · 변수 대입 · 실행 의미 · 잠금 힌트 · 집합 술어 · 트랜잭션 경계 | 각 1 | 각 1 |
| **지역 변수** (검사 D 재료) | 0 | **1** ✔ |
| 세션 옵션 앵커 `NOCOUNT` (표가 아니라 이름 자체가 앵커 — `MechanicalValidator.cs:3230`) | 2 | 1 (**살아 있음**) |
| 크기 | 24,640B | **30,550B (+24%)** · 289 → 332행 |

**전에 있던 여섯이 전부 그대로이고 지역 변수만 늘었다. 재료 손실 0이다.**

> **정정 기록.** 이 설계서의 초안은 「절 여덟이 사라졌고 크기가 −15%」라고 적었다. 크기는 단위 오류였다 —
> 전을 `wc -c`(바이트)로, 후를 문자 수로 재어 한글 3바이트가 사라졌다. 실제로는 늘었다.
> 「사라진 절」은 개명과 산문 절이었고 재료는 하나도 잃지 않았다. reset-ab가 재료 단위 재측정으로 반박했고
> 그 반박이 옳다. **이 자리를 남기는 이유**: 헤딩을 세는 것과 재료를 세는 것이 반대 결론을 낸다는 사실 자체가
> A-1 합격 조건의 근거다.

**그럼에도 이 검사는 필요하다.** 「검사 하나를 켜면서 다른 검사의 재료를 조용히 걷어내는 것」은
이 저장소가 검사 D 18→0으로 이미 한 번 당한 자리다(`2026-08-29-local-variable-table-enforcement-design.md`).
PROC_ETC 한 표본이 깨끗했다는 것이 13개가 깨끗하다는 뜻은 아니다.

## 4. 검증 계약 — 모든 갈래 공통

발화 수와 통과 수는 활동이지 효력이 아니다. 각 갈래의 합격은 **두 판에서 판정이 갈리는 것**으로 정의한다.

| 오라클 | 경로 | 기대 |
| :--- | :--- | :--- |
| 결함 판 | `output.bak-batch1-preregen-20260904/Jobs/POQSettleBatch1/` | **발화한다** |
| 현행 판 | `output/Jobs/POQSettleBatch1/docs/BatchMigrationPlan.md` | **오탐 0** |

**이 두 판이 이 설계서의 고정 오라클이다.** 둘 다 Jobs 트리라 `--sp` 재생성의 영향을 받지 않는다.

A-1의 합격 조건은 여기에 셋을 더한다.

1. **재료 단위 전후 대조** — 재생성 전 스냅샷을 남기고 **세 가지를 잰다.** 절 이름은 모델 재량이라 헤딩 대조는 개명에 오탐하므로 쓰지 않는다(§3 A-1).
   1. **기계 확정 표의 전후 개수** — 헤딩이 `(기계 확정 — 수정 금지)`로 끝나는 표. 정본은 `*Extractor.cs`의 헤딩 리터럴이다.
   2. **앵커 토큰의 전후 개수** — 표가 아닌 재료. 원본 DDL에서 뽑은 이름이 명세서에 몇 번 나오는지(예: 세션 옵션의 `NOCOUNT`).
   3. **`--sweep`의 「재료 분모」 절**(`StepSweepReportWriter.cs:337`) — 재료마다 「원본 DDL 사실 수 대 명세서 행 수」를 이미 센다. 13개 전후로 이 절만 맞대면 재료 손실이 한 표에 나온다. **셋 중 가장 싸고 절 이름에 안 흔들린다 — 이것을 주 계기로 쓴다.** reset-ab의 PROC_ETC 회차에서 `LocalVariables`가 **69·0 → 12**로 움직였고 「소실 프로시저」 목록에서 PROC_ETC가 빠졌다.
2. **카나리아** — 객체마다 **기계 표가 문서의 첫 변수 헤딩인지** 확인한다. `ReadLocalVariables`는 `ReadTable(lines, predicate)`로 먼저 나오는 헤딩 하나만 잡고(`SpecStatementFactsExtractor.cs:285-291`), 후보에 `### 지역 변수`와 `### 내부 변수`가 **둘 다** 있다. 모델이 자기 변수 표를 기계 표 앞에 쓰면 **L1은 초록인데 검사 D만 침묵한다.** PROC_ETC는 깨끗하다(48행 하나). 실물 위험 사례는 `output/Functions/dbo.UF_GET_OUTYMD4REFUND/docs/Spec.md:62`의 `### 내부 변수`인데, 그것은 Function이라 이 13개 밖이다.
3. **종료 상태 확인** — 재생성이 「통과하는 명세서」를 내주지 않는다. PROC_ETC는 6회 전부 통과하지 못해 3차(96점)를 구제 채택했고 헤더에 `검증 상태: 품질 미달`이 찍혔다. **채택본이 마지막 회차가 아니므로 마지막 L2 지적은 반영되어 있지 않다.** 객체마다 `검증 상태`와 몇 차가 채택됐는지를 확인한다.

## 5. 순서 제약 — 재생성을 가운데 두고 걸치지 않는다

§4의 두 판을 **직접 판독**하는 것은 Jobs 트리끼리라 재생성 영향이 없다.
**그러나 A-2에서 스윕으로 오탐을 재면 그것은 다르다** — 스윕은 Jobs를 **Specs라는 오라클에 대고** 잰다.
13개를 재생성하면 그 오라클이 통째로 바뀐다.

**따라서 A-2의 측정을 재생성 전에 끝낸다.** 「없앴을 때로 판정한다」는 입력이 고정이어야 성립한다.

재생성 후에 스윕을 다시 뜨려면 **새 기준선**을 뜬다. reset-ab의 현재 기준선(`33222fcb`)은
A 18 · B 27 · C 20 · D 9 · E 56 · 미분류 1095이며, **D의 9는 전부 `POQSettleProc14`이고 Batch1이 아니다** —
Batch1의 해당 단계는 축 B 로드맵 5가 의사코드로 바꿔 놓아 볼 `DECLARE`가 없어 검사 D가 도달하지 못한다.
**재생성 뒤 Batch1에서 검사 D 발화를 기대하면 안 된다.**

## 6. 범위 밖 — 열린 항목으로 남긴다

**B(채점 축 분할).** `ReviewConsolidatedPlanAsync` 한 호출이 명세서 481KB + 계획서 263KB를 읽고
