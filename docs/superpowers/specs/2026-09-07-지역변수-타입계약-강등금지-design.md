## 1. 무엇을 없애는가

**F1′ — 타입이 걸린 상수가 방출 SQL 의 `DECLARE` 가 아니라 드라이버 바인딩으로 샌다.**

`POQSettleBatch5` 감사가 🔴 로 매긴 둘(S05 · S07)이 이 가족이다. 손해는 금액이다 —
`@v_valIncVat` 가 `DECIMAL(2,1)` 이 아니라 `FLOAT` 으로 묶이면 `CAST(… AS INT)` 의 절사가
달라져 `CLComm`·`CLVT`·`CLTotal`·`POQIncome` 이 어긋난다.

### 1-1. 이것이 모델의 변덕이 아니라 계약의 구멍인 근거

`raw/prompt-context.md:2482` 에 이미 이렇게 실려 있었다.

```
| @v_valIncVat | DECIMAL(2,1) | 1.1 |
```
> `@v_valIncVat`는 라인 408에서 `DECIMAL(2,1) = 1.1`로 선언되며 … 선언 타입이 `DECIMAL(2,1)`
> 이라는 점이 계약이며, 이를 `FLOAT`이나 `MONEY`로 임의 변경하면 나눗셈 결과의 정밀도와
> 이후 `CAST(... AS INT)` 절사 결과가 달라집니다.

**명세서가 위험을 그 단어 그대로 말해줬는데도 스텝 생성이 그 변수를 바인딩으로 강등했다.**
그리고 `POQSettleBatch5/agent/steps/S05.md:71` 이 그 이유를 스스로 적었다.

```

```

**모델은 타입을 알고 있었고 주석에 적었다. 주석은 드라이버에 닿지 않는다.**
정보가 없어서가 아니라 **관용구에 그 정보를 넣을 칸이 없어서** 샌 것이다.

## 3. 계약 — 규칙 `5-1`

규칙 5 는 *A step's interface is exactly the original procedure's parameter list* 다. 새 규칙은
그 형제다 — **5 는 인터페이스에 더하는 것을 막고, 5-1 은 인터페이스로 강등하는 것을 막는다.**

### 3-1. 관할 판별자

`LocalVariableDeclarationFact(Name, DataType, InitialValue)` 가 이미 셋을 내고, 추출기가
**프로시저 파라미터를 이미 제외**한다. 그래서 경계가 저절로 깨끗하다.

| | 관할 | 이유 |
| :--- | :---: | :--- |
| `DECLARE @v_valIncVat DECIMAL(2,1) = 1.1` | **안** | 상수 초기화 — 값도 타입도 컴파일 시점에 정해진다 |
| `DECLARE @v_cnt INT;` (뒤에 `SELECT`/`FETCH` 로 채움) | 밖 | 값이 런타임에 정해진다 |
| `@pi_strYMD` 등 프로시저 파라미터 | 밖 | 추출기가 이미 뺀다 → **바인딩 목록에 남는 것은 정확히 파라미터뿐** |

### 3-2. 프롬프트에 들어갈 문장

> **5-1. [Local Variable Type Contract]** A local variable the source procedure DECLAREs *with an
> initial value* keeps its DECLARE in the SQL this step sends. Write it inside the ```sql block as
> `DECLARE @<name> <declared type> = <initial value>;`, spelled exactly as the machine-derived local
> variable table gives it. Do NOT demote it to a binding parameter of `execute(...)` - the binding
> list carries the original procedure's parameters only (rule 5). A bound value has no declared
> type: the driver picks one, and a `DECIMAL(2,1)` that arrives as `FLOAT` changes what
> `CAST(... AS INT)` truncates. Stating the type in a comment does not pin it.

마지막 문장이 관측된 실패를 그대로 겨냥한다 — `Batch5/S05` 는 타입을 **주석에 적었다.**

## 4. Few-Shot — 생성물이 베낄 본

지금 Few-Shot(`AiService.cs` 2294~2406)의 `DECLARE` 둘(`@v_shadow`·`@v_sql`)은 **신설 인프라
변수**다. 「레거시 지역 변수가 `DECLARE` 로 살아남는」 모양을 **한 번도 보여주지 않는다.**
그래서 대조 한 쌍을 넣는다.

```pseudocode
// 바인딩 목록에는 원본 프로시저의 파라미터만 들어간다 (rule 5-1).
// 레거시 지역 변수의 타입 계약은 SQL 안에 남는다.
execute(SQL_APPLY_RATE, { p_batchDate: batchYmd })
```
```sql
-- SQL_APPLY_RATE
-- (rule 5-1) 원본이 초기값과 함께 선언한 지역 변수는 여기 그대로 남는다.
DECLARE @v_someRate DECIMAL(5,2) = 1.25;
UPDATE ... SET Amt = CAST(Amt / @v_someRate AS INT) WHERE ...;
```

두 가지를 못박는다.

1. **이름과 값을 일부러 코퍼스와 다르게 쓴다**(`@v_someRate`·`1.25`). 실물 `@v_valIncVat`·`1.1`
   을 예시에 쓰면 생성물이 그 리터럴을 아무 데나 베낀다.
2. **틀린 본을 블록 안에 넣지 않는다.** 「이렇게 하지 마라」를 ` ```pseudocode ` 안에 쓰면
   생성물이 그것을 베낀다. 부정 예시는 **블록 밖 산문에만** 둔다.

## 5. L1 검사 — `CheckLocalVariableTypeContract`

### 5-1. 발화 조건은 「`DECLARE` 가 없다」가 **아니다**

T-SQL 에서 리터럴 `1.1` 은 그 자체로 `numeric(2,1)` 이다. 즉 `CAST(CLComm / 1.1 AS INT)` 처럼
**SQL 안에 인라인하는 것은 타입이 안전하다.** 해가 나는 자리는 오직 **드라이버 경계**다.

> **발화 조건.** 원본 DDL 의 「정밀도 있는 수치 타입 · `0` 이 아닌 상수 초기화 · `DECLARE`
> 이후 재대입 없음」 지역 변수에 대해, 그 **초기값 리터럴이 이 단계의 바인딩 목록에 값으로
> 나타나면** 발화한다. **변수 이름은 보지 않는다.**

세 판별자를 모호하지 않게 못박는다.

- **정밀도 있는 수치 타입** — `DataType` 이 `DECIMAL`·`NUMERIC`·`FLOAT`·`REAL`·`MONEY`·
  `SMALLMONEY` 로 시작한다(대소문자 무시).
- **`DECLARE` 이후 재대입 없음** — 같은 DDL 을 ScriptDom 으로 파스해 그 변수를 좌변으로 하는
  `SetVariableStatement` 과 `SelectSetVariable`(즉 `SELECT @x = …`)이 **0 건**이다.
  `LocalVariableDeclarationExtractor` 와 **같은 파스 결과를 쓴다** — 정규식으로 세지 않는다.
- **바인딩 목록** — 단계 본문의 ` ```pseudocode ` 블록에 있는 `execute`·`queryScalar`·
  `queryRow`·`queryList` 호출의 두 번째 인자(중괄호 객체)의 **값 자리**. 키 이름은 보지 않는다.

이름을 안 보는 것이 핵심이다 — `Batch5/S07` 은 `@v_valIncVat` 를 `p_incVat` 으로 개명했다.
**이름 기반 검사는 3 중 2 를 놓친다**(§2-4 에서 실제로 놓쳤다).

정밀도 있는 수치 타입: `DECIMAL` · `NUMERIC` · `FLOAT` · `REAL` · `MONEY` · `SMALLMONEY`.
정수 타입을 뺀 것은 정수는 드라이버가 어떤 정수 타입을 골라도 산술이 같기 때문이고,
동시에 청크 크기(`10000` 같은 `INT` 리터럴) 오탐을 없앤다.

### 5-2. 규칙 ⊃ 검사를 **일부러** 둔다

규칙 5-1 은 `DECLARE` 보존을 요구하고(축자 계약 · 가독성), 검사는 **해로운 부분집합**만
발화한다. 이 간격을 숨기지 않는다 — 검사를 규칙만큼 넓히면 §5-1 의 안전한 인라인에 오탐한다.

### 5-3. 자리와 오라클

- **자리**: `MechanicalValidator.ValidateBatchStep` 에 `private static CheckLocalVariableTypeContract`.
- **오라클**: 이미 들어와 있는 `ddlByProcedure`(N5 조인 짝 때 깔린 배관) → `LocalVariableDeclarationExtractor.Extract`.
  **비순환이다** — 명세서도 단계도 아닌 **원본 DDL** 이다. 재대입 여부도 같은 DDL 의 같은
  파스에서 판정한다(§5-1 의 판별자).
- **결함 종류**: `result.Errors`. 재생성으로 고쳐지므로 `PlanDefects` 가 아니다.
- **중복 없음**: 기존 `@v_valIncVat` 관련 검사(`MechanicalValidatorTests.cs:6609`)는 **명세서 층의
  파라미터 표** 검사라 관할이 겹치지 않는다.
- **새 배관 없음**: `ValidateBatchStep` 이 `ddlByProcedure` 를 이미 받는다.

  **검사는 다루지 않는다.** 「그 재료가 결함이다」라는 증거가 아직 없다(사람 결정, 2026-09-06).

## 8. 알려진 한계

- 초기값 리터럴의 **표기가 달라지면**(`1.1` → `1.10`) 발화 조건이 놓친다. 코퍼스에는 없는
  모양이라 지금은 다루지 않는다.
- 관할이 **2 행**이라, 이 검사의 코퍼스 효력은 그 2 행에 걸려 있다. 원본 DDL 이 바뀌어 정밀도
  수치 상수가 늘면 관할도 함께 는다 — 오라클이 원본 DDL 이므로 저절로 따라간다.
- **감사 자체에 분산이 있다.** 같은 Job 을 두 번 분할 감사했더니 7 단위 중 6 단위의 결함 목록이
  어긋났다. 이 설계가 감사 목록이 아니라 **산출물 본문의 기계 서명**을 과녁으로 삼은 이유다.
