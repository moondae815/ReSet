## 1. 무엇을 없애는가

**F1′ — 타입이 걸린 상수가 방출 SQL 의 `DECLARE` 가 아니라 드라이버 바인딩으로 샌다.**

`POQSettleBatch5` 감사가 🔴 로 매긴 둘(S05 · S07)이 이 가족이다. 손해는 금액이다 —
`@v_valIncVat` 가 `DECIMAL(2,1)` 이 아니라 `FLOAT` 으로 묶이면 `CAST(… AS INT)` 의 절사가
달라져 `CLComm`·`CLVT`·`CLTotal`·`POQIncome` 이 어긋난다.

### 1-1. 이것이 모델의 변덕이 아니라 계약의 구멍인 근거

`raw/prompt-context.md:2482` 에 이미 이렇게 실려 있었다.

```
| @v_valIncVat | DECIMAL(2,1) | 1.1 |
```
> `@v_valIncVat`는 라인 408에서 `DECIMAL(2,1) = 1.1`로 선언되며 … 선언 타입이 `DECIMAL(2,1)`
> 이라는 점이 계약이며, 이를 `FLOAT`이나 `MONEY`로 임의 변경하면 나눗셈 결과의 정밀도와
> 이후 `CAST(... AS INT)` 절사 결과가 달라집니다.

**명세서가 위험을 그 단어 그대로 말해줬는데도 스텝 생성이 그 변수를 바인딩으로 강등했다.**
그리고 `POQSettleBatch5/agent/steps/S05.md:71` 이 그 이유를 스스로 적었다.

```
execute(SQL_UPDATE_13, { p_YMD: p_YMD, p_v_valIncVat: 1.1 })   // 지역 변수 계약 DECIMAL(2,1) 값을 파라미터 바인딩
```

**모델은 타입을 알고 있었고 주석에 적었다. 주석은 드라이버에 닿지 않는다.**
정보가 없어서가 아니라 **관용구에 그 정보를 넣을 칸이 없어서** 샌 것이다.

## 2. 측정 — 모든 수치와 그것을 잰 자

판정 전에 잰 것이다. 자가 두 번 틀렸고 그 사실도 함께 적는다.

### 2-1. 관용구의 분포 (자: 배송 `StepBindingExtractor` 와 같은 정규식, 386 개 단계 파일)

**수마다 분자의 이름을 붙인다** — 「호출」과 「자리」는 다른 것이고, 초판이 그 둘을 섞었다.

| | 단계 파일 | `execute` 호출 | 그중 바인딩 객체를 진 것 | 개별 바인딩 자리 |
| :--- | ---: | ---: | ---: | ---: |
| Batch 계열 3 Job (`Batch1`·`Batch4`·`Batch5`) | **50** | **406** | **393** | **736** |
| Proc 계열 22 Job | 0 | 0 | 0 | 0 |

호출 406 과 객체를 진 것 393 의 차 **13** 은 `execute(SQL_RESTORE_INSERT)` 꼴로 **중괄호
인자가 아예 없는** 호출이다. 사실을 안 내는 것이 옳다 — 바인딩된 값이 없다.

호출 이름을 배송 코드의 일곱(`execute`·`queryScalar`·`queryRow`·`queryList`·`chunkRanges`·
`query`·`queryAll`)으로 넓히면 **호출 506 · 바인딩 객체를 진 것 493 · 개별 자리 894** 다
(Task 3 의 관할 확장). 이름을 가정하지 않는 자로 다시 재도 **493 · 894 로 같다** — 오늘
코퍼스에 그 일곱 밖의 이름은 **0** 이다. 다만 이것은 관측이지 도출이 아니다.

**736 자리(넓힌 자로는 894) 어디에도 타입을 적는 칸이 없다.** 관용구가 Batch 계열에만 살고,
유출도 Batch 계열에서만 난다 — 이 대응이 「계약의 구멍」이라는 진단의 핵심 근거다.

> **초판의 「380 자리」는 두 번 틀렸다(정정 기록).** 첫째, 380 은 **자리(개별 바인딩)** 가
> 아니라 **호출 수**였다 — 분자의 이름이 틀렸다. 둘째, 그 호출 수마저 **줄 단위로 끊는 자**가
> 낸 값이라, 중괄호가 여러 줄에 걸친 호출 **13** 개를 통째로 빠뜨렸다(393 − 13 = 380).
> 같은 자가 개별 자리를 **602** 로 세었는데, 그것은 이어지는 줄에 사는 **134 자리**를 못 본
> 값이다(736 − 134 = 602). **배송 코드의 자는 일부러 개행을 넘는다** —
> `StepBindingExtractor.CallPattern` 주석이 그 이유를 적어 두었다(여러 줄 호출 21 자리에
> 사실 161 개, 전체의 18%). 줄 단위로 좁히면 검사가 그 자리들에 눈이 먼다.

### 2-3. 검사가 지킬 재료 (자: 배송 `LocalVariableDeclarationExtractor`, 프로시저 DDL 14 편 전량 파스 성공)

**재대입은 grep 이 아니라 ScriptDom 파스로 센다.** 초판은 `SET`/`SELECT` 만 세는 자를 썼고,
그래서 아래 표의 둘째 행을 **틀리게 적었다**(재대입 `0` → 실제 `2`).

전 프로시저 DDL 에서 **상수 초기화 지역 변수는 35 행**, 그중 **정밀도 있는 수치 타입은 7 행**,
그중 **실제 관할은 2 행**이다.

| 변수 | 타입 | 초기값 | `DECLARE` 후 재대입 | 판정 |
| :--- | :--- | ---: | ---: | :--- |
| `@v_valIncVat` (COMM_UPD · INS_EXTRA) | `DECIMAL(2,1)` | `1.1` | **0** | **✔ 관할 — 🔴 둘이 여기** |
| `@v_intCLComm` · `@v_intCLVT` · `@v_intCLTotal` | `MONEY` | `0` | **2** (`FETCH … INTO`) | ✘ **둘 다** — 재대입된다(커서 행 수신자라 애초에 상수가 아니다) **그리고** 값이 `0` |
| `@v_intPostChkAmt1` · `@v_intPostChkAmt2` | `MONEY` | `0` | **2** (`SET` + `SELECT`) | ✘ 누산기 — 상수가 아니다 |

둘째 행의 재대입은 `dbo.UP_UTIL_SETTLE_PROC_ETC` 의 **66 · 143 행**이다. 원본 DDL 축자:

```
 66:    FETCH NEXT FROM Cur_SettlePost INTO @v_strClientID, @v_strYMD, @v_strOutYMD, @v_intCLTotal, @v_intCLComm, @v_intCLVT

`SET`/`SELECT` 는 이 셋에 **0 건**이다 — 그래서 초판의 자가 조용했다. 이 셋을 관할 밖으로
미는 이유는 **하나가 아니라 둘**이고, 그 사실이 §5-1 의 판별자를 셋으로 만든 근거다.

**35 · 7 · 2 와 배송 코드의 9 가 어떻게 맞물리는가**(전부 같은 자로 잰 값이다).

- **35** — 초기값을 가진 지역 변수 선언 전량. **재대입을 안 본** 수다.
- **9** — 그 35 중 `ExtractConstants` 가 상수로 인정한 것(`SET`·`SELECT`·`FETCH` 셋으로 걸러
  재대입이 하나도 없는 것). 나머지 **26 개 선언**(= 35 − 9)은 어딘가에서 다시 대입된다.
  (바로 아래 문단의 「**자리**」와 **다른 수다** — 이쪽은 원본 DDL 의 **선언**이고 저쪽은
  단계 본문의 **자리**다. 보존 자리를 23 에서 24 로 고치기 전까지는 둘 다 26 이라 더

- **7** — 그 35 중 **정밀도 있는 수치 타입**인 것. 위 표의 세 행이 이 7 을 전부 열거한다(2+3+2).
- **2** — **9 와 7 의 교집합**, 곧 `@v_valIncVat` 둘(COMM_UPD · INS_EXTRA)뿐이다. 7 에서 빠지는
  다섯은 전부 `MONEY = 0` 이고 **전부 재대입된다** — 타입 필터가 아니라 상수 필터가 떨어뜨린다.

**그러므로 「실제 관할은 2 행」이라는 서술은 그대로 옳다.** 고쳐진 것은 그 2 에 닿는 경로이지
값이 아니다 — 이제 그 2 는 「정밀도 수치」와 「진짜 상수」 **두 필터를 모두 통과한** 행이다.

**정직하게 적는다: 이 검사가 코퍼스에서 지킬 행은 2 다.** 그 2 가 감사의 🔴 둘이고,
검사가 없으면 재생성마다 **27 자리(보존 24 + 직접 유출 3) 중 3** 이 다시 샌다 — `Batch5` 는

## 3. 계약 — 규칙 `5-1`

규칙 5 는 *A step's interface is exactly the original procedure's parameter list* 다. 새 규칙은
그 형제다 — **5 는 인터페이스에 더하는 것을 막고, 5-1 은 인터페이스로 강등하는 것을 막는다.**

### 3-1. 관할 판별자

`LocalVariableDeclarationFact(Name, DataType, InitialValue)` 가 이미 셋을 내고, 추출기가
**프로시저 파라미터를 이미 제외**한다. 그래서 경계가 저절로 깨끗하다.

| | 관할 | 이유 |
| :--- | :---: | :--- |
| `DECLARE @v_valIncVat DECIMAL(2,1) = 1.1` | **안** | 상수 초기화 — 값도 타입도 컴파일 시점에 정해진다 |
| `DECLARE @v_cnt INT;` (뒤에 `SELECT`/`FETCH` 로 채움) | 밖 | 값이 런타임에 정해진다 |
| `@pi_strYMD` 등 프로시저 파라미터 | 밖 | 추출기가 이미 뺀다 → **바인딩 목록에 남는 것은 정확히 파라미터뿐** |

### 3-2. 프롬프트에 들어갈 문장

> **5-1. [Local Variable Type Contract]** A local variable the source procedure DECLAREs *with an
> initial value* keeps its DECLARE in the SQL this step sends. Write it inside the ```sql block as
> `DECLARE @<name> <declared type> = <initial value>;`, spelled exactly as the machine-derived local
> variable table gives it. Do NOT demote it to a binding parameter of `execute(...)` - the binding
> list carries the original procedure's parameters only (rule 5). A bound value has no declared
> type: the driver picks one, and a `DECIMAL(2,1)` that arrives as `FLOAT` changes what
> `CAST(... AS INT)` truncates. Stating the type in a comment does not pin it.

마지막 문장이 관측된 실패를 그대로 겨냥한다 — `Batch5/S05` 는 타입을 **주석에 적었다.**

## 4. Few-Shot — 생성물이 베낄 본

지금 Few-Shot(`AiService.cs` 2294~2406)의 `DECLARE` 둘(`@v_shadow`·`@v_sql`)은 **신설 인프라
변수**다. 「레거시 지역 변수가 `DECLARE` 로 살아남는」 모양을 **한 번도 보여주지 않는다.**
그래서 대조 한 쌍을 넣는다.

```pseudocode
// 바인딩 목록에는 원본 프로시저의 파라미터만 들어간다 (rule 5-1).
// 레거시 지역 변수의 타입 계약은 SQL 안에 남는다.
execute(SQL_APPLY_RATE, { p_batchDate: batchYmd })
```
```sql
-- SQL_APPLY_RATE
-- (rule 5-1) 원본이 초기값과 함께 선언한 지역 변수는 여기 그대로 남는다.
DECLARE @v_someRate DECIMAL(5,2) = 1.25;
UPDATE ... SET Amt = CAST(Amt / @v_someRate AS INT) WHERE ...;
```

두 가지를 못박는다.

1. **이름과 값을 일부러 코퍼스와 다르게 쓴다**(`@v_someRate`·`1.25`). 실물 `@v_valIncVat`·`1.1`
   을 예시에 쓰면 생성물이 그 리터럴을 아무 데나 베낀다.
2. **틀린 본을 블록 안에 넣지 않는다.** 「이렇게 하지 마라」를 ` ```pseudocode ` 안에 쓰면
   생성물이 그것을 베낀다. 부정 예시는 **블록 밖 산문에만** 둔다.

## 5. L1 검사 — `CheckLocalVariableTypeContract`

### 5-1. 발화 조건은 「`DECLARE` 가 없다」가 **아니다**

T-SQL 에서 리터럴 `1.1` 은 그 자체로 `numeric(2,1)` 이다. 즉 `CAST(CLComm / 1.1 AS INT)` 처럼
**SQL 안에 인라인하는 것은 타입이 안전하다.** 해가 나는 자리는 오직 **드라이버 경계**다.

> **발화 조건.** 원본 DDL 의 「정밀도 있는 수치 타입 · `0` 이 아닌 상수 초기화 · 재대입
> 없음」 지역 변수에 대해, 그 초기값 리터럴이 이 단계의 바인딩 값 자리에 **직접** 나타나거나,
> **이 단계의 비-`sql` 펜스에서 그 리터럴을 단 한 번 대입받은 식별자**가 바인딩 값 자리에
> 나타나면 발화한다. **변수 이름은 보지 않는다.**

#### 한 겹 간접까지 보는 이유 (사람 결정, 2026-09-07)

「직접 리터럴」만 보면 **위음성이 코퍼스에 이미 실재한다.**
`POQSettleBatch1/agent/steps/S05.md` 가 그 자리다.

```
 :20   v_valIncVat = 1.1   // 원본 지역 변수 @v_valIncVat(부가세 포함 나눗셈 계수), 값 그대로 유지
 :63   execute(SQL_UPDATE5_CHUNK, { …, p_valIncVat: v_valIncVat, … })
:272   CLComm  = (CAST(CLComm/@p_valIncVat AS INT) + …)
```

그 파일의 `DECLARE` 는 **넷 다 `@v_shadow`·`@v_sql`** 이고 **`@p_valIncVat` 선언은 없다**
(실측: `grep -n DECLARE` → 108·110·294·296 행). 즉 `DECIMAL(2,1)` 이어야 할 값의 타입을
**드라이버가 고른다** — §1 이 말한 손해가 그대로 나는 자리인데 초판 조건은 **조용했다.**
`x = 1.1` 로 한 번 담는 것이 곧 **우회로**이고, 그 우회로는 코퍼스에 이미 나 있다.

**실측 — 넓히는 대가가 얼마인가** (바인딩 사실 **894** 전량, 리터럴 오라클은 원본 DDL 에서
`ExtractConstants` 로 뽑은 관할 상수의 초기값 `{1.1}`).

| 갈래 | 자리 수 | 어디 |
| :--- | ---: | :--- |
| **직접** — 값이 리터럴 그 자체 | **3** | `Batch4/S06` · `Batch5/S05` · `Batch5/S07` |
| **한 겹 간접** — 값이 그 리터럴을 받은 식별자 | **1** | `Batch1/S05` |
| 두 겹 이상 (`a = 1.1; b = a; bind b`) | **0** | — |
| 모호 (그 식별자가 두 번 이상 대입받음) | **0** | — |

**넓혀서 새로 우는 자리는 1 이고, 그 1 은 진짜 결함이다 — 새 오탐 후보는 0 이다.**
(§2-2 의 「보존 **24**」는 리터럴이 `sql` 펜스의 `DECLARE` 안에 있어 애초에 이 조건의 사정권
밖이다. 넓혀도 그 24 는 하나도 안 운다.)

**함께 못박는 것 셋.**

1. **한 겹까지만 쫓는다.** `a = 1.1; b = a; bind b` 는 **안 쫓는다.** 오늘 코퍼스에 0 건이라
   못 잡아도 잃는 것이 없고, 겹을 열면 펜스 안에서 임의 깊이의 값 추적을 해야 한다 —
   그것은 검사가 아니라 인터프리터다.
2. **모호하면 침묵한다.** 식별자가 **단계 전체에서** 그 리터럴을 **정확히 한 번** 대입받고
   **다른 무엇도 받지 않을** 때만 해석한다. 두 번 이상 대입받거나 다른 값도 받으면
   **발화하지 않는다** — 이 검사에서 값싼 쪽은 침묵이 아니라 오탐이다.
3. **관할은 「같은 펜스」가 아니라 「단계의 비-`sql` 펜스 전체」다.** 배송 실물
   (`MechanicalValidator.ResolveSingleAssignmentAliases`)은 단계의 비-`sql` 펜스를 **한
   사전에 모으고** 유일성을 **단계 전역**으로 요구한다. `sql` 펜스만 뺀다 — 방출 SQL 의
   `SET A = 1.1` 을 의사코드 대입으로 오독하지 않기 위해서다.

> **「같은 펜스」는 이 문서 초판의 설계 의도였고, 코드는 그렇게 안 짜였다 — 사실을 적는다.**
> 펜스 귀속을 쓰려면 바인딩을 읽는 호출·인자 정규식을 검사 쪽에 **복제**해야 하고, 그러면
> 바인딩을 읽는 규칙이 두 곳에 생겨 미묘하게 갈린다. 그래서 코드는 복제 대신 **더 좁은
> 유일성**(단계 전역)을 택했다. **어긋남은 두 방향이고 둘 다 적는다** — 한쪽만 적으면
> 다음 사람이 반대 방향에 데인다.
>
> | 어긋나는 모양 | 「같은 펜스」 규칙 | 배송(단계 전역) | 오늘 코퍼스 |
> | :--- | :--- | :--- | ---: |
> | 대입은 펜스 A, 바인딩은 펜스 B | 침묵 | **발화** | **0 건** |
> | 같은 이름이 펜스 A·B 에 갈려 대입 | 각 펜스가 각자 푼다 | **침묵**(유일성 깨짐) | **1 건** |
>
> 즉 **한 방향은 발화, 한 방향은 침묵이다.** 「어긋나면 침묵할 뿐」이라고 한 줄로 닫지 마라.
> 실측(단계 본문 386 편에 두 규칙을 각각 돌림): **발화 파일이 4 == 4 로 같고 차집합이
> 없다.** `Batch1/S05` 의 대입(`:20`)과 바인딩(`:63`)은 **같은 `pseudocode` 펜스
> (`:9`–`:81`)** 안이라 어느 규칙으로도 잡힌다. 비-`sql` 펜스가 둘 이상인 단계는 **12** 이고,
> 이름이 실제로 갈린 자리는 **1**(`Batch5/S03` 의 `po_intRetVal`) — 그 값이 `1.1` 이 아니라
> 오늘은 발화가 안 갈린다. **오늘 같다는 것이지 같은 규칙이라는 뜻이 아니다.**
> (Task 4 리뷰가 돌고 있어 코드가 바뀔 수 있다. 바뀌면 이 표부터 다시 맞춘다.)

> **주의 — 「4」와 「2」는 다른 것을 센 수다.** 위의 **4** 는 단계 본문의 **발화 자리**
> (직접 3 + 한 겹 간접 1)이고, §2-3 의 **2** 는 원본 DDL 의 **관할 지역 변수 행**
> (`@v_valIncVat` × COMM_UPD · INS_EXTRA)이다. 관할 행은 **여전히 2 이고 안 늘었다** —
> 넓어진 것은 그 2 를 **알아보는 경로**뿐이다.

세 판별자를 모호하지 않게 못박는다.

- **정밀도 있는 수치 타입** — `DataType` 이 `DECIMAL`·`NUMERIC`·`FLOAT`·`REAL`·`MONEY`·
  `SMALLMONEY` 로 시작한다(대소문자 무시).
- **`DECLARE` 이후 재대입 없음** — 같은 DDL 을 ScriptDom 으로 파스해 그 변수를 받는
  **갈래 셋**이 모두 **0 건**이다: `SetVariableStatement`(`SET @x = …`) ·
  `SelectSetVariable`(`SELECT @x = …`) · **`FetchCursorStatement`(`FETCH … INTO @x`)**.
  `LocalVariableDeclarationExtractor` 와 **같은 파스 결과를 쓴다** — 정규식으로 세지 않는다.

  **왜 셋인가 — 갈래를 하나씩 없애 보고 정했다(실측, DDL 14 편).**

  | 재대입 갈래 | 상수로 인정되는 수 | 그중 오분류 |
  | :--- | ---: | ---: |
  | `SET` · `SELECT` 둘만 (초판) | **29** | **20** |
  | `SET` · `SELECT` · `FETCH` 셋 (배송) | **9** | 0 |

  FETCH 갈래가 가르는 **20** 중 셋이 `@v_intCLComm`·`@v_intCLVT`·`@v_intCLTotal` 이다.
  이 셋이 위험한 이유는 **타입 필터를 통과하기 때문**이다 — `MONEY` 라 「정밀도 있는 수치
  타입」에 걸린다. 이들을 오늘 조용하게 만든 것은 **오직 초기값이 `0`** 이라는 우연 하나뿐이다.
  그리고 그 우연은 얇다: 코퍼스의 바인딩 값 중 리터럴 `0` 인 자리가 **3** 개 실재한다
  (`Batch5/S00` `p_legacyReturnCode` · `Batch5/S01` `p_retVal` · `Batch5/S09` `p_legacyReturnCode`).
  FETCH 갈래도 `0` 필터도 없으면 그 3 자리가 그대로 오탐이 된다.

  **이 갈래 목록은 열거이지 도출이 아니다 — 「전량」이라고 닫지 마라.** 안 보는 갈래를
  「없다」로 적지 않기 위해, 각각을 **세어서** 적는다(ScriptDom 방문자로 전 DDL 훑은 출력).

  | 안 보는 갈래 | 코퍼스 실측 | 그래서 |
  | :--- | ---: | :--- |
  | `EXEC @x = …` (반환값 대입) | **0 건** | 오늘 실해 없음 |
  | 대입형 `UPDATE … SET @x = …` | **0 건** | 오늘 실해 없음 |
  | `EXEC … @x OUTPUT` | **2 건** | 실재하나 **무해** — 아래 |

  `EXEC … @x OUTPUT` 둘은 `dbo.UP_Util_Settle_Summary` 의 **221 · 230 행**이고 받는 이름이
  **둘 다 `@po_intRetVal`** 이다. 그 이름은 그 프로시저의 **파라미터**(`@po_intRetVal INT
  OUTPUT`)라 `DeclarationVisitor` 가 `ProcedureParameter` 로 이미 배제한다 — 애초에 상수
  후보가 될 수 없어서 재대입을 안 봐도 결과가 안 바뀐다. **원본이 넓어져 지역 변수가
  `OUTPUT` 으로 받히는 날, 이 갈래를 넷째로 더해야 한다.**
- **바인딩 목록** — 단계 본문의 **`sql` 이 아닌 펜스**(의사코드 펜스)에 있는 호출의 두 번째
  인자(중괄호 객체)의 **값 자리**. 키 이름은 보지 않는다. 호출 이름은 배송
  `StepBindingExtractor.Calls` 의 **일곱**이다(리플렉션으로 원소를 세어 확인: 7, 중복 0).

  `execute` · `queryScalar` · `queryRow` · `queryList` · `chunkRanges` · `query` · `queryAll`

  **이 일곱도 열거이지 도출이 아니다 — 「전량」이라고 닫지 마라.** 배송 코드가 이 태도를
  주석에 이미 적어 두었고, 그 주석은 **초판이 실제로 데인 자국**이다: 넷만 두고 「단계 본문의
  호출 492 개가 전량 이 넷」이라고 적었는데 거짓이었다. **네 이름으로 세는 자로는 「다른
  이름이 바인딩 객체를 지고 있는가」라는 물음 자체를 던질 수 없다** — 안 잰 것을 없다고
  적은 것이다. 이름을 가정하지 않는 자로 다시 재어 `chunkRanges`·`query`·`queryAll` 셋이
  더 나왔다(사실 872 → 894).
  **다음 사람은 이 목록을 근거로 관할을 닫지 마라 — 닫으려면 이름을 가정하지 않는 자로
  다시 재라.** (오늘 그 자로 재면 일곱 밖의 이름은 0 이다. 그것은 관측이지 보증이 아니다.)

이름을 안 보는 것이 핵심이다 — `Batch5/S07` 은 `@v_valIncVat` 를 `p_incVat` 으로 개명했다.
**이름 기반 검사는 발화 자리 4 중 2 를 놓친다**(§2-4 에서 실제로 놓쳤다). 실측 — 파일에
`valIncVat` 문자열이 **몇 번 나오는가**: `Batch5/S05` **8 회**(4 줄) · `Batch1/S05` **10 회**
(4 줄) · **`Batch4/S06` 0 회 · `Batch5/S07` 0 회**. 개명한 둘은 이름으로는 **보이지도 않는다.**

> **분자의 이름을 또 틀렸다(정정 기록).** 초판은 이 자리를 「4 회」라 적었는데 **4 는
> `grep -c` 가 낸 「줄 수」**이지 등장 횟수가 아니다. 0/0 쪽은 어느 자로도 0 이라 결론은
> 안 움직였지만, **이 문단은 §2-1 에서 「호출」과 「자리」를 섞은 것을 정정한 바로 그 절
> 안이고 같은 커밋에서 같은 슬립이 재발했다.** 「몇 개인가」를 적을 때마다 **무엇을 하나로
> 세는지**를 함께 적는다 — 줄인가, 출현인가, 자리인가, 호출인가.

정밀도 있는 수치 타입: `DECIMAL` · `NUMERIC` · `FLOAT` · `REAL` · `MONEY` · `SMALLMONEY`.
정수 타입을 뺀 것은 정수는 드라이버가 어떤 정수 타입을 골라도 산술이 같기 때문이고,
동시에 청크 크기(`10000` 같은 `INT` 리터럴) 오탐을 없앤다.

### 5-2. 규칙 ⊃ 검사를 **일부러** 둔다

규칙 5-1 은 `DECLARE` 보존을 요구하고(축자 계약 · 가독성), 검사는 **해로운 부분집합**만
발화한다. 이 간격을 숨기지 않는다 — 검사를 규칙만큼 넓히면 §5-1 의 안전한 인라인에 오탐한다.

### 5-3. 자리와 오라클

- **자리**: `MechanicalValidator.ValidateBatchStep` 에 `private static CheckLocalVariableTypeContract`.
- **오라클**: 이미 들어와 있는 `ddlByProcedure`(N5 조인 짝 때 깔린 배관) → `LocalVariableDeclarationExtractor.Extract`.
  **비순환이다** — 명세서도 단계도 아닌 **원본 DDL** 이다. 재대입 여부도 같은 DDL 의 같은
  파스에서 판정한다(§5-1 의 판별자).
- **결함 종류**: `result.Errors`. 재생성으로 고쳐지므로 `PlanDefects` 가 아니다.
- **중복 없음**: 기존 `@v_valIncVat` 관련 검사(`MechanicalValidatorTests.cs:6609`)는 **명세서 층의
  파라미터 표** 검사라 관할이 겹치지 않는다.
- **새 배관 없음**: `ValidateBatchStep` 이 `ddlByProcedure` 를 이미 받는다.

4. **발화한다.** 단위 시험 통과는 효력이 아니다. **코퍼스에서 4 발화**

   감사에서 상위 브리프가 이미 한 번 단위에게 기각당했다.

   되돌렸을 때 `Batch1/S05` **하나가** 지나가는지. 뒤엣것을 따로 안 재면 넓힌 부분이
   효력이 있는지 알 수 없다.

### 좁힌 처방을 뮤턴트로 확인

「`DECLARE` 없음」으로 판정하는 뮤턴트를 한 번 돌려 무엇이 깨지는지 본다. **안전한 인라인에
발화하면** 좁힌 처방(§5-1)이 옳았다는 증거다.

### 이 결함이 지금 무엇을 우연히 덮고 있나 — ✔ 확인 완료

**네** 결함 자리(`Batch4/S06`·`Batch5/S05`·`Batch5/S07`·`Batch1/S05`)는 **어떤 테스트의
픽스처도 아니다.** 기존 테스트들이 쓰는 `@v_valIncVat` 는 **명세서·DDL 층의 합성 픽스처**다.
고쳐도 잃는 커버리지가 없다.

> **「픽스처가 아니다」와 「훑기에 안 걸린다」는 다른 주장이다.** 앞엣것만 재고 뒤엣것을
> 안 잰 채 넘어갈 뻔했다 — 디렉터리를 통째로 훑는 테스트가 있으면 픽스처가 아니어도
> 기대값이 움직인다. 그래서 **뒤엣것도 쟀다.**
>
> - 테스트 전체에서 **단계 디렉터리를 열거하는 자리는 하나뿐**이다
>   (`StepCheckOracleTests.cs:106`, 대상 디렉터리는 `:104`).
> - 그 디렉터리는 **라이브 `output/` 이 아니라 결함 판**이다 —
>   `CorpusPaths.DefectiveEdition` = `output.bak-batch1-preregen-20260904`, 곧 **재생성 전
>   얼어붙은 사본**이다(`:279` 의 둘째 자리도 같은 트리를 읽는다).
> - **라이브 `output/Jobs/POQSettleBatch1/agent/steps` 를 훑는 테스트는 0 이다.**
>   그래서 `output` 쪽 `S05.md` 를 고쳐도 그 훑기는 **안 움직인다.**
> - 덧붙여 그 훑기가 세는 것은 `OmissionCommentScanner`·SET 산식이라 **이 검사와 관할이
>   겹치지도 않는다.**
>
> **남는 것 하나** — 결함 판은 얼어붙은 사본이라 그 안의 `Batch1/S05` 는 고쳐도 그대로다.
> 결함 판을 **다시 못박는 날** 이 항목을 다시 봐야 한다. 그리고 위 판정은 「오늘 테스트
> 트리」에 대한 관측이므로, **⑤·⑥ 을 잴 때 라이브 코퍼스에서 한 번 더 확인한다.**

### 계약 층은 되돌림으로 못 잰다 — 재생성으로만 잰다

이 저장소가 이미 두 번 물린 자리다. 검사 D 를 강제 완료하고도 **명세서를 재생성하지 않아
오늘도 침묵**했고, 프롬프트 주석만 고쳤더니 **배송본이 안 닫혔다**(생성물은 예시를 베끼지
주석을 베끼지 않는다). 그래서 관문을 명시한다.

- **얼어붙은 입력 트리** · **모델 못박기** · **판마다 Job 이름과 로그를 가른다** · **커밋 해시 기록**
- 재생성본에서 **네 자리**의 바인딩이 `DECLARE` 로 바뀌었는지 확인한다. **`Batch1/S05` 는
  「리터럴이 사라졌는지」로 판정하지 마라** — 그 자리는 원래 리터럴이 바인딩에 없었다
  (`p_valIncVat: v_valIncVat`). **`@p_valIncVat` 가 방출 SQL 에서 `DECLARE` 로 바뀌었는지**로
  판정해야 한다.
- 재생성본에서 **24 가 여전히 `DECLARE` 인지**도 확인한다(계약이 반대로 밀지 않았는지).
  **이름 눈먼 자로 세라** — `Proc15/S10` 은 `@v_incVat` 으로 개명돼 있어 이름 grep 이 못 본다.

## 8. 알려진 한계

- 초기값 리터럴의 **표기가 달라지면**(`1.1` → `1.10`) 발화 조건이 놓친다. 코퍼스에는 없는
  모양이라 지금은 다루지 않는다.
- **간접은 한 겹까지만 쫓는다.** `a = 1.1; b = a; bind b` 는 놓친다(§5-1). 오늘 코퍼스에
  **0 건**이라 잃는 것이 없지만, 재생성이 값을 두 번 옮겨 담는 날 조용해진다.
  **그때 발화가 0 이 되는 것을 「결함이 없다」로 읽지 마라** — 겹 수를 먼저 다시 재라.
- **대입은 단계의 비-`sql` 펜스 전체에서 모으고, 유일성은 단계 전역이다**(§5-1 항목 3).
  그래서 **대입과 바인딩이 다른 펜스에 갈려도 놓치지 않는다** — 오히려 **발화하는 쪽**이다.
  대신 **같은 이름이 두 펜스에 갈려 대입되면 통째로 침묵한다.** 어긋남의 방향이 둘이라
  **한쪽만 기억하면 반대쪽에 데인다.**
- **「관할 행」과 「발화 자리」는 다른 수다 — 섞으면 효력을 잘못 읽는다.**
  - **관할 지역 변수 = 2** (원본 DDL 의 행: `@v_valIncVat` × COMM_UPD · INS_EXTRA).
    이 검사의 코퍼스 효력은 그 **2 행**에 걸려 있다. 원본 DDL 이 바뀌어 정밀도 수치 상수가
    늘면 관할도 함께 는다 — 오라클이 원본 DDL 이므로 저절로 따라간다.
  - **발화 자리 = 4** (단계 본문의 바인딩 자리: 직접 3 + 한 겹 간접 1).
    한 관할 변수가 여러 단계에서 새므로 **둘은 원래 같은 수가 아니다.** 관할이 2 인 채로도
    발화는 늘 수 있고, 실제로 §5-1 을 넓히면서 3 → 4 가 되었다(관할은 2 그대로다).
- **감사 자체에 분산이 있다.** 같은 Job 을 두 번 분할 감사했더니 7 단위 중 6 단위의 결함 목록이
  어긋났다. 이 설계가 감사 목록이 아니라 **산출물 본문의 기계 서명**을 과녁으로 삼은 이유다.
