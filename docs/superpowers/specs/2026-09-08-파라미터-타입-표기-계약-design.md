# 파라미터 타입 표기 계약 — 축 B ②를 계약 층에서 닫는다

`POQSettleBatch6` 축 B 감사 5-1(나). 형제 문서는
`2026-09-07-지역변수-타입계약-강등금지-design.md`(규칙 5-1)이고, 이 문서는 그 문서가
**의도적으로 관할 밖에 둔 자리**를 맡는다.

## 1. 관측

단계가 원본 파라미터를 바인딩으로 넘기는데 **그 파라미터의 선언 타입이 단계 문서에 없다.**

```
execute(SQL_UPDATE_1, { p_ymd: batchYmd })      // S04 - CHAR(8) 인지 어디에도 없다
```

`Batch6` 14개 레거시 단계 실측 — **절반만 적는다.**

자를 **선언 타입 문자열 대조**로 못박아 재면(이름과 그 타입이 같은 줄에 있는가):

| | 단계 |
| :--- | :--- |
| 파라미터를 선언 타입과 함께 적는다 | **6** — S01 S02 S05 S09 S11 S12 |
| 안 적는다 | **8** — S03 S04 S06 S07 S08 S10 S13 S14 |

S04·S07·S14는 `@pi_strYMD`를 **한 번도 부르지 않는다**(바인딩 이름 `p_ymd`만 쓴다).
S03은 더 얄궂다 — `@po_intRetVal (INT OUTPUT)`은 적으면서 **정작 바인딩되는 입력의
`CHAR(8)`을 안 적는다.** 위험과 정반대 방향으로 적고 있다.

(초판은 「타입 어휘가 같은 줄에 있는가」라는 느슨한 자로 7:7을 냈다. 그 자는 `S03`처럼
*다른* 파라미터의 타입이 같은 줄에 있는 경우를 통과시킨다. 위 6:8이 정확한 값이다.)

**「칸이 없다」가 아니다.** 감사 보고서 초판이 「Job 14개 단계 전부가 같은 모양」이라 적었는데
틀렸다 — 표기 자리는 이미 있고 절반은 쓰고 있다. **계약이 요구하지 않아 절반만 하는 것이다.**

## 2. 왜 형제 규칙 5-1이 이것을 안 덮는가

규칙 5-1의 프롬프트 문장이 **위험을 이미 글자 그대로 말한다.**

> A bound value has no declared type: the driver picks one, and a `DECIMAL(2,1)` that arrives as
> `FLOAT` changes what `CAST(... AS INT)` truncates. **Stating the type in a comment does not pin it.**

그런데 그 규칙의 처방은 「바인딩으로 강등하지 마라」이고, **파라미터는 바인딩이 필수다.**
형제 문서가 그 경계를 근거와 함께 그어 두었다.

| 형제 문서 | 내용 |
| :--- | :--- |
| `:173` | `@pi_strYMD` 등 프로시저 파라미터 → **밖** (추출기가 이미 뺀다) |
| `:175` | **바인딩 목록에 무엇이 들어가는지는 이 규칙의 관할이 아니다** |

즉 파라미터가 빠진 이유는 「위험이 없어서」가 아니라 **「그 규칙의 관할이 아니어서」**다.
같은 물리에 처방이 없는 자리가 남았고, 이 문서가 그것을 맡는다.

## 3. 관할 판별자

**원본 프로시저의 파라미터 하나가 단위다 — 입출력을 가르지 않는다.**

| | 관할 | 이유 |
| :--- | :---: | :--- |
| `@pi_strYMD CHAR(8)` (바인딩되는 입력) | **안** | 드라이버가 타입을 고른다 — 이 규칙이 존재하는 이유 |
| `@po_intRetVal INT` (출력) | **안** | 위험은 없지만 §3-1의 이유로 함께 요구한다 |
| `p_runId`·`p_stepCode`·청크 경계 | 밖 | 원본 파라미터가 아니라 오케스트레이션이 공급한다. 규칙 5-1이 이미 「binding a run id … IS correct」로 인정한 값이다 |
| 지역 변수 | 밖 | 규칙 5-1의 관할. 이 규칙은 그것을 볼 일이 없다 |

### 3-1. 왜 입출력을 안 가르는가 — 재료에 판별자가 없고, 실측이 차이를 안 낸다

위험은 **입력에만** 있다(바인딩되는 값은 입력뿐이다). 그런데 재료가 그 구분을 안 담는다 —
`SqlStaticParser.ExplicitVisit(ProcedureParameter)`는 이름과 타입만 넣고 `OUTPUT` 수식어를
버린다. 코퍼스 전수에서 파라미터 표기가 넷뿐인데(`@pi_strYMD CHAR(8)` · `@pi_strYMD VARCHAR(8)` ·
`@po_intRetVal INT` · `@po_strErrMsg VARCHAR(256)`) 어디에도 `OUTPUT`이 없다.

남는 선택지는 셋이고 실측이 그중 둘을 지운다.

| 안 | 발화 | 판정 |
| :--- | :---: | :--- |
| 입력만 (`@po` 접두사로 가름) | **8/14** | 이름 규약을 사실로 오인한다. `OUTPUT`인데 `@po`로 안 시작하는 파라미터에서 거짓 양성 |
| 입출력 전부 | **8/14** | 판별자가 필요 없다 |
| 파서를 고쳐 `OUTPUT`을 담는다 | — | `ProcedureParameters` 문자열 모양이 바뀌어 `[Original Procedure Interface]` 렌더와 `CheckStepInterface`까지 파급된다. 🟡 하나에 과하다 |

**두 안의 발화가 같다**(둘 다 S03 S04 S06 S07 S08 S10 S13 S14). 가를 이유가 없으므로
**전부를 요구한다** — 재료에 없는 판별자를 발명하지 않는 쪽이다. 출력 타입도 이행자가
저널 컬럼을 잡을 때 쓰므로 요구가 낭비도 아니다.

## 4. 재료 — 새로 만들지 않는다

**타입은 이미 기계 확정 재료 안에 있다.**

- `SqlStaticParser.cs:1308` — `ProcedureParameters.Add($"{node.VariableName.Value} {typeStr}")`
- 실물(`UP_Util_Settle_Summary_AcqManual/raw/metadata.json`) — `['@pi_strYMD VARCHAR(8)', '@po_intRetVal INT']`
- `StepInterface(StepCode, Procedures, Parameters)`가 그것을 그대로 나르고,
  **`ValidateBatchStep`에 이미 `stepInterfaces`로 넘어오고 있다**(`CheckStepInterface`가 쓴다).

따라서 `SpecExpectations.From`의 null 판정 체인을 **건드리지 않는다** — L1 작성 계약 §1의
함정(재료를 더하고 항을 안 이어 검사가 한 번도 안 도는 것)이 이 설계에는 없다.

기존 `CheckStepInterface`는 `StepInterfaceFacts.ParameterNames(iface)`로 **이름만** 뽑아 쓴다.
새 검사는 같은 `iface.Parameters`를 **타입까지** 읽는다. 재료는 하나, 소비가 둘이다.

## 5. 프롬프트에 들어갈 문장 (규칙 5-2)

> **5-2. [Parameter Type Contract]** Name each input parameter of the original procedure **with its
> declared type** once in this step's own section, next to the binding name it maps to - for example
> `@pi_strYMD CHAR(8) -> p_ymd`. The machine-derived interface table gives the spelling; copy it.
> A bound value has no declared type, so a `CHAR(8)` that the driver sends as `NVARCHAR` makes the
> comparison non-sargable and the batch scans the settlement table it should seek. Do not rely on
> another file: the person implementing this step reads this section alone. Output parameters are
> not bound and are out of scope, and so are the values the orchestration supplies (run id, step
> code, chunk bounds).

마지막 두 문장이 각각 관측된 실패와 §3의 경계를 겨냥한다.

## 6. L1 검사

`CheckStepParameterTypeStated(stepMarkdown, step, stepInterfaces, result)` — `CheckStepInterface`의
형제로 그 옆에 둔다(같은 재료·같은 소프트 스킵).

- 재료가 없으면(`iface == null`) 조용히 지나간다 — 형제와 같은 관례.
- `iface.Parameters` **전부**를 본다(§3-1).
- 각 파라미터에 대해 **이름과 그 선언 타입이 단계 본문의 같은 줄에** 나오는지 본다. 타입 비교는
  공백을 접어 대조한다(`CHAR(8)`·`char (8)` 동일).
- **검사는 규칙보다 약하다.** 규칙 5-2는 바인딩 이름과의 매핑까지 한 줄에 적으라고 하지만,
  검사는 「이름과 타입이 같은 줄」까지만 본다. 매핑 표기는 Job마다 흔들리는데 타입 표기는
  안 흔들린다 — 검사가 요구하는 것은 되돌릴 수 없는 사실 하나로 좁힌다.
- **단계당 한 건으로 접는다.** 파라미터가 여럿이면 한 오류에 나열한다.
- 메시지의 백틱 토큰은 실제로 지목한 식별자(`@pi_strYMD`·`CHAR(8)`)라 귀속 기본 경로가 옳다
  (작성 계약 §9). 처방 문구에는 백틱을 쓰지 않는다.

예상 발화: `Batch6` **8/14**(S03 S04 S06 S07 S08 S10 S13 S14). 다른 Job은 착수 시 스윕으로 잰다.

## 7. 기각한 두 안과 그 근거

**(b) 바인딩 자리마다 타입을 싣는다** — 기각. 형제 문서 실측으로 바인딩 자리가 **894개**다.
Few-Shot·Critic·L1·규칙 문구 넷을 다 바꿔 같은 사실을 894번 반복하게 되고, 표기를 새로
발명하는 위험이 붙는다. 얻는 것은 §5가 한 줄로 얻는 것과 같다.

**(c) 공용 계약 파일에 한 번만 적는다** — 기각. **틀린 값을 못박는다.**

```
13 × @pi_strYMD CHAR(8)
 1 × @pi_strYMD VARCHAR(8)      ← S11 (UP_Util_Settle_Summary_AcqManual)
     S13 만 출력이 하나 더 있다   @po_strErrMsg VARCHAR(256)
```

매핑이 Job 단위가 아니라 **SP 단위**다. 번들 전체에 `p_ymd → CHAR(8)` 한 줄을 두면 S11이
조용히 오타입된다. 그리고 S11은 **타입을 적은 7단계 중 하나**다 — (c)를 골랐다면 맞게 적혀
있던 것을 틀리게 덮었을 것이다.

참고로 `agent/common/00-architecture.md:4`가 이미 「`@pi_strYMD`, CHAR(8)」을 **산문으로** 담고
있다. 규범이 아니라 개요 문장이고, 정작 규범 자리인 `01-step-contract.md:16`의 바인딩 예시는
`{ p_ymd: batchYmd }`로 타입이 없다. (c)의 절반이 이미 있는데도 절반만 적히는 것이 이 안의
한계를 보여준다.

## 8. 등급 — 🟠이 아니라 🟡이다

감사 단위는 「드라이버가 `DATE`로 바인딩하면 대상 행 집합이 달라진다」를 들어 🟠으로 올렸다.
**문자열 값을 드라이버가 `DATE`로 보낼 현실적 경로가 없다.** 실제 범위는
`char/varchar/nchar/nvarchar`이고 그 안의 진짜 위험은 하나다 — `CHAR` 컬럼과 `NVARCHAR`
파라미터가 만나면 데이터 타입 우선순위상 **컬럼 쪽이 변환돼** 인덱스를 못 쓴다. 정산 테이블
전건 스캔이라 배치에서는 비싸지만 **금액도 행 집합도 안 바뀐다.**

그래서 이 회차의 비용도 그 등급에 맞춘다 — 계약 문구 한 줄과 검사 하나. 캐시 인상은 없다
(명세서 프롬프트도 출력 계약도 안 바뀐다).

## 9. 이 규칙이 하지 않는 것

- **바인딩 이름을 규정하지 않는다.** `p_ymd`든 무엇이든 이 규칙은 말이 없다.
- **타입을 바꾸라고 하지 않는다.** 원본이 `VARCHAR(8)`이면 `VARCHAR(8)`이라 적으라는 것이지
  `CHAR(8)`로 통일하라는 것이 아니다.
- **호스트 코드가 실제로 그 타입으로 바인딩하는지 검증하지 않는다.** L1은 문서만 본다. 이
  규칙이 보증하는 것은 **이행자가 그 단계 하나만 읽고도 타입을 알 수 있다**는 것뿐이다.

### 12-2. 규칙과 검사의 비대칭 — 의도된 것이다

규칙 5-2 의 마지막 문장은 이행자에게 **출력 파라미터는 범위 밖**이라고 말한다.
그런데 검사는 `iface.Parameters` **전부**를 본다. 둘이 어긋나 보이는 것은 사실이고,
§3-1 의 결론을 그대로 집행한 결과다 — 재료에 `OUTPUT` 판별자가 없다
(`SqlStaticParser.ExplicitVisit(ProcedureParameter)` 가 수식어를 버린다). 검사가
출력을 빼려면 `@po` 접두사라는 **이름 규약을 사실로 오인**해야 하고, 그것은 개명에
눈이 먼 판별자다.

실측이 이 선택의 대가가 0 임을 다시 확인해 준다. 발화한 27 단계 중 **누락 목록이
출력 파라미터뿐인 단계는 0 건**이다 — 「입력만」으로 좁혀도 발화 집합이 똑같다(감사
문서 §4 의 27 행 전수 표). 즉 검사가 넓게 보아 더 고발하는 자리는 코퍼스에 없다.
비대칭이 산출물에 미치는 차이는 **누락 목록의 길이**뿐이다: 예컨대 Batch6/S04 는
`@pi_strYMD CHAR(8)` 과 `@po_intRetVal INT` 를 함께 열거한다.

### 12-3. `--sweep` 으로는 이 검사를 못 잰다

`StepSweepService` 는 `ValidateBatchStep` 에 `stepInterfaces: null` 을 넘긴다
(`StepSweepService.cs:191`). 이 검사는 그때 `iface == null` 로 소프트 스킵하므로
**스윕에서는 언제나 발화 0** 이다 — 스윕 차분이 0 이라는 사실은 이 검사에 대해
아무것도 증명하지 않는다.

그래서 §10-2 가 요구한 코퍼스 수치는 스윕이 아니라 **임시 프로브**로 냈다. 프로브는
재료 조달을 제품 코드(`BatchStepPlanParser.TryParse` → `StepInterfaceFacts.Build`)에
맡겨 스윕이 못 주는 `stepInterfaces` 만 채운다. 재고 나서 지웠다(커밋에 없다).

스윕에 이 재료를 태우는 것은 **별건으로 남긴다.** 스윕 주석이 밝힌 대로 그 자리는
DB 메타데이터가 필요 없는 재료만 쓰도록 설계돼 있는데, `stepInterfaces` 는 프로브가
보였듯 산출물만으로 만들 수 있다 — 그러나 그것은 스윕의 재료 계약을 바꾸는 일이라
이 🟡 하나에 묶어 처리하지 않는다.

### 12-4. 되돌림 조건 판정 (§11)

| 조건 | 실측 | 판정 |

다만 **27 은 코퍼스 결함의 총수가 아니라 하한**이다.
