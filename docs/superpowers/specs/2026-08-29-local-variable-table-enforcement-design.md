## 0. 이 설계서의 자리

직전 회차가 **계기**를 붙였다 — 재료마다 「원본 DDL 사실 수 대 명세서 행 수」를 센다.
그 계기가 낸 첫 실측이 이것이다.

```
LocalVariables    DDL 사실 69 · 명세서 행 0 · 14 프로시저 전량 소실
```

(`docs/audit-reports/sweeps/2026-08-29-step-sweep.md` 「재료 분모」 절, 2026-08-29 실측)

**그 회차는 강제를 걸지 않았다.** 로드맵과 (5-3-7) 둘 다 강제를 미결로 적었다.
**이 설계서가 그 강제를 정한다.**

## 1. 결정적 사실 — 이 표를 아무도 요구하지 않는다

검사 D(`CheckSpecLocalVariablesDeclared`)는 명세서의 「지역 변수 표」를 재료로 받는다.
그 표가 어디서 오는지를 전수로 물었다.

| 강제 수단 | 있는가 | 확인 방법 |
| :--- | :--- | :--- |
| 기계 확정 카탈로그 등록 | **없음** | `MachineConfirmedTables.All` 열한 항목에 없음 |
| L1 검사 | **없음** | `Validate` 경로에 이 표를 보는 검사 0건 |
| 프롬프트 문구 | **없음** | `AiService.cs` 전수 grep — 「지역 변수 표를 쓰라」가 **한 줄도 없다** |

**세 층이 전부 비어 있다.** 옛 모델(`gpt-5.6-terra`)은 아무도 안 시켰는데 썼고,
새 모델(`deepseek-v4-pro-0813`)은 아무도 안 시켰으므로 안 썼다.
**검사의 생사가 모델 재량이었다.**

그 재량의 흔적이 헤딩에 남아 있다. 리더가 코퍼스에서 실측해 적어 둔 갈래가 여섯이다
(`SpecStatementFactsExtractor.cs:70-103`).

```
### 지역 변수 및 시스템 값          ### 내부 변수
### 지역 변수 및 시스템 상태값      ### 내부 변수와 컬럼 관계
### 지역 변수와 컬럼 매핑
그리고 헤딩이 아예 없는 하나 (SUMMARY_EXTRA — 리더의 「알려진 한계 6번」)
```

**아무도 이름을 안 정했기 때문에 매번 다른 이름이 나왔다.** 3단계 규칙 재작성 설계서가
「규칙이 정하지 않은 것을 모델이 매번 다르게 찍는다」고 적은 것과 같은 형태다.

## 2. 잃은 것이 진짜 결함이었다

(5-3-7)이 스냅샷 복원으로 확인했다. `POQSettleBatch1/S14`·`POQSettleProc14/S15`의 9 변수가
`FETCH NEXT ... INTO` 대상인데 문서 어디에도 `DECLARE`가 없다.
**선언 없는 변수에 FETCH INTO는 컴파일 오류다.**

검사 D가 그 18건을 잡고 있었고, 재료를 잃으면서 **관측 변화 없이** 놓쳤다.

## 3. 결정 — 재료를 재량 층에서 기계 확정 층으로 옮긴다

지금의 흐름에서 끊긴 자리는 첫 화살표다.

```
원본 DDL의 DECLARE  →  (아무 배선도 없음)  →  모델 재량  →  명세서 표  →  검사 D
```

그 자리에 이 저장소가 기계 확정 표 열한 종에 이미 놓아 둔 배선을 똑같이 놓는다.

```
원본 DDL의 DECLARE  →  LocalVariableDeclarationExtractor  ┬→  Actor 프롬프트에 완성된 표
                                                          └→  SpecExpectations 사실 → L1 대조
                                                                                        ↓
                                                              검사 D  ←  명세서 표  ←──┘
```

**왜 프롬프트 문구만으로는 부족한가.** 표를 「쓰라」고만 하면 내용은 여전히 모델 작문이다.
검사 D의 오류 메시지가 존재하는 이유가 정확히 그것이다 — `@v_intCLTotal`·`@v_intCLComm`·
`@v_intCLVT`는 이름이 int를 시사하는데 원본은 `MONEY`고, 이행자가 이름으로 추측해 int로
선언하면 금액이 절삭된다. **타입을 기계가 주지 않으면 표가 있어도 틀릴 수 있다.**

**왜 L1 검사만으로는 안 되는가.** 프롬프트가 안 시키는 것을 L1이 벌하면
`VerificationPipelineOrchestrator`(`:2006`)가 `ComposeAfterL1Failure`로 자가 수정을
되돌리며 재시도만 태운다. 2026-08-22 재생성에서 같은 교착이 **세 번 났다**
(`MachineConfirmedTables.cs` 주석의 실측).

**강제는 세 층이 겹쳐야 한다** — 인접 축의 보고서 §6-(4)가 같은 결론을 독립으로 냈다.

## 4. 표의 거처 — `## 파라미터 목록` (실측으로 확정)

두 세대를 실제 파일로 읽어 확정했다(2026-08-29 12:40 KST 실측, 실제 리더가 아니라
`^###\s*(지역|내부) 변수` 행마다 직전 `##`를 추적하는 스크립트 — 헤딩 위치만 재므로
표 내용 파싱은 필요 없다).

| 세대 | 실측 |
| :--- | :--- |
| 현 코퍼스(`output/`) | 1건 — `UF_GET_OUTYMD4REFUND`의 `### 내부 변수`, **`## 파라미터 목록` 아래** |
| 승격 전 스냅샷(`output.bak-cache17-20260827`) | 2건 — `### 지역 변수 및 시스템 값` · `### 내부 변수와 컬럼 관계`, **둘 다 `## 파라미터 목록` 아래** |

스냅샷의 2건은 (5-3-7)이 적은 「옛 16행 = EXCEPTION_PROC 4 + PROC_ETC 12」와 프로시저 수가
일치한다 — 독립 경로로 같은 값이 나왔다.

**리더가 적어 둔 여섯 갈래 중 나머지 넷은 더 옛 세대(`output.bak-2026-08-22`)의 것이다.**
이 설계서는 그 세대를 재지 않았다.

## 5. 아키텍처

### 5-1. 새 추출기

`LocalVariableDeclarationExtractor` — DDL AST에서 `DECLARE` 변수의 `(이름, 타입, 초기값)`을 낸다.

`SpecMaterialCensus.CountDeclaredVariablesCore`(`:331`)가 **이미 같은 방문자로 69를 세고 있다.**
판정 로직을 새로 짜는 것이 아니라 **개수 대신 사실을 내는 모양**을 만드는 일이다.

- 커서 선언은 제외한다 — census가 이미 그렇게 세고, 그 경계를 잠그는 테스트가 있다
  (직전 회차 변이 4가 그 자리를 뚫었고 보강으로 닫혔다).
- `TableHeading = "### 지역 변수 " + MachineConfirmedTables.HeadingSuffix`

### 5-2. 카탈로그 등록

`MachineConfirmedTables.All`에 `DdlTranscription` 부류로 **맨 뒤에** 더한다.

**순서 앞쪽을 건드리지 않는다.** 그 목록의 순서가 곧 Critic 프롬프트에 실리는 순서이고,
프롬프트 접두사 캐시가 바이트 일치로 걸린다(같은 파일 주석). 맨 뒤 추가는 기존 항목의
바이트를 안 옮긴다.

등록하면 Critic 면제 블록에 자동으로 편입된다 — 전사 표이므로
「명세서의 사본이 DDL 원문과 다를 때만 보고」 규칙이 붙는다.

### 5-3. 프롬프트 배선 — 네 번째 presentation 파라미터

`BuildMachineFactBlockLines`는 지금 세 종류의 사실을 갈래별로 다르게 싣는다.
지역 변수 표는 목적지 `##`가 기존 셋과 다르므로 **네 번째 파라미터**가 필요하다.

| 호출부 | 갈래 | 이 표의 값 | 근거 |
| :--- | :--- | :--- | :--- |
| `AiService.cs:469` | SP 전체 | `Table` | 모든 `##`를 쓴다 |
| `:1920` | 함수 | `Table` | 함수도 `DECLARE`를 갖는다(현 코퍼스의 유일한 잔존이 함수다) |
| `:3207` | `OverviewAndParameters` | **`Table`** | **이 갈래가 `## 파라미터 목록`을 쓴다** |
| `:3347` | `CrudAnalysis` | `Omit` | `## CRUD 분석` 하나만 쓴다 |
| `:3521` | `LogicAndVisualization` | `Omit` | `## 로직 흐름 요약`·`## 비즈니스 흐름 시각화`만 쓴다 |

**`Omit` 둘을 `Reference`로 하지 않는 이유.** 참고 재료로 주는 것은 「산문이 이 사실을
서술할 수 있을 때」의 선택이다. 변수 선언 목록은 그 두 갈래의 서술 대상이 아니다.

**갈래를 안 가르면 무슨 일이 나는지는 코드에 실측으로 적혀 있다** (Task 14/17,
`BuildMachineFactBlockLines`의 문서 주석). 자기가 쓸 수 없는 `##`에 표를 넣으라는
자기모순 지시를 받은 모델은 둘 중 하나를 한다 — H2 제약을 어기고 헤딩을 합성하거나
(그러면 같은 `###`가 두 번 생기고 `LocateHeadingSection`이 첫 일치만 보므로 뒤 사본이
**조용히 사라진다**), 표를 통째로 버린다.

### 5-4. 리더는 안 고친다 — 이미 맞는다

`LocalVariableHeadingPrefixes = { "### 지역 변수", "### 내부 변수" }`가 `StartsWith` 판정이라
`### 지역 변수 (기계 확정 — 수정 금지)`가 **그대로 걸린다**(`:264-265`).

표 헤더도 기존 파서에 맞춰 낸다.

```
| 변수 명칭 | 데이터 타입 | 초기값 |
```

- `FindColumn(header, "명칭")` → `변수 명칭`이 걸린다.
- `FindColumn([["데이터 타입","구분"], ["데이터 타입"]])` → 둘째 후보로 걸린다.
- `초기값`은 리더가 안 읽지만 이행자에게 필요하다 — `LoopVariableResetExtractor`가
  「지역 변수 표는 `DECLARE` 시점의 초기값을 싣는다」를 전제로 서술한다. 열이 늘어도
  리더는 열 이름으로 찾으므로 안전하다(그 파일이 「열 순서에 기대지 않는 이유」로 적은 것).
- 이 표는 `DECLARE`된 변수만 싣는다 → 모든 행이 `IsSystemValue == false`다.
  `@@ERROR` 같은 시스템 값은 애초에 안 실린다. 검사 D의 `@@` 접두사 이중 방어는 그대로 둔다.

**이 「우연히 맞는다」를 잠근다.** 새 헤딩이 접두사 목록에 걸리는지와 헤더 두 칸이
`FindColumn`에 걸리는지를 단언하는 테스트를 둔다.
**누가 헤딩을 `### 로컬 변수`로 바꾸는 순간 검사 D가 또 조용히 꺼진다** — (5-3-7)이
정확히 그 모양이었고, 이음매를 안 잠그면 같은 결함을 다른 이름으로 되풀이한다.

### 5-5. 새 L1 검사 — 양방향

`Validate(markdown, expectations)` 경로에 `CheckLocalVariableDeclarationTable`을 더한다.

- **정방향**: `expectations`의 모든 `DECLARE` 사실에 표의 행이 있는가.
- **역방향**: 표의 모든 행에 `DECLARE` 사실이 있는가.

**전사 표이므로 사실 없는 행은 그 자체로 위반이다** — 모델이 지어낸 변수다.
(5-3-6)이 지적한 단방향 결함을 **새 검사에서 되풀이할 이유가 없다.**

**단, 이것이 (5-3-6)을 닫지 않는다.** 기존 셋(`CheckErrorCodes`·`CheckSetAssignments`·
`CheckTransactionBoundaries`)의 역방향은 여전히 미결이고 이 회차 범위 밖이다 —
그 셋에 역방향을 넣으면 `UP_UTIL_SETTLE_SUMMARY_EXTRA`가 2건 발화하는데 그것은
오탐이 아니라 진짜 위반이라 재생성이 함께 필요하다.

`Validate`의 catch-all이 검사 하나의 예외로 `Errors`를 통째로 지우므로
**자기 `try/catch`를 둔다**(`CheckMachineTableShape`의 선례와 같은 이유).

### 5-6. 캐시 승격

`CurrentCacheFormatVersion` 17 → 18.

AGENTS.md 95행이 「새 표는 카탈로그에 등록한 뒤 `CurrentCacheFormatVersion`도 함께
올리십시오」로 못박는다. 미루는 길(96행)도 있으나 **선결 조건을 잊을 자리를 만든다** —
강제가 서 있는데 영영 안 도는 상태가 된다.

**이것은 공유 상태다.** 올리는 순간 다음에 생성을 돌리는 사람이 전건 재생성을 문다.
번호를 올리기 전에 동료 세션에 알리고, 커밋 메시지와 로드맵에 명시한다.

**번호 충돌 확인이 필요하다** — `reset-l1-check` 스킬의 규칙이고, 캐시 17 승격 때
코디네이터가 전 브랜치를 확인한 선례가 `CacheManager.cs` 주석에 있다.

## 6. 이 회차의 끝 — 강제만 걸고 재생성은 안 한다

사용자 결정(2026-08-29). 그래서 이 회차가 끝난 시점의 상태는 이렇다.

- 강제 세 층이 전부 서 있다.
- 코퍼스 명세서는 여전히 옛 판이므로 **검사 D는 아직 침묵한다.**
- 다음 재생성이 자동으로 켠다.

**이 상태의 위험을 이 회차에서 닫는다.**

### 6-1. 「한 번도 안 돌아 본 검사」 — 다섯 번째 위험

로드맵이 `CheckErrorCodes`를 두고 그렇게 불렀다. 그 검사는 재료가 0이라 코퍼스에서
한 번도 발화한 적이 없었고, **목록이 채워지는 순간 통째로 켜져 문서마다 오류가 날**
위험을 안고 있었다. 로드맵 4가 승격 **전에** `ErrorCodeTableCorpusTests`로 그 위험을
닫았다 — 31 객체 전건에서 만족 가능성을 재고(사실을 가진 객체 12 · 사실 합 84 ·
갈래 셋 발화 0) 왕복 가드를 걸었다. 예측이 맞았다.

**같은 자를 이 검사에도 만든다** — `LocalVariableTableCorpusTests`. 코퍼스 31 객체
(Procedures 14 · Functions 10 · External 7, 2026-08-29 12:43 KST 실측)에서 갈래 셋을 잰다.

1. 표를 완전히 전사한 객체 → 발화 0
2. 사실 0건 객체 → 조기 반환으로 침묵
3. 사실이 있는데 표가 없는 객체 → 발화

**오탐을 안은 채 다음 재생성이 걸리면 그것이 곧바로 재시도 소진으로 번진다.**

### 6-2. 변이 검증 — 「출력 칸마다 하나씩」

직전 회차의 교훈이다. 변이 여덟이 전부 계수 로직을 겨눴는데 **살아남은 결함 둘은 둘 다
표시 계층에 있었다.** 이번 변이 목록은 출력과 이음매를 겨눈다.

| # | 변이 | 죽어야 할 것 |
| ---: | :--- | :--- |
| 1 | 새 헤딩을 `### 로컬 변수`로 바꾼다 | 리더 접두사 이음매 테스트 |
| 2 | 헤더의 `변수 명칭` 칸을 `변수 이름`으로 바꾼다 | `FindColumn("명칭")` 이음매 테스트 |
| 3 | `MachineConfirmedTables.All` 등록을 뺀다 | 카탈로그 등록 테스트 · Critic 면제 블록 테스트 |
| 4 | `OverviewAndParameters`를 `Omit`으로 바꾼다 | 갈래별 배선 테스트 |
| 5 | `CrudAnalysis`를 `Table`로 바꾼다 | 위와 같은 테스트의 반대 방향 |

| 사실 | 값 | 방법 · 시각 |

**독립 실측 — 인접 축(`reset-a4`)이 다른 경로로 같은 값을 냈다 (2026-08-29, 그 세션의 §3 침묵 검사 분류 작업 중).**

```
명세서 14편 → SpecStatementFacts 14개 → 변수 0개
「지역 변수」 문자열이라도 있는 명세서: 14편 중 2편
  (EXCEPTION_PROC 6회 · SUMMARY_ETC 1회 — 그 둘에서도 파서가 뽑은 변수는 0)
계획서 20편 · 단계 343개 전 구간에서 검사 D 발화 0
```

**이 값이 처방의 방향을 가른다.** 「표는 있는데 파서가 못 읽는다」가 아니라
**표 자체가 안 실린다** — 14편 중 12편은 그 말이 한 번도 안 나온다.
§4의 내 헤딩 실측(Procedures에서 `###` 헤딩 0건)과 독립 경로로 일치한다.
그러므로 처방은 리더를 고치는 쪽이 아니라 **재료를 다시 만드는 쪽**이 맞다.

**(5-3-7)이 남긴 원인 미분류가 여기서 좁혀졌다.** 그 문단은 소실 14건이
「모델이 안 썼다」인지 「리더가 못 읽는다」인지 계기가 못 가른다고 적었다.
위 실측이 **최소한 12건은 「모델이 안 썼다」**임을 보인다(문자열 자체가 없다).
남은 2편은 여전히 미분류다 — 문자열은 있으나 표인지 산문인지 이 실측이 안 갈랐다.

**안 잰 것 — 이행 중에 재야 한다**

- **DDL 사실 69의 재실측.** 직전 회차 계기의 값을 인용했다. 실제 추출기를 만든 뒤
  같은 수가 나오는지 대조해야 한다 — **정규식 근사가 이 저장소에서 세 번 틀렸다.**
- **69가 프로시저별로 어떻게 갈리는지.** 표 크기와 프롬프트 토큰 증가량이 여기서 나온다.
- **함수 10편의 `DECLARE` 사실 수.** 함수 갈래를 `Table`로 두는 대가를 안 쟀다.
- **캐시 버전 18이 비어 있는지.** 전 브랜치 확인이 필요하다(`reset-l1-check`의 규칙).
- **초기값을 AST에서 어디까지 복원할 수 있는지.** `DECLARE @x INT = 0`의 리터럴은
  쉽지만 식이 오면 원문을 어떻게 실을지 정하지 않았다.

**하네스 함정 — 이행 중 이 값을 잴 때 밟지 말 것 (인접 축이 실제로 밟았다).**
`SpecStatementFactsExtractor`에 넘기는 `FileName`에 **`.md`를 붙이면 안 된다.**
그 리더가 키를 `MechanicalValidator.BareObjectName(fileName)`으로 잡으므로
`"dbo.UP_UTIL_SETTLE_INS.md"`는 맨이름이 `"md"`로 읽혀 **14편이 한 키로 뭉갠다**
(그렇게 재면 `SpecStatementFacts`가 1개로 나온다). 운영 값은 `Program.cs:879`가 만드는
`"{Schema}.{Name}"`이라 확장자가 없다. 직전 회차의 계획서 결함 B와 같은 뿌리다.
