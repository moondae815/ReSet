# 시도 저널 2단계 — 재개(읽기)와 쿼터 판정 분리 · 설계

작성일 2026-09-11 · 기준 커밋 `cab64851` (main)
**코드는 안 만졌다 — 이 문서는 착수 전 설계다.**

계기: 1단계(쓰기 전용 저널)를 배송한 뒤 사용자 질문 「재개하는 방법을 알려줘 … 방법이

## 1. 판독 — 지금 무엇이 있고 무엇이 없나

### 1-1. 있는 것 (1단계가 배송한 것)

`PlanAttemptJournal` 이 배치 계획 생성 중의 골격·단계 섹션·회차별 리뷰를
`output/Jobs/[Job]/raw/attempts/run-NNN/` 에 그 자리에서 남긴다. **실물로 돌았다**
(`POQSettleBatch7`, 2026-09-11):

```
run-001 · OpenedBy: run-start · claude-sonnet-5 / effort high
회차 6 (0 → 82 → 92 → 88 → 86 → 94)
skeleton.md · steps 17 · reviews 6
Attempt 갈림: 시도 1 이 만든 13 개 · 시도 6 이 만든 4 개
DefectKind: S03·S07·S08 QualityFloor · S10 Unverifiable
```

`attempt-01`~`03` 의 Critic 지적은 **디스크에만 있다** — 메모리의 `feedbackHistory` 는
`CriticFeedbackLog.MaxRetainedRounds`(3)만 들고 있어 그 셋은 프로세스와 함께 사라졌다.

### 1-2. 없는 것

**읽는 쪽이 없다.** `PlanAttemptJournal` 을 부르는 자리는 `Create` 와 `ComputeSha256`
뿐이다. 중단 후 다시 돌리면 파이프라인은 **처음부터 다시 만든다.**

### 1-3. 쿼터 소진의 실제 경로 (1단계 설계 §1-3 재확인)

- `CliFailureKind.QuotaExhausted` 라는 분류가 **이미 있다**(`CliFailureClassifier` 가
  stderr+extraDetail 을 마커 목록으로 훑는다). 그런데 `AiRetryPolicy.Classify` 는 CLI 예외 중
  `Timeout` 만 `Transient` 로 보고 **나머지를 전부 `Fatal`** 로 둔다 — 쿼터 소진은 재시도 없이
  즉시 포기다.
- HTTP 프로바이더에는 **쿼터 판별 자체가 없다.** 429 는 `Transient` 지만 `RetryPlan.Default`
  가 2회·0.5~1.5초라 시간 단위 쿼터를 못 넘는다.
- 화면에는 「통합 배치 설계서 작성이 중단되었거나 실패했습니다」 한 문장으로 뭉개진다 —
  **중단과 실패가 안 갈린다.**

## 2. 사람 결정 셋 (2026-09-11)

| 축 | 결정 | 기각한 것과 이유 |
| :--- | :--- | :--- |
| 발동 | **찾으면 알리고 고르게 한다** | 자동 재사용은 이 저장소가 반복해 덴 「조용한 재사용」 모양이다 — 산출물이 왜 그 모양인지 나중에 설명할 수 없다 |
| 쿼터 | **즉시 멈추고 안내한다** | 기다리기는 구독 쿼터가 시간 단위라 프로세스를 붙잡는 낭비다. 사람에게 묻기는 밤새 돌릴 때 답할 사람이 없다 |
| 재생성 범위 | **`DefectKind` 가 있는 것만 자동으로** | 사용자 지목은 1단계가 말한 「재개」를 넘어서는 기능이다(YAGNI) |

그리고 구조 축 둘:

- **A1** 읽기 로직은 `PlanAttemptJournal` 에 둔다(`TryResume`). 1단계 설계가
  「읽는 쪽이 생길 때 같은 클래스에 들어가 규약이 갈라지지 않는다」고 약속한 자리다.
- **B1** `AiRetryVerdict` 에 판정을 하나 더한다. 그 열거형은 `AiCallRetry` **한 곳에서만**
  쓰여 반경이 작다.

## 3. 재개 — 판 고르기와 복원

### 3-1. 진입점 하나

`RunConsolidatedPipelineAsync` 에서 **목차가 확정된 직후, `OpenRun("run-start")` 바로 앞**이다.
그 시점에 목차 해시가 정해져 판을 고를 수 있고, 아직 아무것도 안 만들었다.

```
목차 확정 → PlanStructure.md 기록
          → [재개 후보 찾기]   ← 여기
          → 찾았고 사람이 승인하면 복원
          → OpenRun(...)
```

### 3-2. 판 고르기 — `PlanAttemptJournal.TryResume`

`ReuseKey` **일곱 항목이 전부 일치**하는 판 중 최신 것만 후보다
(`ContractVersion`·`PlanStructureSha256`·`SpecsSha256`·`Provider`·`Model`·`Effort`·`TargetLanguage`).
하나라도 다르면 후보가 아니다 — **특히 모델이 다르면 문서의 목소리가 섞인다**(1단계 §6).

후보에서 **제외**할 판 둘:

1. **골격도 섹션도 없는 판** — 1단계 §11-5 가 적어 둔 단일 호출 폴백 판이다. 재개할 재료가 없다.
2. **`manifest.json` 을 못 읽는 판** — 진실이 manifest 이므로(§11-1) 못 읽으면 없는 것으로 친다.

**무결성은 manifest 의 `Sha256` 으로 확인한다.** 파일이 있어도 해시가 다르면 그 항목을
버린다 — 사람이 손댔거나 반쯤 쓰였다는 뜻이다.

### 3-3. 무엇을 복원하나

| 대상 | 규칙 |
| :--- | :--- |
| `lastSkeleton` | 그대로 |
| `lastStepSections` | **`DefectKind` 가 `null` 인 것만.** 결함 표시된 것은 안 넣는다 → `GenerateBySplitAsync` 가 자동으로 다시 만든다 |
| `feedbackHistory` | `reviews/` 에서 **시도 번호가 큰 순으로 최근 3개**(`CriticFeedbackLog.MaxRetainedRounds` 와 같은 상한) |

> **[자체 검토에서 하나로 고정 — 2026-09-11]** 이 자리를 처음에는 「점수가 가장 높았던
> 회차부터 최근 3개」로 적었는데 **두 가지로 읽힌다**(점수 상위 3개인가, 최고점을 포함한
> 시간순 3개인가). **시간순 최근 3개로 고정한다** — `CriticFeedbackLog.Record` 가 시간순으로
> 쌓고 넘치면 앞에서 버리는 그 규칙과 같아야 **재개 전후로 동작이 같다.** 점수로 고르면
> 재개한 회차만 다른 규칙으로 프롬프트를 받는다.

피드백을 넣는 이유는 1단계 설계 §2 가 적은 그대로다 — 없으면 재개 후 첫 회차가 백지에서
시작해 **이미 정리된 결함이 되살아난다**(`CriticFeedbackLog` 주석의 2026-08-04 사고).

### 3-4. 사람에게 묻는다

`IVerificationUserInteraction` 에 메서드 하나를 더한다. `ConfirmMetadataSyncAsync` 와 같은
`Task<bool>` 모양이다:

```csharp
Task<bool> ConfirmResumeAsync(string jobName, PlanAttemptResumeCandidate candidate);
```

화면에 보일 것: 판 번호 · 만든 시각 · **재사용 가능한 단계 수 / 전체** · 다시 만들 단계와
그 사유 · 이어받을 피드백 회차 수. `POQSettleBatch7` 이면
「13/17 재사용, 넷을 다시 만듭니다 (S03·S07·S08 하한 미달, S10 대조 불가)」가 된다.

### 3-5. 새 판을 열되 읽어 온 것을 다시 기록한다

§11-4 대로 이전 판을 이어 쓰지 않는다. 새 판을 열고 **복원한 골격·섹션을 즉시 다시 기록**한다
— 구제 채택(`AdoptPlanStructureForRescueAsync`)이 이미 같은 관용구를 쓴다. 그래야 새 판이
자기만으로 완결된다.

**1단계가 겪은 함정을 피한다.** 구제 재기록은 전량을 한 `Attempt` 로 적어 **과대 표기**가
생겼다(1단계 문서에 유보로 적혀 있다). 재개는 **원래 `Attempt` 값을 그대로 옮기고**,
manifest 에 `ResumedFrom: "run-001"` 을 새로 둔다. 그러면 「이 판의 `Attempt 6` 은 이전 판
것」이라는 사실이 파일 안에 남는다.

## 4. 쿼터 판정 분리와 안내

### 4-1. 판정 하나 추가

`AiRetryVerdict` 에 **`Exhausted`** 를 더한다. 뜻은 **「지금은 안 되고 나중엔 된다」**이고,
`Fatal`(다시 해도 같다)과 `Transient`(금방 풀린다) 어느 쪽도 아닌 것이 지금 없어서
`Fatal` 로 뭉개져 있다.

| 프로바이더 | 판정 근거 |
| :--- | :--- |
| CLI | `CliFailureKind.QuotaExhausted` → 곧바로 `Exhausted` |
| HTTP | **429 가 재시도를 다 쓰면** `Exhausted` 로 승격 |

HTTP 에서 429 를 처음부터 `Exhausted` 로 보지 않는 이유: 상태 코드만으로는 「초당 한도에
잠깐 막힘」과 「구독 소진」이 **구분되지 않는다.** 잠깐 막힘이면 지금의 2회 재시도가 넘긴다.
그걸 다 쓰고도 429 면 짧은 막힘이 아니다. 응답 본문에서 마커를 찾는 길도 있으나
`HttpRequestException` 에 본문이 안 실려 있어 **지금은 안 한다(YAGNI).**

### 4-2. `AiCallRetry` 는 `Fatal` 처럼 즉시 포기하되 이유를 싣는다

`AiCallFailedException` 에 `Verdict` 를 더해 왜 포기했는지가 호출부까지 간다.
**새 예외 타입을 만들지 않는다** — `AiCallRetry` 의 주석이 적은 호출부 55곳이
`when (ex is not OperationCanceledException)` 으로 거르고 있어 새 타입을 들이면 그 55곳을
다시 봐야 한다(`AiCallFailedException` 주석이 그 이음매를 이미 적어 두었다).

### 4-3. 파이프라인은 이유를 결과에 실어 보낸다

`ConsolidatedPipelineResult` 에 필드 하나(`PipelineAbortReason? AbortReason`)를 더한다.

**`VerificationOutcome` 에 값을 넣지 않는다.** 그 열거형은 「문서의 검증 상태」를 뜻하고
배너·헤더가 읽는다. 중단 사유는 다른 축이라 섞으면 두 뜻이 한 필드에 산다
(`VerificationBanner` 가 이미 「`VerificationOutcome` 에 상태를 새로 만들지 않는다」는
선례를 두 자리에 적어 두었다).

**생성 실패는 이미 회차를 더 돌지 않는다** — `RetryRescue` 로 최선을 건지고 그 자리에서
끝난다(실측 확인). 그래서 쿼터의 차이는 「더 돌지 말지」가 아니라 **무엇을 사람에게
말하느냐**다.

### 4-4. CLI 가 갈라서 말한다

지금은 두 자리에서 한 문장으로 뭉갠다: 「통합 배치 설계서 작성이 중단되었거나 실패했습니다」.

쿼터면:

```
쿼터 소진으로 멈췄습니다 — 실패가 아닙니다.
여기까지 저장됐습니다: 단계 13/17 · 골격 · 회차 리뷰 5개
이어서 하려면 쿼터가 풀린 뒤 같은 Job 이름(POQSettleBatch7)으로 다시 실행하십시오.
```

**「여기까지 저장됐다」의 숫자는 저널이 방금 쓴 manifest 에서 읽는다** — 짐작이 아니라
실제 기록이다. 이 문장이 §3 의 재개를 가리키는 자리이고, 그래서 둘을 함께 설계했다.

## 5. 검증

### 5-1. `TryResume` 단위 시험 (임시 디렉터리, 오케스트레이터 없이)

- `ReuseKey` **항목마다** 하나씩 틀렸을 때 후보에서 빠지는지 — **일곱 항목 각각.**
  하나라도 안 재면 그 항목은 무방비다
- `DefectKind` 가 있는 섹션이 복원에서 빠지는지
- `Sha256` 이 안 맞는 항목이 버려지는지
- 골격·섹션이 모두 없는 판이 후보가 아닌지(§11-5)
- 판이 여럿일 때 최신을 고르는지

### 5-2. 오케스트레이터 통합 시험 — 관찰 지점이 핵심이다

- 재개를 승인하면 **`GenerateBatchStepSectionAsync` 호출 수가 결함 단계 수와 같은지.**
  13개를 재사용했다면 넷만 불려야 한다 — 이것이 「재개가 실제로 비용을 줄였다」의 **유일한
  직접 증거**다
- 거절하면 전량 다시 만드는지
- 새 판 manifest 에 `ResumedFrom` 과 **원래 `Attempt` 값**이 남는지

### 5-3. 쿼터 시험

- CLI `QuotaExhausted` → `Exhausted`
- HTTP 429 가 **재시도를 다 쓴 뒤에야** `Exhausted` 로 승격되는지 — 첫 429 에 곧바로
  승격되면 잠깐 막힘에 포기한다. **이 방향 오류를 재는 시험이 따로 필요하다**
- `AbortReason` 이 결과에 실려 CLI 까지 가는지

### 5-4. 실물 검증을 마지막 단계로

시험이 전부 초록이어도 **`POQSettleBatch7` 을 실제로 재개해 보는 것**을 계획의 마지막
단계로 넣는다. 지금 그 판이 실물로 있고(13/17 재사용 가능, 결함 넷), **BOM 이 그랬듯 실물이
아니면 안 드러나는 것이 있다**(§7-2).

## 6. 범위 밖

- **사용자가 특정 단계를 지목해 다시 만들기.** 사람 결정으로 제외했다(YAGNI).
- **HTTP 응답 본문에서 쿼터 마커 찾기.** `HttpRequestException` 에 본문이 안 실린다 — 429
  재시도 소진으로 대신한다.
- **L1 발화 기록(`raw/l1-attempts.json`)의 배치 경로 확장.** 1단계 §10 이 적어 둔 별도 작업.
- **`raw/attempts/` 보존 정책.** 판이 실행마다 늘고 지우는 자가 없다. 1단계 최종 리뷰가
  Minor 로 남겼고 여기서도 다루지 않는다.

## 7. 1단계가 남긴 함정 — 계획서에 명시 조항으로 옮길 것

1단계에서 계획서·설계서가 **열 건 넘게** 틀렸고 **전부 같은 모양**이었다.

1. **「지워도 통과하는 분기」가 반복 결함이었다.** 모든 새 코드에 대해 「이걸 망가뜨리면
   무엇이 빨개지나」를 답하고, 답이 없으면 시험을 먼저 만든다.
2. **시험이 보는 통로가 결함을 가릴 수 있다.** BOM 이 그랬다 — `File.ReadAllText` 가 벗겨
   읽어 왕복 시험 스물둘이 전부 초록이었고 **실물에서야 드러났다.**
   **재개는 파일을 읽는 기능이라 같은 함정이 더 크다.**
3. **자리 수를 세려면 `grep` 으로 세라.** 배선 자리 수가 문서에서 **네 번** 틀렸다
   (넷→다섯→여섯).
4. **`SYMMETRY SWEEP` 을 리포트 필드로 요구한다.** 그걸 넣은 뒤로 워커가 스스로 공백을
   찾기 시작했다.
5. **3단계 넘는 태스크는 중간 커밋을 브리프에 못박는다.** 1단계에서 워커가 100턴 한계에
   **두 번** 걸렸고(848초·1048초), 중간 커밋이 두 번 다 작업을 건졌다.
6. **최종 전체 리뷰는 「합쳐진 결과」를 명시 임무로 준다.** 1단계의 Critical 은 한 태스크가
   `OpenRun` 을 메서드 안에 넣고 다른 태스크가 그 메서드에 인자를 꿰어 생긴 것이라
   **어느 태스크 리뷰도 볼 수 없었다.**
