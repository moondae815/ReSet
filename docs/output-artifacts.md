# output/ 산출물 명세

ReSet이 `output/` 아래에 남기는 파일을 **누가·언제·어디에·무엇을·어떻게·왜** 만드는지 정리한 문서다.

- 작성일: 2026-08-14 · 최종 갱신: 2026-08-25
- `output/` 전체는 Git 추적에서 제외된다. 여기 있는 것은 전부 **재생성 가능한 파생물**이며,
  사람이 직접 편집해 보존할 자리가 아니다.
- 각 산출물을 만드는 모듈의 구조는 [아키텍처 문서](architecture.md)에 있다. 이 문서는
  **무엇이 왜 남는가**만 다룬다.

---

## 1. 산출물을 만드는 다섯 주체

ReSet의 산출물은 전부 AI가 만든 것이 아니다. **어느 주체가 만들었는지가 그 파일을 얼마나
믿어도 되는지를 결정**하므로, 이 구분이 문서 전체의 기준이다.

| 표기 | 주체 | 무엇으로 | 결과의 성격 |
|---|---|---|---|
| 🤖 **AI** | LLM 응답 | Claude / OpenAI / Gemini / Ollama 등 설정된 제공자 | 매번 달라질 수 있다. **검증을 통과해야 신뢰한다** |
| 🔎 **정적 분석** | SQL 구문 트리 파싱 | `Microsoft.SqlServer.TransactSql.ScriptDom` (T-SQL 공식 파서) | 항상 같은 답. AI가 놓친 것을 잡는 근거 |
| 🗄 **DB 조회** | SQL Server 메타데이터 조회 | `Microsoft.Data.SqlClient` | DB의 사실을 그대로 옮긴 것 |
| ⚙️ **결정적 조립** | 프로그램이 계산·포매팅 | 내장 템플릿, `System.Text.Json` | 입력이 같으면 결과가 같다 |
| 🧑‍💻 **외부 에이전트** | 코딩 CLI가 생성하거나, 감사 스킬을 실행한 에이전트가 판정 | Claude Code / Codex CLI / Antigravity CLI | ReSet이 내용을 쓰지 않는다 |

로그는 `Serilog`, 마크다운 구조 검증은 `Markdig`, 다이어그램 문법 검사는 외부 `mermaid-cli`를 쓴다.
마지막 것만 없어도 되는데, `mmdc`가 설치돼 있지 않거나 설정으로 꺼져 있으면 정규식 검사로 내려간다 —
그 경우 문법 판정은 느슨해지지만 검증 자체가 멈추지는 않는다.

**검증 3단계(L1/L2/L3)** 도 같은 축 위에 있다 — **L1은 🔎정적 분석과 ⚙️기계 검사**,
**L2는 🤖AI 교차 리뷰**, **L3는 사람의 승인**이다.

## 2. 큰 그림

산출물은 생성 시점이 다른 네 계층으로 나뉜다. 뒤 계층은 앞 계층을 입력으로 받는다.

```
① 객체 단위 역공학        Procedures/  Functions/  Objects/  External/
        ↓ Spec.md를 읽어
② 통합 Job 계획 수립      Jobs/[Job]/raw/  Jobs/[Job]/docs/
        ↓ 계획서를 잘라
③ 지시서 번들 생성        Jobs/[Job]/agent/
        ↓ 외부 코딩 에이전트가 소비
④ 코드 생성과 검증        Jobs/[Job]/src/  Jobs/[Job]/validation/

곁가지  Jobs/[Job]/consistency/           ← 계층 밖. 앞의 산출물을 사후에 되짚는 감사 결과
        Jobs/[Job]/coverage/CoverageMap.html
        [Procedures|Functions]/[객체]/docs/CoverageMap.html
그 외    logs/  cleansing/  .sp_cache_index.json  offline_snapshot.json
         [Job이름_]Settlement_Policy_Rulebook.md
```

두 개의 CLI가 이 계층을 나눠 갖는다. **분석기(`ReSet.Cli`)가 ①~③과 ④의 기동**을,
**검증기(`ReSet.Validator.Cli`)가 ④의 데이터 정합성 대조**를 담당한다.

산출물이 놓이는 자리는 **객체 종류와 DB 소속** 두 가지만으로 결정된다.
프로시저는 `Procedures/`, 함수는 `Functions/`, 끝내 종류를 판정하지 못하면 `Unresolved/`로 가고,
분석 루트가 아닌 DB의 객체는 앞에 `External/[DB]/`가 붙어 격리된다.
경로에 쓸 수 없는 문자는 `%XX`로 인코딩되므로 이름에 특수문자가 있어도 폴더가 깨지지 않는다.
**이 규칙에는 예외가 없다** — 참조분석을 켜든 끄든 자리를 정하는 것은 `OutputPathResolver`
하나다.

## 3. ① 객체 단위 역공학

**언제** — SP 하나를 골라 분석할 때.

**어디에** — `output/Procedures/[스키마].[이름]/`, UDF는 `output/Functions/[스키마].[이름]/`

**참조분석 설정은 무엇이 어디에 남는지를 가르지 않는다.** 분석도 저장도
`DependencyAnalysisOrchestrator` 한 경로를 타므로 아래의 **자리 규칙**은 켜고 끄고와
무관하게 같다. 끄면 그래프가 루트 한 노드로 끝나므로 **나오는 파일의 집합**이 줄 뿐이다.

**다만 파일 집합이 같다고 내용까지 같지는 않다.** 같은 플래그가 수집 범위도 함께 뒤집어,
루트의 `Spec.md` 머리는 `분석 범위: 직접 의존성` ↔ `전이 의존성`으로 갈리고
`metadata.json`이 담는 의존성의 폭도 직접만 ↔ 전이적으로 갈린다. 왜 한 값이 두 축을
정하는지는 `architecture.md §4.1.1`의 「플래그 하나가 두 축을 함께 정합니다」가 적는다.

**갈리는 것은 머리만이 아니다.** 같은 문서의 「참조 코드 객체」 절도 함께 갈린다 — 켠
회차에 그 절이 비면 「직접 참조하는 코드 객체가 없습니다」이고 이것은 **열거해 보았고
없었다**는 관측이지만, 끈 회차에는 애초에 그래프를 만들지 않으므로 절이 언제나 비어
같은 문장을 쓸 수 없다. 끈 회차는 대신 **참조분석을 껐고 열거하지 않았다**고 적고 수집한
의존성이 있는 곳(`raw/metadata.json`)을 가리킨다. 「없다」와 「모른다」는 산출물만 보고
구분되어야 하기 때문이며, 두 문구는 머리의 도장과 **같은 값 하나**(`AnalysisScope`)를
읽으므로 한 문서가 자기 수집 범위를 두 가지로 신고할 수 없다.

### docs/ — 사람이 읽는 결과물

| 파일 | 생성 주체 | 무엇을 · 왜 |
|---|---|---|
| `Spec.md` | 🤖 AI + ⚙️ 검증 헤더 | **최종 비즈니스 명세서.** 뒤따르는 모든 계층의 입력 원본이다. 문서 맨 앞에 종합 신뢰도·5개 축 점수·검증 결과·커버리지가 붙어, **읽기 전에 얼마나 믿어도 되는지부터 보인다** |
| `Prd.md` | 🤖 AI + ⚙️ 귀속 배너 | **명세서 기반 요구사항 문서.** 메인 메뉴 `5`에서 이미 있는 `Spec.md` 하나만 읽어 사후에 도출한다 — DB 재접속도 재분석도 없다. **L1/L2/L3 검증 파이프라인을 전혀 타지 않는다.** 기계로 확인되는 것은 요구 표 각 행의 근거(`<Spec 헤딩> > "<원문 구절>"`)가 원본 `Spec.md`에 **실재**한다는 것뿐이며, 요구와 근거의 **대응**은 미검증이고 `추정` 표기 행은 원본에 없는 재구성이다. 문서 상단 배너가 이 경계를 항상 명시한다(`architecture.md §4.14`) |
| `BatchMigrationPlan.md` | 🤖 AI | SP 하나짜리 배치 전환 계획서. `MigrationSettings:Enabled`가 켜져 있을 때만 나온다. **L1도 L2도 거치지 않으므로** 헤더에 "검증 없음"을 명시한다 — 검증된 명세서와 나란히 놓였다고 같은 신뢰도로 읽히면 안 되기 때문. **이 문서의 추론 로그는 어디에도 남지 않는다**(CLI가 생성 응답의 추론 부분을 쓰지 않고 버린다 — [알려진 결함](known-defects.md)) |
| `Thinking.md` | 🤖 AI (추론 부분) | 모델이 그 결론에 이른 사고 과정. **담기는 것은 명세서 파이프라인의 추론뿐이다** — 위 `BatchMigrationPlan.md`의 추론은 여기 오지 않는다. **본문이 비어도 반드시 쓴다** — 파일이 없다는 것과 추론이 없었다는 것을 산출물만 보고 구분할 수 있어야 하므로. 단 **남길 추론이 없고 파일이 이미 있으면 덮지 않는다**(캐시 히트 회차가 앞선 기록을 지우지 못하게). 그래서 **헤더의 provider·model·작성일시는 이 파일을 마지막으로 쓴 회차의 것이지 마지막 분석 회차의 것이 아니다** — 같은 폴더의 `Spec.md`는 회차마다 다시 쓰이므로 둘이 서로 다른 모델을 신고할 수 있다 |

### raw/ — 재현과 감사를 위한 원본

| 파일 | 생성 주체 | 무엇을 · 왜 |
|---|---|---|
| `metadata.json` | 🗄 DB 조회 + 🔎 정적 분석 | 대상 SP와 **의존성 전체를 덤프한 것**. 지시서 번들이 참조 테이블 스키마를 만들 때 쓰는 원천이고, 커버리지 맵의 분모(잎 문장)도 여기 담긴 DDL에서 나온다. **끌 수단이 없다** — 뒤 계층이 원천으로 읽는다 |
| `dependency-manifest.json` | ⚙️ 결정적 조립 | 어느 의존 객체의 산출물이 어디로 갔는지 잇는 색인. **크로스 DB 분석에서 흩어진 산출물을 되짚는 유일한 지도**이고, 커버리지 맵이 참조 폐포를 세는 근거이기도 하다. 참조분석을 끄면 **루트 한 노드짜리**로 나온다 |
| `prompt-context.md` | ⚙️ 조립 (🗄 DB 조회 + 🔎 정적 분석 결과 포함) | **AI에 실제로 주입된 원문.** 결과가 이상할 때 모델을 탓하기 전에 입력부터 확인하라고 남긴다. UPDATE 컬럼 매핑 같은 정적 분석 산출도 여기 함께 실린다. **캐시 히트 회차는 이 파일을 덮지 않는다** — 그 회차에는 남길 원문이 없어서 빈 값으로 덮이는데, 그러면 실제로 모델에 보낸 원문이 사라져 이 파일의 존재 이유가 없어진다. 파일이 아예 없을 때만 빈 파일을 만든다 |
| `deconstructed_logic.json` | 🤖 AI (로컬 LLM 전용) | 로컬 모델은 한 번에 명세서를 못 쓰므로 **구조화 추론을 1단계로 분리**한다. 그 중간 결과의 백업본 |
| `chunks/chunk_N.json` | 🤖 AI (로컬 LLM 전용) | 긴 SP를 구문 단위로 쪼개 생성할 때의 **조각별 응답 캐시**. 중단·재시도에서 이미 끝난 조각을 다시 태우지 않기 위한 것 |

**앞의 셋은 분석에 성공한 노드마다 항상 나온다.** 끄는 설정이 없다 — 뒤 계층이 이 셋을
원천으로 읽으므로 끌 수단을 두지 않는 것이 설계 의도이고, 기본 설정(참조분석 끔)도 이제
그 의도를 지킨다. 남은 두 행만 스위치가 아니라 **어느 제공자를 썼는지**에 달렸다.
따라서 어떤 산출물이 안 보이면 그것은 **설정의 결과가 아니다.** 다만 「그 노드가
실패했다」로 단정할 수도 없다 — 내보내기는 취소가 아닌 예외를 **로그에만 남기고 삼키며**
`PersistenceErrors`에 넣지 않으므로, 노드가 성공·저장됨으로 보고된 채 raw 파일만 빠질 수
있다. 그 구분은 산출물이 아니라 로그가 준다.

> **로컬 LLM 전용 두 행의 자리는 이 표의 규칙을 따르지 않는다.** 둘 다 대상 종류와 무관하게
> `Procedures/[스키마].[이름]/raw/` 아래로 가므로, **외부 DB 객체의 것이 `External/[DB]/`
> 격리를 벗어난다.** `chunks/`는 여기에 더해 설정된 출력 디렉터리가 아니라 실행 위치 기준
> `output/`을 본다 — `OutputSettings:Directory`를 기본값에서 바꾸면 조각 캐시만 딴 곳에 쌓인다.

### Objects/ — 표준 DDL 정본

**참조분석을 꺼도 생긴다.** 정본을 쓰는 코드가 유일한 저장 경로에 있기 때문이며,
끄고 돌리면 루트 하나짜리 `Objects/`가 나온다.

| 경로 | 생성 주체 | 무엇을 · 왜 |
|---|---|---|
| `Objects/[스키마].[이름].[종류]/raw/object_definition.sql` | 🗄 DB 조회 | 같은 객체를 여러 경로에서 만나도 **DDL 원본은 한 벌만** 두기 위한 정본. 폴더 이름에 종류까지 붙는 것은 이름이 겹치는 다른 종류의 객체를 구분하기 위한 것 |
| `Objects/[...]/raw/ddl/procedures/*.sql`, `.../functions/*.sql` | 🗄 DB 조회 | 이 객체가 참조하는 코드 객체의 DDL **복사본**. `DependencyArtifactMode`가 `PortableBundle`일 때만 나온다 |

`prompt-context.md`는 여기 없다 — 정본이 아니라 회차별 분석 흔적이므로 객체 디렉터리의
`raw/`로 옮겼다(위 표). 2026-09-04 이전에 만든 `output/` 트리에는 옛 자리에 그대로 남아
있는데, 이행 스크립트를 두지 않았기 때문이다. `output/`은 재생성 가능한 파생물이다.

마지막 행이 기본값(`Reference`)에서 비어 있는 것은 결손이 아니다. 정본은 위 첫 줄로 이미 한 벌
있고, `Reference`는 그것을 가리키기만 한다. `PortableBundle`은 참조 대상까지 폴더 안에 복사해
**객체 폴더 하나만 떼어 옮겨도 자족적이게** 만드는 대신, 같은 DDL이 여러 벌로 불어나는 것을 받아들인다.
참조분석을 끈 실행에서 이 사본은 **손자 객체까지** 담긴다 — 그 모드의 메타데이터 수집이
전이적이라 명세서도 그것을 보고 쓰였기 때문이다. 번들이 ON 때보다 커진다.

## 4. ② 통합 Job 계획 수립

**언제** — 여러 SP를 하나의 배치 Job으로 묶어 통합 전환 계획서를 만들 때.
**3단계로 나눠 진행하며 각 단계가 자기 산출물을 남긴다.**

> **1/3 Brainstorm**(발상) → **2/3 Structure**(목차 확정) → **3/3 Finalize**(본문 작성)

한 번에 쓰게 하지 않고 쪼갠 이유는, 긴 계획서를 통째로 생성하면 뒤로 갈수록 앞의 결정을
잊기 때문이다. 목차를 먼저 못 박아 두면 본문을 **동시에 여러 개 생성해도 순서와 경계가 흔들리지 않는다.**

**어디에** — `output/Jobs/[Job이름]/`

| 파일 | 생성 주체 | 언제 | 무엇을 · 왜 |
|---|---|---|---|
| `raw/Brainstorming.md` | 🤖 AI | 1/3 직후 | 최종 계획서에 남지 않은 초기 발상. **계획이 왜 그 모양이 됐는지는 여기에만 있다** |
| `raw/PlanStructure.md` | 🤖 AI | 2/3 직후 | 3/3이 채워 넣을 **목차 계약** |
| `raw/PlanStructure.superseded-N.md` | 🤖 AI | 목차를 다시 짤 때마다 | 폐기된 이전 목차. **덮어쓰지 않고 번호를 늘려 보존한다** — 목차가 왜 바뀌었는지는 이전 판이 있어야 알 수 있으므로 |

## 5. ③ 지시서 번들 (`Jobs/[Job]/agent/`)

**생성 주체는 대부분 ⚙️ 결정적 조립이다.** AI가 쓴 계획서를 **기계적으로 잘라 재배치**할 뿐,
이 단계에서 새로 생성되는 문장은 없다.

**왜 쪼개는가** — 계획서 한 덩어리를 통째로 주면 에이전트가 매 회차 전부를 읽는다.
계획서를 절 단위로 잘라 공통 문서와 단계 본문으로 나누고, 회차별 지시서는 자기 몫만 링크한다.
본문을 **복사하지 않고 링크만 하는 것**은, 계획서가 교정·재생성으로 계속 바뀌는 동안
두 벌이 조용히 어긋나는 것을 막기 위한 것이다.

| 경로 | 생성 주체 | 무엇을 · 왜 |
|---|---|---|
| `MigrationInstructions.md` | ⚙️ 조립 | 진입점. **지켜야 할 지침이 앞, 나머지는 링크**로만 둔다 |
| `task-00-bootstrap.md` | ⚙️ 조립 | 0회차 — 골격 |
| `task-NN-[단계코드].md` | ⚙️ 조립 | 1..N회차 — 단계별 이행 |
| `task-99-assembly.md` | ⚙️ 조립 | 99회차 — 조립 |
| `common/00-architecture.md` | ⚙️ 계획서 분할 | 전 회차 공통 — 아키텍처 |
| `common/01-step-contract.md` | ⚙️ 계획서 분할 | 전 회차 공통 — 단계 계약 |
| `common/02-data-access-boundary.md` | ⚙️ 계획서 분할 | 전 회차 공통 — 데이터 액세스 경계 규칙 |
| `common/03-hosting-and-config.md` | ⚙️ 계획서 분할 | 전 회차 공통 — 호스팅·설정 |
| `steps/[단계코드].md` | ⚙️ 계획서 분할 | 단계별 이행 상세 본문 |
| `verification/integrity-sql.md` | ⚙️ 계획서 분할 | 이행 결과를 원본과 대조할 무결성 SQL |
| `src/` 뼈대 코드 | ⚙️ 내장 템플릿 | **에이전트에 미리 제공하는 스텁.** 공통 부모 클래스 상속을 강제해 임의 구조와 자의적 에러코드를 막는다. 같은 스텁이 C#에서는 두 파일, Java에서는 여덟 파일로 나간다 — **Java가 파일당 public 최상위 타입 하나만 허용해서지 스텁이 더 많아서가 아니다** |
| `tests/` 테스트 스텁 | ⚙️ 내장 템플릿 | 뼈대를 우회한 구현을 **아키텍처 테스트가 잡아내게** 하기 위한 것 |
| `progress.json` | ⚙️ 도구 상태 | **회차 진행 상태의 진실의 원천.** 도구가 소유하며 에이전트는 쓰지 않는다 |
| `todo.md` | ⚙️ 렌더링 | `progress.json`에서 파생된 사람용 표시 |

계획서에 해당 절이 없으면 그 자리의 파일이나 디렉터리는 **만들지 않고 지운다.**
빈 파일이 남으면 "내용이 없는 것"과 "아직 안 만든 것"을 구분할 수 없기 때문이다.

진행 상태 두 파일은 **임시 파일에 쓴 뒤 옮기는 방식**으로 저장한다. 최종 경로에 바로 쓰면
중단됐을 때 잘린 파일이 남고, 그 시점에 진행 상태가 이미 망가진다. 읽지 못한 `progress.json`은
지우지 않고 `progress.json.corrupt`로 옮겨 보존한다. 그 이름이 이미 있으면 뒤에 타임스탬프를
붙인다 — **두 번째 손상이 첫 번째 증거를 지우게 둘 이유가 없다.**

> **참고** — C# 산출물은 BOM 있는 UTF-8, Java 산출물은 BOM 없는 UTF-8로 쓴다.
> javac가 BOM으로 시작하는 소스를 거부한다는 보고(JDK-4508058) 때문이다.

## 7. 사후에 되짚는 산출물

앞의 네 계층 어디에도 속하지 않는 둘이다 — 산출물을 **만드는** 자리가 아니라 이미 만들어진
산출물이 원천과 여전히 같은 이야기를 하는지 **되짚는** 자리이기 때문이다. 판정 주체가 서로
다르다: 하나는 사람이 붙인 에이전트가, 하나는 기계가 낸다.

### 7.1. 산출물 정합성 감사 (`Jobs/[Job]/consistency/`)

**생성 주체는 🧑‍💻 감사 스킬을 실행한 에이전트다.**

| 경로 | 생성 주체 | 무엇을 · 왜 |
|---|---|---|
| `ConsistencyReport.md` | 🧑‍💻 에이전트 | 최신 감사 보고서. 축별 판정·단위별 커버리지·결함 목록 |
| `ConsistencyReport-Axis[축]-YYYY-MM-DD.md` | 🧑‍💻 에이전트 | 축·날짜별 보존본. **덮어쓰지 않으므로 판정이 언제 뒤집혔는지 되짚을 수 있다** |
| `.cache.json` | 🧑‍💻 에이전트 | 단위별 판정 캐시 |

`.cache.json`의 키가 **그 단위가 근거로 읽은 파일 전부의 해시**인 것이 이 자리의 핵심이다.
근거가 한 글자라도 바뀌면 캐시가 저절로 미스가 나므로, **재생성된 산출물에 낡은 판정이
따라붙지 않는다.** 반대로 근거가 그대로면 다시 검증하지 않는다 — 감사는 비싸고, 같은
입력에 같은 답을 두 번 살 이유가 없다.

이 자리를 `validation/`과 섞지 않는 것은 **판정의 주체와 재현 방식이 다르기 때문**이다.
`validation/`은 검증기 CLI가 결정적으로 다시 만들 수 있지만, 여기는 그렇지 않다.

### 7.2. DDL 커버리지 맵 (`CoverageMap.html`)

**생성 주체는 ⚙️ 결정적 조립이다.** `--coverage-map [대상]`으로 **명시적으로 요청할 때만**
나오며, DB에도 AI에도 붙지 않는다 — 이미 있는 `output/` 산출물(`raw/metadata.json`과
`docs/Spec.md`, 폐포를 세는 데는 `raw/dependency-manifest.json`)만 읽는다.

원본 DDL의 잎 문장마다 「도구가 낸 재료가 있는가」와 「명세서가 그 자리를 짚었는가」를
교차해 네 상태로 가른다 — 🟩 둘 다 · 🟥 재료만 있음(**명세서 결함**) · 🟦 명세서만 짚음 ·
🟧 둘 다 없음(**도구 사각지대**). **뒤의 둘을 한 상태로 합치지 않는 것이 이 맵의 요점이다** —
고칠 대상이 정반대인데 합치면 어느 쪽인지가 사라진다.

| 경로 | 무엇을 · 왜 |
|---|---|
| `Jobs/[Job]/coverage/CoverageMap.html` | Job이 소비한 명세서의 **참조 폐포 전체**를 한 장에 담은 맵. 폐포의 정의는 감사 축 A와 같다 |
| `[Procedures\|Functions]/[객체]/docs/CoverageMap.html` | 객체 하나짜리 맵 |

외부 자산을 참조하지 않는 자립형 HTML이라 **디렉터리째 옮겨도 그대로 열린다.**
재료를 읽지 못해 빠진 객체는 조용히 넘기지 않고 콘솔에 남긴다 — 폐포에서 몇 개가 빠지면
맵은 멀쩡해 보이는데 대조 범위가 줄어든 것을 아무도 모르기 때문이다. 같은 이유로
참조분석을 끄고 만든 산출물에서 폐포는 **분석된 객체 하나**로 끝난다. 매니페스트가
루트 한 노드만 담기 때문이며, 이것은 결손이 아니라 사실이다 — 자식을 분석하지
않았으므로 폐포에 넣을 산출물이 없다. 예전처럼 매니페스트가 없어 조용히 폴백하는
일은 더 이상 없다.

기계 확정 표가 늘면 🟧이 🟥으로 옮겨 간다. 재료를 세는 쪽이 새 추출기를 세기 시작해도
기존 산출물은 옛 프롬프트로 만들어져 그 표가 없기 때문이다. **표를 더한 직후의 🟥 급증은
회귀가 아니라 재생성 전까지의 예정된 중간 상태다.**

이유로 남는 것을 막기 위한 것이다.

## 9. 산출물이 아닌 것

혼동하기 쉬운 두 가지는 `output/` 밖에 있고, 실행이 끝나면 남지 않는다.

- **CLI 제공자 작업 공간** — 코딩 CLI에 프롬프트를 파일로 넘기기 위해 시스템 임시 폴더를 쓴다.
  이 파일에는 BOM을 붙이지 않는데, 맨 앞의 보이지 않는 문자를 모델이 지시로 읽기 때문이다.
- **다이어그램 문법 검사** — L1이 Mermaid 블록을 임시 폴더에서 실제로 렌더해 본다.
  판정 근거일 뿐 산출물이 아니다. `mmdc`가 없거나 설정으로 꺼 두면 정규식 검사로 내려간다.

## 10. 재생성 전에 스냅샷을 뜬다

이 문서 첫머리는 `output/`이 전부 재생성 가능한 파생물이라고 적는다. **재생성으로
같은 것을 다시 만들 수 있다는 뜻이지, 지금 있는 것을 잃어도 된다는 뜻이 아니다.**
재생성은 되돌릴 수 없다.

### 왜 되돌릴 수 없는가

대부분의 경로는 같은 자리에 덮어쓰지만, `InstructionBundleWriter`에는 **하위 트리를
통째로 지우는 경로가 둘** 있다.

| 지우는 것 | 발동 조건 |
| --- | --- |
| `Jobs/[Job]/agent/verification/` | 이번 회차가 검증 SQL을 잘라내지 못했을 때 |
| `Jobs/[Job]/agent/steps/` | 이번 회차가 단계 분할에 실패해 단일 파일로 폴백했을 때 |

둘 다 **의도된 동작이고 그 판단은 옳다** — 낡은 파일이 조용히 남아 그것만 보고
작업을 시작하는 에이전트가 더 나쁘다. 다만 그 대가가 **「이번 회차가 덜 만들면 앞
회차의 멀쩡한 산출물이 사라진다」**이다. 실패나 폴백 한 번에 `steps/` 전체가 없어진다.

### 절차

```bash
cp -a output "output.bak-<작업이름>-$(date +%Y%m%d)"
```

`.git/info/exclude`에 `output.bak-*`가 이미 등록돼 있어 추적되지 않는다. 이름에
**작업 이름을 넣는다** — 날짜만으로는 무엇을 되짚으려던 스냅샷인지 다음 사람이 모른다.

### `output.bak-2026-08-22`은 이 관례가 아니다

**그것은 스냅샷이 아니라 테스트 재료다.** `CorpusPaths.PriorEdition`이 이름을 상수로
들고 `CoverageMapGoldenTests`의 「결함이 늘지 않았는가」가 그것을 기준 세대로 쓴다.
재생성 대상으로 삼거나 덮어쓰면 그 검사가 **실패가 아니라 건너뜀**이 되어, 아무것도
재지 않는 상태로 조용히 바뀐다. 새 스냅샷에는 반드시 새 이름을 쓴다.

## 11. 문제를 되짚는 순서

산출물이 이렇게 잘게 나뉜 이유는, **어디서 어긋났는지 좁혀 들어갈 수 있게** 하기 위한 것이다.

1. **결과가 틀렸다** → `docs/Spec.md` 맨 앞의 검증 결과와 축별 점수부터 본다
2. **왜 그렇게 나왔나** → 같은 폴더의 `Thinking.md`
3. **모델이 무엇을 봤나** → `raw/prompt-context.md`.
   **입력이 부실하면 그 위의 둘을 탓할 이유가 없다**
4. **입력이 왜 부실한가** → `raw/metadata.json`과 `Objects/[객체].[종류]/raw/`의 정본 DDL —
   의존성 수집 단계의 문제다
5. **명세서가 원본의 어디를 안 짚었나** → `--coverage-map`으로 `CoverageMap.html`을 내고
   🟥을 본다. **위 넷은 "틀렸다"를 좁히지만 이것만이 "빠졌다"를 보여 준다**
6. **계획서가 이상하다** → `Brainstorming.md` → `PlanStructure.md`(+ 폐기된 판) 순서로
   3단계 중 어디서 어긋났는지 좁힌다
7. **에이전트가 엉뚱한 코드를 냈다** → `agent/progress.json`으로 회차를 특정하고,
   그 회차의 지시서와 그것이 링크하는 문서만 읽는다
8. **어디가 어긋났는지조차 모르겠다** → `consistency/ConsistencyReport.md`.
   **위 일곱 갈래 중 어디를 볼지 정해 주는 것이 이 보고서의 용도다**
