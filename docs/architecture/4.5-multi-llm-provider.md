### 4.5. 다중 AI 공급자(Multi-LLM Provider) 추상화
* **Decoupling 계약**: LLM 통신과 페이로드 직렬화 사양을 `IAiClient` 계약 뒤로 격리하였습니다. 비즈니스 파이프라인인 `AiService`는 하위 전송 메커니즘을 인지하지 않습니다.
* **공급자별 독립 클라이언트**:
  * **OpenAiClient**: OpenAI 공식 SDK 통신, gpt-5 Responses API 지원 및 gpt-4o 등 최신 모델에 대한 자동 프롬프트 캐싱, Responses API의 `prompt_cache_key` 명시적 라우팅 지원, 복수 `reasoning.summary`의 비어 있지 않은 요약 누적 보존, o1/o3 추론 모델 규격(`reasoning_effort` 등) 대응. Responses API 경로에서는 `volatileUserSuffix`를 세 번째 메시지로 떼어 보내고 공통 메시지 블록에 `prompt_cache_breakpoint: { "mode": "explicit" }`를 찍어 그 지점을 캐시 접두사의 끝으로 지정합니다. breakpoint가 content 블록에 붙는 규격이므로 이때는 세 메시지 모두 `input_text` 타입 블록 배열로 보냅니다. 접미사가 비면 메시지를 만들지도, 블록 배열로 바꾸지도 않습니다 — 빈 메시지가 하나 느는 것 자체가 접두사를 바꿔 접미사를 쓰지 않는 호출들끼리의 캐시를 깨고, 캐시 이득이 없는 호출에서 표현만 바꾸면 형식 오류 위험만 늘기 때문입니다.
  * **ClaudeClient**: Anthropic Messages API 페이로드 규격 대응, System 영역 `cache_control` 적용 및 헤더 추가를 통한 프롬프트 캐싱 지원. 재생성 회차(같은 접두사를 이미 보낸 뒤 `volatileUserSuffix`가 있는 경우)에는 `PromptCacheBreakpointPolicy` 판정에 따라 user 블록에도 `cache_control`을 찍어 명세서 블록을 캐시하는 두 번째 중단점을 추가합니다 — 이 두 번째 중단점은 첫 전송에는 찍히지 않습니다. Claude 4/5세대 추론 토큰 대응 및 temperature 생략 처리.
  * **GoogleClient**: Google AI Studio API Key 주입 및 SystemInstruction 구조 대응.
  * **OllamaClient**: 로컬 실행형 LLM 통신을 위한 Ollama 네이티브 REST API(`/api/chat`) 규격 대응. `ollama-cloud` provider로 지정하면 같은 클라이언트가 Ollama Cloud(`https://ollama.com`) 모드로 생성되어 요청마다 `Authorization: Bearer` 헤더를 붙이고 기본 엔드포인트를 클라우드 호스트로 바꿉니다. 이때 `ProviderName`이 `"Ollama Cloud"`로 갈라져 `IsLocalProvider` 판정에서 빠지므로, 원격 GPU를 쓰는 클라우드에는 AST 분할 파이프라인·1단계 온도 고정·`<think>` 유도 프롬프트가 적용되지 않습니다(API 키가 없으면 생성 시점에 중단). 모델명에 `gemma4` 또는 `qwen3.6`이 포함될 경우 최적 샘플링(`num_ctx`, `top_p`, `top_k` 등)을 `options` 파라미터로 자동 할당하는 하드코딩 우회 로직 및 생각 토큰(<|channel>thought, <think> 등)의 수동 파싱과 본문 분리 기능 지원. 또한 텍스트 무한 반복 루프 방지를 위해 `repeat_penalty`가 자동 매핑됩니다. effort는 temperature로 환산됩니다 — low/medium/high/max = 0.1/0.4/0.7/0.9이며, `gemma4`·`qwen3.6`은 이 매핑을 무시하고 하드코딩된 모델별 최적 설정을 우선합니다. 로컬 모델에는 `repeat_penalty`·`repetition_penalty`·`frequency_penalty`를 주입합니다(`ChatAsync_ShouldDiversifyTemperatureBasedOnEffort`).
  * **ZaiClient**: Z.ai AI 플랫폼 연동 규격 및 추론 과정(Reasoning Process) 수집 대응.
  * **OpenRouterClient**: OpenRouter(`https://openrouter.ai/api/v1`) 연동. OpenAI 호환 규격이지만 `OpenAiClient`를 재사용하지 않습니다 — 그쪽은 모델명에 `gpt-5`가 들어가면 Responses API로 분기하는데, OpenRouter의 모델 ID는 `openai/gpt-5.6`처럼 네임스페이스가 붙어 그 분기에 그대로 걸리기 때문입니다. effort가 지정되면 통합 `reasoning: { effort }`를, 없으면 `temperature`를 배타적으로 보내고 응답의 `reasoning` 필드를 추론 과정으로 수집합니다. 원격 HTTP API이므로 `IsLocalProvider`·`IsCliProvider` 어느 분류에도 들지 않습니다. `Providers:OpenRouter:Routing`으로 백엔드 제공자 선호(`order`·`allow_fallbacks`·`require_parameters`·`quantizations`)를 고정할 수 있으며, 비어 있으면 요청에 `provider` 필드를 넣지 않습니다. 이 구획은 provider 단위여서 Actor/Critic/Consolidator가 하나를 공유하는데, 어느 백엔드가 그 모델을 서빙하는지도 캐시 읽기 단가도 모델마다 다릅니다. 그래서 `Routing:ByModel:<모델ID>`(대소문자 무시) → `Routing:Default` → (하위호환) `Routing` 직하 순으로 찾고, 앞의 둘은 `OpenRouterRoutingOptions.Merge`가 **항목 단위로** 겹칩니다 — 모델별 항목에 `Order`만 적어도 `Default`의 `Quantizations`·`AllowFallbacks`가 살아남습니다. 각 항목의 역할과 근거는 아래와 같습니다(실측 계량기는 `routing_funnel`, 2026-09-08 — 도달 불가능한 `order`로 일부러 404를 내면 응답 `metadata.routing_funnel`에 필터 단계별 잔존 엔드포인트 수가 실려 옵니다. 설정 파일이 아니라 OpenRouter가 채우는 값이라 비순환 오라클입니다):

  - **`Quantizations`가 품질 하한을 겁니다.** `z-ai/glm-5.2`에서 `fp8`을 지정하면 후보가 `29 → 13`으로 줄고(`/endpoints`의 fp8 엔드포인트 수와 일치), unknown·fp4를 원천 배제합니다. **이름으로 지목해도 필터가 이깁니다** — `order: ["fireworks"]`(unknown 양자화)에 `quantizations: ["fp8"]`을 얹으면 404입니다. 전에 모델별 표가 하던 일의 절반("fp8인 곳을 골라 손으로 적는다")이 이 한 줄로 대체됩니다.
  - **`Order`는 캐시 고착성 전용입니다.** OpenRouter 공식 문서는 `sort: "price"`가 sticky routing을 유지한다고 적지만, 이 계정·`z-ai/glm-5.2`(약 8,100토큰 접두사, 2026-09-08 실측)에서는 성립하지 않았습니다 — `order` 고정(`["novita"]` + fp8)은 호출 6회에 고유 공급자 1종·호출당 $0.00258, `fp8 + sort:"price"`는 호출 8회에 4종이 섞여 호출당 $0.00386이었습니다. **못박기가 33% 싸고, 뒤집어 말하면 `sort`가 50% 비쌉니다**(각각 상대를 분모로 삼은 값 — $0.00258 기준 $0.00386은 +49.5%, $0.00386 기준 $0.00258은 −33.1%). `sort`는 후보를 좁히되 고정하지 않으므로 `order`를 대체하지 못합니다. `ByModel`이 갖는 항목은 두 종류입니다 — 백엔드가 여럿이고 캐시 고착이 값어치가 있는 모델, 그리고 아래의 이유로 양자화 하한을 그 모델에서만 낮춰야 하는 모델입니다.
  - **`AllowFallbacks: true`가 죽지 않는 것을 삽니다.** OpenRouter의 필터 순서가 `Quantization → … → Fallback`이라, 양자화로 좁힌 뒤의 폴백은 **이미 fp8 안에서만** 일어납니다. 그래서 `ByModel`에 없는 모델은 `Default`의 `Quantizations`만 물려받아 캐시 고정만 잃고 돕니다 — **단 그 모델에 fp8 엔드포인트가 하나라도 있을 때만입니다**(아래 참조) — 예전에는 `Default:Order`가 그 모델을 서빙하지 않으면 404로 즉시 실패했습니다(실측 사고: glm 캐시 읽기 최저가 `sail-research`를 1순위로 올리자 그곳이 deepseek를 서빙하지 않아 `AllowFallbacks=false`와 맞물려 Critic이 404 "No endpoints found"로 죽었습니다 — 지금은 이 실패 모양 자체가 없습니다).
  - **`RequireParameters`는 비워 둡니다.** `reasoning: { effort }`를 동반한 호출을 `deepseek/deepseek-v4-flash-0731`·`deepseek/deepseek-v4-pro-0813`·`z-ai/glm-5.2`·`z-ai/glm-5.3`·`tencent/hy4-preview` 다섯 모델(2026-09-08 실측)에서 재 봤을 때 배제된 백엔드가 0이었습니다(모든 백엔드가 `reasoning`을 지원). 계량기가 죽은 것이 아니라는 확인은 같은 호출에 `logprobs`를 넣어봤습니다 — 그때는 `Filter by Parameters: 29 → 16`이 떴습니다(16 = `/endpoints`의 logprobs 지원 수).

  - **폐쇄 가중치 모델은 fp8 하한에 걸려 죽습니다 — 그 항목에서만 하한을 내립니다.** `/endpoints`의 `quantization`은 벤더가 자기 모델을 직접 서빙할 때 `unknown`으로만 옵니다. 그래서 `Default:Quantizations: ["fp8"]`을 그대로 물려받으면 후보가 0이 되어 `404 "No endpoints found for the request with quantization: fp8"`입니다 — `AllowFallbacks: true`는 이 죽음을 막지 못합니다(폴백이 이미 fp8 안에서만 일어나므로). 실측 2026-09-10: `openai/gpt-5.6-sol`은 엔드포인트 7개가 전부 `unknown`, `qwen/qwen3.8-max-0902`는 1개가 `unknown`이라 둘 다 404였고, `ByModel` 항목에 `"Quantizations": ["unknown"]`을 적자 각각 OpenAI·Alibaba로 200이 났습니다. 이때 여는 것은 「감사되지 않은 저정밀 양자화」가 아니라 **1차 벤더 엔드포인트**이며, `Merge`가 항목 단위라 열린 범위는 그 모델 항목 안에만 머뭅니다(`Default`는 fp8 그대로). 반대로 열린 가중치 모델에서는 하한이 그대로 의미가 있습니다 — `moonshotai/kimi-k3`은 백엔드 19개 중 fp8이 `baseten/fp8` 하나뿐이라, 하한을 물려받는 것만으로 후보가 그 하나로 정해집니다(그래서 이 항목의 `Order`는 고르는 것이 아니라 이미 정해진 것을 적는 것이고, **baseten이 내려가면 이 모델은 폴백할 fp8 후보가 없습니다**).

  HTTP 실패 두 가지는 라우팅이 아니라 호출 자체가 실패하는 자리라 따로 적습니다. **비싼 모델을 잔액이 적은 계정으로 부르면 모델 상한(예: 65536)을 요청한 것으로 계산되어 `402`가 납니다** — 그때는 `NumCtx`에 그 계정이 감당할 상한을 적습니다. **존재하지 않는 모델명**은 `400 "is not a valid model ID"`로 떨어집니다. 네임스페이스를 빼도 OpenRouter가 해석하지만(실측 2026-09-09: `model="glm-5.2"` → HTTP 200, provider `Together`), 어느 벤더로 풀릴지가 OpenRouter의 판단이라 재현성이 없으므로 `ModelName`에는 반드시 `z-ai/glm-5.3`처럼 네임스페이스를 붙여 적습니다.

  후보와 단가는 `curl https://openrouter.ai/api/v1/models/<author>/<slug>/endpoints`(인증 불필요)로 조회합니다. 보는 칸은 `tag`(변형 접미사 포함 슬러그 — `Order`에는 base 슬러그가 아니라 이 값을 씁니다)·`quantization`·`pricing.input_cache_read`·`context_length`·`uptime_last_30m`이며, **정상 상태 비용은 `pricing.prompt`가 아니라 `input_cache_read`가 지배합니다.** `sort`도 `max_price`도 이 축을 겨냥하지 못합니다 — OpenAPI 스키마상 `max_price`가 받는 키는 `prompt`·`completion`·`request`·`image`·`audio`뿐이고 `input_cache_read`는 없습니다.

  함정 둘(2026-09-08 실측): `/endpoints`의 `supports_implicit_caching: false`여도 캐시가 걸립니다 — `z-ai/glm-5.2`는 33개 백엔드 전부 이 값이 false인데 `cache_control` 없이도 적중이 났습니다(비용 −81%). `/endpoints` 메타데이터를 캐시 가능성의 오라클로 쓰면 안 됩니다. 그리고 처음 보는 접두사에 적중을 보고하는 백엔드가 있습니다(StreamLake, 서로 다른 접두사에서 2회 관측) — 적중 토큰 수를 그대로 믿을 수 없는 백엔드가 있다는 뜻입니다.

  이 고정은 재현성뿐 아니라 **프롬프트 캐싱의 전제 조건**입니다 — 여러 백엔드가 서빙하는 모델은 호출마다 라우팅이 갈려 1회차에 쓴 캐시를 2회차가 읽지 못합니다. 백엔드는 캐시 지원 여부 자체도 갈라, 마커를 정상 전송해도 무시하는 백엔드가 있습니다. 캐시 중단점은 `ClaudeClient`와 같은 `PromptCacheBreakpointPolicy` 판정을 따라 재생성 회차의 공유 블록에만 `cache_control`을 찍고, OpenRouter가 이 표시를 백엔드 규격으로 번역하므로(OpenAI 계열은 `prompt_cache_breakpoint`, Anthropic·Google은 5분 TTL의 `cache_control`) 모델 계열별 분기를 두지 않습니다.

  모델별 목록을 설정과 대조하던 `PinnedBackendsPerModel`(6행 손표, 설정을 설정의 사본과 맞대는 절반 순환)은 폐기했습니다 — 라이브 엔드포인트를 부르지 않아 표가 썩어도(모델 은퇴·백엔드 개편) 원리적으로 못 잡았습니다. 대신 두 `appsettings.json`의 `Routing` 구획을 지키는 검사가 다섯입니다: `Default`가 `Quantizations`를 선언하고 `Order`를 갖지 않는다(`AppSettings_OpenRouterDefault_DeclaresQuantizationFloorWithoutOrder`), `ByModel` 키 모양이 네임스페이스 있고 `Order`가 비어 있지 않다(`AppSettings_ByModelEntries_AreNamespacedWithNonEmptyOrder`), `Merge`가 `Quantizations` 하한을 실제로 물려주는지(`AppSettings_PerModelRouting_InheritsQuantizationFloor`), `AllowFallbacks:false`인데 `Order`가 비어 있는 조합을 막는지(`AppSettings_OpenRouterRouting_NeverBlocksFallbacksWithoutOrder` — 조건문이 아니라 `AllowFallbacks == true || Order?.Count > 0` 총함수 단언이라, 두 설정이 지금 `AllowFallbacks:true`인 것과 무관하게 매 실행마다 실제로 평가됩니다), 그리고 두 CLI(`ReSet.Cli`·`ReSet.Validator.Cli`)의 `appsettings.json`이 `Routing` 구획 전체(잎 노드 전부, 재귀 비교)에서 서로 어긋나지 않는지(`AppSettings_BothCliConfigs_DeclareIdenticalOpenRouterRouting`).
* **토큰 사용량 관측**: API·CLI를 가리지 않고 모든 클라이언트가 응답 봉투의 토큰 집계를 읽어 `TokenUsage`로 옮기고 `{provider} 토큰 사용량` 한 줄을 남깁니다. 봉투 이름은 제공자마다 달라(`usage` / `usageMetadata` / 루트 직하) 매핑은 각 클라이언트가 맡되, 같은 규격을 쓰는 셋은 `ChatCompletionsUsage`를 공유합니다. 캐시 미스는 오류를 내지 않으므로 이 줄이 캐시가 실제로 걸렸는지 볼 수 있는 유일한 신호입니다 — 봉투가 말하지 않는 항목은 0이 아니라 미보고로 남겨, 캐시가 죽은 것과 봉투가 말하지 않은 것을 구별합니다. 어떤 칸이 없는지는 규격 문서가 아니라 실물 봉투가 정합니다: 「`/chat/completions`에는 캐시 쓰기 칸이 없다」고 단정했다가 OpenRouter 실물에 `prompt_tokens_details.cache_write_tokens`가 실려 오는 것을 보고 고쳤습니다. 그래서 없다고 단정하지 않고 읽어 본 뒤, 없을 때만 미보고로 둡니다.
* **설정 기반 동적 DI 및 로컬 프로바이더 라우팅**: `appsettings.json` 내 `Providers` 맵핑 값을 읽어 `AiClientFactory`가 적합한 전용 클라이언트를 빌드해 `AiService`에 주입합니다. 특히 `mlx`, `local-openai`, `vllm` 등의 Alias를 사용할 경우 통신은 `OpenAiClient`를 재사용하면서도, 파이프라인 진입 시 `IsLocalProvider()` 검사를 통해 자동으로 **로컬 모델 전용 AST 분할(Chunking) 파이프라인**을 타고, `repetition_penalty` 및 `frequency_penalty` 파라미터를 주입하여 텍스트 무한 루프를 방어하도록 설계되어 있습니다.
* **CLI 기반 제공자 (`claude-cli` | `codex-cli` | `agy-cli`)**: HTTP API 대신 로컬에 로그인된 코딩 에이전트 CLI를 헤드리스 프로세스로 기동해 `IAiClient`를 구현하는 별도 클라이언트군입니다(`src/ReSet.Core/Services/Clients/Cli/`). `AiService`와 `VerificationPipelineOrchestrator`는 이 클라이언트들을 다른 `IAiClient` 구현체와 동일하게 취급하므로 수정되지 않았습니다. `ApiKey` 설정이 아예 없고 `Command`(실행 파일명 또는 절대 경로)만 존재합니다. 모델은 별도 키를 두지 않고 API 제공자와 같은 `AiSettings:ModelName`(Critic/Consolidator는 각자의 `ModelName`)을 `AiClientFactory`가 그대로 넘겨 `--model`(`claude-cli`·`agy-cli`) 또는 `-m`(`codex-cli`) 인자로 붙이며, 값이 비어 있으면 인자 자체를 생략해 각 CLI의 기본 모델에 맡깁니다. 이름 검증이나 변환은 하지 않으므로 표기는 그 CLI가 받아들이는 형식이어야 합니다. 세 CLI 모두 temperature는 지원하지 않아 생성 시 경고 로그를 남기고 무시합니다. effort는 지원하되 `codex-cli`/`agy-cli`는 low/medium/high 세 단계만 받아 `xhigh`를 `high`로 낮추고 로그로 남깁니다(`CliEffort`). `agy-cli`는 프롬프트를 표준 입력이 아닌 명령행 인자로 전달해야 하는데, ReSet 최대 실측 프롬프트(191KB)가 Windows 명령행 한계(32,767자)를 넘어설 수 있어 기동 전에 길이를 검사해 실패시킵니다(macOS/Linux는 약 1MB 한계라 영향 없음). CLI 프로세스는 매 호출마다 `CliWorkspace`가 만든 빈 임시 디렉터리에서 실행되어, 리포지토리 자체의 CLAUDE.md/AGENTS.md를 컨텍스트로 흡수하지 않습니다. 세 CLI 모두 프로세스 자체는 호출마다 새로 뜨지만, 서버 측 캐시가 프롬프트 접두사를 기준으로 적중되므로 반복되는 시스템 규칙에는 프롬프트 캐싱이 여전히 적용됩니다(실측: `claude-cli` 15,971 · `codex-cli` 29,184 캐시 읽기 토큰). 다만 API 경로와 달리 중단점 위치를 지정할 수단이 없어 ReSet은 캐시를 **제어하지는 못하고 관측만 합니다**. 각 클라이언트는 응답 봉투의 토큰 집계를 `TokenUsage`로 옮겨 `{provider} 토큰 사용량` 로그 한 줄을 남기며, 실패 판정보다 먼저 남겨 실패한 호출이 태운 토큰도 기록에 남깁니다. 필드 이름은 제공자마다 달라(`cache_read_input_tokens` / `cached_input_tokens` / `cache_read_tokens`) 매핑은 각 클라이언트가 맡고, 보고하지 않는 항목(`agy-cli`의 캐시 쓰기)은 0이 아니라 미보고로 남깁니다. `codex-cli`만 stdout이 사람이 읽는 진행 로그여서 `--json`으로 JSONL 이벤트를 받아야 집계가 드러나며, 본문은 그대로 `-o` 파일에서 읽습니다. 호출 실패 시 자동 폴백은 없으며 `CliFailureClassifier`가 원인을 미인증·쿼터 소진·타임아웃·알 수 없음으로 분류해 원본 CLI 출력과 함께 예외를 던지고, 전환은 설정을 고쳐 재실행하는 사람의 판단에 맡깁니다. `CliProviderBatchGuard`는 Actor/Critic/Consolidator 중 하나라도 CLI 제공자면 ReSet.Cli와 ReSet.Validator.Cli 양쪽의 무인 배치 모드를 DB 연결 전에 즉시 중단시킵니다. 이 차단은 `AiSettings:AllowCliProviderInBatch`(기본 `false`)로 열 수 있으나 `agy-cli`는 대상에서 빠집니다.
* **`agy-cli` 역할 경계**: `AntigravityCliClient`는 공통 계약과 실패 분류를 위해 배선돼 있지만 도구 권한을 비활성화할 수 없어 분석 역할로는 지원하지 않습니다. 배치에서는 옵트인 여부와 무관하게 차단하고, Antigravity를 통한 코드 생성은 별도 `CodegenSettings:Engines:agy`의 대화형 경로만 사용합니다.
* **일시적 실패의 재시도와 실패 유형 보존**: 전송 계층의 실패는 두 종류입니다 — 다시 부르면 되는 것(429, 5xx, 연결 끊김, HttpClient 타임아웃)과 다시 불러도 같은 것(4xx 인증·요청 오류, 쿼터 소진, 미인증). `AiRetryPolicy`가 이 판정을 **예외에 실린 유형만 보고** 내리므로, 여섯 개 API 클라이언트는 실패 시 HTTP 상태 코드를 예외에 보존하고 CLI 클라이언트는 분류 결과를 `CliInvocationException.Kind`로 보존합니다. 안내 문구를 되파싱하는 방식은 문구가 바뀌면 아무 신호 없이 오작동하기 때문입니다. `AiCallRetry`는 이 판정에 따라 짧은 무작위 지연을 두고 최대 2회까지 다시 부릅니다. **적용 범위는 현재 L2 리뷰 호출 다섯 곳입니다**(후보 채점·최종 리뷰·재검토·자가 수정 리뷰·통합 계획 리뷰) — 리뷰 한 번의 일시적 오류로 이미 생성된 문서의 검증을 통째로 버리는 것이 가장 비싼 손실이기 때문이며, 생성 경로는 아직 이 인프라를 쓰지 않습니다. 재시도를 다 쓰고도 실패하면 `AiCallFailedException`으로 감싸 올립니다. 이 예외가 `OperationCanceledException`을 상속하지 않는 것이 설계의 핵심입니다 — 타임아웃도 `TaskCanceledException`으로 오므로, 그 형식 그대로 올리면 저장소 곳곳의 `when (ex is not OperationCanceledException)` 필터가 전부 놓쳐 "사용자에 의해 중단되었습니다"로 둔갑합니다. 그 오보는 리뷰 경로 밖에서는 아직 남아 있습니다(`docs/known-defects.md`).
