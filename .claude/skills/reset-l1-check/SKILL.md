# L1 검사를 더한다

## 이 스킬이 있는 이유

2026-08-22 축 A 재감사 결함을 닫는 회차에서, 계획서에 **실질 결함이 여섯** 있었다.
전부 같은 원인이었다 — `MechanicalValidator`의 **형제 검사들이 어떻게 구간을 잡고 재료를
배선하는지 읽지 않고 검사 본문만 새로 썼다.**

그중 둘은 단위 테스트 2308개가 전부 통과하는 상태에서도 보이지 않았고, 실제 산출물
코퍼스를 돌려서야 드러났다. 하나는 검사가 **한 번도 안 도는** 것이었고(스위트는 초록),
하나는 실제 명세서 31개 중 9개에 **거짓 양성 10건**을 내는 것이었다.

거짓 양성이 특히 위험한 이유는 파급이다. `VerificationPipelineOrchestrator`가 L1 오류를
재생성 트리거로 삼고, 소진되면 `L1Exhausted` 배너를 붙인다. 캐시 버전을 올린 회차라면
전건이 재생성되므로 거짓 고발이 곧바로 재시도 소진으로 이어지고, 시정 문구가 틀렸으면
모델이 **베껴야 할 기계 확정 표 자체를 망가뜨린다.**

> 잘못 지목한 L1 오류는 재생성으로 고칠 수 없다. 귀속이 불가능하면 침묵한다.

## 순서

1. **`references/authoring-contract.md`를 읽는다.** 형제 검사들이 이미 정한 관례다.
   여기 적힌 일곱 항목을 어기면 이번 회차가 겪은 실패가 그대로 재현된다.
2. 검사를 TDD로 만든다. 실패를 눈으로 보지 않고 구현으로 넘어가지 않는다.
3. **`references/corpus-sweep.md`의 전수 스윕을 돌린다.** 이것이 이 스킬의 핵심이다.
   단위 테스트만으로는 위 두 부류가 보이지 않는다.
4. 스윕 결과(진짜 양성 수 · 거짓 양성 수)를 보고에 **숫자로** 적는다.

## 프롬프트 계약을 바꿨으면 캐시 버전을 올려라

재료의 **모양**이든 산출물의 **출력 계약**이든, 프롬프트에 실리는 것이 달라졌으면
`CacheManager.CurrentCacheFormatVersion`을 올린다. 안 올리면 재생성이 캐시 적중으로
건너뛰어져 **검증 자체가 일어나지 않는다** — 그리고 옛 계약으로 만든 산출물이 그대로
남아 다음 감사에서 결함으로 잡힌다.

> 실측(2026-08-23): CRUD 설명 칸의 술어 서술을 금지한 뒤 재생성을 돌렸더니
> `(Cache Hit)`으로 건너뛰었다. 버전을 12로 올리고서야 실제로 AI를 탔다.
> 선례는 버전 5다 — "함수 동작 서술이 금지되었다. 프롬프트 입력과 출력 계약이 둘 다
> 달라졌으므로 옛 산출물은 재분석해야 한다."

번호는 **main과 대조해서** 정한다 — 브랜치에서 올리기 전에
`git show main:src/ReSet.Core/Services/CacheManager.cs | grep CurrentCacheFormatVersion`으로
main의 현재 값을 보고, 다른 세션이 같은 번호를 먼저 썼으면 한 번호 더 올린다. 같은 번호
아래 두 계약이 생기면 먼저 병합된 쪽의 캐시가 다른 쪽 코드에서 **적중**해, 새 행이 빠진
명세서가 조용히 복사된다(2026-08-23 두 세션이 각자 11→12로 올려 실제로 일어났다).

캐시 인상은 전건 재생성을 강제하므로 비용이 크다. 그래서 §「완료 기준」의 코퍼스 스윕은
인상 **전에** 돌려 오탐을 먼저 잡는다 — 거짓 양성을 안은 채 전건을 돌리면 그 오탐이
곧바로 재시도 소진으로 번진다.

**예외 — Critic만 느슨해지는 변경은 올리지 않는다.** 인상 규정의 취지는 "옛 계약으로 만든
산출물이 다음 감사에 결함으로 남는 것"을 막는 데 있다. Actor 지시와 출력 계약이 그대로이고
L2 Critic의 판정 기준만 완화됐다면 옛 산출물은 더 엄한 기준을 이미 통과한 것이라 새 기준에서
결함이 되지 않는다 — 올릴 이유가 없고 전건 재생성 비용만 든다.
반대로 Critic을 **조이거나** Actor 지시를 바꾸면 인상 대상이다(v12가 그 경우 — Critic 완화가
CRUD 설명 칸 금지와 함께 들어갔다).

L1만 조이는 변경은 선례가 갈린다. v9~v11은 새 L1 검사를 "캐시 히트에서는 영영 발동하지
않는다"는 이유로 인상 사유에 넣었다(그때는 프롬프트도 함께 바뀌었다). 2026-08-23의 문장 칸
대조는 프롬프트 불변이라 인상하지 않고, 대신 코퍼스 전수 스윕의 수정 전후 차분 0으로 "기존
산출물이 새 기준도 통과한다"를 숫자로 보였다. 즉 **L1만 조일 때 인상을 생략하려면 그 스윕
차분을 보고에 적어야 한다** — 캐시 히트 산출물에는 L1이 영영 안 돌므로(`VerificationPipelineOrchestrator`의
조기 반환) 스윕이 그 자리를 대신하는 유일한 증거다. 스윕을 안 돌렸으면 선례대로 올린다.

> 실측(2026-08-23): SP Critic 기준 1의 `조회합니다` 금지가 독립 SELECT 행의 옳은 읽기 필터
> 서술("…인 행만 조회합니다")까지 보고할 여지를 글자로 남겨, **금지의 적용 범위를 쓰기 문장의
> 대상 행 술어로 좁히고** 표 면제를 앞으로 옮겼다. Critic만 느슨해지는 변경이라 13을 유지했다.

## 완료 기준

아래 넷이 전부 참이어야 한다. 하나라도 확인하지 않았으면 완료가 아니다.

- [ ] `dotnet test` 실패 0 · **건너뜀 0** — 건너뜀 N이면 코퍼스 테스트가 `output/`을 못 찾은 것이다(워크트리에는 없다). 메인 저장소의 `output/`을 심링크하고 다시 돌린다
- [ ] **실제 코퍼스 전수 스윕에서 거짓 양성 0**
- [ ] 스윕에서 겨냥한 진짜 결함이 실제로 잡힌다(0건이면 검사가 자기 존재 이유를 놓친 것이다)
- [ ] 스윕에서 **다른 검사들의 카운트가 변하지 않았다**(재료를 늘렸으면 옆 검사에 번질 수 있다)
- [ ] 프롬프트 계약이 달라졌으면 **캐시 버전을 올렸다**(안 올리면 재생성이 캐시 적중으로 건너뛴다) — 번호는 main 값과 대조해 겹치지 않게

## 흔한 실패

| 실패 | 실제로 벌어진 일 |
|---|---|
| 재료만 더하고 `From`의 null 판정 체인에 항을 안 잇는다 | 검사가 한 번도 안 돌고 스위트는 초록으로 남는다 |
| 문서 전체의 `\|` 줄을 훑는다 | 같은 모양의 다른 표를 자기 결함으로 오귀속한다 |
| 합성 표 하나로 테스트한다 | 인접한 두 표·산문이 낀 표·여러 절을 전부 놓친다 |
| 트리거 문구를 머리로 정한다 | `IS NOT NULL` 같은 SQL 술어에 걸려 정상 서술을 결함으로 만든다 |
| 단위 테스트가 초록이라 끝냈다고 본다 | 위 두 부류는 단위 테스트에 보이지 않는다 |
