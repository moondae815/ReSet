# ReSet 산출물 정합성 감사

## 개요

두 축을 대조한다.

- **축 A** — SP 원본 DDL ↔ `output/Procedures/[SP]/docs/Spec.md`
- **축 B** — `Spec.md` ↔ `output/Jobs/[job]/` 계획서·단계 지시서

**핵심 원칙: 판정의 단위는 Job이 아니라 SP 하나 또는 단계 하나다.** 한 컨텍스트가
8,000줄 계획서와 14개 명세서를 동시에 들면 반드시 표본만 보게 되고, 표본이 달라지면
같은 Job에서 다른 결함 목록이 나온다. 실측: 분할 없이 두 번 돌렸더니 결함 목록이
합집합이 아니라 서로 어긋난 부분집합이었다(한쪽만 `INSERT` 컬럼 수 불일치를,
다른 쪽만 조인 누락을 찾았다).

## 0. 시작 전 — 이 지시는 당신에게 내려진 것이 아니다

`agent/MigrationInstructions.md` 상단에는 **"원본 Stored Procedure 파일을 절대 참조하지
마십시오"** 라는 경고가 있다. 이것은 **코드를 생성할 코딩 에이전트에게** 내린 지시다.
감사자는 정반대다 — 원본 DDL을 읽지 않으면 축 A가 성립하지 않는다. 이 문장을 근거로
원본 열람을 건너뛰지 마라.

## 1. 검증 대상 확정

**관측 가능한 파일에서 읽어낸다. 디렉터리를 열거해 추측하지 않는다.**
`output/Objects/`와 `output/Procedures/`는 분석기가 지금까지 만난 **모든** 객체를 담으므로
이 Job의 대상 목록이 아니다.

| 무엇을 | 어디서 (있는 것 중 첫 번째) |
|---|---|
| 소비 명세서 집합 | ① `agent/MigrationInstructions.md`의 `Spec.md` 링크 ② `raw/prompt-context.md`의 `^Filename:` 행(`Feedback_Log.txt` 제외) |
| 단계 ↔ 레거시 SP 매핑 | ① `raw/prompt-context.md`의 `[Approved Step List]` 블록 `Legacy:` 필드 ② 계획서의 `승인된 단계 체인과 레거시 대응` 표 |
| 단계 목록 | `agent/steps/*.md` 파일명 |

`agent/`가 없으면(번들 미생성) **축 B는 검증 불가**다. 보고서에 그렇게 적고 끝낸다 —
계획서만 놓고 추정하지 않는다.

**중첩 SP 전개**: 확정된 각 SP의 DDL에서 `EXEC`로 호출되는 하위 SP를 한 단계 전개한다.
전개 결과 중 소비 명세서 집합에 없는 것은 **그 자체가 축 B의 결함**이다(단계에 흡수됐지만
명세서가 입력되지 않았다는 뜻). 결함으로 보고하고, 축 A 대상에는 포함한다.

## 2. 검증 단위와 캐시

| 축 | 단위 | 캐시 키의 최소 구성 |
|---|---|---|
| A | SP 1개 | `object_definition.sql` + `Spec.md` + `metadata.json` |
| B | 단계 1개 | `steps/SNN.md` + 그 단계가 흡수한 **모든** SP의 `Spec.md` |

**키는 그 단위가 기준값으로 실제로 읽은 파일 전부의 `sha256`이다.** 위 표는 하한이지
목록이 아니다 — 단위가 표에 없는 파일을 근거로 삼았으면(신설 단계에 들려 보낸 인접
`Spec.md`처럼) 그 해시도 키에 넣는다. 넣지 않으면 판정 근거가 바뀌었는데 캐시가 유효로
남는다. 실측에서 두 자리가 이 이유로 새고 있었다.

캐시는 `output/Jobs/[job]/consistency/.cache.json`에 단위별로 둔다. 키가 같으면
이전 판정과 결함 목록을 그대로 재사용하고, 보고서 커버리지 표에 `캐시`로 표기한다.
**키가 하나라도 다르면 그 단위는 통째로 다시 검증한다** — 부분 갱신하지 않는다.

**단위가 끝날 때마다 즉시 캐시에 쓴다.** 전부 끝난 뒤 한 번에 쓰지 마라 — 실측에서
28개 단위를 한 번에 돌리다 세션 한도로 중단됐고, 끝난 단위의 결과가 통째로 날아갔다.
중단된 실행은 캐시가 있는 단위를 건너뛰고 이어서 돌린다.

원본 DDL 경로는 `output/Objects/[스키마].[이름].Procedure/raw/object_definition.sql`이다.

### 2-1. 축 A 캐시는 Job이 바뀌어도 유효하다

축 A 키의 세 경로는 모두 `output/Jobs/` **바깥**이므로 Job에 의존하지 않는다. 새 Job을
감사할 때 이전 Job의 `axisA:` 항목만 옮겨 두면 그 SP들은 다시 검증하지 않는다. 실측에서
`Spec.md` 14개는 Job 세 개가 새로 만들어지는 동안 한 번도 재생성되지 않았고, 축 A가
서브에이전트 토큰의 약 45%였다.

```bash
python3 -c "
import json
src=json.load(open('output/Jobs/[이전job]/consistency/.cache.json',encoding='utf-8'))
json.dump({k:v for k,v in src.items() if k.startswith('axisA:')},
          open('output/Jobs/[새job]/consistency/.cache.json','w',encoding='utf-8'),
          ensure_ascii=False,indent=1)"
```

**`axisA:`만 걸러서 옮긴다. 통째로 복사하지 마라.** 축 B 키는 `Jobs/[job]/agent/steps/`를
포함해 새 Job에서 히트하지 않지만, 파일에 남아 있으면 보고서를 만들 때 이전 Job의 단계
결과가 커버리지 표에 섞인다.

옮긴 뒤 두 가지를 확인한다. **대상 SP 집합**이 다르면 새 Job이 쓰지 않는 SP의 항목은
커버리지 표에서 뺀다 — 검증하지 않은 SP가 검증된 것으로 실린다. **보고서 4-1**의 서술 중
이전 Job의 귀결을 인용한 문장("축 B의 S07에서 실제로 그 일이 일어났다")은 다시 쓴다.
판정과 결함 목록 자체는 Job과 무관하므로 그대로 재사용한다.

`Spec.md`가 안 바뀌었는지 미리 확인할 필요는 없다. 키가 파일 해시라 바뀌었으면 그 단위만
미스가 나 재검증된다.

## 3. 축 A 대조 계약

**파서가 수집한 항목에 한해 `StaticAnalysis`가 진실의 원천이다.** 이미 확정된 값이므로
DDL에서 손으로 다시 뽑지 않는다(AGENTS.md 범주 4의 같은 규칙). 경로는
`output/Procedures/[SP]/raw/metadata.json`이고 **BOM이 있으므로 `utf-8-sig`로 읽는다**
(`Objects/` 아래에는 이 파일이 없다).

파서가 **수집하지 않는** 것은 DDL 원문으로 채운다. 실측에서 확인된 것:
인라인 TVF 호출(`UIF_SettleYMD` 등)이 `ReferencedFunctions`에 없고,
`ProcedureParameters`는 `OUTPUT` 방향을 표기하지 않는다.
파서에 없다는 것을 "원본에 없다"로 읽지 마라 — 정산일 계산 TVF 하나가 통째로 사라진다.

각 SP마다 아래 표를 채운다. 빈 칸을 남기지 않는다.

| 대조 항목 | 기준값 출처 |
|---|---|
| 파라미터 시그니처 | `StaticAnalysis.ProcedureParameters` |
| INSERT/UPDATE/DELETE 대상 테이블 | `InsertTables` / `UpdateTables` / `DeleteTables` |
| INSERT 컬럼 매핑 | `AstInsertMappings` |
| 참조 함수 | `ReferencedFunctions` |
| 테이블별 참조 컬럼 | `ReferencedColumnsPerTable` |
| 오류·반환 코드 전체 집합과 발생 지점 | **DDL 원문** (`StaticAnalysis`에 없음) |
| 분기 조건식·필터·조인 | **DDL 원문** |
| 트랜잭션 경계, `NOCOUNT`, `NOLOCK`, 주석 처리된 블록 | **DDL 원문** |

Spec.md가 `StaticAnalysis`와 어긋나면 파서가 이긴다. Spec.md가 DDL 원문의 의미와
어긋나면 DDL이 이긴다.

## 4. 축 B 대조 계약

단계 하나마다 그 단계의 `steps/SNN.md`와 대응 레거시 SP의 `Spec.md`만 들고 대조한다.
그 단계가 SP 여러 개를 흡수했다면 흡수한 SP의 `Spec.md`를 **전부** 기준값으로 삼는다.
계획서(`docs/BatchMigrationPlan.md`)는 단계 절을 이어붙인 조립본이므로 따로 읽지 않는다 —
**단, 조립본과 번들이 실제로 같은지는 기계로 확인**하고 결과를 보고서에 남긴다.

**축 B의 기준값은 `Spec.md`이고, 원본 DDL이 아니다.** Spec 자체가 원본과 어긋난 경우는
축 A가 잡는다. 이것은 열람 금지가 아니라 분업이므로, 축 B 단위가 원본을 못 봤다는 사실을
결함이나 한계로 적지 마라 — 축 A 결과와 나란히 읽으면 두 축이 함께 덮는다.

**레거시 대응이 없는 신설 단계**(`Legacy:`가 공란)는 기준값이 없으므로 `검증 불가`로 판정한다.
다만 그 단계가 **앞 단계가 확정한 컬럼을 다시 쓴다면**, 그 컬럼을 확정한 SP의 `Spec.md`를
함께 들려 보내 "덮어쓰는가"만 대조한다. 판정은 여전히 `검증 불가`이고, 대조가 성립한
범위와 그 결과를 커버리지 표에 적는다. 기준값이 없다는 이유로 아무것도 보지 않으면,
실측에서 그 자리에서 나온 🔴 3건을 놓친다.

| 대조 항목 | 무엇을 본다 |
|---|---|
| 오류 코드 보존 | Spec의 반환 코드 집합 ⊆ 단계의 보존 코드 집합 |
| 출력 인터페이스 | 원본에 없는 출력 파라미터를 신설하지 않았는가 |
| 대상 테이블 | Spec의 쓰기 집합과 단계의 변경 대상이 같은가 |
| 계산식 | 상수·계수·반올림 자릿수·부호가 그대로인가 |
| 필터·조인 | 조인 종류(INNER/LEFT), 조건 컬럼, 비교 대상이 그대로인가 |
| UDF 호출 | 함수명과 **인자 개수·순서**가 그대로인가 |
| 컬럼 집합 | `INSERT` 컬럼 수와 값 수, `UPDATE` SET 대상이 빠짐없는가 |
| 후속 단계 간섭 | 뒤 단계가 앞 단계의 결과를 덮어쓰지 않는가 |

## 5. 병렬 분할

축 A는 SP당, 축 B는 단계당 서브에이전트 하나에 맡긴다. 캐시가 유효한 단위는 띄우지 않는다.
각 서브에이전트는 **자기 단위의 파일만** 읽고, 아래를 그대로 반환한다.

- 판정: `정합` / `결함` / `검증 불가`
- 결함 목록: 항목별로 `등급 · 원본 앵커(파일:줄) · 산출물 앵커(파일:줄) · 원본 내용 · 산출물 내용 · 영향`
- 읽지 못했거나 판단을 보류한 절

상위는 이 반환값을 **합치기만 한다.** 상위가 원본이나 계획서를 다시 읽어 판정을 바꾸지 않는다.
단위가 판정과 결함 목록을 어긋나게 반환하면(`정합`이라 쓰고 🔴·🟠·🟡을 함께 냄)
**결함 목록이 이긴다** — 판정 문구를 맞추는 것은 재판정이 아니라 합치기의 일부다.

등급: 🔴 결과 금액이 달라짐 · 🟠 대상 행 집합이 달라짐 · 🟡 표기·추적성 · ⚪ 정보

등급이 갈릴 때는 **영향이 배포 구성에 달려 있으면 높은 쪽**으로 매기고, 그 전제를
결함 행에 적는다. 실측에서 같은 결함(스칼라 서브쿼리 → `CROSS APPLY`)이 한 실행에서는
🟠, 다른 실행에서는 ⚪로 갈렸다.

단위 수가 20개를 넘으면 한 번에 다 띄우지 말고 나눠 돌린다. 각 단위는 끝나는 대로
캐시에 기록되므로, 중단돼도 남은 단위만 이어서 돌리면 된다.

## 6. 보고서

`output/Jobs/[job]/consistency/ConsistencyReport.md`에 쓴다.
(`validation/`은 검증기 CLI가 쓰는 자리이므로 침범하지 않는다.)

아래 여섯 절을 이 순서로 둔다. **3절과 6절은 비워 둘 수 없다.**

```markdown
# [job] 산출물 정합성 감사

## 1. 판정
| 축 | 판정 | 단위 수 | 신규 검증 | 캐시 재사용 | 검증 불가 |

## 2. 검증 대상 확정
대상 목록과 **어느 파일에서 읽었는지**. 중첩 SP 전개 결과.

## 3. 단위별 커버리지
| 단위 | 판정 | 상태(신규/캐시/불가) | 근거 파일 |
단위를 빠짐없이 한 행씩. 검증 불가는 사유를 적는다.

## 4. 축 A 결함
| 등급 | SP | 원본 앵커 | 산출물 앵커 | 원본 | 산출물 | 영향 |

## 5. 축 B 결함
| 등급 | 단계 | Spec 앵커 | 산출물 앵커 | Spec | 산출물 | 영향 |

### 5-1. 전 단계 공통 결함
같은 결함이 단계 대부분에 반복되면 여기에 한 번만 적고 해당 단계를 나열한다.

## 6. 이 감사가 보증하지 않는 것
읽지 않은 파일, 대조하지 않은 축, 판단을 보류한 절. 실행 대조를 하지 않았다면 그 사실.
```

단위 반환값을 합칠 때, 여러 단위에 같은 원인으로 반복되는 결함은 4-1(축 A)·5-1(축 B)에
한 번만 적고 해당 단위를 나열한다. 실측에서 "목차 `ErrorCodes`가 비어 있다"는 품질 배너와
본문의 모순이 13단계에서 나왔다 — 접지 않으면 결함 하나가 13건으로 부풀어 🔴을 가린다.

## 흔한 실패

| 실패 | 실제로 벌어진 일 |
|---|---|
| 디렉터리를 열거해 대상을 정한다 | `output/Objects/`는 전역 목록이다. 이번 Job과 우연히 개수가 맞아 통과한 적이 있다 |
| `StaticAnalysis`를 건너뛰고 DDL을 손으로 읽는다 | 파서가 확정한 값을 재해석하면 축 A 판정이 실행마다 갈린다 |
| 이름이 등장하니 커버됐다고 본다 | S11이 SP 3개를 흡수했는데 단계 표에는 1개만 적혀 있었다. 오류 코드 매트릭스는 세 SP 코드를 한 줄에 합쳐 추적 불가였다 |
| 계획서 전문을 상위가 읽는다 | 8,488줄을 들면 단계 대조가 표본으로 무너진다 |
| "대체로 일치합니다"로 끝낸다 | 앵커 없는 판정은 재확인할 수 없다. 모든 결함 행에 양쪽 `파일:줄`을 단다 |
