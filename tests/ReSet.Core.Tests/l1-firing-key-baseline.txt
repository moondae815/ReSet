# 검사 키가 안 붙는 직접 `result.Errors.Add` 의 파일별 허용 개수.
# 목록에 없는 파일은 0건을 뜻한다.
#
# 단방향이다: 새 위반은 실패, 내려가는 것은 자유.
# cancellation-policy-baseline.txt 의 양방향 잠금을 흉내내지 마라 - 여기서는
# 「0 이 목표」가 분명하므로 상한만 잠근다.
#
# ReSet.Core/Services/MechanicalValidator.cs=37 인 이유(2026-09-09 실측, 리뷰
# Fix Round 1 에서 서술 정정):
#
# 이 37 은 부채이고, 그 부채의 정체는 「다른 C# 타입이라서」가 아니라 「그 갈래
# 전체가 자기강화 게이트 밖이라서」다. `perl -pi -e
# 's/result\.Errors\.Add\(/result.Report(/g'` 를 97 자리에 돌리자 37 곳에서
# `dotnet build --no-incremental` 이 CS1061 을 냈다 - `StepValidationResult`
# (:12213)는 `Report`/`Firings`/`DetailedErrors` 통로가 없는 별개 타입이라 손으로
# `result.Errors.Add(` 로 되돌렸다(38 번째는 `AddRange(:625)` 로, 정규식이 애초에
# `Add\(` 뒤 즉시 괄호를 요구해 안 건드렸다 - 37+1=38 이 이 타입 소속 전체다).
#
# 그런데 타입이 다른 것은 증상이지 원인이 아니다. 이 타입을 쓰는
# `ValidateBatchStep` 재시도 루프(VerificationPipelineOrchestrator.cs 약
# 4311행)는 `L1AttemptLog.Append(...)` 를 한 번도 부르지 않는다 - 그건 오직
# 문서 단위 `_validator.Validate(...)` 갈래(약 1045행 근방, 1059행에서 Append)
# 에서만 난다. 즉 이 38 곳은 `Firings`에도 안 실리고 `raw/l1-attempts.json`
# 에도 안 남으므로, `SelfReinforcingCheckTests` 가 재는 코퍼스에 이 갈래의
# 발화가 원천적으로 들어오지 않는다 - CheckErrorCodeUniquenessClaim 이 낸
# 재시도 6 회짜리 반복 발화 사고가 여기서 나면 자동 탐지가 없다.
#
# 0 으로 가는 길은 하나가 아니라 **두 가지를 한 커밋에서** 해야 닫힌다:
#   1. `StepValidationResult` 에도 `Report()`/`Firings` 를 놓아 이 37(+1) 곳을
#      마저 옮기고,
#   2. `ValidateBatchStep` 실패를 `L1AttemptLog.Append(...)` 에 연결해 그
#      결과가 자기강화 게이트가 보는 코퍼스에 들어가게 한다.
# 1 번만 하면(`StepValidationResult`에 `Report` 시그니처만 복붙) `Firings`는
# 채워지지만 그 값을 아무도 `L1AttemptLog`로 옮기지 않으므로 게이트는 여전히
# 이 갈래를 못 본다 - 「닫혔다」는 거짓 신호만 남긴다. 그래서 이 수는 스캐너
# 관할 밖이 아니라(스캐너는 타입을 모르고 여전히 정확히 잡는다) 파이프라인
# 배선 밖이고, 배선을 고치기 전까지는 단방향 상한만 걸어 둔다.
ReSet.Core/Services/MechanicalValidator.cs=37
